思觉智贸 — 技术架构简历大纲
  
  一句话定位

  ▎ 从零设计并落地跨境电商竞品分析平台，支撑日均 X 万条商品数据的采集、评分、AI 分析与可视化。
  
  ---
  1. 架构演进：单体 → 微服务双后端渐进式迁移

  问题背景：原系统是 Python FastAPI 单体，业务膨胀后出现三个痛点——
  - AI 推理（CLIP 模型加载）和 HTTP 请求争抢 GIL，接口响应抖动
  - 数据密集型计算（竞品分析、评分引擎）MySQL 全表扫描扛不住
  - 团队有 Java 和 Python 两拨人，各自效率高但单体只能选一个语言

  设计决策：
  - 按业务边界而非技术栈拆分：认证+竞品分析迁移到 Java Spring Boot（高性能计算），AI+图片处理留在
  Python（模型生态），前端通过 API 前缀无感路由
  - 引入 Spring Cloud Gateway + Nacos 做统一入口和服务发现，网关层完成 JWT 鉴权和 RBAC，下游服务只关心业务逻辑
  - 迁移期间双后端并行运行，零停机，前后端都不感知后端变化

  讲的时候可以展开的点：
  - 为什么选 Spring Boot 4.0 + Spring Cloud 而不是继续 FastAPI？—— 类型安全、事务管理、MyBatis-Plus 对复杂 SQL 的支持    
  - 为什么不用 K8s 而用 Docker Compose？—— 团队规模和运维成本权衡，3 台机器没必要上编排
  - 网关兼容 Python 后端怎么做？—— 不经过网关，Vite/Nginx 直接按路径代理分流

  2. 多级缓存体系：从 DB 慢查询到 95% 命中率

  问题：竞品查询单个 ASIN 调用卖家精灵 API 耗时 2-3 秒，100 个 ASIN 不做缓存要 200+ 秒。

  设计：
  请求 → 布隆过滤器(不存在直接返回) → Caffeine 本地(10min±随机) → Redis(30min) → API/DB
                  ↑ 防穿透                    ↑ 防雪崩(抖动TTL)         ↑ 防击穿

  关键实现：
  - Caffeine 本地缓存：热点商品（评分 A/S 级）缓存命中率高，减少 Redis 网络往返
  - Redis 分布式缓存：跨实例共享，Redisson 提供分布式锁防缓存击穿
  - 布隆过滤器：预加载全量 ASIN，拦截不存在的查询，避免无效 API 调用
  - TTL 随机抖动：每个 Key 的过期时间叠加 ±5 分钟随机偏移，避免同时过期引发"惊群"
  - 声明式注解 @CacheWithMultiLevel：业务方加一个注解即可接入三级缓存，零代码侵入

  讲的时候可以展开：
  - 缓存一致性怎么保证？—— Cache-Aside 模式 + 写操作主动失效
  - 缓存命中率怎么监控？—— 前端 CacheManager.getCacheStats() 实时统计
  - 为什么不用 Spring Cache 抽象？—— 需要控制每一层的 TTL 和淘汰策略不同

  3. 可观测性：全链路追踪 + 限流 + 熔断

  分层设计：

  │    层    │     机制     │                            实现                            │
  ├──────────┼──────────────┼────────────────────────────────────────────────────────────┤
  │ 接入层   │ 接口限流     │ AOP @RateLimit + Guava 令牌桶，按 IP+方法粒度              │
  ├──────────┼──────────────┼────────────────────────────────────────────────────────────┤
  │ 业务层   │ 全链路追踪   │ @TraceOperation 注解 + TraceId 跨服务传递                  │
  ├──────────┼──────────────┼────────────────────────────────────────────────────────────┤
  │ 数据层   │ API 调用限流 │ ApiRateLimitService 滑动窗口 + 月度配额，DB 可动态调整     │
  ├──────────┼──────────────┼────────────────────────────────────────────────────────────┤
  │ 基础设施 │ 优雅降级     │ RocketMQ @Autowired(required=false)，MQ 不可用不阻塞主流程 │
  └──────────┴──────────────┴────────────────────────────────────────────────────────────┘

  亮点：
  - 限流配额运行时动态可调：运营反馈调用太频繁，直接调接口改 api_config 表，volatile + AtomicInteger 即刻生效，不重启    
  - TraceId 从 Gateway 生成 → 通过请求头透传 → Python/Java 后端均记录，跨语言追踪

  4. AI 推理 Pipeline：异步非阻塞模型服务

  挑战：Chinese CLIP 模型加载耗时 10s+、占用 2GB+ 显存/内存，不能阻塞 HTTP 事件循环。

  设计：
  FastAPI 启动 → 懒加载模型(首次请求触发) → run_in_executor(线程池加载)
                          ↓
  用户上传图片 → Celery 异步任务 → asyncio.run() 连接 Qdrant → 写入特征向量
                          ↓
  搜索请求 → 特征提取 → Qdrant 向量相似度 → 返回 Top-K

  关键决策：
  - 模型单例：__new__ 控制只加载一次，多请求复用
  - 动态标签库：候选标签从 txt 文件热加载，改标签不需要重新训练/部署
  - Celery 内异步嵌套：asyncio.run() 让同步 Celery Worker 也能访问异步的 Redis/Qdrant 客户端
  - Qdrant 向量数据库：替代 MySQL LIKE 模糊搜索，图片相似度检索从秒级降到毫秒级

  5. 前端性能架构：从"能跑"到"流畅"

  三层优化策略：

  加载层 — 分阶段初始化：
  阶段1(阻塞): 用户信息 + 站点配置       → 立刻渲染布局
  阶段2(并行): 核心数据 + 筛选选项       → 主内容可见
  阶段3(空闲): 趋势图 + TOP榜 + 广告数据 → requestIdleCallback 低优先级加载

  缓存层 — 双层图片缓存：
  - localStorage（持久化，7 天 TTL）+ 内存 Map（LRU，50 条上限）
  - 淘汰策略：内存超 75% 时踢掉访问最少的 30% 条目
  - MemoryMonitor 定期采样 performance.memory，趋势分析检测泄漏

  交互层 — 乐观更新：
  - 用户点击"选中产品" → 立即切换 UI（不等待服务端）
  - 后台 POST 记录 → 拉取最新全量状态 → 校准展示
  - 失败时回滚本地状态，提示用户
