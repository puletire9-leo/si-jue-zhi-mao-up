## 四阶段数据流

```
开发者标记产品
    │
    │  POST /api/v1/click-logs  { action: "select", asin: "B0XXX" }
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段一：标记                                                      │
│                                                                  │
│ product_click_log 表                                             │
│   userId | userName | asin | action | marketplace | clickedAt   │
│                                                                  │
│ 前端实时乐观更新 + 全员可见选中用户列表                               │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           │ 触发方式（三选一）：
                           │  A. 用户标记时 WebSocket 实时触发
                           │  B. Celery 定时任务（凌晨批量）
                           │  C. 用户在 SuperMew 对话中手动查询
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段二：分析                                                      │
│                                                                  │
│ 1. AnalyzeProductTool.get_product_data(asin)                    │
│    → competitor_products 表查询 20+ 维度                          │
│                                                                  │
│ 2. AnalyzeProductTool.get_historical_data(asin)                 │
│    → 同 ASIN 历史月度数据                                         │
│                                                                  │
│ 3. LLM 分析生成报告 (豆包/火山引擎 API)                             │
│    → 结构化 JSON: 总结 / 优势 / 风险 / 建议 / 标签 / 评分解读        │
│                                                                  │
│ 输出: ProductAnalysisReport                                    │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段三：保存                                                      │
│                                                                  │
│ 1. PostgreSQL: product_analysis 表                               │
│    asin | analysis_json | grade | tags | week_tag | created_at  │
│                                                                  │
│ 2. 文本分块 (复用 DocumentLoader 三级滑动窗口)                      │
│    L1 (1200+) → L2 (600+) → L3 (300+)                           │
│                                                                  │
│ 3. 向量化 (复用 EmbeddingService: BAAI/bge-m3 + BM25)            │
│    稠密向量(1024维) + 稀疏向量(BM25)                               │
│                                                                  │
│ 4. Milvus 入库 (复用 MilvusManager)                               │
│    collection: product_analysis                                  │
│    metadata: { asin, marketplace, week_tag, grade, tags }        │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段四：迭代                                                      │
│                                                                  │
│ 每周新数据入库 → Celery 定时任务触发 →                              │
│                                                                  │
│ 1. 同 ASIN 新旧数据对比                                           │
│    salesVolume: 3200 → 2700 (-15.6%)                            │
│    bsr: 1200 → 1800 (+50%)                                      │
│    price: 19.99 → 17.99 (-10%)                                  │
│                                                                  │
│ 2. LLM 生成变化摘要                                               │
│    "本周销量环比下降 15.6%，BSR 排名回升至 #1,800..."               │
│                                                                  │
│ 3. 追加到 Milvus（同一产品的时间序列知识链）                         │
│                                                                  │
│ 4. RAG 查询时可检索到产品完整演化历史                               │
└─────────────────────────────────────────────────────────────────┘
```

## 技术分层

| 层 | 技术 | 现有 vs 新建 |
|----|------|-------------|
| **标记层** | Java Spring Boot + MyBatis-Plus + MySQL | ✅ 已有 `ProductClickLogService` |
| **分析层** | Java 数据查询 + Python LLM Agent 工具 | 🆕 需新建 `ProductAnalysisTool` |
| **知识层** | Python FastAPI + Milvus + BGE-M3 嵌入 | 🔀 复用 SuperMew 组件 |
| **迭代层** | Python Celery + LangGraph RAG Pipeline | 🔀 复用 + 新建对比逻辑 |

## 与 SuperMew 的关系

| SuperMew 组件 | 在本飞轮中的角色 |
|---------------|-----------------|
| `EmbeddingService` (bge-m3 + BM25) | 产品分析报告的向量化 |
| `MilvusManager` (hybrid_retrieve) | 产品知识库的存储和检索 |
| `DocumentLoader` (三级分块) | 分析报告的分块入库 |
| `rag_pipeline` (LangGraph 5 节点) | 产品知识 RAG 检索流水线 |
| `agent.py` (create_agent + SSE) | 产品分析 Agent 的对话入口 |
| `tools.py` (search_knowledge_base) | ✅ 直接复用 |
| `ConversationStorage` (PostgreSQL + Redis) | 分析对话历史持久化 |

## 关键设计决策

### 1. 为什么分析报告要向量化而不是只存 DB？

纯 DB 只能做精确查询（`WHERE asin = 'B0XXX'`）和模糊搜索（`LIKE '%收纳%'`）。向量化后可以做**语义检索**：

> 用户问："有哪些厨房产品最近销量在涨？"
> → 稠密向量匹配"厨房"语义 + 稀疏向量匹配"销量"关键词 + Milvus 过滤 `grade:S`
> → DB 只能返回 `WHERE nodeLabelPath LIKE '%厨房%'`，但"灶台""锅具"等就不会被查到

### 2. 为什么用双后端而不是纯 Python/纯 Java？

- **Java** 管数据密集型：`competitor_products` 表百万级数据、多维筛选、分页、事务 —— Spring Boot + MyBatis-Plus 是最佳选择
- **Python** 管 AI 密集型：LLM 调用、向量嵌入、Milvus 操作 —— Python 生态（LangChain/LangGraph/HuggingFace）无可替代
- 通过 HTTP API 解耦，未来可以独立扩展

### 3. 为什么选增强型 RAG 而非完全自主 Agent？

参考论文《Agentic RAG 值得吗？》(2026.01)：纯增强型 RAG 的 F1 分数 (87.9) 优于完全自主 Agentic RAG (64.6)。本系统采用 SuperMew 的策略：Agent 仅做路由决策（是否检索、是否分析），实际检索和分析走确定性流水线。
