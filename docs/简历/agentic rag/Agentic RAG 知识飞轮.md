  四个阶段

  阶段一：标记（已有）

  开发者在新品榜页面浏览产品，点击"选中此产品"→ product_click_log 表记录 (userId, asin,
  action='select')。这是人工筛选，把有潜力的产品从噪音中挑出来。

  当前数据：product_click_log 表已有 userId、userName、asin、marketplace、source、action、productTitle、clickedAt。      

  阶段二：分析（Agent 接通后实现）

  当一个产品被标记（或积累一定数量标记后），触发自动分析流程：

  触发方式（选一种）：
    A. 用户标记时实时触发  ── 轻量，适合单产品
    B. Celery 定时任务批量  ── 每天凌晨跑一次，分析前一天所有新标记
    C. 用户在 SuperMew 里问 ── "分析一下最近一周标记的产品"

  分析内容（从 competitor_products 表能拿到的数据）：

  ┌──────────┬────────────────────────────────┬─────────────────────────────┐
  │   维度   │             数据源             │        AI 可以做什么        │
  ├──────────┼────────────────────────────────┼─────────────────────────────┤
  │ 基础信息 │ title, brand, price, imageUrl  │ 生成产品摘要卡片            │
  ├──────────┼────────────────────────────────┼─────────────────────────────┤
  │ 销量趋势 │ units, unitsGr, revenue        │ 判断增长/衰退趋势，标注异常 │
  ├──────────┼────────────────────────────────┼─────────────────────────────┤
  │ 竞争格局 │ bsr, bsrCr, sellers, ratings   │ 分析竞争激烈度，进入壁垒    │
  ├──────────┼────────────────────────────────┼─────────────────────────────┤
  │ 上架时间 │ availableDate, listingDays     │ 判断产品生命周期阶段        │
  ├──────────┼────────────────────────────────┼─────────────────────────────┤
  │ 配送     │ fulfillment, weight, dimension │ 分析物流成本                │
  ├──────────┼────────────────────────────────┼─────────────────────────────┤
  │ 评分     │ score, grade (S/A/B/C/D)       │ 解读评分含义，对比同类      │
  └──────────┴────────────────────────────────┴─────────────────────────────┘

  LLM 生成结构化分析报告，例如：

  ## 产品分析：B0XXXXXXX

  ### 总结
  这是一款上架 45 天的厨房收纳产品，FBA 配送，BSR 排名 #1,200 呈下降趋势，
  月销 3,200 件且环比增长 23%，综合评分 A 级（85 分）。

  ### 优势
  - 销量增速强劲（23% MoM），超过同品类平均 8%
  - BSR 持续下降，近 30 天从 #2,500 → #1,200
  - 评分 4.5 星 / 1,200 评价，质量口碑好

  ### 风险
  - 卖家数量 15 且增长中，竞争加剧
  - FBA 费用可能导致利润率偏低
  - 产品重量 2.3kg，物流成本偏高

  ### 建议
  适合小批量试销，重点关注竞品价格变化和 FBA 费用波动。

  阶段三：保存

  分析报告不是发完就丢——要存进向量知识库，变成可检索的长期记忆。

  LLM 生成的分析报告
    │
    ├─ 结构化 JSON（产品档案）──→ PostgreSQL (product_analysis 表)
    │     asin, analysis_text, score, tags, created_at, week_tag
    │
    └─ 文本分块 + 向量化 ──────→ Milvus
          每个产品报告作为一个文档
          元数据：asin, marketplace, week, grade, tags

  SuperMew 已有完整的分块→向量化→Milvus 入库链路（document_loader.py → embedding.py → milvus_writer.py），直接复用。     

  阶段四：迭代

  这是最关键的一步——数据每周更新，分析也每周迭代。

  新一周数据进来（competitor_products 月表更新）
    │
    ├─ 同一 ASIN 的新旧数据对比
    │     ├─ 销量变化（上升/下降/平稳）
    │     ├─ BSR 变化
    │     ├─ 价格变动
    │     └─ 卖家数变化
    │
    ├─ LLM 生成"本周变化摘要"
    │     "B0XXXXX 本周销量环比下降 15%，BSR 从 #1,200 回升至 #1,800，
    │      可能进入平台期。建议关注竞品是否在降价。
    │      上周分析的风险点'竞争加剧'已开始应验。"
    │
    └─ 追加到 Milvus（同一产品的时间序列分析链）

  这样的 RAG 查询效果：

  ▎ 用户问："最近一个月标记的产品里，哪些销量下滑了？"
  ▎
  ▎ RAG 检索到：
  ▎ - 第 21 周报告："B0XXX 月销 3,200，增长 23%"
  ▎ - 第 22 周报告："B0XXX 月销 2,700，下降 15%，BSR 回升"
  ▎ - Agent 综合回答："B0XXX 本周出现销量拐点，从增长转为下降..."
  ▎
  ▎ 而不只是："B0XXX 月销 2,700"（单点数据）

  ▎  辅助决策的闭环。

  展开版（面试讲）

  背景：跨境电商竞品分析每天面对数百个新品，开发者需要逐个判断哪些值得跟进。纯人工效率低，纯 AI 分析没有方向。

  方案：
  1. 标记层 — 前端新品榜卡片 + 一键标记，开发者凭经验快速筛选，数据落 product_click_log
  2. 分析层 — Agent 自动拉取被标记产品的销量/BSR/价格/配送等 20+ 维度数据，LLM 生成结构化分析（优势/风险/建议）
  3. 知识层 — 分析报告经稠密+稀疏向量化存入 Milvus，支持混合检索 + Jina Rerank 精排
  4. 迭代层 — 每周新数据进来，自动对比同产品历史分析，生成变化摘要，形成时间序列知识链

  亮点：
  - 不是"接个 LLM API"的 demo，而是工程化闭环
  - 纯增强型 RAG（80% 检索 + 20% Agent 路由），避免了完全自主 Agent 的幻觉和成本问题
  - 跨语言架构：Java 管数据采集+筛选，Python 管 AI 分析+向量检索
