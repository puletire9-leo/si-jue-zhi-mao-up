# 筛选系统统一接入建议（2026-06-30）

> 目标：基于当前真实代码，说明 `product-line-selection` 与 `AllSelection` 的筛选链路差异，给出如何继续统一到一套结构分层中的落地建议。

---

## 1. 当前结论

`AllSelection` 已经完成了三层统一：

1. 页面状态层
2. 查询编译层
3. 查询运行层

而 `product-line-selection` 目前仍然是一条并行实现，特点是：

1. 页面自己维护抽屉草稿状态
2. store 自己拼请求参数
3. M02 方法卡在 store 内部分支执行
4. 区间筛选、预设、chip 删除逻辑分散在页面和 store 两处

所以现在系统并不是“一套筛选系统，多页面复用”，而是：

- `AllSelection`：新分层
- `product-line-selection`：旧式页面/store直连

---

## 2. 当前真实差异

## 2.1 AllSelection

当前主链：

```text
SelectionQueryForm / unified-filter-bar / FilterDrawer / RangeFilterPanel
  -> useSelectionFilterState
  -> buildSelectionFilterIntent
  -> buildSelectionQueryPlan
  -> resolveSelectionQueryPlan
  -> executor
```

特点：

- 页面不再手工拼 competitor / zheng / method card 请求参数
- 来源能力通过 `SOURCE_CAPABILITIES` 描述
- 方法卡通过 `METHOD_LENS_DEFINITIONS` 描述
- 快照回退统一走 runtime

---

## 2.2 product-line-selection

当前主链：

```text
ProductLineSelection UI
  -> page draft state
  -> productLineSelection store
  -> loadProducts()
  -> competitorApi.getList() / methodCardsApi.getM02Products()
```

关键现状：

1. `store.ts` 自己维护：
   - `rangeFilter`
   - `qualifyRules`
   - `activeMethodCard`
   - `zhengBatchDate`
   - `searchSellerName`
   - `searchBrand`
   - `activeFilters`

2. `store.ts` 自己拼：
   - `priceMin/priceMax`
   - `unitsMin/unitsMax`
   - `listingDaysMin/listingDaysMax`
   - `bsrMax`
   - `weightMax`
   - `maxVariantCount`
   - `fulfillment`
   - `grade`
   - `createdWeeks`
   - `keywords`
   - `qualifyRules`

3. `index.vue` 自己维护：
   - `draftSeller`
   - `draftBrand`
   - `draftRange`
   - `filterChips`
   - `presetConfig`
   - `removeChip`
   - `clearAllFilters`

这意味着它和 `AllSelection` 的重复不只是“字段重复”，而是“分层职责也重复”。

## 4. product-line-selection 为什么还不能直接复用 queryPlan

`AllSelection` 的 `queryPlan` 当前主要面向：

- `scene`
- `methodId`
- `marketplace`
- 标题/卖家/大类
- 区间筛选
- 快照筛选
- clean/raw/zheng 三类来源

而 `product-line-selection` 额外还有自己的业务上下文：

1. `bsrId`
2. `nodeId`
3. `brand`
4. element/carrier/combo 组合成的 `keywords`
5. `groupByParent=false`
6. L1 / L2 选择驱动的树视图

所以它现在不能“直接把 store 丢进 queryPlan”，原因不是技术问题，而是意图模型还不完整。

换句话说：

- `AllSelection` 的统一已经把“列表筛选”收住了
- 但 `product-line-selection` 还是“品线语境下的列表筛选”

它需要的是扩展统一意图模型，而不是简单 copy 一次 `queryPlan.ts`

---

## 5. 推荐统一路径

## 第一步：继续抽公共状态基元

优先抽这三类，不碰业务接口：

1. range filter helpers
2. preset config builder
3. chip mutation helpers

这样可以先把两个页面里重复的：

- `emptyRange`
- `cloneRange`
- `presetConfig`
- `removeChip`
- `clearAllFilters`

收成共享函数。

这是低风险、高回报的一步。

## 第二步：扩展统一意图模型

建议把当前 `SelectionFilterIntent` 扩成能表达品线语境：

```ts
interface SelectionScope {
  marketplace?: "UK" | "US" | "DE";
  scene?: "all" | "new" | "reference" | "zheng";
  bsrId?: string;
  nodeId?: number;
}
```

再把：

- `brand`
- `keywords`
- `groupByParent`

也纳入统一 intent。

这样 `product-line-selection` 才能被视为“同一查询系统下的另一个场景”，而不是独立系统。

## 第三步：扩展 QueryPlan capability

当 intent 能表达 `bsrId/nodeId/brand/keywords` 之后，再扩 `queryPlan.ts`：

1. competitor executor 支持品线作用域
2. M02 lens 支持 `bsrId/nodeId`
3. zheng 执行器支持 `batchDate + node scope`

这一步完成后，`product-line-selection/store.ts` 才适合真正改成：

```text
UI/store state
  -> buildSelectionFilterIntent
  -> buildSelectionQueryPlan
  -> resolveSelectionQueryPlan
```

## 第四步：最后再决定是否统一页面状态层

页面状态层是否也统一，不必过早强推。

更稳的顺序是：

1. 先统一 intent
2. 再统一 queryPlan/runtime
3. 最后才统一 filterState composable

原因很简单：

- `AllSelection` 的状态源是 `SelectionQueryForm + bar + drawer`
- `product-line-selection` 的状态源是 `tree + drawer + method card + activeFilters`

两者 UI 入口不同，先强拉到同一个 state composable，容易把代码绑死。

---

## 6. 建议的结构目标

长期目标建议收成这几层：

```text
Layer 1: Page UI
Layer 2: Scenario State
Layer 3: Filter Intent
Layer 4: Query Plan
Layer 5: Query Runtime / Executor
```

具体到当前仓库：

### Layer 1: Page UI

- `AllSelection/index.vue`
- `modules/product-line-selection/index.vue`

### Layer 2: Scenario State

- `useSelectionFilterState`
- `useProductLineFilterState`（未来可新增，而不是硬复用）

### Layer 3: Filter Intent

- 统一 `SelectionFilterIntent`

### Layer 4: Query Plan

- `queryPlan.ts`

### Layer 5: Query Runtime

- `queryRuntime.ts`

这样会比“所有页面强共用一个状态 composable”更清晰，也更符合当前代码现实。

---

## 7. 最推荐的下一步

如果继续开发，我建议按这个顺序推进：

1. 抽公共 preset / chip helper
2. 扩 `SelectionFilterIntent` 支持 `bsrId/nodeId/brand/keywords`
3. 让 `product-line-selection/store.ts` 先复用 `queryPlan + runtime`
4. 最后视情况决定是否新增 `useProductLineFilterState`

一句话总结：

> `product-line-selection` 不该继续保留一套独立查询拼装链，但也不该生硬套进 `AllSelection` 的页面状态模型；正确做法是先统一 intent 和 plan，再按场景保留各自的状态层。
