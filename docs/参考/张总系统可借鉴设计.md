## 一、领星 ERP 对接

源码：`cool-admin-midway/src/modules/app/utils/lingxing/`、`service/*lingxing*.ts`、`entity/lingxing_*.ts`

### 值得借鉴

1. **⭐「业务列 + 整包 raw_data JSON」双写落库**
   每张领星表 = 结构化列（服务查询/聚合）+ `raw_data` JSON 整包留底。利润报表 200+ 费用项、平台还在演进，结构化列没映射全的也不丢数据。
   → 本项目 `BazhuayuWeeklyRaw` 已有 `rawJson`，思路一致，扩到领星落库实体即可。

2. **⭐ 唯一键 = 业务查询维度 + 手动幂等 upsert**
   - 报表类用「维度 + 查询时间窗」组合唯一键（如 `msku+sid+start_date+end_date+currency`）
   - 有稳定主键的（FBA货件）用领星 `record_id`
   - 落库走「先按唯一键查存在 → 命中回填 id → save → 分批 500」，同一时间窗反复同步只更新不堆积，天然可重跑
   → 本项目领星 SyncService 直接套此模式。

3. **token 提前 10 分钟刷新 + 被动重放**（实战教训）
   它**没用 refresh_token**（规避一次性 refresh_token 用错即废的并发陷阱），而是 `过期前10分钟直接用 appId/appSecret 重新换 token`，再加请求后检测 "access token not match" 强刷重放一次。靠 `@Singleton` 单例共享 token + 提前量，而非分布式锁。
   → 本项目 `LingxingClient` 当前实现了 refresh_token 续约。建议改成「优先重换、refresh 当可选兜底」——成熟系统的经验是生产环境直接重换更稳。

4. **主流程原子、旁支降级**
   核心数据（Listing+补货）放单事务，失败整体回滚；次要报表（利润/产品表现）用 `.catch()` 只记日志不回滚。按数据重要性分层定事务边界。

5. **客户端预防式限流（pacing）**
   固定 `REQUEST_INTERVAL=500ms` + 批次并发上限 20 + 报表 2s/页。不依赖服务端 429/3001008 重试，用「主动慢」换「不触发限流」。
   ⚠️ 也是其薄弱点：真触发限流会被 catch 吞掉提前结束。旁路降级要和「必须拉全」的场景区分。

6. **批次标记 traceId 串联跨表关联**：补货数据写入打 `时间戳+随机串` traceId，落库后按 traceId 回查再与 listing 多级匹配。「先标记本批、再按批回查」避免与历史数据串味。

7. **API 调用日志旁路化 + 归因化**（付费 API 成本监控范式）
   `recordApiLog` 整体 try/catch（日志失败绝不拖垮业务），`credit_count` 求和算配额，`caller`/`call_location` 把消耗归因到「人/业务位置」，`asins_sample` 只留前 5 个 + `duration_ms`/`response_code` 排障。

### ⚠️ 反面教材
- `app_id/app_secret` 明文硬编码在源码当默认值 → 本项目已做对：凭证进 `config/secrets` + gitignore，保持。

## 二、八爪鱼采集

源码：`cool-admin-midway/src/modules/app/utils/bazhuayu/bazhuayuUtils.ts`、`service/amazon_product_Listing_Lingxing.ts`、`service/bsr_candidate.ts`

> 事实更正：报告所称 `app_amz_bzy_task_management` 实体不存在。真实是 `app_task_management`（通用任务监控表，多种任务共用），文件名 `bzy_task_management.ts` 是历史遗留。

### 值得借鉴

1. **⭐⭐ 固定任务模板 + 内存 slot 状态机做并行采集**（直击本项目痛点）
   每个国家预配 3 个固定 taskId 当「并行槽」，状态轮转 IDLE→STARTING→RUNNING→SAVING，一个槽采完立即喂下一个 URL，不必等整批结束。每次「停旧任务→换 loopItems→启动」复用模板（不创建新任务）。
   ```
   slots = 3个固定taskId
   while (有待处理 || 有槽非IDLE):
     A. 填充空闲槽: 取下一个item → stop旧 → updateLoopItems换URL → start → RUNNING
     B. 批量查RUNNING槽状态: Finished/Stopped → SAVING
     C. SAVING槽: notexported拉数据 → 落库 → markexported → 释放回IDLE
     D. 自适应等待: 有空闲且有待处理 sleep(200), 否则 sleep(5000)
   ```
   → 本项目以图识图曾卡在「10个URL串行、9个Waiting不动」。slot 池正是解法：3-6 个固定任务并行。

2. **⭐ 云端托管增量游标（notexported/markexported）**
   不在本地存 offset，靠八爪鱼「未导出/标记导出」语义保证不重不漏。**严格在落库成功后才 markexported**（否则丢数据）。
   → 本项目 `BazhuayuClient.drainNotExported` 已实现（先 pageHandler 落库再 markExported），方向与成熟系统一致，可放心。

3. **token 三层兜底**：提前10分钟刷新 → refresh_token → 失败则 username/password 重登 → 落库持久化；`httpDo` 对 `Invalid.Token` 自动强刷重发。

4. **实战容错细节（直接抄）**
   - `stopTask` 返回 500 当成功（停已停止的任务会 500）
   - 429 限流递增退避（`10000 * retries`）
   - `updateLoopItems` 固定重试 3 次、间隔 3s
   - 多币种价格清洗：「最后一个分隔符是小数点」启发式区分千分位（€19.99 vs 德式 1.234,56）
   - 超时数据标 `image_state=9`(TIMEOUT)

5. **两层去重**：全局 ASIN 注册表 `bsr_deduplicate`（ASIN 当主键 + source + upsert 幂等）+ 落库时实时区间/重复过滤（竞品价须在原品价 0.5x~2x）。

### 数据流（八爪鱼是 BSR 选品的「竞品发现引擎」）
```
候选品(bsr_candidate) → 八爪鱼以图搜图(stylesnap?q=image_url)找视觉相似竞品
  → 落 bsr_candidate_competitor → Oxylabs关键词补量 → 阿里云算相似度(>0.72)
  → 去重 → 卖家精灵补竞品详情 → 供BSR选品分析
```

### ⚠️ 反面教材
- 长流程在 HTTP 请求里**同步跑、无队列、无重试入口**，靠前端轮询数据库表 → 本项目有 `bazhuayuExecutor` 线程池 + `BazhuayuRunStateService`，已更优；量大可参考其 Go 微服务用 RocketMQ 异步化。
- `taskStatus` 字段混存八爪鱼原始状态和自定义状态；八爪鱼方法在两个 service 大段重复 → 是技术债，勿学。

### 旁证：Go 微服务（长任务正确异步姿势）
`keyword-research-ms-go`：API/Worker 分离 + Asynq 队列 + 立即返回 taskId + 进度流式上报 + retry 端点。缓存 key 设计值得抄：
- **URL 规范化**：抹掉 Amazon 图片尺寸 token，同图不同尺寸 URL 命中同一缓存
- **版本号进 key**（`imgsim:...:v1`）：算法升级换版本号即整体失效
- **对称 key**：成对比较 `(a,b)==(b,a)`
- **分层 TTL**：SERP 12h、图片相似度 7天
- **Redis SETNX 信号量带 TTL 兜底**：跨进程并发限流，持有者崩溃自动释放

## 三、RBAC（用户/角色/权限/菜单）—— 下期「角色管理界面」样板

源码：`cool-admin-midway/src/modules/base/`、`cool-admin-vue/src/modules/base/`

### 数据模型：用户—角色—菜单 三层，四张关联表
```
sys_user ──< user_role >── sys_role ──< role_menu >── sys_menu
                              └──< role_department >── 部门(数据权限)
```

### 核心设计（最该借鉴）

1. **⭐⭐ 一张 `sys_menu` + `type` 字段同时承载「路由 + 按钮权限点」**
   - type=0 目录、type=1 菜单（路由页面，带 router/viewPath）、type=2 按钮（纯权限点，带 `perms` 如 `base:sys:user:add`，逗号分隔可多个）
   - 角色授权 = 勾选这棵菜单树，**一个 UI 同时分配「能看哪些页面」+「能点哪些按钮」**
   - 不建「菜单表+独立权限表」两套，最大简化

2. **⭐⭐ 权限点压成扁平 `Set<String>`，登录时算好放 Redis，校验 O(1)**
   - JWT 只放 `userId/roleIds/username/passwordVersion`，**不放 perms**（要可实时刷新、可能很大）
   - 权限点 `base:sys:user:add` 把 `:` 换 `/` 即 URL → 校验退化成 `perms.contains(uri)`，**接口零注解、新增接口零改代码**
   - 改角色/菜单后立即 `refreshPerms(userId)` 刷新缓存，权限变更实时生效

3. **⭐ passwordVersion 改密踢人**：用户表加 `password_version` 列 + Redis 缓存，改密 +1，拦截器比对 token 里版本号 → 即时失效。低成本解决 JWT 无状态「改密旧token仍有效」通病。

4. **超管短路 + 通用接口白名单**：`username=='admin'` 直接全放行、`/comm/` 人人可访问，99% 请求不查权限表。

5. **数据权限（部门维度）**：`role_department` 中间表 + `relevance`(是否含下级)，查列表自动注入 `where department_id in (授权部门)`。需要「某角色只能看某区域数据」时可抄。

6. **多对多更新「先全删再插入」**：`updateUserRole`/`updatePerms` 都是 delete 后逐条 save，处理多对多最简方案。

### 对照本项目现状
| | 本项目（现状） | 张总系统（样板） |
|---|---|---|
| 用户↔角色 | `users.role` 单字符串 | user_role 多对多中间表 |
| 角色管理界面 | 纯摆设（无API、刷新即丢） | 菜单树勾选授权，落库 |
| 权限映射 | 网关 yml 静态写死，改权限发版 | sys_menu 表，页面点几下即时生效 |
| RBAC 五表 | 已建但闲置（死代码） | 正常使用 |
| 权限校验 | 网关读 yml | 拦截器读 Redis perms |

### 迁移路线（最小可行，给本项目 Spring Boot + 自研 Vue）
1. 建五表 `sys_user/sys_role/sys_menu/user_role/role_menu`，menu 带 `type`+`perms`。把现有 `users.role` 单字符串迁成 user_role 关联（账号中文化刚做完，顺势）。
2. 登录聚合 perms 存 Redis（key `auth:perms:{userId}`）；JWT 加 `password_version`。
3. 写 Spring Interceptor / OncePerRequestFilter：验JWT → 超管短路 → 白名单 → `redisPerms.contains(uri)` → 否则 403。**彻底删掉网关 yml 静态映射**。
4. 前端加 `v-permission` 指令（抄 COOL `checkPerm` 那 30 行，支持 `{or:[]}`/`{and:[]}`），登录后拉 `/permmenu` 拿 `{menus, perms}`，菜单动态渲染、按钮按 perms 显隐。
5. 后台加「菜单管理」页（type 区分目录/菜单/按钮）+「角色管理」页（菜单树勾选授权）——把现在那个摆设 Tab 变成真功能。

权限校验两种风格选其一：
- **A（贴近 COOL，省事）**：权限点用 URL 风格，拦截器直接比对 `request.getRequestURI()`，新增接口零注解。建议起步用 A 替换网关 yml。
- **B（Spring 习惯）**：`@PreAuthorize("hasAuthority('sys:user:add')")` + 自定义 `PermissionEvaluator` 从 Redis 读 perms。更灵活但每接口要标注解。

### ⚠️ 别照抄
- COOL 用 **md5 存密码**（历史包袱）→ 本项目保持 bcrypt/PasswordEncoder。
- COOL `@CoolController` 声明式 CRUD 是 MidwayJS 特有 → 本项目用 MyBatis-Plus `IService` + 泛型 BaseController 达到类似效果。
