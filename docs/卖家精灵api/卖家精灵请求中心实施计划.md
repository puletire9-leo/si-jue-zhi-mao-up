# 卖家精灵请求中心实施计划

> 目标：以后所有卖家精灵请求都能在一个页面看见实况，包含 ASIN 补数、店铺名抓全集、候选池批量抓取、精品店铺复抓。

## 一、为什么要单独做请求中心

候选池、观察池、ASIN 导入页都只是“业务入口”，不应该各自维护一套请求进度。

卖家精灵请求中心负责统一回答：

```text
现在有哪些卖家精灵任务在跑？
跑到第几个请求/第几个店/第几批 ASIN？
已经消耗多少使用次数？
下一次请求预计什么时候发出？
哪些成功、哪些失败、失败原因是什么？
是否可以暂停、继续、停止？
```

核心口径：

- 卖家精灵叫“使用次数”，当前 20000 次/月。
- 一次 HTTP 请求 = 1 次使用次数。
- 店铺名查询一页最多 100 个商品，一页 = 1 次使用次数。
- 店铺名查询按 2 秒/请求限速；实际总时间由总页数决定。
- 暂停/停止是协作式控制：不会强杀已经发出的 HTTP 请求，只在下一次请求前生效。

## 二、覆盖范围

第一版必须覆盖两类请求：

| 类型 | 说明 | 当前来源 |
|------|------|----------|
| `ASIN_LOOKUP` | ASIN 批量补数 / 新品榜补数 | `AsinImportService` / `competitorLookup` |
| `SHOP_LOOKUP` | 店铺名查询抓店铺全集 | `ShopProductSyncService` |

后续继续接入：

| 类型 | 说明 |
|------|------|
| `SHOP_CANDIDATE_BATCH` | 候选池批量确认抓取 |
| `SHOP_PREMIUM_REFRESH` | 精品店铺周期复抓 |
| `MANUAL_SHOP_LOOKUP` | 人工单店抓全集 |

## 三、后端数据结构

### 1. `sellersprite_request_run`

记录一个卖家精灵请求任务。

关键字段：

```text
run_id                  -- 全局任务 ID
request_type            -- ASIN_LOOKUP / SHOP_LOOKUP / SHOP_CANDIDATE_BATCH / SHOP_PREMIUM_REFRESH
trigger_source          -- ASIN_IMPORT / SHOP_CANDIDATE / SHOP_WATCHLIST / SHOP_PREMIUM / MANUAL
trigger_id              -- 来源任务/候选池/观察池/精品池 ID
marketplace             -- UK / DE / US
batch_code              -- 周批次 yyyy-Www
status                  -- PENDING / RUNNING / PAUSED / STOPPING / STOPPED / SUCCESS / PARTIAL_SUCCESS / FAILED
total_units             -- 总工作单元：ASIN 批次数或店铺数
finished_units
success_units
failed_units
total_http_requests     -- 已发出的 HTTP 请求数，即已消耗使用次数
estimated_http_requests -- 预估使用次数，可为空
current_label           -- 当前正在处理的店铺名 / ASIN 批次摘要
next_request_at         -- 下一次请求预计时间，按 2 秒节奏显示
last_error_message
started_at
paused_at
finished_at
created_at
updated_at
```

### 2. `sellersprite_request_item`

记录任务内每个工作单元。

```text
id
run_id
item_type               -- ASIN_BATCH / SELLER_SHOP
item_key                -- ASIN 批次 hash / sellerName
marketplace
status                  -- PENDING / RUNNING / SUCCESS / PARTIAL_SUCCESS / FAILED / SKIPPED
http_requests
total
fetched_count
written_count
failed_count
error_message
started_at
finished_at
raw_context_json        -- 来源候选池 id、watchlist id、ASIN 列表摘要等
```

### 3. 兼容现有表

短期不推翻现有表：

- `competitor_lookup_log` 继续记录每次真实 HTTP 调用，用于月度使用次数统计。
- `asin_import_tasks` 继续记录 ASIN 导入业务任务。
- `shop_fetch_run` 继续记录单店抓取结果。

请求中心作为“运行层”，通过 `run_id / trigger_id / source_run_id` 串起这些表。

## 四、后端服务设计

新增模块：

```text
modules/sellerspriterequest
```

核心服务：

```text
SellerspriteRequestRunService
SellerspriteRequestControlService
SellerspriteRequestWorker
```

能力：

- 创建请求任务。
- 查询任务列表、任务详情、item 明细。
- 暂停：状态置 `PAUSED_REQUESTED` 或直接 `PAUSED`，worker 在下一次 HTTP 请求前停住。
- 继续：`PAUSED -> RUNNING`。
- 停止：`STOPPING`，当前请求结束后不再发下一次请求，最终 `STOPPED`。
- 失败重试：只重试失败 item，不重复成功 item。
- 使用次数统计：每发出一次 HTTP 请求，`total_http_requests + 1`，同时写 `competitor_lookup_log`。

控制规则：

```text
PENDING -> RUNNING
RUNNING -> PAUSED
PAUSED -> RUNNING
RUNNING -> STOPPING -> STOPPED
RUNNING -> SUCCESS / PARTIAL_SUCCESS / FAILED
FAILED / PARTIAL_SUCCESS -> RETRY_RUNNING
```

## 六、前端页面设计

新增页面：

```text
店铺分析 / 卖家精灵请求中心
```

页面结构：

1. 顶部总览
   - 本月已用 / 月上限 / 剩余使用次数。
   - 今日请求数。
   - 正在运行任务数。
   - 下一个请求倒计时。

2. 任务列表
   - 类型：ASIN 补数 / 店铺全集 / 候选池批量 / 精品复抓。
   - 来源：ASIN 导入任务、候选池、观察池、精品池、人工。
   - 状态、站点、批次、开始时间、当前处理对象。
   - 进度：finished / total。
   - 已消耗使用次数。
   - 操作：详情、暂停、继续、停止、重试失败。

3. 任务详情抽屉
   - 当前请求实况。
   - item 明细：店铺名或 ASIN 批次、状态、请求次数、total/fetched/written/failed、错误原因。
   - 关联入口：候选池记录、店铺画像、ASIN 导入任务。

4. 实况刷新
   - 第一版轮询：3 秒一次。
   - 后续可升级 SSE/WebSocket。

## 七、与阶段一的关系

阶段一当前同步抓取逻辑可以保留，用于小批量验证。

但从“大批量店铺抓取”开始，必须走请求中心：

```text
候选池选择店铺
  -> 创建 sellersprite_request_run
  -> worker 按 2 秒/请求执行
  -> 每个店铺仍写 shop_fetch_run
  -> 每次 HTTP 请求仍写 competitor_lookup_log
  -> 前端请求中心看实况、暂停、停止、重试
```

阶段一需要立即修复的小问题：

- 候选池状态流转要收紧，避免已抓取店铺被随意重置回 PENDING。
- 候选池页面不要展示不存在的 `apiCalls` 字段；请求次数实况交给请求中心。
- 文档统一：卖家精灵叫使用次数，不写配额。

## 八、验收标准

1. 同时能看到 ASIN 补数和店铺抓取任务。
2. 单个任务能看到当前处理到哪个店铺/哪批 ASIN。
3. 暂停后不会继续发下一次卖家精灵 HTTP 请求。
4. 停止后不再处理剩余 item，已完成数据保留。
5. 每次真实 HTTP 请求都写 `competitor_lookup_log`，月度使用次数正确增加。
6. 店铺抓取任务完成后，每家店仍有 `shop_fetch_run`，并能跳转店铺画像。
7. 失败 item 可单独重试，不重复成功 item。
