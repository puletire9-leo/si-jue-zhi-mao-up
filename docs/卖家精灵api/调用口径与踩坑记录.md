# 卖家精灵 API 调用口径与踩坑记录

> 本文专门记录系统调用卖家精灵时容易忘的小细节。后续新增卖家精灵能力前，先看这里。

## 1. 市场编码 marketplace

当前系统只支持具体国家站点：

```text
UK
DE
US
```

注意：

- 每次请求必须传具体 `marketplace`。
- 不存在 `ALL` 这个卖家精灵市场编码。
- 系统层如果要查多个国家，应拆成多次请求，而不是传 `ALL`。

参考：

```text
docs/卖家精灵api/表 1.2 市场.md
```

## 2. 店铺名查询 variation 口径

店铺名查询用于抓店铺商品全集、店铺画像、店铺上新流时，默认固定：

```json
{
  "variation": "Y"
}
```

含义：

| 参数 | 含义 | 使用场景 |
|---|---|---|
| `variation=Y` | 不含变体，仅父体/独立商品口径 | 店铺分析、店铺画像、店铺商品数、店铺全集 |
| `variation=N` | 含变体，子 ASIN 也会返回 | 专门研究变体策略、颜色/尺寸/套装结构 |
| 不传 | 默认倾向含变体 | 不建议在店铺分析中省略 |

为什么店铺分析必须默认 `variation=Y`：

- 亚马逊店铺页面显示的总商品数是不含变体的父体商品数量。
- 店铺画像要看“独立商品方向”，不是颜色/尺寸/套装子 ASIN 数。
- 含变体会放大商品数、销量等级分布、方法卡命中数，造成店铺虚高。

已验证细节：

- `variationString=Y` 在当前店铺名查询场景下不可靠或可能被忽略。
- 系统请求统一使用 `variation=Y`，不要用 `variationString` 替代。

## 3. 新品榜 / ASIN 补数 variation 口径

新品榜数据线与店铺全集数据线不同。

```text
competitor_products
  八爪鱼新品榜 + ASIN 卖家精灵补数
  可以含变体
  后续走 competitor_products_clean 去变体
  方法卡主要读 clean 表

shop_products
  店铺名查询返回的店铺商品全集
  固定 variation=Y
  不再做 shop_products_clean
```

也就是说：

- 新品榜/ASIN 补数可以接受含变体，因为后面有 `competitor_products_clean`。
- 店铺全集不应含变体，因为它本身就要对齐店铺页面父体商品数。

## 4. 请求次数怎么算

当前已经明确：

```text
一次 HTTP 请求 = 一次卖家精灵请求次数
当前月度使用次数上限 = 20000 次
```

对 `competitor-lookup` 来说：

```text
每页 size 最多 100 个商品
一页最多 100 个，算 1 次请求
如果一个店铺返回 230 个商品，需要 3 页，也就是 3 次请求
```

判断示例：

| total | size | 预计请求次数 |
|---:|---:|---:|
| 1-100 | 100 | 1 |
| 101-200 | 100 | 2 |
| 201-300 | 100 | 3 |

系统测试时要看返回：

```json
{
  "total": 230,
  "fetched": 230,
  "apiCalls": 3
}
```

如果：

```text
total > 100 但 apiCalls = 1
```

说明分页逻辑可能提前停止，必须暂停继续抓取并排查。

## 5. 店铺名查询分页规则

店铺名查询请求体示例：

```json
{
  "marketplace": "UK",
  "sellerName": "ExampleShop",
  "asins": [],
  "variation": "Y",
  "page": 1,
  "size": 100,
  "orderDesc": true
}
```

分页停止规则建议：

```text
fetched += items.size()

停止条件：
1. total > 0 且 fetched >= total
2. 本页 items.size() < pageSize
3. items 为空
4. API 返回错误
```

不要用“入库成功数 inserted”判断是否继续翻页。

原因：

- upsert 更新行也可能计入 affected rows。
- 重复抓同一批时，inserted/affected 不等于本次真实拉取数量。
- 用 inserted 判断分页，可能导致只抓第一页。

## 6. ASIN 查询分页与页数上限

ASIN 查询也可能出现“一批 ASIN 返回多页”的情况。

当前业务约定：

```text
ASIN 自动分批已经实现。
每批最多自动取 2 页。
```

原因：

- 一批 ASIN 有时会有 2-3 页数据。
- 但为了控制卖家精灵请求次数，当前不无限翻页。
- 先最多 2 页，后续如有明确场景再扩展。

系统通过 `competitor_lookup_log` 记录卖家精灵调用。


## 8. IP 白名单

如果返回：

```json
{
  "message": "Your IP address is not allowed"
}
```

说明是接口后台 IP 白名单问题，不是签名、token 或代码问题。

处理：

1. 查询当前公网出口 IP。
2. 到卖家精灵/对应 API 后台加入 IP 白名单。
3. 再重试请求。

当前查公网 IP 可用：

```powershell
Invoke-RestMethod -Uri 'https://ipinfo.io/json'
Invoke-RestMethod -Uri 'https://ifconfig.me/ip'
```

注意：

- 家宽/办公宽带 IP 可能变化。
- VPN 打开/关闭后出口 IP 可能变化。
- 长期稳定调用最好走固定公网 IP 的服务器。

## 9. 数据落库边界

### 新品榜数据线

```text
competitor_products
competitor_products_clean
```

用途：

- 八爪鱼新品榜。
- ASIN 卖家精灵补数。
- 新品方法卡 M01/M03 等。

### 店铺全集数据线

```text
shop_watchlist
shop_products
```

用途：

- 记录哪些店铺值得抓。
- 记录为什么值得抓。
- 店铺名查询返回的全集商品。
- 店铺画像、店铺上新流、单店详情。

不要再把店铺全集混进 `competitor_products`。

## 10. 常用排查 SQL

看 M01 当前命中：

```sql
SELECT marketplace, COUNT(*)
FROM competitor_products_clean
WHERE m01_active = 1
GROUP BY marketplace;
```

看店铺观察池：

```sql
SELECT marketplace, seller_name, source_type, source_code, hit_count, top_category, status, reason
FROM shop_watchlist
ORDER BY hit_count DESC
LIMIT 20;
```

看店铺全集抓取批次：

```sql
SELECT marketplace, seller_name, batch_date, variation_mode, COUNT(*) AS cnt
FROM shop_products
GROUP BY marketplace, seller_name, batch_date, variation_mode
ORDER BY batch_date DESC, cnt DESC
LIMIT 20;
```

看某店销量分级：

```sql
SELECT sales_tier, COUNT(*)
FROM shop_products
WHERE marketplace = 'UK'
  AND seller_name = '填入店铺名'
  AND batch_date = (SELECT MAX(batch_date) FROM shop_products WHERE marketplace = 'UK')
GROUP BY sales_tier;
```
