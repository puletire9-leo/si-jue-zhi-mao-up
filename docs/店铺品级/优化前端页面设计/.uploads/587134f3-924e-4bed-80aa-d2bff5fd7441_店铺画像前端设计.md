# 店铺画像前端设计

> 给前端实现 AI 使用。目标是把 `analysis-baseline` 后端已经准备好的店铺画像、店铺基线、基线定位能力做成可验证、可复盘、可继续扩展的方法页。当前前端还没有完成这块；已有 `frontend/src/modules/zheng-shop-analysis` 是旧的郑总/选品店铺混合总览，不建议继续往里堆新逻辑。

## 一、页面定位

这不是营销页，也不是静态报表页。

它是一个面向选品/店铺研究的工作台，用来回答：

- 这个店铺在某个国家站点的商品结构是什么？
- A/B/C/D 各层有多少商品？
- A、ABC、D 的主要榜单类目是什么？
- 这家店像不像郑总 UK/DE 精铺基线、自有优质店基线、方法卡高命中店基线？
- 点进单店后，能否直接看到每个等级有哪些商品、ASIN、链接、榜单类目？

页面应安静、密集、可扫描，像运营后台工具，而不是做成大卡片宣传页。

## 五、页面一：店铺画像列表

路径：

```text
/shop-profile
```

### 顶部筛选

使用紧凑工具条，不做大 hero。

控件：

- `marketplace` segmented control：UK / DE / US，默认 UK。
- 数据源切换：实时聚合 / 物化快照。
- `batchDate` 输入或选择器，可空，空时后端取该市场最新批次。
- 店铺名搜索。
- 最小商品数。
- 排序：商品数、A 数、AB 数、ABC 数、D 占比、相似度。
- 刷新按钮。
- 物化按钮：`compute`，需要二次确认。

### 摘要区

用 4 到 6 个紧凑指标块：

- 店铺数
- 商品数
- A 商品数
- ABC 商品数
- D 商品数
- 当前批次

不要用大面积卡片堆叠。

### 表格

主表用 `el-table`，列建议：

| 列 | 说明 |
|---|---|
| 市场 | UK / DE / US |
| 店铺 | sellerName，可点击进入详情 |
| 商品数 | productCount |
| A/B/C/D/未知 | 数字 + 小型分布条 |
| A 占比 | aRatio |
| ABC 占比 | abcRatio |
| D 占比 | dRatio |
| A 类目 | topACategory |
| ABC 类目 | topABCCategory |
| D 类目 | topDCategory |
| 结构标签 | profileType |
| 批次 | latestBatchDate |
| 操作 | 查看详情、查看定位 |

行内分布条用 `SalesTierStack`，固定高度，不要让文字撑开行高。

### 行点击

跳转：

```text
/shop-profile/:marketplace/:sellerName?batchDate=...
```

注意 `sellerName` 需要 URL encode。

## 八、状态与错误处理

### loading

- 列表首次加载用骨架或表格 loading。
- 切换 marketplace 时保留旧数据直到新数据返回，避免闪屏。
- compute / computePositioning 是写操作，按钮必须 loading 且禁用重复点击。

### 错误

必须明确处理：

- SQL 表没建：提示“请先执行 create_analysis_baseline_tables.sql”。
- 没有快照：提示“请先执行店铺画像物化 compute”。
- marketplace 非 UK/DE/US：前端不允许选择，手输参数报错时显示后端 message。
- 基线没有成员：提示先添加成员。
- 基线成员没有快照：提示先执行对应市场 compute。

### 二次确认

以下操作要 `ElMessageBox.confirm`：

- `compute`
- `computePositioning`
- 删除基线成员

确认文案要写清楚市场：

```text
将重新计算 UK 的店铺画像快照，确认继续？
```

## 九、接口调用顺序

开发模式最小验证：

```text
1. 打开 /shop-profile
2. 默认 marketplace=UK
3. GET /api/v1/shop-profile/summary?marketplace=UK&limit=100
4. 点击“物化 UK”
5. POST /api/v1/shop-profile/compute?marketplace=UK
6. 切到“快照”
7. GET /api/v1/shop-profile/snapshots?marketplace=UK&limit=100
8. 进入单店详情
9. GET /api/v1/shop-profile/UK/{sellerName}
10. GET /api/v1/shop-profile/UK/{sellerName}/products?page=1&size=60
11. 创建 ZHENG_UK_DE 基线
12. 添加成员
13. GET /api/v1/shop-profile/positioning?baselineCode=ZHENG_UK_DE&marketplace=UK
```

负向验证：

```text
GET /api/v1/shop-profile/summary?marketplace=ALL
```

前端不应产生这个请求；如果手动访问，后端应报错。

## 十一、验收标准

- 只出现 UK / DE / US 市场选择，不出现 ALL。
- 列表页能看到店铺 A/B/C/D 分布和 top 类目。
- 单店详情能按等级查看商品，包含 ASIN、链接、榜单类目。
- 基线页能创建 `ZHENG_UK_DE`，添加成员。
- 定位页能显示 similarityScore、positioningLabel、profileAdvice。
- 所有写操作都有二次确认和 loading。
- 移动端不要求完整高效，但 1366px 桌面宽度下不能横向崩坏。
- 不使用 landing page、hero、装饰大图、营销文案。

## 十二、当前不做

- 不在前端实现商品族自动聚类。
- 不在前端临时拼 M06 策略。
- 不把旧 M01 店铺排名当成店铺画像。
- 不做跨市场 ALL 汇总；需要时后续由后端显式提供或前端分别请求 UK/DE/US 后组合。
