# 店铺候选池与精品店铺池完整实施计划

> 目标：把“方法卡找店铺”升级为完整店铺作战链路。系统要能从每周几万新品中筛出候选店铺，人工确认后抓取店铺全集，再沉淀精品店铺池，后续按周期复抓并做历史对比，最终反推市场机会和选品方法。

## 一、当前已经实现到哪里

### 1. 新品榜数据线

已具备：

- `competitor_products`：八爪鱼新品榜原始数据 + 卖家精灵 ASIN 补数。
- `competitor_products_clean`：清洗变体后的方法卡消费表。
- M01 当前已能通过 `m01_active` 或等价逻辑筛出命中商品。

当前定位：

```text
新品榜数据线负责发现商品机会。
方法卡从 clean 表筛出合格商品。
```

### 2. 方法卡找店铺雏形

已具备：

- M01 方法卡命中结果可以按店铺聚合排名（`ShopMethodRankService.rankByMethod`，目前仅 M01，传其它方法卡抛异常）。
- 聚合时已按 `marketplace + seller_name + parent_asin/asin` 去重，避免跨周/变体重复放大命中数（`ShopMethodRankMapper.selectM01ShopRanking` 的 base CTE + ROW_NUMBER）。
- `shop_watchlist` 已作为“观察池”记录为什么盯这家店。

当前不足：

- 缺少“候选池”中间层。
- 方法卡命中的几百/上千店铺不应该直接进入正式观察池。
- 需要按批次、来源、原因、状态管理候选店铺。
- 方法卡店铺排名必须支持 `batchCode / effectiveWeekTag` 过滤，否则“本周候选店铺”会混入历史周命中。

> ⚠️ 已落地代码与本计划的衔接（务必先读，否则实现会撞车）：
>
> 现有 `ShopWatchlistService.syncFromMethodRank` + 前端「按方法卡刷新观察池」按钮，
> 干的正是“M01 命中达标 → 直接 upsert 进 `shop_watchlist`（source_type=METHOD_CARD）”。
> 这与本计划“方法卡命中先进候选池、确认后才进观察池”的分层**直接冲突**。
>
> 本计划的最终边界（改造方向，实现时按此收口）：
>
> - **方法卡命中只能落 `shop_candidate_pool`**，`sync-from-method-rank` 改为写候选池。
> - **`shop_watchlist` 只接“候选池确认(SELECTED)后”的店**，source_type 收敛为
>   `CANDIDATE_CONFIRM / MANUAL / BASELINE`，不再直接接 `METHOD_CARD` 批量刷入。
> - 现有 `shop_watchlist.source_type=METHOD_CARD` 的历史数据视为过渡态，改造后由候选池回填，
>   或保留只读、新链路不再写入。
> - 迁移期两条路可短暂并存，但前端菜单只暴露新链路入口，避免用户从两个页面写同一批店。
> - 历史 `shop_watchlist.source_type=METHOD_CARD` 数据迁移策略二选一：
>   1. 保留只读，不参与新候选池流程；
>   2. 回填到 `shop_candidate_pool`，已抓全集的置为 `FETCHED`，未抓的置为 `SELECTED`。
>   实现阶段 1 时必须选择一种，不允许同一批店铺同时从旧观察池和新候选池双入口写入。

### 3. 店铺全集抓取

已具备：

- `shop_products` 已作为店铺全集表。
- 店铺名查询固定使用卖家精灵 `variation=Y`，即不含变体父体口径。
- 抓取后直接用于店铺画像，不再做 `shop_products_clean`。
- 店铺名查询分页已按 `fetched += items.size()` 判断，不用 inserted/affected rows。
- 一页最多 100 个商品，一页 HTTP 请求算 1 次卖家精灵调用。
- 店铺名查询必须按 2 秒/请求限速；分页翻页和批量抓店铺都走同一限速口径，目标不超过 1 分钟 30 次。

当前定位：

```text
只有确认要看的店铺，才抓店铺全集并写入 shop_products。
```

### 4. 店铺画像

已具备：

- `shop-profile` 和 `shop-collection` 已能产出店铺 A/B/C/D 商品结构。
- 能展示商品数、A/B/C/D、ABC 稳定盘、D 测品池、主类目、商品明细。
- 前端已有：
  - `店铺观察池`
  - `店铺全集画像`
  - 旧的 `店铺画像`

当前不足：

- 单店详情仍偏表格，需要补商品图片墙。
- 方法卡命中商品、整店全集商品、精品池历史对比之间的前端跳转还不够顺。

## 二、这次新增的核心业务链路

完整链路：

```text
每周新品批次
  -> 方法卡筛商品
  -> 按店铺聚合候选店铺
  -> 写入店铺候选池
  -> 人工筛选 / 批量确认
  -> 调卖家精灵店铺名 API 抓全集
  -> 抓取成功后进入正式观察 / 画像体系
  -> 从画像中筛精品店铺
  -> 精品店铺池长期维护
  -> 月度/周期复抓全集
  -> 店铺历史对比 + 多店同上分析
  -> 反哺新的选品方法卡
```

关键边界：

| 层级 | 是否消耗卖家精灵店铺 API | 是否有全集商品 | 作用 |
|---|---:|---:|---|
| 方法卡店铺排名 | 否 | 否 | 从新品 clean 表聚合出潜在店铺 |
| 店铺候选池 | 否 | 否 | 承接大批量候选，人工筛选 |
| 店铺观察池 | 可选 | 部分有 | 管理已决定要盯的店铺和原因 |
| 店铺全集画像 | 是 | 是 | 看整店结构和商品明细 |
| 精品店铺池 | 后续周期消耗 | 是 | 长期复用、复抓和对比 |

## 三、后端数据结构计划

### 1. `shop_candidate_pool` 店铺候选池

用途：

```text
记录“某一批、某个方法卡、某个原因下，这家店为什么可能值得抓”。
```

建议字段：

| 字段 | 说明 |
|---|---|
| id | 主键 |
| marketplace | `UK / DE / US` |
| seller_name | 店铺名 |
| seller_id | 店铺 ID，可为空 |
| source_type | `METHOD_CARD / BASELINE / MANUAL / CATEGORY / OWN_GOOD_SIMILAR` |
| source_code | 如 `M01`、`ZHENG_UK_DE`；**NOT NULL DEFAULT ''**（进唯一键，禁止 NULL） |
| batch_code | 周批次，如 `2026-W28`；**NOT NULL DEFAULT ''**（进唯一键，禁止 NULL） |
| batch_date | 数据批次日期，如 `20260708` |
| reason | 入池原因，前端必须展示 |
| hit_count | 方法卡命中商品数（父体去重后，等于排名接口 hitCount） |
| top_category | 主命中类目 |
| sales_tier_summary_json | 命中商品 A/B/C/D 摘要 |
| sample_products_json | 命中商品样例，含图片、ASIN、标题、类目 |
| status | `PENDING / SELECTED / FETCHING / FETCHED / FETCH_FAILED / IGNORED / PROMOTED` |
| watchlist_id | 转入观察池后的关联 ID |
| fetch_run_id | 抓全集后的关联 run |
| premium_id | 转入精品池后的关联 ID，可为空 |
| last_error_message | 最近一次抓取失败原因 |
| last_fetch_at | 最近一次触发抓取时间 |
| operator | 操作人 |
| note | 人工备注 |
| created_at / updated_at | 时间 |

唯一键建议：

```sql
UNIQUE KEY uk_candidate_source (
  marketplace,
  seller_name,
  source_type,
  source_code,
  batch_code
)
```

原因：

- 同一家店在同一周同一方法卡只保留一条候选。
- 不同周可以重复出现，便于观察持续命中。
- 不同方法卡可以分别记录原因。

状态机：

```text
PENDING -> SELECTED -> FETCHING -> FETCHED -> PROMOTED
FETCHING -> FETCH_FAILED
FETCH_FAILED -> FETCHING
任意状态 -> IGNORED
```

规则：

- `PROMOTED` 必须先经过 `FETCHED`，禁止没抓全集、没看画像就进精品池。
- `FETCH_FAILED` 必须保留 `fetch_run_id / last_error_message / last_fetch_at`，允许人工重试。
- 批量确认抓取必须先用原子状态更新抢锁，只有抢锁成功的记录才能实际调用卖家精灵：

```sql
UPDATE shop_candidate_pool
SET status = 'FETCHING'
WHERE id = ?
  AND status IN ('PENDING', 'SELECTED', 'FETCH_FAILED')
```

如果 affected rows = 0，说明已被其它操作占用或状态不允许，必须跳过，防止重复抓取消耗卖家精灵使用次数。

> ⚠️ `batch_code` 必须复用系统现成的 ISO 周口径，禁止另写一套：
>
> - 生成口径唯一真相源 = `ScoringService.getCurrentWeekTag()`，格式 `yyyy-Www`（如 `2026-W28`，
>   基于 `IsoFields.WEEK_BASED_YEAR` + `WEEK_OF_WEEK_BASED_YEAR`）。与 `competitor_products.week_tag`、
>   M04 基线 `tagAsinsByWeek` 完全同源，跨表可直接 JOIN 对齐。
> - 候选池同步时，`batch_code` 从触发时刻的 `getCurrentWeekTag()` 取，或由调用方显式传入历史周次。
> - **禁止 NULL**：`source_code / batch_code` 都进唯一键，MySQL 唯一键放行多个 NULL，一旦留空
>   去重直接失效、候选池堆重复。二者建表都 `NOT NULL DEFAULT ''`。
> - 需要把 `getCurrentWeekTag()` 从 `ScoringService` 提到公共工具（如 `WeekTagUtil`），供候选池/
>   竞品/基线共用，避免复制粘贴出第二套周次算法（对齐铁律8「单一真相源」）。

### 2. `shop_fetch_run` 店铺抓取运行记录

用途：

```text
记录每次卖家精灵店铺名查询的运行情况、使用次数消耗和抓取原因。
```

建议字段：

| 字段 | 说明 |
|---|---|
| run_id | 抓取批次 ID |
| marketplace | 市场 |
| seller_name | 店铺名 |
| trigger_type | `CANDIDATE_CONFIRM / WATCHLIST / PREMIUM_REFRESH / MANUAL` |
| trigger_id | 来源记录 ID |
| fetch_reason | 抓取原因 |
| batch_code | 周/月批次 |
| batch_date | 入库日期 |
| variation_mode | 固定 `Y` |
| total | 卖家精灵返回总数 |
| fetched | 实际拉取数量 |
| inserted | 入库影响数量 |
| api_calls | 请求次数 |
| status | `RUNNING / SUCCESS / PARTIAL_SUCCESS / FAILED` |
| error_message | 错误 |
| started_at / finished_at | 时间 |

要求：

- `shop_products.source_run_id` 必须关联该表 `run_id`（列名以 shop_products 现状 `source_run_id` 为准）。
- 候选池 `shop_candidate_pool.fetch_run_id`、精品池 `shop_premium_pool.last_fetch_run_id` 同样存 `run_id` 值，
  仅列名不同（各表语义命名），指向的都是 `shop_fetch_run.run_id`。
- 前端抓取完成后显示 `api_calls`。
- 请求失败也要落 run，方便复盘。
- `inserted` 不能解释为“新增行数”。由于 `upsert` affected rows 可能包含更新，前后端展示统一使用：
  - `fetched_count`：接口实际拉回的商品行数；
  - `written_count`：成功写入/更新的商品行数；
  - `failed_count`：解析或写入失败的商品行数；
  - `api_calls`：实际消耗的卖家精灵使用次数。

### 3. `shop_premium_pool` 精品店铺池

用途：

```text
长期维护值得重复爬取和学习的精品店铺。
```

建议字段：

| 字段 | 说明 |
|---|---|
| id | 主键 |
| marketplace | 市场 |
| seller_name | 店铺名 |
| seller_id | 店铺 ID |
| source_type | 入选来源 |
| source_id | 来源记录 ID |
| reason | 入选原因，前端必须展示 |
| tags_json | 标签数组，如 `["精铺","上新快","测品强","类目强"]` |
| quality_level | `A / B / C` 或 `HIGH / MID / LOW` |
| refresh_frequency | `WEEKLY / MONTHLY / MANUAL` |
| last_fetch_run_id | 最近抓取 run |
| last_fetch_date | 最近抓取日期 |
| next_fetch_date | 下次计划抓取日期 |
| refresh_status | `IDLE / RUNNING / FAILED`，复抓任务状态 |
| last_error_message | 最近一次复抓失败原因 |
| status | `ACTIVE / PAUSED / REMOVED` |
| note | 备注 |
| created_at / updated_at | 时间 |

唯一键：

```sql
UNIQUE KEY uk_premium_shop (marketplace, seller_name)
```

阶段 2 硬规则：

- `status` 表示这家店是否属于精品池；`refresh_status` 表示当前是否正在复抓，两者不能混用。
- `REMOVED` 是软删除。再次加入同一 `marketplace + seller_name` 时，不新建重复行，而是恢复原行并更新原因、标签和状态。
- 除非明确走“人工强制加入”并立刻触发抓取，否则精品池入池必须要求该店已存在成功的 `shop_products` 最新快照。
- 从候选池加入精品池时，候选池必须已 `FETCHED`，成功后候选池状态推进到 `PROMOTED`，并回填 `premium_id`。
- 从观察池/画像页加入精品池时，也必须能定位到该店最近一次成功抓取 run，用于初始化 `last_fetch_run_id / last_fetch_date`。
- `tags_json` 使用 JSON 数组，前端按标签筛选；不要用逗号字符串做长期事实来源，避免后续标签包含空格、别名或多语言时难以维护。
- 批量复抓精品店铺必须使用和候选抓取同一套 `shop_fetch_run` 与 2 秒/请求限速，`trigger_type=PREMIUM_REFRESH`。
- 复抓抢锁规则：只有 `status=ACTIVE AND refresh_status IN ('IDLE','FAILED')` 的精品店可进入 `RUNNING`；抢锁失败必须跳过。
- 复抓成功后更新 `last_fetch_run_id / last_fetch_date / next_fetch_date / refresh_status=IDLE`；失败后 `refresh_status=FAILED` 并写 `last_error_message`。
- `next_fetch_date` 只作为“建议复抓时间”，第一版不要求自动定时任务；前端先提供按到期筛选和批量手动复抓。

### 4. `shop_products` 批次保留原则

`shop_products` 不能覆盖历史批次。

必须保留：

```text
marketplace
seller_name
asin
batch_date      -- 已有：抓取当天 yyyyMMdd
batch_code      -- 【需补列】ISO 周批次 yyyy-Www，历史对比按周/月聚合归组用
source_run_id   -- 已有：本次抓取 run，关联 shop_fetch_run.run_id
```

> ⚠️ 与已落地建表（`create_shop_collection_tables.sql`）的差异，实现时必须先对齐，否则历史对比缺字段：
>
> - **现状**：`shop_products` 只有 `batch_date`（天粒度）+ `source_run_id`，**没有 `batch_code` 列**。
> - **run 关联字段名**：`shop_fetch_run` 主键叫 `run_id`（run 的唯一标识）。各表关联列存的都是这个
>   `run_id` 值，只是列名随各表语义不同：`shop_products.source_run_id`(以现状为准)、
>   `shop_candidate_pool.fetch_run_id`、`shop_premium_pool.last_fetch_run_id`。
>   **关键：`shop_products` 那列必须是 `source_run_id`（已落地），不要在 shop_products 上新造 `fetch_run_id`。**
> - **必须补 `batch_code` 列**：只有 `batch_date`（天）做不了“本月 vs 上月”“W28 vs W27”的按周/月归组，
>   历史对比与多店同上分析(本计划核心价值)会缺聚合维度。补列 SQL 走 information_schema 守卫，幂等可重跑。
> - `唯一键 uk_shop_asin_batch (marketplace, seller_name, asin, batch_date)` 保持不变——
>   同一天多次抓取覆盖同一行是期望行为，跨天/跨周才留快照。
> - 同一 `batch_code` 内如果存在多个 `batch_date` / `source_run_id`，周度画像和历史对比默认取该店该周最新
>   `batch_date` + 最新成功 `source_run_id` 作为周快照，避免同周多次抓取重复计数。

同一店铺每月复抓一次，就形成不同时间点的全集快照。

后续可基于这些快照实时或物化计算：

- 本期新增商品
- 本期消失商品
- 连续保留商品
- 销量等级上升商品
- 销量等级下降商品
- 多个精品店同周期同时上架的商品族

硬性要求：

### 2. 店铺抓取记录

```http
GET /api/v1/modules/shop-fetch-runs
GET /api/v1/modules/shop-fetch-runs/{runId}
```

筛选参数：

```text
marketplace
sellerName
triggerType
batchCode
status
dateFrom
dateTo
```

候选确认抓取顺序必须固定：

```text
1. candidate 原子抢锁：PENDING/SELECTED/FETCH_FAILED -> FETCHING
2. 创建或更新 shop_watchlist，拿到 watchlist_id
3. 创建 shop_fetch_run，状态 RUNNING
4. 调用 ShopProductSyncService.syncBySellerName(..., watchlistId)
5. 写 shop_products：source_run_id + batch_code + watchlist_id
6. 成功：shop_fetch_run=SUCCESS/PARTIAL_SUCCESS，candidate=FETCHED，watchlist=FETCHED
7. 失败：shop_fetch_run=FAILED，candidate=FETCH_FAILED，记录 last_error_message
```

注意：不能抓完后才创建观察池，否则 `shop_products.watchlist_id` 无法写入。

运行记录必须暴露只读查询接口：

```text
GET /api/v1/modules/shop-candidates/fetch-runs
GET /api/v1/modules/shop-candidates/fetch-runs/{runId}
```

```http
DELETE /api/v1/modules/shop-premium/{id}
```

筛选参数：

```text
marketplace
status
qualityLevel
tag
refreshFrequency
nextFetchBefore
sellerName
```

补充接口要求：

- `POST /shop-premium` 如果同店已存在 `REMOVED` 记录，应恢复该记录，不创建重复精品店。
- `POST /shop-premium/{id}/refresh` 和 `batch-refresh` 返回 `runId / apiCalls / fetchedCount / writtenCount / failedCount`。`apiCalls` 统一表示外部接口调用次数；卖家精灵场景中就是卖家精灵使用次数，一次 HTTP 请求/一页 = 1 次。
- `batch-refresh` 必须支持 dry-run 或预览模式，先返回本次将复抓多少店、哪些已暂停、哪些未到期、预计会消耗多少卖家精灵使用次数。
- 精品池列表必须显示最近成功抓取批次、下次建议抓取日期、最近复抓状态和失败原因。

### 4. 历史对比与多店同上

第一阶段可实时查询，后续再物化。

```http
GET /api/v1/modules/shop-history/{marketplace}/{sellerName}/batches
GET /api/v1/modules/shop-history/{marketplace}/{sellerName}/compare
GET /api/v1/modules/shop-history/multi-shop-new-products
```

重点参数：

```text
baselineBatchCode
compareBatchCode
premiumOnly
minShopCount
category
salesTier
listingDaysMax
```

历史对比硬规则：

- 对比单位不是“任意一行商品”，而是店铺在某个 `batch_code` 下的代表快照。
- 同一 `marketplace + seller_name + batch_code` 有多次成功抓取时，默认取最新成功 `source_run_id`。
- 新增商品定义：compare 快照存在 `product_key`，baseline 快照不存在。
- 消失商品定义：baseline 快照存在 `product_key`，compare 快照不存在。
- 连续保留商品定义：两个快照都存在同一 `product_key`。
- 等级变化只在连续保留商品上计算，例如 `D -> C`、`C -> B`、`B -> A`。
- 商品 key 统一使用 `COALESCE(parent_asin, asin)`，与店铺画像父体口径一致。
- 历史对比第一版按实时 SQL 查询即可，但必须限制参数：单店、两个批次、分页返回商品明细，避免一次拉爆。
- 多店同上第一版先使用可解释的 `product_family_key` 或临时规则键，不直接做黑盒相似判断。
- 如果商品族证据层已有 `product_family_group/member`，优先消费商品族证据；如果暂未聚类，临时规则键必须在结果中明示生成方式。

## 七、第一阶段实现顺序

### 阶段 1：候选池闭环 + 抓取运行记录（合并）

> `shop_fetch_run` 不能后置到阶段2。阶段1 一旦“确认抓取”，就必须同时有 run 表兜底，
> 否则 api_calls / 失败原因只能丢日志，候选池 `FETCHING→FETCHED` 状态机失败无法回滚追溯。
> 而 `syncBySellerName` 现已返回 `total/fetched/written/failed/apiCalls/runId`，落一张表成本极低。

后端：

- 建 `shop_candidate_pool` + `shop_fetch_run`（同批建表）。
- `shop_products` 补 `batch_code` 列，写入时回填 `source_run_id / batch_code`。
- 方法卡排名写入候选池（`sync-from-method-rank` 收口为写候选池，不再写观察池），并且必须按
  `batchCode / effectiveWeekTag` 过滤具体周批次。
- 候选池查询、状态、人工新增。
- 候选确认抓取时先创建/更新观察池拿到 `watchlist_id`，再调用现有
  `ShopProductSyncService.syncBySellerName`，抓取前后落 `shop_fetch_run`：
  - 抓取前插一条 `RUNNING`；
  - 抓取后按结果更新 `SUCCESS/PARTIAL_SUCCESS/FAILED` + `total/fetched_count/written_count/failed_count/api_calls/error_message`；
  - 抓取成功把候选池状态推进到 `FETCHED` 并回填 `fetch_run_id`（关联 run_id）。
- 抓取失败把候选池推进到 `FETCH_FAILED`，写 `last_error_message`，允许重试。
- 批量确认抓取必须用原子状态更新抢锁，避免多人/重试导致同店重复抓取。
- 店铺名查询分页和批量抓取必须 2 秒一次请求限速。
- 当前 `batch-confirm-fetch` 只保留为阶段 1 同步小批验证/兼容入口。
  页面主入口已改为创建阶段 1.5 的 `CANDIDATE_BATCH` 请求中心任务；几百/上千店铺的大批量抓取必须在请求中心推进、暂停、停止和重试。

前端：

- 新增“店铺候选池”页面。
- 支持按批次、方法卡、命中数、类目筛选。
- 支持单店/批量创建请求中心任务，跳转请求中心查看抓取实况、使用次数、成功/失败和错误原因。
- 支持查看命中商品样例。
- 列表分页/排序，默认 `hit_count DESC`，每页 50/100。

验收：

```text
一周几万新品可以聚合出几百/上千候选店铺；
前端能筛选；
只有确认并在请求中心推进后才消耗卖家精灵使用次数抓全集；
每次抓取都能追溯原因、来源、请求次数、成功失败（shop_fetch_run 有记录）；
方法卡候选只来自指定 `batchCode / effectiveWeekTag`，不会混入历史批次。
```

### 阶段 1.5：卖家精灵请求中心（跨模块运行层）

> 详细计划见：`docs/卖家精灵api/卖家精灵请求中心实施计划.md`。
>
> 候选池负责回答“为什么盯这家店、哪些店要抓”；请求中心负责回答“卖家精灵请求现在跑到哪、消耗了多少使用次数、
> 什么时候发下一次、能不能暂停/停止/重试”。

后端：

- 新建统一运行层 `modules/requestcenter`，承接卖家精灵长任务实况。
- 建 `sellersprite_request_run` + `sellersprite_request_item`：
  - run 记录任务维度：类型、来源、站点、批次、状态、总工作单元、已完成、失败数、已消耗使用次数、当前处理对象、下一次请求预计时间。
  - item 记录明细维度：ASIN 批次或店铺名、状态、HTTP 请求数、total/fetched/written/failed、错误原因、来源上下文。
- 第一版已接入：
  - `CANDIDATE_BATCH`：候选池批量确认抓店铺全集。
  - `PREMIUM_REFRESH`：精品店铺池周期复抓。
  - `SHOP_FULL_LOOKUP`：通用店铺全集任务（手工创建/后续扩展）。
- 后续再接入：
  - `ASIN_LOOKUP`：ASIN 批量补数 / 新品榜补数。
- 候选池大批量确认抓取改为创建请求中心任务：
  - 前端调用 `POST /api/v1/modules/request-center/tasks`，`request_type=CANDIDATE_BATCH`，item.trigger_id 写 candidate_id。
  - 返回 `runId/status/totalUnits`，任务创建接口不逐家抓完。
  - 请求中心消费 item 时桥接 `ShopCandidateService.fetchFromRequestCenter`，复用候选池抢锁、观察池、`shop_fetch_run`、成功/失败回写逻辑。
- consumer 执行时统一做：
  - 每次真实卖家精灵 HTTP 请求前检查暂停/停止状态。
  - 每次真实卖家精灵 HTTP 请求前执行 2 秒限速。
  - 每发一次 HTTP 请求，`total_http_requests + 1`，并继续写 `competitor_lookup_log`。
  - 店铺抓取仍然逐店写 `shop_fetch_run`，用于画像快照和历史对比。
- 暂停/停止是协作式控制：不会强杀已经发出的 HTTP 请求，只在下一次请求前生效。
  当前实现的前端推进粒度为每次 1 家店，所以暂停/停止在当前店铺抓完后生效。

前端：

- 新增“卖家精灵请求中心”页面，作为所有卖家精灵请求实况入口。
- 顶部展示本月已用/剩余使用次数、今日请求数、运行中任务、下一次请求倒计时。
- 列表展示 ASIN 补数、店铺全集、候选池批量、精品复抓等任务。
- 详情抽屉展示 item 明细：店铺名或 ASIN 批次、状态、使用次数、total/fetched/written/failed、失败原因。
- 支持暂停、继续、停止、失败重试。
- 候选池页面保留“为什么入池”和“选择哪些店”，抓取实况跳转到请求中心看。

验收：

```text
同一个页面能看见 ASIN 请求和店铺请求；
批量店铺抓取不会卡住前端请求线程；
暂停后不再发下一次卖家精灵 HTTP 请求；
停止后剩余 item 不再处理，已完成数据保留；
每次 HTTP 请求都能正确计入卖家精灵使用次数；
店铺任务完成后仍能通过 shop_fetch_run 跳转店铺画像。
```

## 八、关键设计原则

1. 候选池不等于正式店铺库。方法卡命中只落候选池，不直接进观察池。
2. 候选池是临时候选记录，不代表正式盯店；确认抓取成功后进入 `watchlist/shop_products/画像体系`，才算正式店铺入库。
3. 状态机单向不可跳级：`PENDING → SELECTED → FETCHING → FETCHED → PROMOTED`。
   `PROMOTED`(进精品池)**必须**先经过 `FETCHED`(抓过全集、看过画像)，
   禁止 `PENDING/SELECTED` 直接 `PROMOTED` 绕过画像验证。`FETCH_FAILED` 可重试，`IGNORED` 可从任意态进入。
4. 方法卡找店铺必须按 `batchCode / effectiveWeekTag` 过滤，不能拿全历史排名冒充本周候选。
5. 确认抓取成功后，才进入全集画像。
6. 店铺全集固定 `variation=Y`，不含变体。
7. 店铺名查询请求按 2 秒一次限速；每页最多 100 商品，每页算一次卖家精灵请求。
8. 每次店铺抓取都必须记录 run 和请求次数（`shop_fetch_run`，阶段1 即落地）。
9. `shop_products` 保存历史批次，不覆盖；批次归组用 `batch_code`(ISO 周)。
10. 精品店铺池是可 CRUD 的长期复用池，不是一次性结果。
11. 前端必须展示“为什么入池”，否则后续无法判断筛选质量。
12. 大数据量页面必须有批次、方法卡、类目、命中数、状态筛选，并且接口分页。
13. 单店详情必须图片主导，表格只是补充。
14. 历史对比和多店同上分析最终要反哺新方法卡。
15. 周次口径单一真相源：`batch_code` 全系统只走 `getCurrentWeekTag()`(建议提为 `WeekTagUtil`)，
    禁止各表各写一套 ISO 周算法（对齐 Java 铁律8）。
16. 精品池状态和复抓状态分离：`status` 管这家店是不是精品，`refresh_status` 管复抓任务是否运行/失败。
17. 精品池删除为软删除；再次加入同一店铺应恢复旧记录，不创建重复精品店。
18. 画像、历史对比、商品墙必须绑定同一个快照参数，不能指标来自最新批次、商品来自旧批次。
19. 历史对比以 `product_key = COALESCE(parent_asin, asin)` 判断新增/消失/保留，与不含变体父体口径一致。
20. 多店同上第一版只做可解释规则，不做黑盒相似；结果必须能展开到参与店铺和样例商品。

## 九、最终闭环

这套系统最终要能回答：

- 本周哪些店铺通过了 M01/M03 方法卡？
- 哪些店铺值得消耗 API 抓全集？
- 这些店铺为什么进候选池？
- 哪些店铺已经确认值得长期盯？
- 精品店铺这个月相比上个月新增了什么？
- 多家精品店是否同时上了相似方向？
- 这些共同动作能不能生成新的选品候选或方法卡？

最终形态：

```text
新品批次 -> 方法卡 -> 店铺候选 -> 店铺全集 -> 精品池 -> 周期复抓 -> 历史对比 -> 市场信号 -> 新方法卡
```
