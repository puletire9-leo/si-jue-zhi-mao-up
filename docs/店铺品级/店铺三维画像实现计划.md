# 店铺三维画像实现计划

## 目标

把店铺画像从单维 A/B/C/D 解释升级为三维结构：

```text
销量层：A / B / C / D / UNKNOWN
时间层：新品 / 成长期 / 成熟品 / 老品 / 未知
注意与倾向层：好品倾向 / 普通 / 需复核 / 强注意 / 未知
```

三维画像回答：

```text
卖得动吗？
是最近卖动的吗？
我们能不能学习复制？
```

它不替代方法卡命中数。方法卡命中数继续负责“找店、排序、筛选”；三维画像负责解释“这家店为什么值得看，哪里值得学，哪里要注意”。

## 阶段 1：字段与口径统一

后端需要把每个店铺商品统一加工出三个基础维度。

### 1. 销量层

沿用 `sales_tier`：

| 条件 | salesTier |
|---|---|
| units >= 100 | A |
| units >= 50 | B |
| units >= 15 | C |
| units < 15 | D |
| units 为空 | UNKNOWN |

### 2. 时间层

新增统一枚举字段，建议命名：

```text
ageBucket
```

| 条件 | ageBucket | 中文 |
|---|---|---|
| listing_days <= 90 | NEW | 新品 |
| listing_days <= 180 | GROWING | 成长期 |
| listing_days <= 365 | MATURE | 成熟品 |
| listing_days > 365 | OLD | 老品 |
| listing_days 为空 | UNKNOWN | 未知 |

必须拍板的口径：

- `ageBucket` 是互斥分桶，一个商品只能落一个桶。
- 三维画像、矩阵统计、店铺类型判断，都必须使用互斥 `ageBucket`。
- 现有 `new30Count / new90Count / new180Count / old180Count` 是累计窗口统计，不是时间层分桶。
- `new30Count` 用于观察“超新商品”，`new90Count` 可辅助表示新品规模，`new180Count` 用于观察半年内动向，`old180Count` 只是 180 天以上沉淀窗口；它包含成熟品和老品，不能等同于 `OLD`。
- 前端展示累计窗口时必须写清楚“累计窗口”，不能把 `new30 + new90 + new180 + old180` 相加，也不能拿它们做三维矩阵。

后端字段建议：

| 字段 | 口径 | 用途 |
|---|---|---|
| `ageBucketStats.NEW` | `listing_days <= 90` | 三维画像时间层 |
| `ageBucketStats.GROWING` | `91 <= listing_days <= 180` | 三维画像时间层 |
| `ageBucketStats.MATURE` | `181 <= listing_days <= 365` | 三维画像时间层 |
| `ageBucketStats.OLD` | `listing_days > 365` | 三维画像时间层 |
| `ageBucketStats.UNKNOWN` | `listing_days 为空` | 三维画像时间层 |
| `new30Count` | `listing_days <= 30` | 运营观察窗口 |
| `new90Count` | `listing_days <= 90` | 兼容/筛选窗口 |
| `new180Count` | `listing_days <= 180` | 运营观察窗口 |
| `old180Count` | `listing_days > 180` | 兼容/沉淀窗口 |

### 3. 注意与倾向层

当前后端 `insight` 已返回：

- `attentionLevel`
- `attentionReason`
- `labelMeaning`
- `attentionTags`
- `tendencyTags`
- `categoryLabelStats`

后续需要把规则从 `ShopCollectionService` 中抽出，形成独立规则类：

```text
ShopProfileLabelRule
```

第一版规则仍可硬编码，后续再配置化。

## 阶段 2：后端聚合指标

在 `shop_products` 父体去重后的基础上，增加三维聚合。

### 1. 店铺列表指标

`GET /api/v1/modules/shop-collection/selection-shops`

建议新增或补齐：

| 字段 | 含义 |
|---|---|
| newProductCount | 新品商品数 |
| newABCCount | 新品 A/B/C 数 |
| newABCRatio | 新品 A/B/C 占比 |
| oldDCount | 老 D 数 |
| oldDRatio | 老 D 占比 |
| goodTendencyCount | 好品倾向数量 |
| attentionStrongCount | 强注意数量 |
| attentionReviewCount | 需复核数量 |
| shopProfile3dType | 三维店铺类型 |

### 2. 单店详情指标

`GET /api/v1/modules/shop-collection/{marketplace}/{sellerName}/insight`

当前已有：

- M01 命中数

- 平均上架天数
- 平均销量
- A/B/C/D 各层时间统计

- 注意/倾向标签聚合

下一步补充：

| 指标 | 说明 |

## 阶段 3：店铺类型规则

先做规则标签，不做复杂黑盒评分。

| 店铺类型 | 初版判断方向 |
|---|---|
| 新品发动机型 | 新品 A/B/C 多，M01 命中多，好品倾向高 |
| 健康精铺飞轮型 | 老 A/B 有利润，新 D 有测品，新 B/C 有成长 |
| 成熟利润型 | A/B 多但偏成熟/老品，新品能力一般 |
| 成长测品型 | 新 D 多，开始出现新 C/B |
| 稳定候选池型 | B/C 成熟品厚，A 不多 |
| 高注意高销量型 | 新 A/B/C 不少，但强注意或需复核占比高 |
| 老品沉淀型 | 老 D 多，新品少 |
| 小样本待观察型 | 商品数不足 |

说明：

- 店铺类型只是解释标签，不是最终评级。
- 前端必须展示解释，不只展示标签名。
- 后续可基于郑总基线、自有优质店基线调阈值。

## 阶段 4：商品明细筛选

店铺商品明细需要支持按三维筛选：

```text
GET /api/v1/modules/shop-collection/{marketplace}/{sellerName}/products
```

建议新增参数：

| 参数 | 说明 |
|---|---|
| salesTier | A/B/C/D/UNKNOWN |
| ageBucket | NEW/GROWING/MATURE/OLD/UNKNOWN |
| attentionLevel | ATTENTION_STRONG/ATTENTION_REVIEW/GOOD_TENDENCY/NEUTRAL/UNKNOWN |
| m01Only | 只看 M01 命中商品 |
| category | 类目 |
| keyword | 标题关键词 |

这样前端可以直接查看：

- 新品 A/B/C 商品
- 老 D 商品
- 好品倾向新品
- 强注意高销量商品
- M01 命中商品墙

## 阶段 5：前端接入

### 1. 竞品店铺列表

读取：

```text
GET /api/v1/modules/shop-collection/selection-shops
```

展示：

- M01 命中数
- 新品 A/B/C
- 老 D
- 好品倾向
- 强注意 / 需复核
- 三维店铺类型
- 点击进入单店画像

### 2. 单店画像详情

读取：

```text
GET /api/v1/modules/shop-collection/{marketplace}/{sellerName}/insight
```

展示：

- 店铺总览
- 销量 × 时间矩阵
- 销量 × 注意/倾向矩阵
- A/B/C/D 商品图片墙
- 新品 B/C 商品墙
- 老 D 商品墙
- 好品倾向 top 类目
- 强注意/需复核解释

前端文案必须强调：

```text
注意标签用于提醒人工复核，不代表系统拒绝。
好品倾向表示类目形态接近验证好品线，不代表一定能做。
```

## 阶段 6：验收标准

### 后端验收

- 单店能返回三维画像数据。
- 单店能同时返回互斥 `ageBucketStats` 和累计窗口 `new30/new90/new180/old180`，且前端不会混用二者。
- 店铺列表能按新品 A/B/C、老 D、好品倾向、强注意筛选。
- 商品明细能按销量层、时间层、注意/倾向层筛选。
- 标签说明不出现“系统拒绝”“禁做判断”等误导语义。

### 前端验收

- 用户能看出这家店的 A 是新 A 还是老 A。
- 用户能看出 B/C 是新品起量还是老长尾。
- 用户能看出 D 是正常测品池还是老品沉淀池。
- 用户能看出哪些类目有好品倾向，哪些类目需要人工复核。
- 用户能从店铺列表跳到单店画像，再进入商品墙查看具体 ASIN。

### 业务验收

系统应能回答：

```text
这家店卖得动吗？
这家店最近还在出新品吗？
这家店的新品是否接近我们的好品模型？
这家店哪些方向值得学？
这家店哪些方向需要谨慎？
```

## 当前状态

截至 2026-07-09：

- 销量层已经实现。
- 时间层已在 `insight` 中实现：最早上架时间、平均上架天数、A/B/C/D 分层年龄统计、互斥 `ageBucketStats`、销量 × 时间矩阵。
- 注意与倾向层已在 `insight` 中实现：`attentionLevel / attentionTags / tendencyTags / categoryLabelStats`，并补充销量 × 注意、时间 × 注意矩阵。
- 商品明细已支持三维筛选，并在每行返回 `ageBucket / m01Hit / attentionLevel / attentionReason / labelMeaning`，前端可直接解释每个 ASIN 为什么被筛出。
- `attentionLevel` 商品筛选已从“末级类目粗筛”修正为逐商品精确打标签，避免同名末级类目但完整路径不同导致误带入。
- 店铺列表已补三维摘要：`newABCCount / oldDCount / goodTendencyCount / attentionStrongCount / shopProfile3dType` 等，并支持按好品倾向下限、强注意上限筛店。
- 店铺列表三维摘要已从“每个店铺逐个补算”优化为批量 SQL 拉取 `销量层 × 时间层 × 类目` cells 后 Java 侧分组补标签，避免默认列表扩大后出现 N+1 查询。
- 文档口径已从“禁做/拒绝”修正为“注意/倾向”。

仍可继续优化：

```text
1. 注意/倾向层当前是硬编码规则类，后续应配置化，并记录规则版本。
2. 商品级标签目前请求时计算，后续可落到 method_product_hit / shop_product_label_cache 这类缓存层。
3. M01 已接入，后续 M03/Mxx 应统一进入方法卡命中缓存，不要在店铺画像里为每张卡重复写规则。
4. 批量 SQL 已解决列表 N+1，但如果以后一次看几万家，还应增加标签缓存/画像快照表，避免实时聚合压力过大。
5. 需要用生产真实店铺跑接口验收，校验三维类型是否符合人工直觉。
```

新增计划文档：

```text
docs/店铺品级/店铺总览与竞品店铺选品联动计划.md
```

核心调整：

- 旧“选品中心 / 竞品店铺”仍可保留为历史竞品商品池，但不再作为研究某个店铺的主入口。
