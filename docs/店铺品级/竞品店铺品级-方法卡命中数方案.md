# 竞品店铺品级改造：方法卡命中数（方案B）

> 讨论定稿于 2026-07-06。核心：店铺品级从"像不像郑总"（相似度评分 A/B/C/D/F）
> 改为"按方法卡标准，产出了多少合格新品"。
>
> 2026-07-07 修订：补充两层边界。商品基础特征处理层只产出辅助数据（如 `sales_tier`、`listing_days`、`weight_g`），消费层的方法卡片独立筛选合格品。`m01_active` 是当前 M01 店铺排名的性能优化，不作为未来所有方法卡的默认建模方式。

## 一、业务背景

新品榜合格数据严重不足，需要找新的稳定新品来源。思路：
**从已筛选的好品榜单反推——在这些榜单里持续上合格新品多的店铺，就是值得盯的货源/竞品店铺。**

把"选品"升级为"选店铺"：找到能持续产出合格新品的店铺 = 找到稳定新品来源。

## 二、核心设计

### 2.0 两层口径：数据处理层与消费层

店铺品级依赖两层能力：

| 层级 | 职责 | 示例 |
|------|------|------|
| 数据处理层（辅助） | 把原始商品数据加工成可复用基础特征，不直接判定方法卡命中 | `listing_days`、`weight_g`、`sales_tier`、`dedup_key` |
| 消费层（方法卡片） | 每张方法卡独立消费基础特征和业务证据，直接筛选合格品 | M01、M02、M03、未来基于销量分级的新方法卡 |

因此：

- 单品销量 A/B/C/D 分级是基础特征，不是方法卡。
- 方法卡可以引用销量分级，但命中逻辑必须由该方法卡自己定义。
- 店铺命中数 = 选择某张方法卡后，按这张卡的命中商品聚合到店铺。

### 2.0.1 店铺商品数口径：不含变体

店铺维度的商品数量、方法卡命中数、销量分级分布，默认按“不含变体”的父体商品口径统计。

原因：

- 亚马逊店铺页面展示的总商品数，本身就是不含变体的父体商品数量。
- 店铺筛选要判断一家店有多少独立商品方向，而不是多少颜色/尺寸/套装子 ASIN。
- 含变体数据会把同一父体商品重复计入，放大店铺规模和方法卡命中数。

因此后续通过卖家精灵 API 获取店铺/统计类数据时，默认请求：

```json
{
  "variation": "Y"
}
```

只有在专门分析变体策略时，才使用 `variation=N`。

### 2.1 方法卡 = 可插拔的"合格标准"定义器

方法卡（M01 新品榜加速法 / M02 郑总模型 / 未来 Mxx）已经把"什么是合格新品"
封装成可复用的 SQL 片段（`MethodCardMapper.xml` 的 `<sql id="M01Where">`）。

店铺品级不再写死，而是：
> **店铺分 = 用某张方法卡的标准去筛这家店的品，命中（合格新品）越多，越值得盯。**

新增方法卡 → 店铺品级面板按卡片切换口径评店 = 模块化可调节。
彻底废弃 A/B/C/D/F 相似度品级，全面改成"卡片命中数"口径。

### 2.2 关键机制：上架天数实时算，老品自动新陈代谢

- M01 合格标准里含"上架≤30/60/90天 + 对应销量门槛"。
- 一个品只要还命中 M01，就说明它此刻仍够新、仍合格。
- 上架超 90 天的品自动掉出 M01 池 → 店铺合格数随之下降。
- **不需要额外的"入库周/月"窗口**——上架天数就是天然时效阀门。
- 常年高分的店 = 持续产出合格新品 = 稳定货源。

### 2.3 两套口径各司其职

| | 普通 M01（选品列表） | 竞品店铺品级 |
|---|---|---|
| 批次范围 | 单个周批次（最新周） | **所有周批次** |
| 为什么 | 只看最新批，避免全表筛选卡顿 | 要看一家店全部还合格的品，必须跨批次 |
| 时效控制 | 上架≤90天 + 周批次双重限 | 上架≤90天（单一阀门，把数据量压小） |

### 2.4 店铺分级消费层 = 方法卡命中品聚合

店铺分级不是重新定义商品是否合格，而是消费某张方法卡已经圈出的命中商品，再按店铺聚合。

第一版店铺分级行以“命中品画像”为核心：

| 字段 | 含义 |
|------|------|
| `methodId` | 当前店铺分级使用的方法卡，如 M01 |
| `hitCount` | 该店铺命中当前方法卡的商品数（按 clean 表父群组代表行） |
| `topCategory` | 命中品里最高频的末级类目 |
| `avgPrice` / `minPrice` / `maxPrice` | 命中品价格带 |
| `salesTierACount` / `B` / `C` / `D` / `Unknown` | 命中品的基础销量分级分布 |

注意：

- 销量分级分布只描述“命中当前方法卡的商品”，不是整家店所有商品。
- `sales_tier` 是商品基础特征，不能单独推出方法卡命中。
- 旧的“像不像郑总”相似度评级保留为独立可选视图，不混进方法卡命中排名。
- 未来 M02/M03/Mxx 要接入店铺分级，必须显式定义自己的 hit source，不默认新增 `mxx_active` 基础字段。

### 2.5 精铺店铺画像：销量分级作为辅助模型

2026-07-07 郑总 UK/DE 双市场样本验证后，补充一层“精铺店铺画像”：

- A 级产品代表利润锚点，适合观察一家店最终靠什么赚钱。
- A+B+C 更适合代表店铺稳定经营画像和主打法。
- D 级不能直接判死，必须叠加上架时间判断它是新测品还是长期失败品。
- 对精铺卖家，D 层规模本身是测品能力的一部分，不应按精品店逻辑简单扣分。

因此，方法卡命中数仍是店铺分级主线；销量分级画像作为辅助解释层：

```text
方法卡命中数：回答这家店产出了多少符合当前方法卡的合格品
销量分级画像：回答这家店的利润锚点、稳定候选池、测品池结构是什么
```

未来店铺品级分析面板建议并列展示：

| 模块 | 作用 |
|------|------|
| 方法卡命中数 | 直接排名与筛选店铺 |
| A/B/C/D 整店分布 | 判断精铺结构 |
| A 层 top 类目 | 抽取利润方向 |
| ABC 层 top 类目 | 抽取稳定打法 |
| D 层 top 类目 | 观察测品方向 |
| D × 上架时间 | 区分新测品与老失败品 |

详细样本分析见：`docs/店铺品级/郑总店铺精铺模型观察.md`。

## 三、技术方案（打标 m01_active + 增量维护）

### 3.1 现状问题

- `listing_days` 是**入库时冻结的快照**（`CompetitorFilterService:42` 入库时算一次存死）。
  60 天后库里还是旧值，老品永不掉出 M01 → 池子只涨不缩 → 堵塞 + 店铺分虚高。
- `filter_mode`(MODE1/MODE2/FAIL) 同样是入库冻结快照，别处（选品列表/店铺候选）在用，不能动。
- 没有任何 @Scheduled 任务刷新时效（现有 @Scheduled 都是八爪鱼采集）。
- available_date 为空的品 → listing_days=999 → 天然被 M01 排除（正确，空上架日不算合格新品）。

### 3.2 为什么选"打标"而非"每次实时算全表"

纯实时算（每次查询跑全表 DATEDIFF）：准，但数据量大时慢，且反复对已过期数据做无用计算。
每天全表 UPDATE 刷新：40万+行写压力大。

**选定方案：新增独立字段 `m01_active`，增量维护，查询只读标记。**
- 查询快：`WHERE m01_active=1 GROUP BY seller` 秒出，不碰 DATEDIFF、完全不扫过期数据。
- 不重复算过时数据：过期品每天被摘标退场，之后不再参与。
- 店铺分自然新陈代谢：新品进、老品出。

### 3.3 m01_active 维护机制（两个入口，分工不重叠）

**唯一变化来源拆成两类，各管各的，都是增量小操作，永不全表重算：**

| 入口 | 时机 | 做什么 | 为什么 |
|------|------|--------|--------|
| 导入时补标 | 每次 API 导入 | 数据过 `CompetitorFilterService` 算 filter_mode 的**同一遍**里，顺手算 `m01_active` | 零额外成本；新数据立即正确 |
| 每日摘标 | 每天 0 点 @Scheduled | `UPDATE ... SET m01_active=0 WHERE m01_active=1 AND DATEDIFF(NOW,available_date)>=90` | 纯因时间流逝而过期的品退场；只动"刚满90天"的一小批 |

- 新品靠导入补标，过期靠每日摘标 → 两边加起来永远准。
- 打标标准 = M01 全套（价格/重量/销量档 + 上架<90天 + available_date 非空），
  **分站点**（UK/DE/US 阈值不同），复用 `MethodCardServiceImpl.ruleFor()` 同一套参数，阈值只一处定义，避免漂移。

### 3.4 落地清单（按序）

1. **数据库**：`competitor_products` + `competitor_products_clean` 加字段
   `m01_active TINYINT DEFAULT 0`，加索引 `(marketplace, m01_active, seller_name)`。
   不碰 filter_mode。
2. **导入补标**：`CompetitorFilterService` 算 filter_mode 那一遍里，按 M01Rule 算 m01_active 一并写入。
3. **每日摘标任务**：新增 @Scheduled(每天0点)，按站点增量 UPDATE 过期品 m01_active=0。
4. **店铺排名 SQL**：新增 `selectM01ShopRanking`，`WHERE m01_active=1 GROUP BY seller_name`，
   `COUNT(DISTINCT 父ASIN) DESC`，带主打子类目 + 均价聚合。走 clean 表（已去变体）。
5. **后端接口**：ShopRating 模块新增"方法卡命中数排名"，与现有相似度评分并存（先不删）。
6. **前端店铺总览**（本阶段先不做）：主口径切换成方法卡命中数；列 = 店铺名 / 合格新品数（排序）
   / 主打子类目 / 均价。支持方法卡切换（M01 先做通，后续卡片照抄）。

### 3.5 边界与约定

- available_date 为空 / <=0 的品：不打标（m01_active=0），天然排除。
- 未来加 M02/M03：M02 是 deng_zong 店铺维度数据，本身按店铺组织，另行处理；
  m01_active 只服务 competitor_products 的 M01 口径。若未来要多卡片打标，再评估是否泛化成 method_active。
- 现有相似度品级（ShopRatingServiceImpl）保留不动，前端默认展示新口径，相似度作为可选 tab。
- 不过度设计：暂不做"周/月/3个月"多档切换，固定 90 天上架阀门（M01 最宽档）。
