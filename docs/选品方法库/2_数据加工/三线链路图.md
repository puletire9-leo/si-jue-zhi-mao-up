# 三线链路图 · 当前系统状态版

> 状态：2026-06-26 重新对照 Java 代码 / Mapper SQL / 当前方法库整理。
> 早期 H1-H4 文档里的“复活计划”已经不是当前状态；本文件只记录当前代码能支撑的链路边界。

---

## 一句话总判断

当前系统已经不是“三条空管线待复活”，而是：

- L1 已有 `competitor_products_clean` 物化清洗层，给 ①②M04/部分 ④ 候选拉取做干净底座
- ①销量基线、②错位机会、③自有战绩、M04 新品分级都已有 Java 后端能力
- ④元素机会引擎已有预览/人工审阅能力，但三张正式元素表还不是运行主事实
- M05 老品稳态分级仍是 L3 方法卡片占位，L2 暂无对应计算产物
- 三线合成的完整 `40/30/30` 打分引擎还没落地；当前已落地的是 `③×② 可行动机会` 交集视图

---

## 共用底座：先清洗，再加工

```
competitor_products 原表
  ├─ 保留全部父子变体、详情、写入、查重
  └─ 每次导入后清洗
        ↓
competitor_products_clean 物化清洗表
  ├─ 按 marketplace × effective_week_tag × dedup_key 去重
  ├─ 每个父 ASIN 群组选一行代表
  └─ 给统计、分位、聚合、候选排序使用
```

**当前代码证据**

| 能力 | 入口 / 文件 |
|---|---|
| 增量清洗接口 | `CleanLayerController`：`/api/v1/clean-layer/refresh-week-batch`、`refresh-by-effective-week-tag` |
| 清洗实现 | `CleanLayerServiceImpl` + `CompetitorProductsCleanMapper.xml` |
| ①大类基线 | `CategoryBsrBaselineMapper.xml` FROM `competitor_products_clean` |
| ①小类基线 | `SubcategoryBaselineMapper.xml` FROM `competitor_products_clean` |
| ②错位机会 | `CategoryDislocationMapper.xml` FROM `competitor_products_clean` |
| M04 新品基线 | `CategoryAgeTierBaselineMapper.xml` FROM `competitor_products_clean` |
| ④候选拉取 | `ElementDiscoveryServiceImpl` 调 `selectCleanCandidatesForDiscovery` |

**维护规则**

- 聚合、分位、COUNT/AVG/SUM、候选排序：用 `competitor_products_clean`
- 单 ASIN 详情、父子展开、查重、写入、UPDATE：用 `competitor_products`

## ①线：销量基线

**回答的问题**：这个大类/小类在当前市场里到底有多少量？候选放在对应位置是头部、中位，还是长尾？

```
competitor_products_clean
  ↓
category_bsr_baseline       大类：marketplace × bsr_id × bsr_bucket × month
subcategory_baseline        小类：marketplace × bsr_id × Amazon leaf × month
  ↓
/api/v1/category-baseline/compute-bsr
/api/v1/category-baseline/bsr-health
/api/v1/category-baseline/compute-subcategory
/api/v1/category-baseline/subcategory-health
```

**当前状态**

- 已落地：大类 BSR 分桶基线、小类 leaf 基线、查询接口、单测
- 小类粒度已收紧到 `marketplace × bsr_id × sub_category × month`
- `manual-candidates` 已能把 ①线大类/小类基线挂到候选说明里

**边界**

- 基线是参照尺，不是最终推荐结论
- leaf 样本 `<30` 时不会形成小类基线，需要回退到大类/M04 或人工判断

---

## ②线：聪明卖家 / 错位机会

**回答的问题**：哪个小类“本土在做、CN 还没卷满”，值得作为方向机会看？

```
competitor_products_clean
  + deng_zong_shop
  + subcategory_alias_map(APPROVED competitor alias)
        ↓
category_dislocation
        ↓
/api/v1/category-dislocation/compute
/api/v1/category-dislocation/health
/api/v1/category-dislocation/opportunities
```

**当前状态**

- 已落地：三层卖家统计、`dislocation_score`、`heat_signal`
- GREEN/RED/YELLOW/COLD 规则在 SQL 中计算
- 计算前会 bootstrap 小类别名层，避免 raw leaf 和 canonical 断开

**边界**

- ②线只说明“方向错位”，不说明“我们一定能做”
- ②线依赖 `subcategory_alias_map` 的 approved competitor alias；没有 alias 的小类不会进入当前主计算范围

---

## ③线：自有战绩

**回答的问题**：我们真实赢过什么？哪些 archetype / carrier / element / subcategory 应该指挥后续猎场？

```
docs/选品方法库/1_底层数据/产品表现ASIN原始数据.md
  ↓ import
product_performance_actual
  ↓
/api/v1/product-performance/import
/api/v1/product-performance/winners
/api/v1/product-performance/by-archetype
/api/v1/product-performance/count
```

**当前状态**

- 已落地：`product_performance_actual` 表、Markdown 导入器、查询接口
- 导入时会解析标题，半自动打 `STD/CUSTOM`、`element`、`carrier`
- `is_green` / `is_eliminated` 从 listing 标签里抽取，用作回测正负样本的基础

**边界**

- element/carrier 解析是半自动规则，不等于已人工核准的最终元素库
- 绿标、淘汰、销量周期这些业务语义仍适合在回测前再做一次人工确认

---

## ③×②：可行动机会

**回答的问题**：哪些当前错位小类，和我们历史赢家方向存在交集？

```
category_dislocation
  ∩ subcategory_alias_map(WINNER approved canonical)
  ∩ product_performance_actual
        ↓
/api/v1/category-dislocation/actionable-opportunities
```

**当前状态**

- 已落地：`actionable-opportunities` 接口
- 返回赢家统计：`winnerCount`、`greenCount`、`eliminatedCount`、`winnerMarketplaces`、`topArchetypes`、`topCarriers`、`topElements`
- 这是当前最接近“产品卡片”的推荐能力

**边界**

- 这是交集视图，不是完整三线总分模型
- 还没有把 ①小类销量分位、M04 tier、④元素候选一起编成一个统一 score

---

## M04：新品大类销量基础分级

**回答的问题**：一个新品在同国家、同大类、同账龄段里是 S/A/B/C/D 哪一档？

```
competitor_products_clean
  ↓ 月度刷新
category_age_tier_baseline
  ↓ 月度/周度打标
competitor_products.m04_age_bucket
competitor_products.m04_tier
competitor_products.m04_units_pct
competitor_products.m04_bsr_pct
competitor_products.m04_computed_at
```

**接口**

- `POST /api/v1/category-baseline/compute-age-tier?month=YYYYMM`
- `POST /api/v1/category-baseline/tag-asins-by-week?weekTag=YYYY-Www&month=YYYYMM`

**当前状态**

- 已落地：service、mapper、建表 SQL、产品表 5 列打标、单测
- 基线计算消费 `competitor_products_clean`
- 打标回写 `competitor_products` 原表；clean 表的 M04 列当前只是预留，不是下游主事实

**边界**

- 只服务 `listing_days < 90` 且 `weight_g < 300` 的新品
- 没命中基线的行会标 `unknown`；不在范围内标 `out_of_scope`
- 周度打标前必须先至少跑过一次 `compute-age-tier`

## ④线：元素机会引擎

**回答的问题**：具体什么元素、什么载体组合正在冒头？

```
competitor_products_clean 候选
  ↓ 标题解析
path2-preview / carrier-match-preview / manual-candidates
```

**当前接口**

- `GET /api/v1/element-discovery/path2-preview`
- `GET /api/v1/element-discovery/carrier-match-preview`
- `GET /api/v1/element-discovery/manual-candidates`

**当前状态**

- 已落地：路径2市场反向发现预览、载体命中审计、手动非标候选导出
- 已叠加明显标准品过滤、载体误判修正规则、①线 baseline 说明

**边界**

- `element_carrier_dict` / `element_library` / `element_discovery` 三张表仍是设计稿，不是当前运行主事实
- 当前 ④ 更适合叫“人工审阅工具”，不要包装成全自动元素库产品

---

## M05：老品稳态分级

**当前状态**：只有 L3 方法卡片占位，还没有表、接口、Service 或 Mapper。

**边界**：上架 `>=90` 天的成熟品不走 M04；后续需要单独定义稳态、衰退、反弹等生命周期规则。

---

## 当前产品化优先级

| 优先级 | 卡片 | 理由 |
|---|---|---|
| 1 | `③×② 可行动机会卡` | 有表、有接口、有历史赢家背书，最接近可用推荐 |
| 2 | `M04 新品分级卡` | 已能批量打 S/A/B/C/D，适合新品批次分层 |
| 3 | `③ 赢家方向卡` | 能解释我们真实赢过的 archetype / carrier / element |
| 4 | `① 基线解释卡` | 适合作为候选详情旁的参照尺 |
| 5 | `④ 非标候选卡` | 适合人工审阅，暂不包装成全自动机会卡 |
