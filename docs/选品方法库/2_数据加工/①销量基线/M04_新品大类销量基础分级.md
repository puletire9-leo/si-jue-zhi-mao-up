## 〔身份〕

`id: method-newproduct-category-sales-tier` · `状态: 代码已落地 / 基线需按月刷新` · `精度层级: 地板(国家×大类×账龄) — 可被①线小类基线覆盖`

**一句话**：在一个国家某个大类某个**新品账龄段**里，给"日均销量"或"月销量"划一组粗带（S/A/B/C/D），让任何一个**新品**候选 ASIN 一眼能看出"它在这个国家这个大类是哪一档"。

> 🔒 **新品边界（不可越**）：本卡只服务于 `listingDays < 90 天` 且 `weight < 300g` 的新品。这两条边界**完全继承自 \[\[M01\_新品榜加速法]] 的硬门槛**——不是 M04 自己定的，是新品方法论的统一前提。
> 上架 ≥ 90 天的成熟品**不走 M04**，走老品分级方法卡（待立，老品分级是另一套逻辑：稳态销量、衰退/反弹判断、生命周期）。

## 〔何时用〕

- ✅ 拿到一个 ASIN，知道它的国家、大类（bsr\_id）和上架天数（< 90 天），**还不需要查到具体小类**就想先粗筛一道
- ✅ 看一个新品榜批次，想知道整批的销量分布在哪一档
- ✅ ①线小类基线缺数据时（leaf 样本<30）用作回退
- ❌ 已经有 ①线小类基线数据时 → 走 \[\[实现\_①销量基线]] 的 `getSubcategoryHealth`，更准
- ❌ 自发货品 → 走 \[\[M03\_FBM自发货简单道]]（不分段）
- ❌ **上架 ≥ 90 天的成熟品 → 不走 M04**，新品判档对老品没有意义（老品要看的是稳态/衰退，不是爬量分位）
- ❌ **重量 ≥ 300g → 不走 M04**（M01 硬门槛已挡，是"轻小件 FBA"的物理前提）

***

## 〔输入〕

- ASIN 的 `marketplace`（UK / DE / US）
- ASIN 的 `bsr_id`（kitchen / fashion / automotive ...）
- ASIN 的 `listingDays`（上架天数，从 `competitor_products.listing_days` 取，**必须 < 90**）
- ASIN 的 `weight`（克，**必须 < 300**）
- ASIN 的 `units`（月销，卖家精灵预估）

可选：

- 同 (marketplace, bsr\_id) 同账龄段在 `competitor_products` 里的整批样本（用于在线计算百分位带）

> 输入侧的硬门槛检查（listingDays < 90 且 weight < 300g）是 M04 的前置条件。如果上游忘了过 M01 直接喂老品/重物给 M04，M04 应当在 SOP 步骤 0 拒绝，不进入分档。

***

## 〔SOP 步骤〕

0. **守门 + 周批次过滤 + 变体去重**：
   - 原料按 `competitor_products.week_tag = ?` 过滤当周新导入的行（**新品爬量是周级事件**，月度跑会让刚跨档的品延迟最多 4 周——见 \[\[依据\]\]）
   - 校验 `listing_days < 90` 且 `weight_g < 300`。任一不满足 → 返回 `out_of_scope`，不分档（这条是 M01 硬门槛在 M04 里的镜像）
   - **变体去重（v7 必须）**：每个父 ASIN 群组 `COALESCE(parent_asin, asin)` 只保留一行代表，避免卖家精灵把父销量复制到所有子变体造成的污染。代表行选择规则：`ORDER BY listing_days DESC, units DESC`——选父系列里**最新上架达标 + 销量最高**的那一行
1. **算账龄段**：listingDays 落入 0–30 / 30–60 / 60–90 哪一档（**只有三档，没有 >90**）
2. **查国家×大类×账龄基线**：去 `category_age_tier_baseline` 查同三元组的 units 百分位带 P25/P50/P75/P90 + bsr 百分位带
3. **判档**：本 ASIN 的 units 落在哪一档 → S(P90+)/A(P75–P90)/B(P50–P75)/C(P25–P50)/D(\<P25)；同时算 BSR 在本档百分位
4. **粗筛**：D 档直接淘汰；S/A 优先；B 看 ①线小类基线再决定；C 看是否有元素优势

> **节奏**：基线（层一）月度刷新一次（样本累积要稳），打标（层二）周度跟进（按 week_tag 过滤当周新行）。每周新品规模约 4-8 千行，<5 秒打完。
>
> **三层分工**（v7 厘清）：`WHERE` 子句 = 硬门槛过滤 / `WITH ranked_variants` = 父群组聚合选代表 / 最外层 = 分位计算。三层各管一件事，不重复也不重叠。

## 〔判定标准〕 ← 核心

**先说清楚一件事：当前是"占位"标准，数据回填后阈值要重算。**

**新品账龄分段（三档，全部在 M01 90 天硬门槛内）：**

| 账龄段     | 含义                                       |
| ------- | ---------------------------------------- |
| 0–30 天  | 早期爬量期，BSR 不稳，看趋势                         |
| 30–60 天 | 中段，能开始拿数据                                |
| 60–90 天 | **本卡的主战场** — 接近稳态但仍在新品期，数据最有信号、最接近"它能不能成" |

> 〔老品分级 ≥ 90 天〕走另一张方法卡，本卡不涉及。

**销量 + BSR 双分级（占位，待 dev 库 `category_age_tier_baseline` 算出真值后回填）：**

每个 (marketplace, bsr\_id, ageBucket) 三元组维护**两组**百分位带：

| 等级    | 销量分位         | BSR 分位※        | 含义                 |
| ----- | ------------ | -------------- | ------------------ |
| **S** | units ≥ P90  | bsr ≤ P10（最靠前）| 本国本大类本账龄前 10% — 爆款 |
| **A** | P75 – P90    | P10 – P25      | 前 25% — 头部         |
| **B** | P50 – P75    | P25 – P50      | 中位偏上 — 主力          |
| **C** | P25 – P50    | P50 – P75      | 中位偏下 — 边缘          |
| **D** | < P25        | > P75（最靠后）    | 后 25% — 淘汰         |

※ BSR 数字越小 = 排名越靠前 = 越好。`m04_bsr_pct` 字段已做归一化（0=最靠后，1=最靠前），与 `m04_units_pct` 同向比较。

> **判档优先级**：以 units 分位为主、BSR 分位为辅。两者背离时（如 units 在 P75 但 BSR 在 P25）触发**可信度警告**，不直接降档——交给合成层处理（见 \[\[C01\_数据可信度]]）。

**站点底线（M04 独立校准；阈值待数据回填后微调）：**

某些档不仅看百分位，还有绝对底线兜底（占位）：

| 站点      | 最低进档线（月销） | 价格带          |
| ------- | --------- | ------------ |
| 🇬🇧 UK | ≥ 5       | £4.99–£17.99 |
| 🇩🇪 DE | ≥ 10      | €5.99–€18.99 |
| 🇺🇸 US | ≥ 50      | $6.99–$25.99 |

低于站点底线 = 直接 D 档，不参与百分位评估。

**Confidence 标定规则（v6 实测重校）：**

| confidence | 判定条件                                          | 含义                |
| ---------- | --------------------------------------------- | ----------------- |
| `high`     | sample_size ≥ 100 **且** P50/P75/P90 三个分位互不相同 | 数据稳，分位有信号         |
| `mid`      | sample_size ≥ 50 **且** P50/P75/P90 三个分位互不相同  | 样本中等，分位可用         |
| `low`      | sample_size < 50 **或** P50/P75/P90 中至少两个相同   | 小样本 / 分位塌缩，仅供参考   |

> ⚠️ **分位塌缩规则（v6 实测发现）**：当 P50/P75/P90 中至少两个完全相同时（如 DE ce-de 0_30 n=48 出现 P50=P75=P90=492），表明卖家精灵对该桶预估有大量重复值，**强制降为 low**，不参与 S/A 档判定。
>
> ⚠️ **小样本阈值上调**：v4 原写"≥30=mid"，v6 实测发现 n=48 已塌缩，阈值上调到"≥50=mid"。geji 202606 实测 19,575 行新品里约 80% 落在 high/mid 桶。

## 〔依据 / 为什么〕 ← 最重的一格

- **为什么 M04 是"新品卡"，把 ≥90 天彻底挡在外面？**
  - 新品和老品的判档逻辑根本不是同一套：新品看"在同账龄段排第几"（爬量速度），老品看"是不是稳态、有没有衰退"（生命周期阶段）
  - 把两类品揉在一张分级表里，等于让爬量期的好品和稳态衰退期的差品共享一个 P50 — 既冤枉新品，也让老品的衰退信号被稀释
  - 见 \[\[M01\_新品榜加速法]] 的核心硬门槛：上架<90 天 + 重量<300g — M04 是 M01 之后的"对已通过批次的细粒度分档"，不能突破上游的硬门槛

- **为什么按"大类×账龄"切，不直接用①线小类基线？**
  - ①线小类基线（`subcategory_baseline`）按 `marketplace × bsr_id × Amazon leaf × month` 切，需要每个 leaf 样本 ≥30
  - 现实是：相当一部分小类 leaf 在 dev/geji 里样本不足 30（H5 收紧后会更稀疏）
  - 这时退一层到"大类×账龄"就能保住基本的"卖得动/卖不动"判断
  - 见 \[\[实现\_①销量基线]] 的"当前还没完成的点"

- **为什么是百分位，不是固定阈值？**
  - \[\[07-动态基线与相对评分]] §1.3 明确证明过：邓总 UK 站 12 个品类，均月销从 12 (Notebook) 到 138 (Sunglasses)，差 11.5 倍
  - 用"月销 ≥100 进候选池"在 Sunglasses 是平庸品、在 Wall Art 是极品
  - 百分位等于"跟同站点同大类同账龄的同类比"，自动抹平品类间体量差异

- **为什么必须按父 ASIN 去重（v7 救命修正）？**
  - **数据来源**：卖家精灵把父 ASIN 的销量和 BSR 复制到每个子变体行。同一个父系列可能有 200 个颜色×尺码变体，每个子行的 `units` 和 `bsr` 都是同一个数字
  - **污染规模实测**（geji 202606）：DE 9434 行新品里 6025 行是变体子（64%）、UK 51%、US 77%。最大父 `B0GZPX8PXN` 一个父有 1677 个子变体
  - **不去重的后果**：
    - DE fashion 0_30 v6 跑出 P50=126 → v7 去重后 P50=**7**（数量级颠覆）
    - 一个父系列有 139 个变体全部 units=126 → 让"P50"这个位置被这一个产品卡死
    - 下游 `WHERE m04_tier = 'A'` 拉候选，60%+ 是同一个父 ASIN 的颜色变体
  - **BSR 同样污染**：DE fashion ~85% 父群组的 `distinct_bsr=1`（所有变体共享父系列 BSR）。A 方案选代表同时解决 units 和 BSR 污染
  - **A 方案规则**：每父群组 `ORDER BY listing_days DESC, units DESC LIMIT 1`——选最新上架达标 + 销量最高的代表
    - 优先 `listing_days DESC`：体现"看最新"偏好（新变体说明父系列还在加 SKU）
    - 次序 `units DESC`：同账龄变体里选卖得最好的最有代表性
    - 没有按 BSR 排：M04 目的是"代表行参与同档比较"，不是"选最好 BSR"
  - **污染按大类分化**：fashion / sports 重灾区（变体 100+），garden / kitchen 几乎无污染（变体少）。但代码不做"按大类区别对待"——统一规则对低污染大类无害，对高污染大类是救命
  - **真正样本量缩 91%**：DE fashion 0_30 v6 = 1914 行污染样本 → v7 = 128 行干净独立产品。**91% 是冗余**

- **为什么 units 分位 + BSR 分位都要存？**
  - **units 是预测、BSR 是事实**：units 来自卖家精灵的预估算法（基于历史 BSR→销量映射），不同品类、不同账龄段的预估准度差异很大；BSR 是亚马逊给的硬数据，每天刷
  - **两者背离 = 数据可信度风险信号**（见 \[\[C01\_数据可信度]]）：
    - units 在 P75 但 BSR 在 P25 → 销量预估可能虚高（卖家精灵高估了爬量速度）
    - units 在 P25 但 BSR 在 P75 → 销量预估可能保守（亚马逊已经给了好排名但销量还没追上）
    - 两者同向（都 P75 或都 P25）→ 可信度高
  - 把这两个分位都灌进 `competitor_products` 表，下游不仅能筛"A 档"，还能筛"A 档但 BSR 不达标 → 待复核"
  - 这一条在 ①线小类基线已有先例（H5 同时存了 units_p50/75/90 + price_p50），M04 把这个习惯延伸到 BSR 维度

- **为什么基线月度刷新、打标周度跟进？**
  - **新品爬量是周级事件**：一个 ASIN 在 30→60 天的转折期可能就 1-2 周，月度跑一次会让"刚跨过 60 天门槛"的品延迟最多 4 周才被重新分档
  - 但**基线本身需要月级累积样本才稳定**：周级样本（4-8 千行 / 周）按 (国家 × 大类 × 账龄档) 切下去，部分桶可能 <30 样本，HAVING 一过就没了
  - 所以拆成两套节奏：
    - 基线：月度跑一次 INSERT...SELECT，用满月样本算 PERCENT_RANK 分位（稳）
    - 打标：每周扫一次 `WHERE week_tag = 当前周 AND listing_days < 90`，UPDATE 当周新行（快）
  - 代码层用 `competitor_products.week_tag` (`yyyy-Www` ISO 周标记) 做周批次过滤——这字段已经在用了，`ScoringService.updateWeekTags()` 每周一刷一次
  - 月末重算基线：月底最后一周打标完成后，用累积的整月新品数据重算 `category_age_tier_baseline`，下个月跑新基线

- **为什么加账龄维度？**
  - 一个上架 15 天月销 50 的品，和一个上架 80 天月销 50 的品，在同一个大类里**完全不是一回事**
  - 前者 15 天 50 单 = 日均 3+，是潜力股；后者 80 天 50 单 = 日均 0.6，是基本没起量的边缘品
  - 没有账龄维度，"月销 50"在三档新品里的含义混在一起，分位数失去意义
  - 见 \[\[M01\_新品榜加速法]] 的账龄达标线（30/60/90 三段，正好对应 M04 的三档）

- **为什么三国月销底线是 UK ≥5 / DE ≥10 / US ≥50？**
  - 三档量级反映三国市场体量差：US 是 UK 的 5–10 倍，DE 介于两者之间但更接近 UK
  - 底线只做"硬过滤垃圾"——把月销 1 件、刚上架还没爬量的彻底挡掉
  - 过线之后真正的判档还是看百分位（在本国本大类本账龄里排第几）
  - **为什么 UK 比 DE 还低（≥5 vs ≥10）？** UK 站本身基线偏小、高利润长尾品类多（笔记本、贺卡、小饰品的均月销在 12–43 之间），如果跟 DE 一样设 ≥10，会把 UK 大量"小而美"长尾候选误杀
  - DE 设 ≥10 是因为：DE 用户购买力强但品类总体客单价更稳，月销低于 10 的基本是没起量的
  - 这三个数字仍是**占位**——真值要等 `category_age_tier_baseline` 在 geji 全量上算出来后再校准

- **为什么是"地板线"不是"门槛线"？**
  - 本卡给的是参照系，不是淘汰线
  - D 档直接淘汰是硬过滤的延伸，S/A 是优先，但 B/C 不淘汰
  - 真正"值不值得做"是合成层（\[\[三线合成\_打分与回测模型]]）的判断，要 ①+②+③ 三线一起看

- **本卡和 M01 的关系：**
  - M01 是**门**：用账龄×销量绝对值地板线 + 重量 + 价格带把垃圾批次拦在外面（硬门槛：上架<90 + 重量<300g）
  - M04 是**尺**：M01 已通过的批次进来，按账龄×百分位给每个 ASIN 标 tier
  - **M04 的输入空间 ⊂ M01 已通过的空间**——上游守好门，下游只管量
  - 两张卡接力：M01 把批次过到候选池 → M04 给候选池里每条标 tier

**v7 完整计算 SQL（落代码可直接用）**：

```sql
INSERT INTO category_age_tier_baseline (...)
WITH ranked_variants AS (
  SELECT marketplace, bsr_id, listing_days, units, bsr,
         COALESCE(NULLIF(parent_asin, ''), asin) AS dedup_key,
         ROW_NUMBER() OVER (
           PARTITION BY marketplace, COALESCE(NULLIF(parent_asin, ''), asin)
           ORDER BY listing_days DESC, units DESC
         ) AS rn
  FROM competitor_products
  WHERE month = ?
    AND listing_days < 90 AND weight_g < 300                    -- M01 硬门槛
    AND bsr_id IS NOT NULL AND bsr_id != '' AND LOWER(bsr_id) != 'null'
    AND units IS NOT NULL AND bsr IS NOT NULL AND bsr > 0
),
representatives AS (
  SELECT marketplace, bsr_id, units, bsr,
         CASE WHEN listing_days < 30 THEN '0_30'
              WHEN listing_days < 60 THEN '30_60'
              ELSE '60_90' END AS age_bucket
  FROM ranked_variants WHERE rn = 1                              -- 每父群组只留代表
),
ranked AS (
  SELECT marketplace, bsr_id, age_bucket, units, bsr,
         PERCENT_RANK() OVER (PARTITION BY marketplace, bsr_id, age_bucket ORDER BY units ASC) AS units_pr,
         PERCENT_RANK() OVER (PARTITION BY marketplace, bsr_id, age_bucket ORDER BY bsr ASC)   AS bsr_pr
  FROM representatives
)
SELECT marketplace, bsr_id, age_bucket, ? /* baseline_month */,
       COUNT(*) AS sample_size,
       MAX(CASE WHEN units_pr <= 0.25 THEN units END) AS units_p25,
       MAX(CASE WHEN units_pr <= 0.50 THEN units END) AS units_p50,
       MAX(CASE WHEN units_pr <= 0.75 THEN units END) AS units_p75,
       MAX(CASE WHEN units_pr <= 0.90 THEN units END) AS units_p90,
       MAX(CASE WHEN bsr_pr <= 0.10 THEN bsr END) AS bsr_p10,
       MAX(CASE WHEN bsr_pr <= 0.25 THEN bsr END) AS bsr_p25,
       MAX(CASE WHEN bsr_pr <= 0.50 THEN bsr END) AS bsr_p50,
       MAX(CASE WHEN bsr_pr <= 0.75 THEN bsr END) AS bsr_p75,
       CASE
         WHEN COUNT(*) >= 100
          AND MAX(CASE WHEN units_pr <= 0.50 THEN units END) <> MAX(CASE WHEN units_pr <= 0.75 THEN units END)
          AND MAX(CASE WHEN units_pr <= 0.75 THEN units END) <> MAX(CASE WHEN units_pr <= 0.90 THEN units END) THEN 'high'
         WHEN COUNT(*) >= 50  AND ... THEN 'mid'
         ELSE 'low'
       END AS confidence,
       NOW()
FROM ranked
GROUP BY marketplace, bsr_id, age_bucket
HAVING COUNT(*) >= 30;
```

> 关键 CTE 是 `ranked_variants`——这是 v7 最重要的修正。如果未来谁手抖把它去掉，基线数字会被变体污染 80-90%。SQL 注释里已经标注，但代码层应有单测锁死："输入含变体行 → 输出 父群组数 ≠ 行数"。

**为什么拆两个接口**：基线需要月级样本稳定（PERCENT_RANK 分位用整月数据），打标需要周级及时（新品爬量是周级事件，月度跑会让刚跨档的品延迟最多 4 周）。`competitor_products.week_tag` 字段已在用，当前代码与清洗层注释口径均为 `yyyy-Www`，`ScoringService.updateWeekTags()` 每周一刷一次。

**查询入口（可选，调试用）**：`GET /api/v1/category-baseline/age-tier-health?marketplace=UK&bsrId=kitchen&listingDays=45&units=80&bsr=20000`

- 入参 listingDays ≥ 90 → 返回 `{tier: "out_of_scope", reason: "listing_days >= 90, see 老品分级方法卡"}`
- 真正的下游消费是直接 SQL `WHERE m04_tier = ?`，不走这个接口

**性能预算**（v7 实测重估，参考 ①线小类基线 H5）：

| 节奏     | 步骤              | 数据量                        | 时间        |
| ------ | --------------- | -------------------------- | --------- |
| 月度     | 父群组聚合 + PERCENT_RANK 双窗口 | 14 万源行 → 12k 代表 → 58 桶 | **2–3 秒**  |
| 月度     | 全量打标 UPDATE     | 14 万行 × 5 列（变体子继承父）          | **5–10 秒** |
| 周度     | 增量打标 UPDATE（按 week_tag） | 4-8 千行 × 5 列                | **<5 秒**   |

依据：①线小类基线在 geji 14 万源行 → 934 基线行，实测 <3 秒（H5）。M04 v7 多了一层父群组 ROW_NUMBER 聚合，预估 +1 秒。

**v7 实测桶分布**（geji 202606）：

| 站点 | 桶数 | high | mid | low | 覆盖大类 |
| --- | -- | ---- | --- | --- | ----- |
| DE | 27 | 19 | 5 | 3 | 12 个 |
| UK | 10 | 6  | 3 | 1 | 4 个（sports/automotive/outdoors/kids） |
| US | 21 | 14 | 4 | 2 | 9 个 |
| 合计 | **58** | **39** | **12** | **6** | |

可信桶（high+mid）合计 51 / 58 = **88%**——v6 版本是 90%（70 桶里 63 可信）。v7 桶变少但更干净——v6 那些"被变体撑起来的伪 high 桶"（如 DE sports 0_30 n=460 P50=183）在 v7 里直接消失或正常化。

**结论**：M04 v7 是廉价同步任务，月度跑全量 + 周度跑增量，都不需要 Celery / 不需要分批 / 不需要异步。**v7 父 ASIN 去重是必备前置**，不去重则 60-90% 数字被污染。

  **背景**：v7 的"父 ASIN 去重"在 M04 一张方法卡里成立，但**这是个数据基线层的通用问题**——①线小类基线、②线错位机会、未来所有用 `competitor_products` 做统计的方法卡都会遇到。用户拍板："建立数据处理层，确保下游消费的都是干净数据"。

  **v8 架构**：建物化清洗表 `competitor_products_clean`，所有统计 SQL FROM 改成清洗表。

  **关键设计决策**：
  - 物化表（不是 VIEW）—— v1 VIEW 方案在 21 万行 geji 上窗口函数 OOM 容器
  - 按 `(marketplace, effective_week_tag, dedup_key)` 三元组唯一键 —— 同周同父群组幂等，跨周快照独立
  - 老数据 `effective_week_tag = month-W00` 占位，全数据进清洗表
  - 分批 INSERT 全量首次清洗（按 marketplace × effective_week_tag 一批一批跑，避免 OOM）
  - 增量周清洗（每次新批次导入触发）

  **M04 v8 SQL 简化**：
  - v7 SQL 含 `WITH ranked_variants AS (... ROW_NUMBER ...)` CTE
  - v8 直接 `FROM competitor_products_clean` ——CTE 删掉，每张方法卡 SQL 瘦身一半
  - 落代码时 `compute-age-tier?month=` 接口 SQL 模板见〔产出位置〕段（已更新）

  **真实修复影响**（geji 实测）：
  - ①线小类基线 v7 → v8 桶数从 **934 → 174**（减少 81%）
  - 减少的 760 个桶都是被变体撑起的"伪有效桶"，本不该参与决策
  - UK Flags `automotive` 桶从 n=37 P50=0 P90=852 → **直接消失**（去重后 n=9 < 30 阈值）
  - UK Flags `outdoors` 桶 v7=178 P50=22 → v8=**44 P50=31**（数字大幅修正）

  **触发原因**：用户洞察"变体污染是数据基线层的通用问题，不是 M04 一张卡的事"——这是架构级别的认知升级
  - **当时未做**：到 `2026-06-25` 这一步为止，M04 代码（`compute-age-tier` 接口）仍未落地。但 v8 已为落代码做好准备——SQL 模板可直接消费 `competitor_products_clean`，不再需要每张方法卡重写 `WITH ranked_variants` CTE
