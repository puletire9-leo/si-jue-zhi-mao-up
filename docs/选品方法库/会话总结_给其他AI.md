## 一、项目背景

我们做一个亚马逊跨境电商选品系统（英国/德国/美国三国），要自动推荐"元素主导非标品"——不是卖功能性商品（如螺丝刀、手机壳），而是卖"元素+载体"（如高地牛图案的帆布袋、卡皮巴拉图案的化妆包）。元素（高地牛、蝴蝶结、卡皮巴拉、F1）是灵魂，载体（帆布袋、挂牌、马克杯、束口袋）是附着面。同一个表情可以印在 10 种载体上——元素决定了受众，载体只是承载形式。

**我的角色**：Claude（外部大脑），帮用户整理思路、写实现文档、规划 coding。**用户的角色**：拍板、提供 domain knowledge（什么是好卖的元素、玩法有哪些）。

**铁律**：
- 文件先行，思路不能错
- 完成大于完美
- 代码仓库是唯一事实来源

## 三、三线选品模型的完整进化历程

### 3.1 初始框架（H1-H3）

最初设计三条独立的推荐线：

```
①线 = 销量基线：跟着大盘走
②线 = 聪明卖家密度：跟着同行扎堆放向走
③线 = 自有战绩：跟着自己成功经验走
```

三线各自打分，等权投票合成推荐。

### 3.2 第①线踩过的坑（已排雷）

**坑1：品类主键选 `node_label_path` 第2级 → 跨国对不齐**
- DE 出 "Damen"，UK 出 "Women's" → 没法跨国家对比
- 实际数据验证后改用 `bsr_id`（卖家精灵 API 返回的品类 slug，跨国统一）

**坑2：不分 BSR 桶 → 中位数没意义**
- 全品类 7758 个品揉成一个中位数 72 单 → 指导不了任何决策
- 改用 `bsr_id + BSR 分桶（5k/20k/50k/150k）+ 窗口函数 PERCENT_RANK()` 算精准分位
- 老 `category_baselines` 表和 `computeBaseline()` 废弃，新建 `category_bsr_baseline` + `subcategory_baseline` 表

**坑3（已修复的计算 bug）**：
- 用 `GROUP_CONCAT` 装 units 算中位数 → 默认 1024 字符截断 → 大桶中位数=0
- 用 `JOIN ON (units, price)` 做窗口函数 → (units, price) 不唯一 → 10-40x 行爆炸
- 最终正确解法：单 CTE + `PERCENT_RANK()` 窗口函数，零 JOIN

### 3.3 第②线的方向反转（关键纠正）

**最初**：聪明卖家密度高 = 机会信号（跟风做）

**用户纠正**：`deng_zong_shop` 是 29 家 **中国同行**。他们扎堆 = 时间差关闭 = 红海，不是蓝海。
**真正的信号 = 错位**：本土优质卖家在做（验证了需求）、中国卖家没发现（你还有时间差）。

**最终定稿**：
- 三层卖家模型：郑总系 / 其他CN / 非CN本土
- 错位分 = 本土占比 × ln(平均销量 + 1)，归一化 0~1
- heat_signal：GREEN（非CN>30% + 郑总=0）/ RED（郑总>20%）/ YELLOW / COLD

**关键技术细节**：跨表 JOIN `competitor_products.seller_id`（utf8mb4_0900_ai_ci）和 `deng_zong_shop.seller_id`（utf8mb4_unicode_ci）必须加 `COLLATE` 子句，否则 MySQL 报错。

### 3.4 H4 发现：翻盘的全局发现（2026-06-23）

**用 591 个真实赢家做回测发现**：
- 73% 的赢家大类 BSR > 50,000（大类末尾）
- 0 个赢家在大类 BSR < 5,000（大类头部）
- 赢家的共同特征：**不是大类爆款，是小类爆款**

**结论**："打法是做大类中后段的小类爆款，不是大类头部直球竞争"。

**影响**：
- 老的三线等权投票 → 推翻，改为**③线是大脑定方向，①②当参照系**
- 需要建「小类基线」（subcategory baseline），不只是大类 BSR 分桶
- 合成打分公式改为：③线类型 40 分 + ①线小类容量 30 分 + ②线错位信号 30 分 / -20 分 + 退款率 -15 分

### 3.5 第④线的大重构（从元素库到双路径引擎）

**原始设计**：把 final_drafts 的 426 个元素全灌进元素库，用中英双语映射表匹配。

**用户纠正（两次）**：

第一次纠正："元素才是根本，一个优秀元素可以跨多个载体。不是所有元素都好卖。"

第二次纠正："载体是通用的（55个全覆盖），元素是动态发现的。两大路径：
- 路径1（正向）：已验证好卖的元素 → 去市场找补位载体 → 我们有这个元素×那家载体没做过 → 推荐
- 路径2（反向）：全载体锚点扫市场 → 提取元素候选 → 按跨载体数×销量排名 → 你确认好卖 → 入元素库 → 下次路径1自动覆盖"

**最终定稿**：
- 元素库只收验证过的种子（~73 个：591 赢家中的高频元素 + final_drafts 高频≥6 次）
- 261 个 final_drafts 低频（出现 1 次）不入库——是设计草稿，不是市场验证
- 双路径并行跑，互相喂养闭环
- 标题提取三步算法（载体锚点最长匹配→向左取1-3词→剥离品牌/材质/颜色）

**载体库**：55 个载体，完整三语（CN↔EN↔DE）锚点，从真实亚马逊标题验证过。

分布：

- 标签：欧洲精铺2025（414）、非标品（123）、淘汰（66）、绿标（16）
- **标签不互斥**：同一个品可以同时挂"非标品、绿标、淘汰"——曾被看好、是微定制、最终下市

### 4.2 标题语言规律（实战验证）

英国和美国：英文标题，如 "Dachshund Birthday Decoration Set..."
德国：德语标题，如 "Flaschentasche mit 12 Fächer..."
- 但是德国站标题偶尔混英文（如 "Flaschentasche" 标题中也含 "Wine Bottle"）
- 所以 DE 搜索策略 = 德文锚点 + 英文锚点双搜

**德语锚点实战数据**：
| 中文 | 德语锚点 | DE 匹配数 |
|------|---------|-----------|
| 挂牌 | Sonnenfänger / Fensterbild | 285（Fensterbild） |
| 束口袋 | Turnbeutel | 41 |
| 化妆包 | Kosmetiktasche | 56 |
| 枕套 | Kissenbezug | 585 |
| 帽子 | Mütze | 635 |

### 4.3 标题提取防错模型（总结六类错误）

| 类型 | 问题 | 解法 |
|------|------|------|
| A | 材质词被误当元素（"Acrylic Ornament"→Acrylic） | 材质词黑名单 60+ |
| B | 品牌词被误当元素（"zhongko Figure"→zhongko） | 品牌词黑名单（本地观测到4个） |
| C | 子串误匹配（"Cat"命中 "Cake Topper"） | 最长匹配 + 词边界 |
| D | SEO 尾词 false positive（"...for Bag"命中"Bag"） | 取最左匹配，排除"for [载体]" |
| E | 功能性词误当元素 | carrier_type 校验 |
| F | 单字母变体 | 跳过 LOW 置信度 |

### 审查发现的 3 个补丁
1. **价格符号是全角 ￡(U+FFE1) 不是半角 £(U+00A3)** → 用了正则 `[￡€$¥]` 但要注意字符不腐蚀

## 九、所有踩过的坑汇总（别重踩）

1. **collation 坑**：`competitor_products.seller_id`=utf8mb4_0900_ai_ci vs `deng_zong_shop.seller_id`=utf8mb4_unicode_ci → 所有 JOIN 必须 COLLATE
2. **GROUP_CONCAT 截断坑**：算中位数不要用 GROUP_CONCAT，用窗口函数 PERCENT_RANK()
3. **JOIN 行爆炸坑**：(units, price) 不唯一 → 不要在窗口函数结果集上 JOIN
4. **"聪明卖家密度"方向坑**：郑总系是 29 家中国同行不是完全卖家→密度高不是机会是红海
5. **"426 元素全灌"坑**：final_drafts 有 261 个只出现一次的元素，是设计草稿不是市场验证
6. **"标题 `|` 偏移"坑**：本数据集没发生（0/591），但留了防御逻辑
7. **全角 vs 半角坑**：UK 价格的磅符号是全角 ￡(U+FFE1)，大类排名的冒号是全角 ：(U+FF1A)——字符串 split 和 replaceAll 都要用全角字符
