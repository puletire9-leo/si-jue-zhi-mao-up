# 🏗️ 数据清洗层 · 架构卡

> 解决卖家精灵变体数据污染问题，让所有下游统计自动消费干净数据。
> 2026-06-25 建卡 v1（VIEW 方案）。同日实测 VIEW 在 geji 21 万行规模上性能崩塌，
> 升级 v2 → 物化表 + 周度增量刷新。

---

## 一句话

**`competitor_products_clean` 是 `competitor_products` 的物化清洗表，按周父 ASIN 去重。**
所有用于统计/分位/聚合的 SQL，FROM 必须用 clean 表，不是原表。

---

## 双层数据架构

| 表 | 用途 | 频率 | 保留策略 |
| --- | --- | --- | --- |
| `competitor_products`（原表） | 商品详情、父-子展开、前端 UI | 每周 2 次导入 | 永久存档 |
| `competitor_products_clean`（清洗表） | 系统筛选/排序/分位/聚合 | 每次新批次导入后增量清洗 | 永久存档（按周累积快照） |

**核心原则**：
- 不删原表数据（前端要展开变体，每行都有用）
- 不全量重刷清洗表（性能浪费）
- 每次新批次进来 → 增量清洗新批次的 week_tag → 写进清洗表
- 历史周的清洗数据不动（"事实快照"语义）

## 为什么需要清洗层

### 卖家精灵的数据结构

卖家精灵把**父 ASIN** 的销量 (`units`)、BSR (`bsr`)、价格 (`price`) **复制到所有子变体行**。一个父 ASIN 系列可能有 50-1677 个子变体（颜色 × 尺码 × 包装），每行都报相同的销量数字。

### 实测污染规模（geji 2026-06）

| 站点 | 总行数 | 变体子行 | 占比 |
| --- | ------ | ------- | --- |
| DE | 9,434 | 6,025 | **64%** |
| UK | 2,861 | 1,467 | **51%** |
| US | 7,280 | 5,597 | **77%** |
| 合计 | **19,575** | **13,089** | **67%** |

DE fashion 大类下，96% 的父群组（1000 / 1040）所有子变体 `distinct_units = 1`——全部子行报同一个销量数字。

### 不去重的后果

| 例子 | 污染版（v6） | 去重版（v7） | 差距 |
| --- | --------- | --------- | --- |
| DE fashion 0_30 P50 | 126 | **7** | -94% |
| DE fashion 0_30 P75 | 244 | **31** | -87% |
| UK Flags @ automotive 大类 | 桶 n=37 | 桶 n=9（< 30 阈值） | **桶不该存在** |
| DE sports 0_30 | n=460 但 P50=P75=183 塌缩 | n=141 P50=4 P75=21 | 数据塌缩自动解决 |

不清洗会让：
- 单个父 ASIN 以 N 倍权重影响分位 → P50 被卡死在父系列的数字上
- 真实独立产品 < 30 的桶被变体撑起 → 制造"伪有效桶"
- 下游 `WHERE m04_tier = 'A'` 拉候选，60%+ 是同一个父 ASIN 的颜色版本

## 清洗规则（A 方案）

每个父 ASIN 群组只保留一行代表，**代表选择优先级**：

```sql
ROW_NUMBER() OVER (
  PARTITION BY marketplace, effective_week_tag, COALESCE(parent_asin, asin)
  ORDER BY listing_days DESC, units DESC, asin ASC
)
```

1. **`listing_days DESC`**：父系列里最新变体优先
   - 体现"看最新"偏好——新变体说明父系列还在加 SKU 是健康的
2. **`units DESC`**：同账龄变体里销量最高的最有代表性
3. **`asin ASC`**：完全相同时按 ASIN 字典序稳定排序（避免月之间代表抖动）

`COALESCE(parent_asin, asin)` 处理：
- 父行（`parent_asin = asin` 或 `parent_asin IS NULL`）：dedup_key = asin
- 子行：dedup_key = parent_asin
- 同一父群组（父 + 所有子）共享同一个 dedup_key

## 清洗表 schema 与唯一键

```sql
CREATE TABLE competitor_products_clean LIKE competitor_products;
ALTER TABLE competitor_products_clean DROP INDEX uk_asin_month;
ALTER TABLE competitor_products_clean
  ADD COLUMN dedup_key VARCHAR(20) NOT NULL COMMENT 'COALESCE(parent_asin, asin)',
  ADD COLUMN effective_week_tag VARCHAR(10) NOT NULL COMMENT '老数据 month-W00 占位',
  ADD COLUMN cleaned_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  ADD UNIQUE KEY uk_batch_dedup (marketplace, effective_week_tag, dedup_key),
  ADD KEY idx_marketplace_month_clean (marketplace, month),
  ADD KEY idx_bsr_id_month_clean (marketplace, bsr_id, month),
  ADD KEY idx_parent_asin_clean (parent_asin),
  ADD KEY idx_effective_week (effective_week_tag);
```

### 唯一键 `(marketplace, effective_week_tag, dedup_key)` 的核心意义

这个三元组同时回答 3 个问题：
1. **同一周同一父群组只有一行** —— 重复导入幂等
2. **不同周保留独立快照** —— 月内 W23/W24/W25 各自一行，可对比销量演化
3. **跨站点同 ASIN 独立** —— UK 和 DE 的同一个 ASIN 不冲突

### `effective_week_tag` 字段（X 方案）

老数据 `week_tag = NULL` → 用 `CONCAT(month, '-W00')` 占位（如 `202605-W00`）。
新数据 `week_tag` 有值 → 直接用。

这样所有数据都进清洗表，没有"老数据丢了"的问题。

## 增量周清洗（每次导入触发）

```sql
INSERT INTO competitor_products_clean
SELECT ranked.<all 64 columns from competitor_products>,
       COALESCE(NULLIF(ranked.parent_asin, ''), ranked.asin) AS dedup_key,
       ranked.week_tag AS effective_week_tag,
       NOW() AS cleaned_at
FROM (
  SELECT cp.*,
    ROW_NUMBER() OVER (
      PARTITION BY cp.marketplace, cp.week_tag,
                   COALESCE(NULLIF(cp.parent_asin, ''), cp.asin)
      ORDER BY cp.listing_days DESC, cp.units DESC, cp.asin ASC
    ) AS variant_rank
  FROM competitor_products cp
  WHERE cp.week_tag = ?            -- 只处理本次新批次
    AND cp.week_tag IS NOT NULL    -- 排除老数据
) ranked
WHERE ranked.variant_rank = 1
ON DUPLICATE KEY UPDATE
  units = VALUES(units),
  bsr = VALUES(bsr),
  price = VALUES(price),
  listing_days = VALUES(listing_days),
  bsr_id = VALUES(bsr_id),
  node_label_path = VALUES(node_label_path),
  rating = VALUES(rating),
  ratings = VALUES(ratings),
  cleaned_at = NOW();
```

**性能预算**：每周新批次 4-8k 行 → 2-3k 代表，**< 2 秒**

| 场景 | FROM 表 |
| ------------------- | ------------------ |
| 基线计算（①线、M04、②线） | `competitor_products_clean` |
| 分位 / 聚合统计 | `competitor_products_clean` |
| GROUP BY + COUNT/AVG/SUM | `competitor_products_clean` |

- 凡是把多行聚合成一个统计指标的 → 用 clean

## 依据 / 为什么这样设计

### v1 → v2 的演进（实测验证教训）

**v1**: VIEW 方案，2026-06-25 上午建立。dev 16 万行测试通过。

**v1 失败**: geji 21 万行规模上 VIEW 查询卡死 28 分钟，`SHOW PROCESSLIST` 显示窗口函数无法走索引，多个连接形成死锁链。教训：**任何含窗口函数的 VIEW 都不应该跨数据规模通用**。

**v2**: 物化表方案，同日下午改建。性能问题从"每次查询"降到"每周一次刷新"。**这是数据库工程的标准模式**。

### 为什么不删原表的变体？

- 前端商品详情、父-子展开 UI 都要变体（一个父系列每个颜色都展示）
- 老用户/产品详情查询路径走原表
- 清洗只是**派生层**，不是替代层

### 为什么按 week_tag 增量？

- 用户业务节奏：每周 2 次导入（不是月度）
- 新品 30→60 天的转折期可能就 1-2 周，不能等到月底才看到分级变化
- 增量刷新避免重复扫表

### 为什么 effective_week_tag 用 month-W00 占位？

- 历史数据 week_tag NULL（US 全表 NULL，DE/UK 60-75% NULL）
- 用 `month-W00` 占位让所有数据都进清洗表
- W00 标记表明"这是补录的老数据"，未来可以根据需要排除

### 为什么是 A 方案（选代表），不是 GROUP BY 聚合（如 MAX/AVG）

- 父群组内 95%+ 行的 units 和 bsr 完全相同 → GROUP BY MAX(units) 和选代表行结果一致
- 但 listing_days / weight / title / price 这些字段在变体间真的有差异 → 必须**选一整行**而不是按列聚合
- A 方案选最新+最高的代表，能保留代表行的全字段一致性

### 为什么把"独立性检查"提到数据层

之前 ①线 H5 / M04 v3-v6 都是"凭逻辑设计"基线 SQL，没有"输入数据是否独立"的检查。直到 M04 v7 实测才发现变体污染——这是个**架构级别的方法论缺陷**。

教训：**任何基于"独立观测点"假设的统计（百分位、回归、分类）落到真实数据上之前必须先验证独立性**。这条原则在选品业普遍适用，本卡是这条原则的工程化实现。
