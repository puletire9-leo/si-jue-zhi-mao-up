# 自有战绩文档与数据库关系

> 这张补充卡只回答一个问题：`产品表现ASIN_转换版2.md`、Docker 容器、`product_performance_actual` 表之间到底是什么关系。

---

## 一句话

`产品表现ASIN_转换版2.md` 是**原始种子数据文件**，  
`product_performance_actual` 是**导入后的结构化业务表**，  
Docker 只是让 `java-product` 容器**能读到这份文档**。

---

## 三者关系

### 1. Markdown 文档

文件：`docs/选品方法库/产品表现ASIN_转换版2.md`

它的角色是：
- 人工整理/导出的真实战绩快照
- 保留原始字段和原始语义
- 作为 ③线的**导入源头**

它不是业务查询表，也不是运行时主数据源。

### 2. Docker 容器里的文档

开发环境里，`java-product` 容器会把仓库 `docs/` 目录只读挂进去：

```yaml
java-product:
  volumes:
    - ./java-backend:/app
    - ./docs:/docs:ro
```

所以：
- 宿主机文件在仓库里
- 容器里可见路径是 `/docs/...`
- Java 导入接口可以直接读这份文件

Docker 本身不存业务数据，它只是提供“读取文档”的运行环境。

### 3. MySQL 表

表名：`product_performance_actual`

它的角色是：
- 存导入后的结构化记录
- 补齐衍生字段：`archetype / element / carrier / is_green / is_eliminated / bsr_id / source_batch / imported_at`
- 提供后续查询、回测、合成打分的真实数据源

后面 ③线、①②④线联动、回测，都应该以这张表为主，不再直接读 Markdown。

---

## 数据流

```
docs/选品方法库/产品表现ASIN_转换版2.md
          ↓
java-product 容器读取文件
          ↓
ProductPerformanceServiceImpl.importFromMarkdown()
          ↓
解析18列 + 清洗字段 + 自动打标
          ↓
upsert 写入 product_performance_actual
```

---

## 同步规则（很重要）

### 单向同步

方向只有一个：

```text
Markdown 文档  ->  数据库表
```

不会自动反向回写。

### 文档改了，不会自动改数据库

如果你手动改了 `产品表现ASIN_转换版2.md`：
- 数据库不会自己更新
- 必须重新调用一次导入接口

### 数据库改了，不会自动改文档

如果你在数据库里修了某行：
- Markdown 不会自动更新
- 文档仍然是原始种子快照

---

## 为什么重复导入不会爆炸

导入不是盲插，而是按：

```text
asin + marketplace
```

做唯一键 `upsert`。

这意味着：
- 同一条记录重复导入，不会无限新增
- 会更新已有行的字段和最新 `source_batch / imported_at`

所以导入接口更像“刷新 ③线真值表”，不是一次性的迁移脚本。

---

## 当前默认导入方式

接口：

```text
POST /api/v1/product-performance/import
```

默认读取：

```text
docs/选品方法库/产品表现ASIN_转换版2.md
```

开发环境下因为 `docs/` 已挂进容器，所以这条默认路径可以直接使用。

---

## 使用建议

1. 把 Markdown 当作**原始凭证/种子文件**
2. 把 `product_performance_actual` 当作**正式业务数据层**
3. 后续所有查询、回测、推荐，都优先读数据库
4. 只有当原始战绩文件有新版本时，才重新导入

---

## 结论

这三者不是并列关系，而是前后链路：

```text
Markdown 提供原始战绩
Docker 提供读取环境
MySQL 提供结构化真值表
```

真正给系统喂数据的是文档，真正给系统跑业务的是数据库。
