# 当前系统能力与产品卡片边界

> 用途：当你想快速搞清“现在系统到底已经实现了什么、用了哪些表、哪些适合做成产品卡片、②/④/方法卡边界在哪”时，先读这张。
> 状态：基于当前仓库代码 + 当前文档整理（2026-06-26）。本文讲的是**当前实现边界**，不是未来设计稿。

---

## 一句话总判断

现在系统里真正已经落成“系统能力”的，是：

- `①销量基线`
- `②错位机会（聪明卖家）`
- `③自有战绩`
- `M04 新品大类销量基础分级`
- `④元素机会引擎的预览版`

而 **方法卡不是数据库表/接口模块**，它是上层的“判断镜头”；  
**产品卡片** 则是把底层能力做成前端可读、可筛、可复盘的展示视图。

---

## 先把四层分开

| 层 | 是什么 | 当前仓库里对应什么 |
|----|--------|------------------|
| 数据底座层 | 原始数据、清洗数据、卖家样本、真值样本 | `competitor_products` / `competitor_products_clean` / `deng_zong_shop` / `product_performance_actual` |
| 能力引擎层 | 真正跑 SQL、算结果、对外给接口 | ① / ② / ③ / ④ / M04 对应的 Service + Mapper + Controller |
| 方法卡层 | 你怎么理解市场、怎么判断机会 | `M01~M05` 等 markdown 卡 |
| 产品卡片层 | 给前端/用户看的结果视图 | 新品分级卡、错位机会卡、赢家方向卡、元素候选卡等 |

**不要混：**

- `方法卡` 不是 `category_dislocation` 这种表
- `方法卡` 也不是 `ElementDiscoveryController` 这种接口
- `产品卡片` 可以建在能力引擎上，但不等于底层表结构

## ②聪明卖家 和 ④元素机会引擎，到底差在哪

### ② 聪明卖家 / 错位机会

它回答的是：

> **“哪个小类/方向值得打？”**

看的核心不是标题内容，而是**卖家竞争结构**：

- 本土卖家有没有在做
- CN 卖家有没有扎堆
- 郑总系有没有进来
- 这个小类是不是“本土验证了需求，但中国同行还没挤满”

所以 ② 的输出粒度更像：

- `Sun Catchers` 这个方向值不值得看
- `Soils` 这类方向虽然错位，但不一定适合我们

也就是说，② 的产出是 **方向机会 / 小类机会**。

### ④ 元素机会引擎

它回答的是：

> **“在我们要打的非标商品里，具体什么元素、什么载体组合在冒头？”**

看的核心不是卖家结构，而是**标题里的 element + carrier**：

- 标题里出现了什么元素
- 这个元素跨了多少载体
- 哪些元素热、哪些元素冷门但有量
- 某个已验证元素能不能补位到我们还没做过的载体

所以 ④ 的输出粒度更像：

- `卡皮巴拉 × 束口袋` 值得补位
- `豹纹樱桃` 这个元素正在多个载体上冒头

也就是说，④ 的产出是 **内容机会 / 元素机会 / 商品候选**。

### 记一句就够

- `②` 回答：**去哪一类打**
- `④` 回答：**打什么内容**

## 方法卡 和 ②/④ 的边界

`方法卡` 比 ②/④ 更高一层。

| 对比项 | 方法卡 | ②/④ 这类能力引擎 |
|--------|--------|------------------|
| 本质 | 判断镜头 / 业务打法 | 证据引擎 / 计算模块 |
| 关注点 | 我应该怎么看市场 | 系统能拿出什么证据 |
| 产出 | 一种规则、一种读法、一种筛法 | 一批结果、一组信号、一张清单 |
| 是否必须有独立表 | 不必须 | 通常会有表或接口 |

最重要的一句：

> **方法卡不是自动判生死的数据库标签，而是一个可展示、可复盘、可改写的“视角”。**

这和 [[系统落地映射]] 里定下来的原则一致：  
**当前阶段先做显示镜头，不做入库自动打标。**

## 什么最适合直接做成“产品卡片”

### 适合做主卡的

| 卡片 | 为什么适合 |
|------|------------|
| `③×② 可行动机会卡` | 既有市场错位，又有我们历史上赢过的证据，最接近“能行动的方向” |
| `M04 新品分级卡` | 已经能批量给 `S/A/B/C/D`，适合大盘筛货 |
| `③ 赢家方向卡` | 能告诉你“我们真实赢过什么 archetype / carrier / element” |

### 适合做辅助卡的

| 卡片 | 为什么适合 |
|------|------------|
| `① 销量基线解释卡` | 更像“尺子”和解释层，适合挂在详情边上 |
| `④ 非标候选卡` | 当前更适合做“人工审阅卡”，不要包装成全自动正式机会卡 |

### 当前不建议包装过头的

- `④` 不要现在就讲成“正式元素库 + 全自动机会推荐系统”
- `M05` 现在还没真实内容，不建议做前端产品卡

## 当前最容易混淆的三件事

### 1. ④ 已经有代码，不等于 ④ 已经正式产品化

当前 ④ 真正落下来的，是：

- `path2-preview`
- `carrier-match-preview`
- `manual-candidates`

其中 `manual-candidates` 还会叠加 ① 的 baseline 作为说明。  
但这仍然属于 **预览/人工审阅链路**，不是正式 `element_discovery` 日跑产物。

### 2. ② 比 ④ 更接近“现成产品卡”

因为 ② 已经有：

- 稳定结果表 `category_dislocation`
- 查询接口
- `actionable-opportunities`
- 和 ③ 真值库的交集逻辑

所以如果现在就要做一个“真能用”的机会卡，② 会比 ④ 更成熟。

### 3. 方法卡不是“数据库字段打标”

`mo1 / mo2` 那套定义，本质是**方法来源溯源**，不是质量分档。  
方法卡应该是“这批货是按哪张卡被圈出来的”，而不是“入库时系统替你判了它好坏”。

## 建议的前端卡片化视图

如果现在要收口成一组前端卡片，建议先按下面几类理解：

1. `新品分级卡（M04）`
   用来批量看新品强弱，解决“新导入的货先分层”。

2. `错位机会卡（②）`
   用来看“本土在做、CN 还没挤满”的小类方向。

3. `赢家方向卡（③）`
   用来看“我们真实赢过哪些 archetype / carrier / element / subcategory”。

4. `非标候选卡（④）`
   用来看标题解析出来的候选元素和载体命中，偏人工审阅。

5. `基线解释卡（①）`
   用来告诉你：这个候选放在所属大类/小类里，销量和价格处在什么位置。

---

## 当前一句产品化建议

如果只允许先推一张“最像产品”的卡：

> 先推 `③×② 可行动机会卡`

因为它同时满足：

- 有真实结果表
- 有查询接口
- 有历史赢家真值背书
- 不是纯算法幻想

而 `④` 更适合先继续做成“高质量人工审阅工具”，等正式元素表稳定后再升级成产品主卡。
