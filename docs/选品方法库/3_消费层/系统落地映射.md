## 核心模型(用户拍板 2026-06-22):方法卡 = 独立的"显示镜头",不入库自动打标

**否决**:`CompetitorFilterService` 在**入库时自动**打 MODE1/MODE2/FAIL 标 —— 不要了。入库归入库,不自动判生死。

**要的**:
1. 每张方法卡 = 一个**独立的视图/镜头**。前端展示**它自己圈出的那批数据**(M01 一批、M02 另一批)。
2. 用户**看着**这批数据,**手动点击**,才往数据表某字段写标。
3. **当前阶段只做"显示"**(看每张卡圈出哪些货,只读、不写库);**手动打标(统一更改)以后再做**。

为什么对:方法不替你自动下判断,你看方法圈出什么、再亲手认定。这个"手动标"将来是最值钱的复盘数据(哪张方法卡圈的货最后成了爆款)→ 喂养 [[00_业务认知]] 的进化。

### ✅ 已定:`mo1 / mo2` = 方法溯源标记(读法A,用户拍板 2026-06-22)
- 语义 = **"这货是被哪张方法卡找到的"**(M01→`mo1`、M02→`mo2`…),**不是**质量分档(不是老的 MODE1/MODE2 好坏档)。
- 为什么:溯源才接得上复盘闭环 —— 将来能回答"哪张方法卡圈的货最后成了爆款"。质量分档做不到这点。
- 字段:**复用现有 `filterMode` 列**(解耦后入库不再写它,正好空出来接管),不新增列、不动表结构。
- 注意:解耦后 `filterMode` 的取值含义从"MODE1/MODE2/FAIL(质量)"变为"mo1/mo2/…(方法来源)"。历史值需在切换时一并清理/迁移(以后做)。

## 两套机制现状(纠正:解耦后各自的去向)

| | 机制① 精筛引擎 | 机制② 筛选规则回灌 |
|--|--|--|
| 代码 | `CompetitorFilterService.checkMode1/2`(Java) | `filterRules` / 前端 qualifyRules + 模型JSON |
| 现在干啥 | **入库时**自动打 MODE1/MODE2/FAIL | **看数据时**对已入库数据实时再筛 |
| 解耦后去向 | ❌ 退役自动打标(入库不再判生死) | ✅ **留用** —— 这就是方法卡的"显示镜头" |
| 支持账龄分段? | ❌ 只有单条销量线 `salesMin` | ✅ **规则间OR+规则内AND,天然支持** |
| 支持价格带? | ✅ 有 `price` | ❌ 白名单缺 price(但前端 RangeFilterPanel 已有 priceMin/Max) |

**结论:M01 走机制②(显示镜头)。** M01 命根子是**账龄分段**(30/60/90 三条不同销量线),机制②的"规则间 OR、规则内 AND"天然能表达;机制①单值 `salesMin` 表达不了。
(我最初建议"改 api_config 折中值"被机制①带偏了——既丢分段,又违背"不入库自动打标"。已废弃。)

## M01 账龄分段 → 编译成 filterRules(机制②)

**英国**(units=月销量,listingDays=上架天数,规则间 OR=满足任一即合格):

| 规则 | 条件(AND) | 含义 |
|--|--|--|
| A | listingDays ≤ 30 且 units > 2 | 新品宽松 |
| B | listingDays ≤ 60 且 units > 10 | 中期抬高 |
| C | listingDays ≤ 90 且 units > 30 | 90天要够硬 |
| D | bsr < 20000 | BSR 达标也算(代理) |

OR 语义天然实现"品越老、要求越高":50天的品 A 不中(>30天)、落到 B 需 >10;20天的品 A 就放行。**这正是 M01 比现有引擎细的地方,而机制②跑得起来。**

德国同构:价格 5.99–17.99,分段 4 / 20 / 50,bsr < 25000。

**唯一缺口 = 价格带 4.99–16.99。** filterRules 白名单只有 `listingDays/units/bsr/weightG`,没 `price`。
但前端 `RangeFilterPanel` **已经有** priceMin/priceMax 输入框。所以缺口只是"把 price 加进 filterRules 白名单 + 应用逻辑"——**小改,思路对就好动**。已记进 [[README]] 待补缺口。

## 三个思路层面的 gap(最重要,思路别错)

1. **账龄分段**:机制①不支持、机制②支持 → 所以 M01 走机制②。(已在上面解决)

2. **M03(FBM简单道)≠ 系统 Mode2 —— 我上一条说反了,纠正:**
   - 系统 `checkMode2` = "BSR够低 *或* 销量够高就捞回",**不看配送方式**,是给 Mode1 没过的品一条信号兜底。
   - M03 = "FBM 自发货走更简单标准",**看配送方式**(只对 FBM)。
   - 系统现在 FBM 和 FBA **一样**走 checkMode1,**没有** M03 那条简单道。要实现 M03 得加"按 fulfillment 区分"的逻辑。这是真 gap,不是改个值。

3. **销量天花板**:系统有 `salesMax=200`(滤掉太成熟的品),M01 方法卡**没提**。要不要把这道也写进 M01?待你定。
