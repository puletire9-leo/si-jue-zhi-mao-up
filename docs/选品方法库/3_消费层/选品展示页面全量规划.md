# 选品展示页面全量规划

> 给前端实现 AI 使用。目标：补齐“所有选品展示页面”，把当前散在 `AllSelection` 里的新品、竞品、郑总、方法卡、店铺、品线、商品族、候选池拆成清晰可用的工作台。实现时以当前代码为事实来源，优先复用已有 API、组件和模块体系。

## 一、当前问题

当前前端入口不少，但真正的选品展示视角偏少。

已有核心入口：

| 入口 | 路由 | 当前实现 | 问题 |
|---|---|---|---|
| 总选品管理 | `/all-selection` | `views/AllSelection/index.vue` | 大而全，适合管理，不适合专门看机会 |
| 新品榜 | `/new-products` | 复用 `AllSelection` | 只是默认绑定 M01，没有独立新品视角 |
| 竞品店铺 | `/reference-products` | 复用 `AllSelection` | 仍是商品流，不是竞品店铺研究 |
| 郑总店铺上新 | `/zheng-products` | 复用 `AllSelection` | 无法按店铺、品线、ABC/D 结构看 |
| 品线选品 | `/product-line-selection` | 独立模块 | 当前最接近真正工作台 |
| 店铺总览 | `/zheng-shop-overview` | 旧模块 | 与新店铺画像能力重复，后续应迁移或隐藏 |
| 以图识图 | `/image-search` | 独立功能入口 | 更像工具，不是完整选品展示页 |
| 卖家精灵数据获取 | `/asin-import` | 数据获取页 | 不是选品观看页 |

核心问题：

```text
现在很多业务问题都被迫用同一个 AllSelection 页面看：
今天新来了什么？
哪些新品已经起量？
哪些新品虽然没销量但像爆款？
哪些店铺持续上新？
哪些类目突然冒出来？
哪些商品被多家优质店铺验证？
哪些商品应该进入候选池？
```

下一阶段不要继续把所有东西塞进 `AllSelection`。应新增多个“按业务问题组织”的展示页面。

## 三、实现通用规则

### 1. 前端结构

新增页面放到模块体系：

```text
frontend/src/modules/{module-name}/
├─ manifest.ts
├─ index.vue
├─ components/
└─ composables/
```

新增 API：

```text
frontend/src/api/{domain}.ts
frontend/src/types/{domain}.ts
```

所有请求必须使用：

```text
frontend/src/utils/request.ts
```

### 2. 市场编码

所有页面只允许：

```text
UK / DE / US
```

禁止前端出现 `ALL` 市场编码。跨市场统计需要分别请求 UK/DE/US 后在前端明确组合，或等待后端提供聚合接口。

### 3. 变体口径

选品展示默认使用去变体父体口径：

```text
variation=Y / useCleanTable=true / clean no-variants
```

含变体只用于专门的“同款/变体检查页”。

### 4. 页面风格

- 这是运营后台，不做 landing page、hero、营销文案。
- 页面要安静、密集、可扫描。
- 表格、筛选、分页、弹窗优先使用 Element Plus。
- 商品列表可复用 `UniversalCard`，但关键决策页应提供表格视图。
- 每个页面都要有明确的筛选条、排序、批次、站点、刷新。
- 所有写操作必须二次确认并有 loading。

### 5. 共同筛选项

大多数页面都应支持：

| 筛选项 | 说明 |
|---|---|
| marketplace | UK / DE / US |
| batchDate / createdWeek / month | 根据数据源选择 |
| sellerName | 店铺名 |
| asin / title / brand | 商品检索 |
| category / nodeId / bsrId | 类目筛选 |
| salesTier | A/B/C/D/UNKNOWN |
| methodId | M01/M02/M03/M06 |
| unitsMin / unitsMax | 月销量 |
| listingDaysMin / listingDaysMax | 上架天数 |
| priceMin / priceMax | 价格 |
| bsrMax | BSR 上限 |
| fulfillment | FBA/FBM/AMZ |

### 6. 共同动作

所有商品展示页尽量支持：

- 查看商品详情
- 打开 Amazon 链接
- 以图识图
- 复制 ASIN
- 加入选品候选池
- 标记观察
- 导出选中 ASIN
- 查看所属店铺
- 查看相似商品族

## 四、页面规格

## 1. 今日选品工作台

### 定位

每天打开第一眼看的总控页。不是大表，而是把今天最值得看的内容集中成模块。

### 路由

```text
/selection-workbench
```

### 模块建议

| 模块 | 内容 |
|---|---|
| 今日新增 | 最近 24 小时 / 当前周新入库商品数 |
| 新品起量 | 短账龄 units 达标商品 |
| 方法卡新增命中 | M01/M02/M03 今日新增命中 |
| 优质店铺上新 | 郑总相似店/自有优质店/方法卡高命中店新上商品 |
| 待复查 | 已加入观察清单且到复查时间 |
| 候选池变化 | 新增、推进、放弃、进入定稿 |

### 核心交互

- 点击模块跳转到对应详情页并带上筛选条件。
- 顶部切换 marketplace。
- 默认展示今天/本周，不做复杂筛选。

### 数据来源

第一版可分别调用现有 API：

- `competitorApi.getList`
- `methodCardsApi.getM01Products / getM02Products / getM03Products`
- 后续接候选池 API。

## 2. 新品雷达

### 定位

按时间流查看最新入库商品，解决“今天新来了什么”。

### 路由

```text
/new-product-radar
```

### 展示

| 区域 | 内容 |
|---|---|
| 顶部指标 | 今日新增、本周新增、M01 命中、已收藏 |
| 时间轴 | 按入库时间/周次分组 |
| 商品表/卡片 | 图片、ASIN、标题、店铺、类目、月销量、BSR、价格、上架天数、方法卡命中 |
| 右侧摘要 | 当前筛选下 top 类目、top 店铺、销量等级分布 |

### 默认筛选

```text
source=新品榜
useCleanTable=true
createdWeek=latest
marketplace=UK
```

### 关键排序

- 入库时间倒序
- 上架天数升序
- units 降序
- BSR 升序
- 方法卡命中优先

### API

第一版：

```ts
competitorApi.getList({
  marketplace,
  source: '新品',
  useCleanTable: true,
  createdWeek,
  page,
  size
})
```

## 5. 方法卡结果中心

### 定位

### 页面结构


## 15. 爆款多店验证页

### 定位

实现 M06 思路：一个爆款或相似商品被多家优质店铺验证后，即使一个新品目前没销量，也可以提前圈出。

### 路由

```text
/multi-shop-validated-products
```

### 判断逻辑

候选商品不是只看当前销量，而是看证据：

```text
相似商品族中存在 A/B/C 爆款
+ 出现在多家优质画像店铺
+ 店铺来源可信
+ 类目方向与稳定盘一致
+ 当前新品账龄短
= 可提前进入候选
```

### 页面字段

| 列 | 说明 |
|---|---|
| 商品族 | familyCode / familyName |
| 种子爆款 | A/B/C 商品 |
| 新品候选 | 当前待跟商品 |
| 出现店铺数 | 多店验证强度 |
| 优质店铺数 | 来自基线店铺数量 |
| 最高销量等级 | A/B/C |
| 类目一致性 | 类目是否一致 |
| 推荐动作 | 候选/观察/放弃 |

### 后端依赖

当前已有骨架：

```text
product_family_group
product_family_member
```

后续需自动聚类：

- 同 ASIN
- 同父体
- 标题相似
- 图片相似
- 多店出现

第一版可先做手动录入和展示。

## 17. 同款/变体检查页

### 定位

专门看变体、父体、重复 ASIN、同款跨店污染，避免选品判断被污染。

### 路由

```text
/variant-duplicate-check
```

### 功能

- 输入 ASIN 查父体/变体
- 查看 clean 代表行
- 查看被清理掉的子体
- 查看同 ASIN 跨 UK/DE/US 出现
- 查看同 ASIN 跨店铺出现
- 对比含变体和不含变体数据差异

### 口径

默认展示 clean 父体；只有这个页面允许主动切含变体。

## 18. 选品候选池

### 定位

所有观看页最后都要沉淀到候选池，否则只是看数据。候选池负责承接人工决策。

### 路由

```text
/selection-candidates
```

### 状态流

```text
待看 → 观察中 → 准备开发 → 已定稿 → 已上架
          ↓
        已放弃
```

### 字段

| 字段 | 说明 |
|---|---|
| asin | 商品 |
| marketplace | 市场 |
| title/image | 基础信息 |
| sourcePage | 来自哪个页面 |
| sourceEvidence | 方法卡/店铺/商品族/类目证据 |
| status | 当前状态 |
| nextReviewAt | 下次复查时间 |
| owner | 负责人 |
| note | 人工备注 |
| createdAt/updatedAt | 时间 |

### 第一版后端缺口

如果后端暂未有候选池表，先前端设计 API 契约，不硬塞进 `selection_products`：

```text
selection_candidate_evidence
selection_candidate_review_log
```

## 九、验收标准

### 页面级

- 每个 P1 页面都能从菜单进入。
- 每个页面顶部都有 marketplace，且只有 UK/DE/US。
- 每个页面都能刷新、筛选、分页。
- 每个商品列表都能看到 ASIN、标题、图片、店铺、类目、月销量、BSR、价格。
- 能从商品跳到 Amazon 链接。
- 能从店铺跳到店铺画像。
- 能复制 ASIN。
- 写操作有二次确认、loading、错误提示。

### 业务级

- 新品雷达能回答“今天/本周新来了什么”。
- 新品起量榜能回答“哪些新品已经跑出来”。
- 方法卡结果中心能回答“每张方法卡命中了哪些商品”。
- 店铺画像能回答“这家店是什么结构”。
- 店铺上新流能回答“优质店最近上了什么”。
- 类目机会榜能回答“哪些方向值得看”。
- 候选池能承接人工决策。

### 技术级

- 不新增 Tailwind CDN。
- 不绕过 `utils/request.ts`。
- 不在前端传 `marketplace=ALL`。
- 不把含变体数据混入默认选品展示。
- 不继续向 `AllSelection` 堆复杂新视角。
- 新模块必须有 `manifest.ts`。
- `npm run type-check` 和 `npm run build` 应通过。

## 十、不要做什么

- 不要把所有新增页面做成一个超级大页面。
- 不要把方法卡命中、销量等级、店铺画像合成一个黑盒大分。
- 不要把 M01/M02/M03 写死成同一个规则。
- 不要用静态假数据冒充真实接口。
- 不要为了页面方便引入 `ALL` 市场。
- 不要默认展示含变体数据。
- 不要删除旧 `AllSelection`，第一阶段只新增专门视角。

## 十一、最终目标

最终前端不是“数据列表集合”，而是一个选品决策系统：

```text
数据获取
  ↓
干净商品 / 店铺 / 类目 / 商品族证据
  ↓
新品雷达 / 方法卡 / 店铺画像 / 类目机会 / 多店验证
  ↓
选品候选池
  ↓
观察 / 开发 / 定稿 / 上架 / 复盘
```

这套页面补齐后，系统才能从“能筛选商品”升级成“能持续发现、解释、跟踪、复盘选品机会”。
