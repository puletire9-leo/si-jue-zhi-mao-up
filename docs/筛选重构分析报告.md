# 商品筛选重构分析报告

> 范围：新品榜 / 全部选品 / 品线选品 的"筛选查询层"（前端 + Java 后端）
> 参考目标：卖家精灵筛选页（`docs/PixPin_2026-06-17_23-54-30.png`）的三栏归类、统一 min/max、统一操作区
> 现状对照：`docs/PixPin_2026-06-18_13-42-30.png`（顶部 bar + 合格规则卡 + 区间三栏，三套各自为政）

## 一、现状结论

筛选逻辑并非"单页写乱"，而是 **6 处独立实现**，其中 3 处直接服务竞品查询，构成本次重构核心：

| # | 实现 | 文件 | 交互模型 |
|---|------|------|---------|
| A | 顶部查询栏 | `components/SelectionQueryForm/index.vue` | dropdown + 输入框 + 弹窗 |
| B | 合格规则引擎 | `components/QualifyRuleFilter/index.vue` | 规则条（field+op+value，规则间 OR / 内 AND） |
| C | 区间面板 | `components/RangeFilterPanel/index.vue` | 三列 min~max + 预设按钮 + checkbox |
| D | 我的筛选预设 | `components/FilterPresetSelector/index.vue` | radio 槽位 + 服务端持久化 |
| E | 品线选品筛选 | `modules/product-line-selection/{index.vue,store.ts}` | 内联 dropdown + 输入框（Pinia） |
| F | 初筛/精筛配置（死引用） | `components/FilterConfigPanel/index.vue` | collapse + input-number（写库，非查询） |

另有第四处"散落状态"：`groupByParent`、`maxVariantCount`、`pinSelected` 直接写在 `AllSelection/index.vue` 页面 ref，既不属 A 也不属 C。

**割裂的本质**：三套筛选（A 顶部 bar、B 合格规则、C 区间面板）在 `loadProducts` 里被串行拼成一个 `competitorParams`（`AllSelection/index.vue:1003-1063`），但三者状态分散、命名不一致、触发方式各异，用户看到的是"三块互不相干的筛选区"。

## 二、问题清单（按严重度分级）

### CRITICAL — 影响正确性，必须修

**C1. 去折叠路径静默吞筛选条件。**
后端 `groupByParent=true` 时走 `queryGroupedByParent`（`CompetitorService.java:349-360`），其方法签名根本不传 `unitsMin/Max`、`listingDaysMin/Max`、`fulfillment`、`createdWeeks`，SQL 也无对应条件。结果：用户开"合并变体"后，**销量区间 / 上架天数 / 配送方式 / 多选周 这四类筛选被无声忽略**，前端无任何反馈。多选周在该路径退化为单值 `createdWeek`。
> 这是"看起来生效、实际没生效"的隐性 bug，比报错更危险。

**C2. 合格规则实现了两遍，易行为分叉。**
扁平路径在 Java Service 用白名单 Map（`CompetitorService.java:606-675`），去折叠路径在 XML 用 `<choose>/<when>`（`CompetitorProductMapper.java:79-107`）。语义虽一致（规则间 OR、规则内 AND），但两份代码不共享，改一处漏一处必然分叉——C1 正是这类问题的体现。

**C3. `maxVariantCount` 双入口互相覆盖。**
页面级 `maxVariantCount`（`index.vue:1022-1023`）和区间面板 `rf.variantCountMax`（`index.vue:1007`）都写 `competitorParams.maxVariantCount`，后写覆盖前写，用户在顶部设的变体数上限会被区间面板悄悄覆盖。且该字段只在去折叠路径生效，扁平路径完全不处理。

### HIGH — 影响一致性/可维护性

**H1. 同一概念多套字段名**（统一 UI 前必须先统一契约）：

| 概念 | A 顶部 | C 区间 | E 品线 | 后端 |
|------|--------|--------|--------|------|
| 价格区间 | — | `priceMin/Max` | `searchPriceMin/Max` | `priceMin/Max` |
| 站点 | `country` | `country`(仅货币符号) | `marketplace` | `marketplace` |
| 入库周 | `weekTag`(单值) | `createdWeeks[]` | `selectedWeekTags[]` | `createdWeeks[]` |
| 月销量 | — | `unitsMin/Max` | — | `unitsMin/Max` |
| 等级 grade | 逗号串 | `string[]` | — | 逗号串 |

**H2. 预设存取不对称。** `getCurrentFilterConfig`（`index.vue:1353-1373`）收集了 rangeFilter + 部分顶部字段 + qualifyRules，但漏了 `asin/productTitle/storeName/weekTag`；回填 `handlePresetApply`（`1375-1400`）也只挑部分字段。存进去和取出来的不是同一组。

**H3. 触发方式四种并存。** A 部分 `@change` 即时触发、部分要点"搜索"；C 靠 watch 深度监听自动 emit；B 要显式点"应用筛选"；E 用 `@change/@keyup.enter`。用户无法形成稳定预期。

### MEDIUM — 死代码/技术债

- **M1. MODE 概念半残留**：`dataFilterMode`(MODE1/MODE2/FAIL) 被 `v-if="false"` 隐藏但字段/映射/默认值仍在，已被 qualifyRules 取代，属死代码。
- **M2. FilterConfigPanel(F) 死引用**：`AsinImport/index.vue:81` 整行注释，但仍 import（`line 355`），字段名与 C/B 高度重叠易混淆。
- **M3. 合格规则默认值硬编码两份**：新品榜 `newQualifyRules`（`index.vue:742`）与品线 `store.qualifyRules`（`store.ts:79`）各写一份"上架≤30天且月销>30"。

### 性能隐患（仅记录，非本次必改）

- `DATE_FORMAT(created_at,'%x-W%v')` 用于 WHERE（`CompetitorService.java:505`、`Mapper:73`）：函数包裹列，无法走 created_at 索引，多选周筛选全表/全索引扫描。
- `LIKE CONCAT('%',x,'%')`（brand/seller/title）前导通配符无法走索引；`FIND_IN_SET`（grade/weekTag/category）无法走索引。
- 去折叠路径窗口函数 `ROW_NUMBER/COUNT OVER` + 外层 count 子查询，大表开销显著。

### 安全（已确认无注入）

qualifyRule 动态字段/运算符两条路径均有防护：扁平用白名单 Map、去折叠用 `<choose>` 硬编码列名，阈值一律参数绑定（`{0}` / `#{c.value}`）。`sortOrder` 的 `${}` 替换在传入前已归一化为 ASC/DESC。**无 SQL 注入风险。**

## 三、目标架构（统一筛选）

借鉴卖家精灵的"三栏归类 + 统一 min/max + 统一操作区"，但保留本系统已有的合格规则引擎能力。核心原则：**单一数据源 + 单一字段契约 + 单一查询路径**。

### 3.1 前端：单一 FilterModel + 单一面板

```
components/ProductFilter/
├── types.ts            # 唯一 FilterModel 定义（前后端字段名对齐）
├── ProductFilter.vue   # 容器：站点/周次 tab + 三栏分组 + 操作区 + 预设
├── sections/
│   ├── SalesSection.vue        # 销售表现：units/price/bsr min~max
│   ├── ProductInfoSection.vue  # 产品信息：listingDays/weight/variantCount/grade/fulfillment
│   └── QualifyRuleSection.vue  # 合格规则（保留 B 的规则引擎，作为"高级"分组）
└── useFilterModel.ts   # 唯一状态 + 拼参（取代散落的 ref + competitorParams 手工拼装）
```

- **状态唯一**：用一个 `reactive<FilterModel>` 或 Pinia store 承载全部筛选，删除 A/C/页面级 ref 三处来源。
- **字段唯一**：`FilterModel` 字段名直接采用后端 DTO 名（`marketplace/priceMin/createdWeeks/...`），消灭 `country↔marketplace`、`weekTag↔createdWeeks`、grade 字符串↔数组 的映射层。
- **拼参唯一**：`useFilterModel.toRequestParams()` 一处出参，替代 `loadProducts` 里 60 行手工拼装。
- **触发统一**：草稿态 + 显式"开始筛选/重置"（对齐卖家精灵），去掉部分控件的即时 `@change`，避免误触发查询。

### 3.2 后端：合并双查询路径的筛选条件集

- **抽取 `CompetitorFilterBuilder`**：把"区间条件 + fulfillment IN + 多选周 + 合格规则"的 WHERE 构造抽成一处（Service 层方法或独立类），扁平路径和去折叠路径**共用同一套条件拼装**，只让 `groupByParent` 决定是否额外套窗口函数去重。彻底消灭 C1（去折叠丢字段）和 C2（规则两份实现）。
- **合格规则单一实现**：去折叠路径也走 Service 拼好的 wrapper 条件，或把 XML 规则片段抽成共享 SQL fragment，二选一，不再两套。
- **DTO 清理**：标注/移除 `asins`(@Deprecated)、`createdWeek`(单值，被 createdWeeks 取代)、`filterMode`(被 qualifyRules 取代) 等过渡字段。

### 3.3 字段契约（统一后，前后端共用）

| 分组 | 字段 | 类型 | 语义 |
|------|------|------|------|
| 定位 | marketplace, month, createdWeeks[] | str/str/str[] | 站点/月份/多选周 |
| 销售表现 | unitsMin/Max, priceMin/Max, bsrMax | num | min~max 区间 |
| 产品信息 | listingDaysMin/Max, weightMax, ratingMin, maxVariantCount, grade[], fulfillment[] | num/str[] | 区间 + 多选 |
| 高级 | qualifyRules[] | Rule[] | 规则间 OR / 内 AND，与上方条件 AND 叠加 |
| 控制 | groupByParent, sortBy, sortOrder, page, size | — | 去折叠/排序/分页 |

> 关键决策：**合格规则与区间筛选保持 AND 叠加**（现状语义不变），但在 UI 上把合格规则收进"高级"分组并加冲突提示——当用户在区间设了 `bsrMax` 又在规则里设 `bsr`，给出"两处都会生效（取交集）"的提示，避免矛盾配置。

## 四、分阶段修复建议

按"先正确、再统一、后清理"推进，每阶段可独立验收：

### 阶段 1：修正确性（CRITICAL，独立可上线）
1. **C1**：去折叠路径补全 `unitsMin/Max`、`listingDaysMin/Max`、`fulfillment`、`createdWeeks` 条件。最小改法是在 `queryGroupedByParent` 调用前，把这些条件统一拼进 SQL（或抽 builder）。
2. **C3**：`maxVariantCount` 与 `variantCountMax` 二选一保留，拼参处去掉覆盖。
3. 验收：开/关"合并变体"两种状态下，同一组销量/上架/配送筛选返回结果一致受控。

### 阶段 2：统一字段契约（HIGH）
1. 前端 `FilterModel` 落地，字段名对齐后端 DTO，删除 `FILTER_TO_API_KEY` 映射与 grade join。
2. **H2**：预设 `getCurrentFilterConfig`/`handlePresetApply` 改为序列化/反序列化整个 `FilterModel`，存取对称。
3. 验收：保存预设→刷新→应用，所有筛选字段完整还原。

### 阶段 3：统一 UI 与交互（HIGH）
1. 新 `ProductFilter.vue` 三栏分组 + 统一操作区，替换 A/C/页面级散落控件。
2. **H3**：统一为"草稿态 + 显式开始筛选"。
3. 品线选品模块复用同一组件（E 接入），消灭第 4 处实现。
4. 验收：新品榜与品线选品筛选 UI/字段一致；视觉对齐卖家精灵三栏。

### 阶段 4：清理死代码（MEDIUM）
- 移除 `dataFilterMode`(M1)、`FilterConfigPanel` 死引用(M2)、合格规则重复默认值(M3)、DTO 过渡字段。

## 五、验收与风险

- **回归重点**：阶段 1 改动后端 SQL，需对"去折叠 + 各类区间"做交叉验证（开/关合并变体 × 每类区间），确保不改变现有正确路径结果。
- **数据一致性**：`variant_count`(窗口函数算) vs `variations`(API 上报列) 当前被混用于 maxVariantCount 过滤，统一时需明确以哪个为准。
- **不在本次范围**：性能隐患（DATE_FORMAT 索引失效等）建议单独立项，涉及加归一化周列 + 建索引，属 schema 变更需谨慎。
- **本报告为只读分析，未改动任何代码。** 落地按阶段开分支、逐阶段 code-review。
