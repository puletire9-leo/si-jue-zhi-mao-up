# 筛选系统统一分层方案（2026-06-30）

> 目标：前端页面保持现状，不重做交互；把“普通竞品 / 清洗表切换 / 郑总店铺 / 方法卡 / 自由筛选 / 批次筛选 / 变体筛选”统一进一套清晰的逻辑层和查询分层。
>
> 核心要求：
> 1. 页面不必重做。
> 2. 逻辑必须单一路径、可解释。
> 3. 结构要能承接后续继续加 M03/M04、更多来源、更多自由筛选。

---

## 1. 先讲结论：应该统一什么，不应该统一什么

这套系统里，真正应该统一的是 4 件事：

1. **统一筛选语义**
   - “变体数”“批次”“卖家”“大类”“排序”“评分等级”这些词，在所有来源里都必须有统一业务含义。

2. **统一筛选状态**
   - 页面上可以有多个控件入口，但提交查询前只能收敛成一个 `FilterIntent`。

3. **统一查询编译**
   - 不是每个页面/方法卡自己拼接口参数。
   - 而是统一先生成 `QueryPlan`，再决定打哪个数据源。

4. **统一来源切换规则**
   - 清洗表、原表、郑总表、方法卡不是四套平行系统。
   - 它们应该被统一描述为“数据源 + 镜头（Lens）”。

不需要强行统一的是：

1. 页面控件外观
2. 方法卡的业务解释文案
3. 某些来源天然不支持的字段

所以这次建议不是“所有来源都用同一个 SQL”，而是：

- **同一个过滤意图模型**
- **同一个查询编译层**
- **多个数据源执行器**

---

## 2. 当前系统应该怎样抽象

我建议把当前筛选系统抽成 5 层。

## L1：View Layer（页面层）

保留你现在满意的页面：

- `SelectionQueryForm`
- `unified-filter-bar`
- `FilterDrawer`
- `RangeFilterPanel`
- 方法卡按钮 / 详情弹窗

这一层只负责：

- 展示控件
- 采集用户输入
- 展示当前已选条件

**不负责决定打哪个接口，也不负责拼请求参数。**

---

## L2：FilterIntent Layer（统一筛选意图层）

这一层是整个统一方案的核心。

无论用户是从：

- 顶部搜索
- 主栏站点/大类
- 抽屉区间筛选
- 预设恢复
- 方法卡入口

进入的，最终都先汇总成一个统一对象，例如：

```ts
interface SelectionFilterIntent {
  scene: "all" | "new" | "reference" | "zheng";
  methodId?: "M01" | "M02" | null;

  search: {
    asin?: string[];
    title?: string;
    sellerName?: string;
    category?: string[];
  };

  scope: {
    marketplace?: "UK" | "US" | "DE";
    source?: string;
  };

  freshness: {
    mode?: "latest" | "manual";
    snapshotKeys?: string[];
  };

  metrics: {
    priceMin?: number;
    priceMax?: number;
    unitsMin?: number;
    unitsMax?: number;
    listingDaysMin?: number;
    listingDaysMax?: number;
    bsrMax?: number;
    weightMax?: number;
    variantCountMax?: number;
    grade?: string[];
    fulfillment?: string[];
  };

  sort: {
    field?: string;
    order?: "asc" | "desc";
  };

  switches: {
    dataView?: "clean" | "raw";
  };
}
```

注意这里的关键点：

- 页面有多少入口不重要。
- 最终只能有一个 `SelectionFilterIntent`。

也就是说：

- `SelectionQueryForm` 不再是请求参数事实源。
- `activeFilters` 也不再直接代表接口参数。
- 它们都只是输入来源，最后要 merge 进统一 intent。

---

## L3：Lens Layer（镜头层）

方法卡不应该再被看成“特殊页面分支”，而应该被建模成镜头。

也就是：

- **数据源**决定“从哪张表查”
- **镜头**决定“默认带什么约束、锁哪些字段、解释如何展示”

建议定义：

```ts
interface SelectionLens {
  id: "default" | "M01" | "M02";
  baseSource: "competitor_clean" | "competitor_raw" | "deng_zong";
  fixedFilters?: Partial<SelectionFilterIntent>;
  lockedFields?: string[];
  defaultFreshness?: "latest";
  explanation?: {
    title: string;
    summary: string;
  };
}
```

### 当前镜头怎么落

#### `default`

- `baseSource = competitor_clean`
- 不强加业务规则
- 自由筛选全部开放

#### `M01`

- `baseSource = competitor_clean`
- 固定 `scene = new`
- 固定新品来源
- 固定方法阈值
- 默认 freshness = latest
- 自由筛选允许在方法规则之上做二次收窄，但不能破坏方法核心约束

#### `M02`

- `baseSource = deng_zong`
- 默认 freshness = latest batch
- 默认按郑总同行镜头排序
- 自由筛选允许做二次收窄

这意味着：

- 方法卡仍然可以保留独立文案和解释
- 但逻辑上它不是一条“旁路接口”
- 它只是 `FilterIntent + Lens` 编译成查询计划

---

## L4：QueryPlan Layer（查询计划层）

这是逻辑清晰的关键层。

`FilterIntent + Lens + SourceCapability` 最终编译为 `QueryPlan`：

```ts
interface SelectionQueryPlan {
  targetSource: "competitor_clean" | "competitor_raw" | "deng_zong";
  lensId: "default" | "M01" | "M02";
  normalizedFilters: Record<string, any>;
  unsupportedFilters: string[];
  forcedFilters: string[];
  sortPlan: {
    field: string;
    order: "asc" | "desc";
  };
}
```

这个层干的事是：

1. 决定当前查哪个来源
2. 把统一业务语义翻译成具体来源语义
3. 记录哪些筛选项：
   - 被支持
   - 被忽略
   - 被方法卡强制覆盖

这一步最重要，因为它解决了“页面一样，但不同来源字段口径不一样”的问题。

---

## L5：Source Executor Layer（数据源执行层）

最后一层才是具体请求。

建议统一成 3 个执行器：

1. `CompetitorCleanExecutor`
2. `CompetitorRawExecutor`
3. `DengZongExecutor`

如果暂时不改后端大接口，前端也可以先这样落：

- `CompetitorCleanExecutor -> /api/v1/competitor/products + useCleanTable=true`
- `CompetitorRawExecutor -> /api/v1/competitor/products + useCleanTable=false`
- `DengZongExecutor -> /api/v1/deng-zong-shop/products`

方法卡不单独作为执行器，而是走：

- `M01 -> LensCompiler -> CompetitorCleanExecutor`
- `M02 -> LensCompiler -> DengZongExecutor`

---

## 3. 数据库来源切换应该怎么统一

这里建议你明确区分：

## 3.1 “来源 source” 不是“数据库来源”

当前代码里有两个容易混的概念：

1. 业务来源 `source`
   - 新品榜
   - 竞品店铺
   - 郑总店铺

2. 数据库来源 `data source`
   - `competitor_products`
   - `competitor_products_clean`
   - `deng_zong_shop`

这两个不应该混在一个字段里。

建议统一命名：

```ts
scene/source business
dataView/dataSource storage
```

也就是：

- `scene = new/reference/zheng/all`
- `dataSource = competitor_clean / competitor_raw / deng_zong`

---

## 3.2 推荐的数据源统一模型

```ts
interface SourceCapability {
  source: "competitor_clean" | "competitor_raw" | "deng_zong";
  dedupUnit: "parent_group" | "raw_row";
  freshnessField: "effectiveWeekTag" | "createdWeek" | "batchDate";
  variantMetric: "variantCount";
  supports: {
    grade: boolean;
    fulfillment: boolean;
    listingDays: boolean;
    weightG: boolean;
    snapshotFilter: boolean;
    methodOverlay: boolean;
  };
}
```

### 建议的真实来源定义

#### `competitor_clean`

- 面向日常选品主视图
- 去变体污染后的代表行
- 以父群组为主视图单位
- 适合普通筛选、方法卡、排序、评分

#### `competitor_raw`

- 面向排查、校验、看原始变体
- 不作为默认业务视图
- 主要用于详情、变体验证、调试

#### `deng_zong`

- 面向郑总同行
- 自己有 `batchDate`
- 不是 competitor 的简单 source 变体
- 必须单独看作来源执行器

---

## 4. 方法卡链路应该怎么统一

当前方法卡最大的问题不是“有独立接口”，而是它们被放成了普通筛选系统外的一条旁路。

更合理的统一方式是：

## 4.1 方法卡 = Lens，不是页面特判

方法卡只定义三件事：

1. 基础来源是什么
2. 默认约束是什么
3. 哪些自由筛选允许继续叠加

### M01

- 基础来源：`competitor_clean`
- 固定镜头：新品榜方法
- 默认新鲜度：最新 `effective_week_tag`
- 允许叠加：
  - 大类
  - 卖家
  - 价格收窄
  - 批次手动改
  - 变体数
  - 配送方式
- 不建议允许覆盖：
  - 方法核心销量/账龄规则

### M02

- 基础来源：`deng_zong`
- 固定镜头：最新郑总同行批次
- 允许叠加：
  - 大类
  - 卖家
  - 标题
  - 价格
  - 批次切换
  - 变体数

## 4.2 方法卡接口的目标形态

推荐长期目标是后端统一成：

```http
POST /api/v1/selection-query
{
  "scene": "all",
  "methodId": "M01",
  "filters": {...},
  "dataView": "clean"
}
```

由后端：

1. 先根据 `methodId` 找到 lens definition
2. 再编译成具体 source query
3. 最后交给对应 executor

这样方法卡的独立接口可以逐渐退化成兼容封装层，而不是主链路。

---

## 5. 当前所有自由筛选，应该怎么统一成一张能力表

建议把自由筛选统一分成 7 组业务语义，而不是按页面控件分：

## A. 搜索类

- ASIN
- 标题
- 卖家名
- 大类

## B. 作用域类

- 站点 marketplace
- scene（新品/竞品/郑总/全部）
- source（新品榜/竞品店铺等业务来源）

## C. 新鲜度类

- 批次/周次
- 是否最新
- 手动指定快照

## D. 数值区间类

- 价格
- 月销
- 上架天数
- BSR
- 重量
- 评分

## E. 结构类

- 变体数
- 配送方式

## F. 质量类

- 等级
- 方法命中

## G. 排序类

- 排序字段
- 排序方向

然后为每个来源定义一张能力矩阵：

| 语义 | competitor_clean | competitor_raw | deng_zong | M01 | M02 |
|---|---|---|---|---|---|
| marketplace | 支持 | 支持 | 支持 | 支持 | 支持 |
| sellerName | 支持 | 支持 | 支持 | 支持 | 支持 |
| category | 支持 | 支持 | 支持 | 支持 | 支持 |
| snapshot | 支持 | 支持 | 支持 | 支持 | 支持 |
| grade | 支持 | 支持 | 当前无统一语义 | 支持 | 当前建议关闭 |
| listingDays | 支持 | 支持 | 当前无真实字段 | 方法内固定 + 只允许收窄 | 不支持 |
| weightG | 支持 | 支持 | 当前字段不统一 | 支持 | 当前需映射后再开放 |
| variantCount | 支持 | 支持 | 支持 | 支持 | 支持 |

这里的重点不是“所有格子都必须支持”，而是：

- **每个格子都必须有明确答案**
  - 支持
  - 不支持
  - 需转换
  - 被镜头锁定

---

## 6. 批次 / 快照应该怎样统一

这是现在最容易混乱的地方，建议你统一成“快照维度”。

不要再让前端同时理解：

- `createdWeeks`
- `createdWeek`
- `effective_week_tag`
- `batchDate`
- `month`
- `weekTag`

建议统一成：

```ts
interface SnapshotSelector {
  type: "effectiveWeek" | "createdWeek" | "batchDate";
  values: string[];
  mode: "latest" | "manual";
}
```

然后由编译层做映射：

- `competitor_clean`：
  - 首选 `effectiveWeekTag`
- `competitor_raw`：
  - 用 `createdWeek`
- `deng_zong`：
  - 用 `batchDate`
- `M01`：
  - 默认 latest `effectiveWeekTag`
- `M02`：
  - 默认 latest `batchDate`

这样前端自由筛选只有一个“批次/快照”概念，不再自己知道底表字段名。

---

## 7. 变体数应该怎样统一

建议统一业务语义：

> 变体数 = 当前结果行所属父群组的真实变体总数

不再允许：

- 某些地方用 `variations`
- 某些地方用 `variantCount`
- 某些地方用“代表行字段”

建议统一成后端输出字段：

```ts
variantCount
```

并要求所有来源执行器都保证：

1. 返回结果时一定有 `variantCount`
2. 筛选时也按同一个语义筛

也就是：

- 过滤条件和展示字段必须同名、同义

这个点非常重要，因为它会直接决定系统是否“用户可理解”。

---

## 8. 前端应该怎样分层，但不改页面

推荐保留现有页面模板，只改逻辑组织：

## 8.1 页面层

`AllSelection/index.vue`

只保留：

- UI 展示
- 事件转发
- 列表渲染

## 8.2 统一筛选状态层

新增 composable，例如：

```ts
useSelectionFilterState()
```

负责：

- 管 `SelectionQueryForm`
- 管主栏
- 管抽屉
- 管预设回放
- 合并成单一 `filterIntent`

## 8.3 查询编译层

新增 composable / service，例如：

```ts
buildSelectionQueryPlan(intent, lens, sourceCaps)
```

负责：

- 合并方法卡
- 解析来源
- 生成 query plan

## 8.4 执行层

```ts
executeSelectionQuery(plan)
```

内部再分：

- `executeCompetitorCleanQuery`
- `executeCompetitorRawQuery`
- `executeDengZongQuery`

这样页面完全不用知道：

- 现在是不是 clean 表
- 现在是不是方法卡
- 现在是不是郑总链路

页面只知道：

- 当前有一个 `queryPlan`
- 执行完返回统一 list

---

## 9. 后端应该怎样分层

后端建议也不要再继续把逻辑散在 controller 分支里。

推荐目标分层：

## 9.1 Controller 层

提供统一入口：

```http
POST /api/v1/selection-query
```

## 9.2 Query Compiler 层

例如：

```java
SelectionQueryCompiler
```

职责：

- 接收前端统一请求
- 合并 method lens
- 决定 target source
- 生成 source query

## 9.3 Source Executor 层

- `CompetitorCleanQueryExecutor`
- `CompetitorRawQueryExecutor`
- `DengZongQueryExecutor`

## 9.4 Method Lens Registry

```java
MethodLensRegistry
```

职责：

- 保存 M01/M02/M03... 的定义
- 返回默认约束、锁定字段、解释信息

这样以后新增方法卡时：

- 不改页面主链
- 不改 controller if/else
- 只新增 lens definition

---

## 10. 推荐落地顺序

为了不把当前功能链路一次打散，建议分 3 期做。

## 第一期：只统一前端逻辑层，不改后端接口

目标：

- 页面不变
- 统一 `FilterIntent`
- 统一 `QueryPlan`
- 保留现有 3 个执行器：
  - competitor products
  - deng_zong_shop
  - method-cards

这是最稳的第一步。

## 第二期：方法卡改成 Lens + Adapter

目标：

- 方法卡不再在页面里特判接口分支
- 页面只传 `methodId`
- 查询编译层决定是不是走 `method-cards`

## 第三期：后端统一成单一 selection-query

目标：

- 所有查询入口统一走一个后端入口
- `method-cards` / `deng-zong-shop` 作为底层执行器存在
- 前端不再知道底层表结构细节

---

## 11. 最终建议

如果你要的是“逻辑清晰，结构分层”，最重要的不是先改某个字段，而是先统一下面这条主链：

```text
页面多个控件
  -> 单一 FilterIntent
  -> Lens(method/default)
  -> QueryPlan
  -> Source Executor
  -> 统一结果模型
```

这个链一旦立住：

- 数据库来源切换就清楚了
- 方法卡链路就清楚了
- 所有自由筛选就不会再是“每条分支自己拼一点”

一句话总结：

> **前端保留现在的页面，逻辑上把“筛选”从控件拼接改成“意图编译”；后端把“方法卡”从特判接口改成“镜头定义 + 数据源执行器”。**
