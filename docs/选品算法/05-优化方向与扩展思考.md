## 二、缺失的信号维度

以下是当前设计未覆盖、但对选品决策有实质影响的方向。

### 2.1 卖家行为画像（Seller Behavior Modeling）

> **⚠️ 已升级为独立文档**：[10-卖家行为画像.md](./10-卖家行为画像.md)
>
> 聪明卖家综合评分、品类跟品节奏、产品级跟品追踪。以下内容为初始思考，以10文档为准。

**当前问题**：算法只看"商品好不好"，不看"谁在卖、卖得怎么样"。

邓总29家店铺的 `seller_name` 字段天然支持跨店铺分析，但当前设计完全没用这个维度。

**可挖掘的信号**：

| 信号 | 数据来源 | 选品价值 |
|------|---------|---------|
| 邓总跟品节奏 | A店先上→B/C/D店跟上，时间差分析 | 验证品类的"可复制性" |
| 聪明卖家识别 | 哪些卖家选的品后来BSR涨得好 | 学习优秀选品眼光 |
| 新品同步率 | 多个邓总店铺同时上同一品类 | 赛道热度验证（开品模型"紧急信号"） |
| 邓总 vs 非邓总 | 同品类中邓总卖家与外部卖家的表现差异 | 判断是"品好"还是"人好" |

**与现有系统的关系**：
- `competitor_products.seller_name` 已有数据
- 竞品格局分析工具（03文档）可扩展为"卖家维度聚合"
- SQL按seller_name分组即可，无需额外数据源

**思考**：从"这个品好不好"升级到"聪明人在做什么"。

### 2.2 多站点交叉发现（Cross-Marketplace Arbitrage）

> **⚠️ 已升级为独立文档**：[13-跨站点套利发现.md](./13-跨站点套利发现.md)
>
> 3层套利发现（品类级/产品级/利润级）+ 窗口期判断 + 跨站综合评分。以下内容为初始思考，以13文档为准。

**当前问题**：算法以 `marketplace` 为独立维度分析，UK和DE是隔离的。

邓总有多家店铺同时做UK+DE（SDGHJZ、ZUOQUANGUIDIANPU、xinchenliang等），同一ASIN可出现在两个站点。

**可挖掘的信号**：

| 信号 | 判断逻辑 | 选品价值 |
|------|---------|---------|
| UK有DE无 | UK卖得好但DE无同款 | DE市场的套利窗口 |
| DE有UK无 | DE已有但UK空白 | UK抢先布局机会 |
| 价差分析 | 同ASIN在UK/DE的利润率差异 | 选择利润更高的站点 |
| 成熟度对比 | 同品类在两个站点的BSR/新品占比差异 | 判断市场发展阶段 |

**与现有系统的关系**：
- `competitor_products.marketplace` 已有UK/DE两种数据
- 蓝海信号发现工具（03文档）可扩展为跨站点蓝海对比
- 需要新增SQL：按ASIN跨站点JOIN查询

**思考**：从"单站点选品"升级到"跨站点套利发现"。

### 2.3 新品爆发信号（Early Explosion Detection）

> **⚠️ 已升级为独立文档**：[12-新品爆发信号检测.md](./12-新品爆发信号检测.md)
>
> 4类信号（速度/密度/跟品/质量）× 3级紧急度。以下内容为初始思考，以12文档为准。

**当前问题**：趋势分析依赖"跨月数据"，但最有价值的信号是**月内变化**。

邓总开品模型原文定义了三级信号体系（紧急/重要/一般），但当前三层架构完全没有覆盖"实时信号"这个维度。

**邓总原文的三级信号体系**：

| 级别 | 信号 | 当前设计是否覆盖 |
|------|------|---------------|
| 🔴 紧急 | 郑总+3个竞品同时上同一类产品 | **未覆盖** |
| 🟡 重要 | BSR新品榜出现多个同类产品 | **未覆盖** |
| 🟢 一般 | 单个竞品上了新品 | **部分覆盖**（listing_days≤90筛选） |

**可挖掘的信号**：

| 信号 | 判断逻辑 | 选品价值 |
|------|---------|---------|
| 多店同步上新 | 同一品类30天内≥3个邓总店铺上新品 | 紧急信号，当天决策 |
| BSR骤降 | 新品7天内BSR从10万降到1万 | 爆发信号 |
| 品类热度突增 | 某品类近30天新品数是上月的3倍 | 赛道爆发 |
| 新品评论增速 | 30天内评论增长>50 | 自然流量验证 |

**与现有系统的关系**：
- `competitor_products.listing_days` 已有（由available_date计算）
- `competitor_products.bsr` 跨月数据已有
- 需要新增"月内快照"能力（每周或每日数据导入时保留增量变化）
- 可作为第3层Agent分析的新工具：`detect_explosion_signals`

**思考**：选品的核心竞争力是"比别人早"。当前设计解决的是"好不好"，没解决"快不快"。

### 2.4 标题/关键词智能（Title Intelligence）

**当前问题**：软维度分析只依赖图片（CLIP向量），完全没用 `title` 字段。

标题包含大量选品信号，且NLP处理成本极低（不需要视觉模型调用）。

**可挖掘的信号**：

| 信号 | 标题特征 | 选品价值 |
|------|---------|---------|
| 情绪价值佐证 | "Motivational"、"Inspirational"、"Funny"、"Memorial" | 文本维度验证情绪评分 |
| 场景识别 | "Birthday"、"Christmas"、"Wedding"、"Graduation" | 季节性/场景标签自动提取 |
| 裂变线索 | "Pack of 6"、"Set of 3"、"Bundle" | 已有变体策略 |
| 目标人群 | "Mom"、"Dad"、"Teacher"、"Pet Owner" | 身份认同场景识别 |
| 品类成熟度 | 标题高度模板化（同类标题相似度>80%） | 品类已固化，进入难 |
| 差异化空间 | 标题多样性高（同类标题相似度<50%） | 品类未固化，有差异化机会 |

**与现有系统的关系**：
- `competitor_products.title` 已有完整数据
- 可用简单的文本分析（关键词匹配、TF-IDF）提取信号，无需LLM
- 高级用法：标题文本embedding → 补充CLIP图片embedding → 多模态向量传播

**思考**：标题是"免费的信号源"，不用白不用。

### 2.5 利润精度模型（Profit Accuracy Enhancement）

> **⚠️ 已升级**：精确利润计算算法已纳入 [08-品类专属评分模型.md §10.2](./08-品类专属评分模型.md)
>
> 4输入精确计算（重量/长宽高/价格/FBA配送费），参考`利润计算器_最终版.py`。以下内容为初始思考。

**当前问题**：利润维度直接用 `profit` 字段（卖家精灵估算），精度不可控。

利润是权重最高的维度（8维评分中20% + 5维决策中30%），但依赖第三方估算值。邓总开品模型有完整的成本拆解：

```
售价 → 佣金15% → FBA配送费（查表） → 头程运费 → 采购成本 → 广告10-15% → 退货2-3% → 净利润
```

**精度提升路径**：

| 成本项 | 当前处理 | 可改进方式 |
|--------|---------|-----------|
| 佣金 | 粗估 | 按品类精确（大多数15%，部分8%） |
| FBA配送费 | 用 `fba` 字段 | 系统已有FBA速查表数据，可自行计算验证 |
| 头程运费 | 未算 | 按重量区间估算（空运¥30-40/kg，海运¥8-12/kg） |
| 采购成本 | 未算 | 需外部数据（1688），短期无法自动化 |
| 广告费 | 粗估 | 按品类均值估算（售价10-15%） |
| 退货损耗 | 未算 | 按品类均值估算（售价2-3%） |

**与现有系统的关系**：
- 开品模型附录C有完整的FBA配送费速查表（UK/DE）
- `competitor_products.weight_g` + `fba` + `price` 已有基础数据
- 可新增 `calc_real_profit()` 函数，输出更精确的利润率

**思考**：利润精度提升10%，决策质量可能提升30%（因为利润权重最高）。

### 2.6 决策反馈闭环（Decision Feedback Loop） → [已实现：14文档](./14-决策反馈闭环.md)

> **已确认方案**：竞品验证为主 + 3个月窗口 + 算法建议人工审批 + S1/S2记录范围
>
> 完整设计详见 [14-决策反馈闭环.md](./14-决策反馈闭环.md)（三件套：决策记录表 + 验证流程 + 权重校准规则）

**当前问题**：算法是单向流（评分→决策→结束），没有学习机制。

选品是一个需要持续校准的系统：
- 8维权重（15%/20%/10%...）是否合理？——需要实际结果验证
- 标记为LAUNCH的产品，后来卖得好不好？
- 标记为ABANDON的产品，后来是不是爆了？（漏网之鱼分析）

**反馈闭环设计**：

```
选品决策
    │
    ▼ 3-6个月后
实际结果验证
    │
    ├─→ LAUNCH的产品：BSR表现好？利润达标？
    │   ├─ 表现好 → 强化当前权重
    │   └─ 表现差 → 分析原因，调整权重
    │
    └─→ ABANDON的产品：后来BSR涨了？
        ├─ 没涨 → 放弃决策正确
        └─ 涨了 → 漏网之鱼，分析遗漏原因
```

**与现有系统的关系**：
- `competitor_products` 跨月数据天然支持"后来卖得好不好"的验证
- 需要新增"决策记录表"（哪个ASIN、什么时间、什么决策、实际结果）
- 权重调整可以是人工的（每月review），也可以未来用ML自动校准

**思考**：没有反馈闭环的系统，永远不会变好。这是长期竞争力的核心。

### 2.7 评论痛点挖掘（Review Pain Point Mining）

**当前问题**：`ratings` 字段只有评论数量，没有评论内容。

邓总开品模型明确提到"差评集中点 = 产品改进机会"。

**理想状态**：
- 同品类TOP10的差评关键词 → 差异化方向
- "too small" → 我们的版本做大一号
- "broke quickly" → 我们用更好的材质
- "not as pictured" → 我们的主图更真实

**现实约束**：
- 卖家精灵API不提供评论文本数据
- 需要额外的数据源（Amazon评论抓取、第三方工具）
- 作为**可选增强**，不影响核心流程

**思考**：从"能不能做"升级到"怎么做得更好"。数据源解决后再做。

### 2.8 品类关联与替代效应（Category Correlation）

**当前问题**：蓝海分析是品类独立的，品类之间的关联未被利用。

**品类间的关系类型**：

| 关系 | 示例 | 选品价值 |
|------|------|---------|
| 替代关系 | Wall Art ↔ Wall Sticker（消费者二选一） | 两个品类总量有限，选其一 |
| 互补关系 | Card + Mug（礼品组合） | 礼品季两个品类同步涨 |
| 场景关联 | Storage + Vase & Plant（家居装饰组合） | 家居换新季联动 |
| 上下游 | Fidget Toy → Toy Storage（买了玩具需要收纳） | 衍生需求 |

**与现有系统的关系**：
- `competitor_products.node_label_path` 有品类层级
- 跨月数据可计算品类间的"销量联动系数"
- 蓝海信号发现工具可扩展为"关联蓝海"发现

**思考**：品类不是孤岛。发现联动关系 = 提前预判需求变化。

### 2.9 价格带微观分析（Price Band Micro-Analysis）

**当前问题**：只做了"€5.99-€16.99"的区间筛选，没有深入分析价格带内的微观结构。

**可挖掘的信号**：

| 信号 | 分析方式 | 选品价值 |
|------|---------|---------|
| 价格甜蜜点 | 同品类不同价格带的销量/利润分布 | 找到最优定价区间 |
| 价格空白 | 品类内"无人区"价格段 | 差异化定价机会 |
| 价格敏感度 | 价格变动1%对销量的影响 | 判断品类是否价格驱动 |
| 价格天花板 | 品类内最高售价的销量表现 | 判断溢价空间 |

**与现有系统的关系**：
- `competitor_products.price` + `units` + `profit` 已有完整数据
- 竞品格局分析工具（03文档）可扩展价格分布分析
- SQL聚合即可，无需额外数据

**思考**：从"选什么品"升级到"定什么价"。

### 2.10 供应链难度评估（Supply Chain Difficulty）

**当前问题**：算法完全基于需求端（市场数据），没有供给端信息。

一个商品市场需求再好，如果找不到供应商或MOQ太高，也无法开品。

**理想状态**：

| 供给端指标 | 来源 | 选品价值 |
|-----------|------|---------|
| 1688供应商数量 | 1688搜索API | 供应商多=议价空间大 |
| 最低起订量(MOQ) | 1688 | MOQ低=试错成本低 |
| 生产周期 | 1688 | 周期短=上架快 |
| 是否需定制模具 | 1688 | 需要模具=初始投入大 |

**现实约束**：
- 当前系统没有1688数据接入
- 短期可通过人工标注补充（对S1级商品手动查1688）
- 长期可接入1688搜索API自动化

**思考**：需求端高分 + 供给端容易 = 真正的LAUNCH决策。

## 三、"分散"方向的思考

当前架构是**中心化**的：所有数据 → 三层决策 → 一个分数。以下角度值得思考是否需要"分散"。

### 3.1 管道化（Pipeline-based Selection）

**含义**：不同人用不同选品策略，而不是统一一套评分权重。

系统已有 `AI 选品 Agent — 实施方案.md` 设计了完整的Pipeline执行器：
- 用户通过对话构建个人选品管道
- 管道持久化，可重跑、可分享
- 每个人可以有自己的筛选-评分-决策方法

**当前状态**：设计完成，未实现。

**价值**：
- 邓总的选品方法 ≠ 所有人的选品方法
- 管道库允许"邓总选品法"、"BSR追踪法"、"蓝海发现法"并存
- 不同管道产出对比，找到最优方法

**与当前设计的关系**：
- 01-04文档定义的是"邓总选品法"的**一个具体管道**
- 未来可以泛化为可配置的管道框架

---

### 3.2 品类专属模型（Category-specific Models）

**含义**：不同品类用不同的评分权重，而不是统一8维权重。

**为什么需要**：

| 品类 | 核心权重维度 | 邓总数据证据 |
|------|------------|-------------|
| Wall Art | 装饰价值(高) + 裂变能力(高) | 997条，裂变极强 |
| Storage | 体积成本(高) + 轻小件(高) | 689条，物流敏感 |
| Fidget Toy | 情绪价值(高) + 裂变能力(中) | 160条，解压场景 |
| Card | 情绪价值(极高) + 文化匹配(高) | 352条，场景驱动 |
| Mug | 裂变能力(高) + 利润(高) | 292条，图案驱动 |

统一的15%/20%/10%权重对所有品类一视同仁，但不同品类的成功因子完全不同。

**实现思路**：
- Phase 1：统一权重（当前设计）
- Phase 2：按TOP5品类各设一套权重
- Phase 3：反馈闭环自动学习品类最优权重

---

### 3.3 信号源分散（Multi-source Signals）

**含义**：除卖家精灵外，接入更多数据源。

| 数据源 | 补充信号 | 优先级 |
|--------|---------|-------|
| Google Trends | 搜索量趋势、季节性验证 | 高（免费API） |
| 1688 | 供应端难度、采购成本 | 中（需接入） |
| 社交媒体（Pinterest/TikTok） | 趋势先行信号 | 低（成本高） |
| Amazon评论 | 差评痛点、差异化方向 | 中（需接入） |
| Keepa | 历史价格/BSR曲线 | 低（付费） |

**当前设计的扩展性**：
- `competitor_products` 是核心表，外部数据可以通过新增字段或关联表接入
- Agent分析工具（03文档）天然支持多数据源聚合
- 但需要避免"数据源越多越准"的陷阱——先把现有数据用好

---

### 3.4 决策分散（Multi-dimensional Decision）

**含义**：不追求统一分数，而是给出多维度雷达图让人决策。

**当前设计**：8维 → 加权求和 → 一个分数 → 一个等级。

**分散后**：
- 保留8维分数，但不强制加权为一个分数
- 前端展示为**雷达图**（8个维度的可视化）
- 让人看到"利润高但竞争也激烈"的全貌，自己判断
- AI给建议，但不替人决策

**适用场景**：
- 对S1/S2级商品（已有深度分析），雷达图+AI建议已足够
- 对S3级商品（数据不够深），统一分数更方便快速筛选

**思考**：机器给分 vs 人做决策，找到平衡点。

## 四、优化方向优先级矩阵

按"价值 × 可行性"排序：

| 优先级 | 方向 | 价值 | 数据就绪 | 改动量 | 建议时机 |
|-------|------|------|---------|-------|---------|
| ⭐⭐⭐ | 新品爆发信号(2.3) | 极高 | 部分（需增量快照） | 中 | Phase 3后 |
| ⭐⭐⭐ | 决策反馈闭环(2.6) | 极高 | 有（跨月数据） | 小 | Phase 4同步 |
