## 🔴 阻断级问题

### P1：weight 解析不支持德语 "Gramm"

**发现来源**：实施级自检，对照真实 JSON 数据

**问题描述**：

`CompetitorFilterService.extractWeightGrams()` 的正则：

```java
Pattern.compile("(\\d+\\.?\\d*)\\s*(g|kg|pounds|ounces)")
```

但 DE 站真实数据格式是 `"180 Gramm"`、`"510 Gramm"`。"Gramm" 不在匹配组里，直接返回 `null`。

**真实数据验证**：

```
DE_SDGHJZ.json:  "weight": "510 Gramm"  → null（漏解析）
DE_SDGHJZ.json:  "weight": "25 g"       → 25（正常）
DE_SDGHJZ.json:  "weight": null         → null（真的没有）
UK_BENHUANZPZ.json: "weight": "50 g"    → 50（正常）
DE_xinchenliang.json: "weight": "1.12 kg" → 1120（正常）
```

**影响范围**：6991 条数据中 1013 条 weight=null（14.5%），其中大量是 "Gramm" 被漏解析。

**影响模块**：
- L1 硬筛选：重量阈值判断失效（null 重量产品可能通过筛选）
- L2 评分：轻小件指数（15%权重）无法计算
- 利润计算：体积重量需要真实重量做 max() 比较

**解决思路**：

1. 正则扩展支持所有已知单位：
```java
Pattern.compile("(\\d+\\.?\\d*)\\s*(g|gramm|gram|kg|kilogramm|kilogram|pounds|pound|lb|ounces|ounce|oz)")
```
2. 单位归一化：gramm/gram → g, kilogramm/kilogram → kg, pound/lb → pounds, ounce/oz → ounces
3. 对已入库的 1013 条 weight=null 数据**补跑解析**（脚本）
4. 加日志：解析失败时记录原始 weight 字符串，便于发现新格式

**实施优先级**：Phase 1 第一件事

### P2：品类原型映射只在文档里，没有系统路径

**发现来源**：08 文档 §2.3 定义了 52 个品类→6 个原型映射，但系统中无存储

**问题描述**：

L2 评分时需要知道每个产品属于哪个原型（DA/FH/FP/TN/PE/PS），以选择对应的权重矩阵。当前流程断裂点：

```
node_label_path = "Home:Wall Art:Canvas Print"
    → 取第2级 "Wall Art"                    ← 这一步怎么取？
    → 查映射表得到 "DA"                      ← 映射表在哪？
    → 使用 DA 专属权重评分                    ← 权重配置在哪？
```

三个断裂点：
1. **路径解析**：`node_label_path` 的分隔符是冒号还是其他？层级结构是否稳定？
2. **映射表存储**：52 条映射规则存在哪里？`api_config` 表？硬编码常量？独立配置表？
3. **权重配置存储**：6 套权重矩阵（每套 8 个值）存哪里？

**真实数据验证**：

08 文档 §2.3 列出 52 个品类，数据量从 1 条（Slime & Clay）到 941 条（Storage）。

**解决思路**：

1. **映射表存入 `api_config`**：
```
key: "category_prototype_mapping"
value: {
  "Wall Art": "DA", "Light": "DA", "Wall Sticker": "DA", ...
  "Storage": "FH", "Bathroom": "FH", ...
  "Fidget Toy": "TN", ...
}
```

2. **路径解析规则**：按冒号分割取 index=1（第 2 级），如果只有 1 级则用 index=0

3. **权重矩阵存入 `api_config`**（14 文档已定义 `selection_weights_basic`）：
```
key: "selection_weights_DA"
value: {"size":15,"volume":10,"profit":15,"emotion":10,"decor":20,"fission":20,"culture":5,"market":5}
```

4. **回退逻辑**：品类不在映射表中 → 使用 `selection_weights_basic`（BASIC 基础权重）

**实施优先级**：Phase 1 与 P1 同步

### P3：L2 评分的新增字段（10 个）DDL 缺失

**发现来源**：01 文档 §4.3 定义了 10 个新字段，但数据库和实体都没有

**问题描述**：

01 文档定义了以下字段需要写入 `competitor_products` 表：

| 字段 | 类型 | 说明 |
|------|------|------|
| `selection_score` | INT | 选品总分(0-100) |
| `selection_grade` | VARCHAR(2) | S1/S2/S3/X |
| `sel_size_score` | TINYINT | 轻小件指数 |
| `sel_volume_score` | TINYINT | 体积成本指数 |
| `sel_profit_score` | TINYINT | 利润指数 |
| `sel_emotion_score` | TINYINT | 情绪价值指数 |
| `sel_decor_score` | TINYINT | 装饰价值指数 |
| `sel_fission_score` | TINYINT | 裂变能力指数 |
| `sel_culture_score` | TINYINT | 文化匹配度 |
| `sel_market_score` | TINYINT | 市场容量指数 |

**当前状态**：CompetitorProduct 实体只有 `score`(INT) 和 `grade`(VARCHAR)，是旧的 4 维评分。

**解决思路**：

1. 编写 DDL 迁移脚本 `add_selection_score_fields.sql`
2. 在 CompetitorProduct 实体中添加对应 Java 字段
3. 在 CompetitorProductMapper 的 SELECT/UPDATE 语句中包含新字段
4. 旧字段 `score`/`grade` 保留不动（与选品评分并存，见06文档§九决策表）

**实施优先级**：Phase 1 基础设施

## 🟡 准确级问题

### P4：weight/dimension 缺失时的评分降级策略

**发现来源**：真实数据统计

**问题描述**：

| 字段 | 缺失量 | 占比 | 影响的评分维度 |
|------|--------|------|-------------|
| weight=null | 1013 条 | 14.5% | 轻小件指数(15%)、利润计算 |
| dimension=null | 482 条 | 6.9% | 体积成本指数(15%)、利润计算 |

08 文档提到"使用同品类中位数替代"，但**没有定义这个替代在代码中由谁执行、在什么时机执行**。

**解决思路**：

1. **导入时填充**：数据导入时，如果 weight 为 null，尝试从 `pkgWeight` 读取；如果 `pkgWeight` 也为 null，查找同品类（同 node_label_path 第 2 级）的 weight_g 中位数填充，并标记 `weight_source = 'estimated'`
2. **评分时兜底**：如果填充后仍为 null（该品类全部无重量数据），轻小件指数给**中位分**（如 10/15），并在评分报告中注明"重量缺失，使用默认分"
3. **前端标记**：对估算数据展示"⚠️估算"标签，让用户知道这不是原始数据

**代码归属**：
- 填充逻辑 → `CompetitorDataImportService`（导入时）
- 兜底评分 → L2 评分引擎（评分时）

**实施优先级**：Phase 1

### P5：1 个月验证窗口的数据间隔不稳定

**发现来源**：14 文档验证流程设计

**问题描述**：

竞品数据是卖家精灵月度导入，但**导入时间不固定**：

```
场景A: 1月数据 1/15导入 → 2月数据 2/10导入（间隔26天）→ 验证有效
场景B: 1月数据 1/30导入 → 2月数据 3/5导入（间隔34天）→ 验证有效
场景C: 1月数据 1/5导入  → 2月数据 2/28导入（间隔54天）→ 实际间隔过长
```

"decision_month + 1" 的 SQL 查询在场景 C 中，实际间隔了 54 天，产品变化可能已经不是"1 个月表现"了。

**解决思路**：

1. 在 `selection_decisions` 表新增 `decision_date` 字段（精确到日），记录实际决策执行日期
2. 验证时检查间隔：`DATEDIFF(verify_import_date, decision_date) >= 25 AND <= 45`
3. 间隔不在 25-45 天范围的记录，标记为 `VERIFY_SKIPPED`，等下个月再验证
4. 或者更简单：不检查间隔，只按 month 字段匹配（接受噪声，用样本量平滑）

**实施优先级**：Phase 5b（验证流程实施时）

### P6：同月多次导入的决策记录覆盖策略

**发现来源**：14 文档表设计

**问题描述**：

`selection_decisions` 唯一键 `(marketplace, asin, decision_month)`。如果同月数据被重新导入（修数据/补数据），L2 评分重跑后：

- 新分数覆盖了旧分数 → 决策记录应该也更新
- 但 `INSERT IGNORE` 会跳过已存在记录 → 保留的是旧分数

**解决思路**：

使用 `INSERT ... ON DUPLICATE KEY UPDATE`：

```sql
INSERT INTO selection_decisions (marketplace, asin, decision_month, ...)
VALUES (...)
ON DUPLICATE KEY UPDATE
    selection_score = VALUES(selection_score),
    selection_grade = VALUES(selection_grade),
    sel_size_score = VALUES(sel_size_score),
    ...
    baseline_bsr = VALUES(baseline_bsr),
    baseline_units = VALUES(baseline_units);
```

**注意**：如果该记录已经被验证（outcome IS NOT NULL），不应覆盖。加条件：

```sql
ON DUPLICATE KEY UPDATE
    selection_score = IF(outcome IS NULL, VALUES(selection_score), selection_score),
    ...
```

**实施优先级**：Phase 5a

### P7：品类原型映射中的边缘品类数据量不足

**发现来源**：08 文档 §2.3 映射表

**问题描述**：

08 文档映射了 52 个品类，但部分品类数据量极低：

| 品类 | 原型 | 数据量 | 问题 |
|------|------|--------|------|
| Slime & Clay | TN | 1 条 | 1 条数据无法计算百分位 |
| Coaster | PS | 9 条 | 百分位 TOP10% = 1 条 |
| Envelope | PS | 4 条 | 几乎无统计意义 |
| Car Freshener | FH | 8 条 | 百分位不稳定 |
| Charger | FH | 5 条 | 同上 |

**解决思路**：

1. **数据量 < 20 的品类**：不单独计算百分位基线，合并到上级 nodeLabelPath 第 1 级
2. **映射表标注**：在 `api_config` 的映射 JSON 中加入 `min_count` 字段
3. **运行时回退**：L2 评分时检查品类数据量，< 20 自动回退上级品类

**实施优先级**：Phase 1（百分位基线计算时）

## 🟢 细节级问题

### P8：product_analysis 表结构未定义

**发现来源**：01 文档 §3.3 + 04 文档都提到此表

**问题描述**：

多个文档提到"Agent 深度分析报告存入 `product_analysis` 表"，但 15 个文档中没有任何一个定义该表的字段结构。

**已知需求**（从 01/03/04 文档拼凑）：

- 存储每个 ASIN 的深度分析报告（JSON 格式）
- 包含竞品格局、趋势判断、蓝海匹配、决策建议
- 关联到 competitor_products（通过 marketplace + asin）
- 需要记录分析时间、使用的工具版本

**解决思路**：Phase 3 实施前补充表设计。核心字段：

```sql
CREATE TABLE product_analysis (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    marketplace VARCHAR(10) NOT NULL,
    asin VARCHAR(20) NOT NULL,
    analysis_month VARCHAR(7),
    report_json JSON,              -- 完整分析报告
    tools_version VARCHAR(20),     -- 分析工具版本
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_analysis (marketplace, asin, analysis_month)
);
```

**实施优先级**：Phase 3

### P9：L2 评分 → 决策记录写入的流水线时序

**发现来源**：06 文档工作流设计

**问题描述**：

如果 L2 评分是异步执行（Celery 任务或 Java 线程池），决策记录写入需要等 L2 **全部完成**后再触发。否则可能出现：

```
产品A: L2评分完成 → 写入决策记录（selection_score=82, S1）
产品B: L2评分还在排队...
产品C: L2评分完成 → 写入决策记录（selection_score=75, S2）
...（产品B还没评分，但决策记录批次已经结束了）
```

**解决思路**：

1. **批量完成后触发**：L2 评分使用计数器/回调机制，所有候选池产品评分完成后，统一触发决策记录写入
2. **或者：单产品级写入**：每个产品 L2 评分完成后立即写入自己的决策记录（用 ON DUPLICATE KEY UPDATE 防重）
3. **推荐方案 2**：单产品级写入更简单，不依赖批次完成信号

**实施优先级**：Phase 5a

---

### P10：百分位基线计算的最小品类样本量

**发现来源**：07 文档 §三

**问题描述**：

07 文档说"第 2 级品类 < 20 条时回退到第 1 级"。但 20 条数据算百分位：
- TOP 10% = 2 条
- TOP 25% = 5 条

统计意义极弱。如果这 2 条恰好是异常值，百分位基线会严重偏移。

**解决思路**：

1. 最小样本量从 20 提高到 **30**
2. 低于 30 的品类强制回退上级品类
3. 在基线计算日志中记录哪些品类触发了回退

**实施优先级**：Phase 1（百分位基线计算时）

---

### P11：1 个月窗口的噪声问题

**发现来源**：14 文档验证流程

**问题描述**：

1 个月窗口虽然提供快速反馈，但产品 1 个月的变化可能不大：
- BSR 变化 ±20% 可能只是正常波动
- 月销变化 ±15% 可能在误差范围内
- 大量产品会被判定为 STABLE → 验证结果缺乏区分度

**解决思路**：

1. **接受噪声，用样本量平滑**：单次验证噪声大，但累积 6 个月（~1500 条）后统计趋势可靠
2. **权重校准不依赖单次验证**：校准使用累计数据（所有历史验证），不依赖单月结果
3. **增加 EXCEEDED/DISAPPOINTED 的信号强度**：只在变化显著时标记（BSR 变化 > 30%，月销变化 > 25%），中间地带全部归 STABLE
4. **长期可考虑双窗口**：1 个月快速验证 + 6 个月深度验证（Phase 5c 后再加）

**实施优先级**：Phase 5b
