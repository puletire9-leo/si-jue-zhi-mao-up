# 决策反馈闭环 — 让算法越用越准

> 解决的问题：选品算法前向链路（数据→决策）完全自通，但缺少"决策→验证→校准"的回路。
> 没有反馈的系统永远不会进步。
>
> 前置依赖：[01-选品算法总体设计](./01-选品算法总体设计.md)（8维评分）、[04-决策模型](./04-决策模型与实施路线.md)（5维决策）
>
> 替代：[05-优化方向与扩展思考](./05-优化方向与扩展思考.md) §2.6（本文档是§2.6的完整实现设计）

| # | 决策项 | 已确认方案 |
|---|--------|----------|

## 三、① 决策记录表

### 3.1 表结构

```sql
CREATE TABLE selection_decisions (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    
    -- 产品标识
    marketplace VARCHAR(10) NOT NULL,           -- UK / DE / US
    asin VARCHAR(20) NOT NULL,                  -- 被评估的ASIN
    decision_month VARCHAR(7) NOT NULL,         -- 决策月份 "2026-01"
    
    -- 品类信息
    category_label VARCHAR(200),                -- 第2级品类名
    category_prototype VARCHAR(20),             -- 品类原型（DA/FH/FP/TN/PE/PS/BASIC）
    
    -- 评分快照（决策时刻的8维分数）
    selection_score INT,                        -- 选品总分 (0-100)
    selection_grade VARCHAR(2),                 -- S1 / S2
    sel_size_score TINYINT,                     -- 轻小件指数
    sel_volume_score TINYINT,                   -- 体积成本指数
    sel_profit_score TINYINT,                   -- 利润指数
    sel_emotion_score TINYINT,                  -- 情绪价值指数
    sel_decor_score TINYINT,                    -- 装饰价值指数
    sel_fission_score TINYINT,                  -- 裂变能力指数
    sel_culture_score TINYINT,                  -- 文化匹配度
    sel_market_score TINYINT,                   -- 市场容量指数
    
    -- 决策快照
    decision_score DECIMAL(3,1),                -- 5维决策评分 (0-10)
    decision_status VARCHAR(20),                -- LAUNCH / CONDITIONAL / WATCH
    signal_boosts JSON,                         -- 信号加成记录 {"explosion":"🔴","arbitrage":72}
    
    -- 决策时基线数据（用于下月对比）
    baseline_bsr INT,                           -- 决策时BSR
    baseline_units INT,                         -- 决策时月销量
    baseline_price DECIMAL(8,2),                -- 决策时售价
    baseline_ratings INT,                       -- 决策时评论数
    
    -- 验证结果（下月填充）
    verify_month VARCHAR(7),                    -- 验证月份 "2026-04"
    verify_bsr INT,                             -- 验证时BSR
    verify_units INT,                           -- 验证时月销量
    verify_price DECIMAL(8,2),                  -- 验证时售价
    verify_ratings INT,                         -- 验证时评论数
    
    -- 验证判定
    outcome VARCHAR(20),                        -- 见§四.3
    outcome_detail TEXT,                         -- 判定细节说明
    
    -- 元数据
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    verified_at DATETIME,
    verified_by VARCHAR(50),                    -- 'auto' 或 审核人
    
    UNIQUE KEY uk_decision (marketplace, asin, decision_month),
    INDEX idx_grade (selection_grade),
    INDEX idx_outcome (outcome),
    INDEX idx_verify_month (verify_month)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3.2 写入时机

```
L2评分完成（每月数据导入后）
    │
    ├─ 遍历所有 selection_grade IN ('S1', 'S2') 的产品
    │
    ├─ 对每个产品，写入 selection_decisions 表
    │   └─ 记录8维分数 + 决策状态 + 基线数据
    │
    └─ 如果 (marketplace, asin, decision_month) 已存在
        └─ 跳过（同月不重复记录）
```

### 3.3 每批数据量估算

| 参数 | 值 | 依据 |
|------|-----|------|
| 每月S1数量 | ~50条 | 04文档§一估算 |
| 每月S2数量 | ~200条 | 04文档§一估算 |
| 每月新增记录 | ~250条 | S1+S2 |
| 每年累计 | ~3000条 | 足够做统计分析 |
| 3年累计 | ~9000条 | 权重校准的长期数据池 |

## 四、② 验证流程

### 4.1 触发条件

```
每月数据导入完成后
    │
    ├─ 查询 selection_decisions 中 verify_month IS NULL 的记录
    │
    ├─ 筛选：decision_month = 上上个月
    │   例：当前导入 "2026-03"，验证 "2026-01" 的决策记录
    │
    └─ 逐条执行验证
```

### 4.2 验证数据获取

对每条决策记录，从 competitor_products 获取下个月的数据：

```sql
SELECT bsr, units, price, ratings
FROM competitor_products
WHERE marketplace = #{record.marketplace}
  AND asin = #{record.asin}
  AND month = #{record.decision_month + 1}  -- 下个月
```

**找不到数据的情况**：
- ASIN在下个月消失（下架/断货） → 标记为 `DATA_MISSING`，不计入统计
- ASIN仍在但数据不完整 → 用可获取的字段做部分验证

### 4.3 验证判定标准

核心问题：**"我们说这个产品好，它后来真的好了吗？"**

| outcome | 判定条件 | 含义 |
|---------|---------|------|
| **CONFIRMED** | BSR改善(baseline_bsr × 0.8以下) AND 月销增长(units增长≥10%) | ✅ 预测准确，好产品如预期 |
| **STABLE** | BSR稳定(baseline_bsr ± 30%) AND 月销持平(±15%) | ⚠️ 产品没爆发也没崩，预测基本对 |
| **EXCEEDED** | BSR大幅改善(× 0.6以下) AND 月销大涨(增长≥50%) | 🔥 超预期，可能权重低估了某些维度 |
| **DISAPPOINTED** | BSR恶化(× 1.5以上) OR 月销腰斩(下降≥50%) | ❌ 预测偏差，高估了这个产品 |
| **DATA_MISSING** | 下个月ASIN不存在 | ⚪ 无法验证，排除出统计 |

**判定逻辑（伪代码）**：

```python
def verify_decision(record, verify_data):
    if verify_data is None:
        return "DATA_MISSING"
    
    bsr_ratio = verify_data.bsr / record.baseline_bsr  # <1 表示BSR改善
    units_growth = (verify_data.units - record.baseline_units) / max(record.baseline_units, 1)
    
    # CONFIRMED: BSR改善 + 销量增长
    if bsr_ratio <= 0.8 and units_growth >= 0.10:
        return "CONFIRMED"
    
    # EXCEEDED: 大幅改善（1个月窗口，50%已非常显著）
    if bsr_ratio <= 0.6 and units_growth >= 0.5:
        return "EXCEEDED"
    
    # DISAPPOINTED: 恶化
    if bsr_ratio >= 1.5 or units_growth <= -0.5:
        return "DISAPPOINTED"
    
    # STABLE: 其他情况
    return "STABLE"
```

### 4.4 验证报告

每次验证批次完成后，生成汇总报告：

```json
{
    "batch_month": "2026-04",
    "verified_count": 248,
    "decision_months": ["2026-01"],
    "outcome_distribution": {
        "CONFIRMED": 89,       // 36%
        "EXCEEDED": 23,        // 9%
        "STABLE": 74,          // 30%
        "DISAPPOINTED": 47,    // 19%
        "DATA_MISSING": 15     // 6%
    },
    "accuracy_rate": 0.75,     // (CONFIRMED+EXCEEDED+STABLE) / total_verified
    "grade_breakdown": {
        "S1_accuracy": 0.82,   // S1级准确率
        "S2_accuracy": 0.71    // S2级准确率
    },
    "category_breakdown": {
        "Wall Art": {"accuracy": 0.78, "count": 45},
        "Card": {"accuracy": 0.81, "count": 32}
    },
    "dimension_analysis": { /* 见§五 */ },
    "recommendations": [ /* 见§五.3 */ ]
}
```

**准确率计算**：
- `accuracy_rate = (CONFIRMED + EXCEEDED + STABLE) / (total - DATA_MISSING)`
- S1准确率应高于S2（S1标准更严格）
- 如果S2准确率 < S1准确率：评分区分度好 ✅
- 如果S2准确率 > S1准确率：评分可能有问题 ⚠️

## 五、③ 权重校准规则

### 5.1 维度预测力分析

核心问题：**"8个维度中，哪个最能预测下个月的成功？"**

对每个维度，计算其**预测力系数**：

```
对于维度 D（如利润指数）：
    confirmed_avg_D = CONFIRMED+EXCEEDED 产品在该维度的平均得分
    disappointed_avg_D = DISAPPOINTED 产品在该维度的平均得分
    
    预测力系数 = confirmed_avg_D / max(disappointed_avg_D, 1)
    
    预测力 > 1.3 → 该维度是强预测因子（高分的确实表现好）
    预测力 < 0.8 → 该维度是反向信号（高分的反而表现差）
    预测力 0.8-1.3 → 该维度预测力一般
```

**最小样本量要求**：每个品类原型至少 30 条已验证记录才做分析，否则标注"数据不足，暂不建议调整"。

### 5.2 校准建议生成

```
当前权重: W_current = [w1, w2, ..., w8]  (总和=100%)
预测力系数: P = [p1, p2, ..., p8]

// 按预测力重新分配
raw_new_weights = [w1*p1, w2*p2, ..., w8*p8]
sum = Σ(raw_new_weights)
normalized = [w/sum * 100% for w in raw_new_weights]

// 调整幅度限制：单个维度变化不超过 ±5%
capped = [
    min(max(n, w - 5%), w + 5%)
    for n, w in zip(normalized, W_current)
]

// 重新归一化到100%
final = [c/sum(capped) * 100% for c in capped]

// 生成建议
对每个维度：
    如果 |final[i] - W_current[i]| >= 2%:
        输出建议: "{维度名} 从 {current}% 调整为 {final}%"
        原因: "预测力系数 {P[i]:.2f}，验证 {confirmed}条准确/{disappointed}条偏差"
```

### 5.3 校准建议报告格式

```
┌─────────────────────────────────────────────────┐
│  2026 Q2 权重校准建议（基于2026-01月决策验证）  │
├─────────────────────────────────────────────────┤
│  验证样本：248条（CONFIRMED 89 / EXCEEDED 23    │
│            / STABLE 74 / DISAPPOINTED 47）       │
│  总准确率：75%（S1: 82%, S2: 71%）              │
├─────────────────────────────────────────────────┤
│  维度        当前权重  建议权重  预测力  动作    │
│  ────────────────────────────────────────────    │
│  轻小件       15%      15%     1.05    保持     │
│  体积成本     15%      13%     0.85    ↓ 2%    │
│  利润         20%      23%     1.42    ↑ 3%    │
│  情绪价值     15%      15%     1.10    保持     │
│  装饰价值     10%      10%     1.02    保持     │
│  裂变能力     10%      12%     1.35    ↑ 2%    │
│  文化匹配      5%       5%     0.95    保持     │
│  市场容量     10%       7%     0.78    ↓ 3%    │
├─────────────────────────────────────────────────┤
│  ⚠️ 以上为算法建议，需人工审批后执行             │
│  调整幅度已限制在±5%以内，防止过拟合             │
└─────────────────────────────────────────────────┘
```

### 5.4 品类级校准

除了全局权重校准，还可以做品类级发现：

```
对每个品类原型（DA/FH/FP/TN/PE/PS）：
    统计该品类的 CONFIRMED vs DISAPPOINTED 分布
    
    如果某品类准确率 < 60%:
        建议: "{品类} 准确率偏低({rate}%)，建议Review该品类的专属权重(08文档)"
    
    如果某品类准确率 > 85%:
        标记: "{品类} 模型拟合度高，权重无需调整"
```

### 5.5 漏网之鱼检测

虽然只记录S1/S2，但可以额外检测"被忽略的好品"：

```sql
-- 查找决策月为S3或X级，但下个月后BSR大幅改善的产品
SELECT cp1.asin, cp1.bsr AS decision_bsr, cp2.bsr AS verify_bsr,
       cp1.selection_grade
FROM competitor_products cp1
JOIN competitor_products cp2
  ON cp1.marketplace = cp2.marketplace
  AND cp1.asin = cp2.asin
  AND cp2.month = DATE_ADD(cp1.month, INTERVAL 3 MONTH)
WHERE cp1.month = #{decision_month}
  AND cp1.selection_grade IN ('S3', 'X')
  AND cp2.bsr < cp1.bsr * 0.3   -- BSR改善70%以上
  AND cp2.units > cp1.units * 2  -- 月销翻倍以上
ORDER BY (cp1.bsr / NULLIF(cp2.bsr, 0)) DESC
LIMIT 20;
```

如果漏网之鱼数量较多（>候选池的5%），说明评分模型有系统性偏差，需要Review评分标准。

### 6.2 新增模块

| 模块 | 职责 | 对应文档 |
|------|------|---------|
| `SelectionDecisionService` | 决策记录写入 | 本文档§三 |
| `SelectionFeedbackService` | 验证流程 + 校准报告 | 本文档§四+§五 |
| `selection_decisions` 表 | 决策记录存储 | 本文档§三.1 |

### 6.3 权重更新路径

```
校准报告生成
    │
    ▼ 人工审批（Dashboard弹窗 / 邮件通知）
    │
    ├─ 审批通过
    │   └─ 更新 api_config 表中的权重配置
    │       → key: "selection_weights_{prototype}"
    │       → value: JSON {"size":15, "volume":13, ...}
    │       → L2评分自动使用新权重
    │
    ├─ 审批拒绝
    │   └─ 记录拒绝原因，保持当前权重
    │
    └─ 审批搁置
        └─ 下季度再Review
```

## 七、实施路线

### Phase 5a：决策记录（与Phase 1同步）

| 任务 | 改动 | 产出 |
|------|------|------|
| 创建selection_decisions表 | SQL迁移 | DDL |
| L2评分后自动写入S1/S2记录 | Java Service | 决策记录写入 |
| 基线数据快照采集 | Java Service | BSR/销量/价格/评论 |

> 与Phase 1同步实施，零额外依赖。只要L2评分在跑，决策记录就在积累。

### Phase 5b：验证流程（次月启动）

| 任务 | 改动 | 产出 |
|------|------|------|
| 实现下月自动验证 | Celery定时任务 | verify_pending() |
| 验证判定逻辑 | Python | CONFIRMED/EXCEEDED/STABLE/DISAPPOINTED |
| 验证报告生成 | Python + LLM | 批次报告JSON |

> 第一次验证在系统上线次月数据导入后自动触发（1个月窗口，快速反馈）。

### Phase 5c：权重校准（6个月后启动）

| 任务 | 改动 | 产出 |
|------|------|------|
| 维度预测力分析 | Python | 8个维度的预测力系数 |
| 校准建议生成 | Python | 权重调整建议 |
| 人工审批界面 | 前端 | 审批弹窗 + 确认/拒绝 |
| 权重配置更新 | Java | api_config表更新 |

> 需要至少6个月的验证数据（~1500条记录）才做首次校准。
