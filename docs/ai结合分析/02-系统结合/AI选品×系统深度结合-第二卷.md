## 一、完整工作流闭环

### 1.1 当前系统的"断路"

系统当前的数据流是**单向**的：

```
导入数据 → 筛选 → 选品 → 定稿 → 生产 → ???
```

到了"生产"就结束了。系统不知道：
- 生产出来的产品**卖得好不好**
- 上次选的品**哪些成功哪些失败**
- 某个品类的历史选品**命中率多高**

**没有反馈，AI就无法进步。**

### 1.2 闭环设计：从单向管道到循环系统

```
                    ┌──────────────┐
                    │   数据导入    │
                    │ (AsinImport) │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │  规则筛选     │
                    │ (Filter)     │
                    └──────┬───────┘
                           ↓
              ┌────────────────────────┐
              │    ★ AI品类分析 ★     │
              │ (品类评级+机会识别)    │
              └────────────┬───────────┘
                           ↓
                    ┌──────────────┐
                    │  选品池       │
                    │ (Selection)  │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │  定稿池       │
                    │ (FinalDraft) │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │  生产         │
                    │ (Production) │
                    └──────┬───────┘

```

### 1.3 "结果反馈"环节的设计

**问题**：产品卖得好不好，系统目前没有数据。

**思路**：不要求对接销售系统（太重），而是用**轻量级反馈机制**：

#### 方案A：手动标记（最简单，立即可做）

在FinalDraft页面增加"结果标记"：

```
定稿卡片上新增操作: 
  [标记成功 ✓] [标记观望 ⏳] [标记失败 ✗]

用户（开发人/运营）在产品上架1-2个月后回来标记：
  - 成功：销量达到预期
  - 观望：还在观察
  - 失败：卖不动/退货多/利润不行
```

**好处**：零对接成本，用户5秒就能标记。
**坏处**：依赖用户主动回来标记，可能标记率低。

#### 方案B：ASIN反查（中等成本，最有价值）

> **重要：现状约束（与代码对齐）**  
> `final_drafts` 表（`create_final_drafts_table.sql:2`）**当前没有 `asin` 字段**，只有 `sku`。
> 卖家精灵 API 必须用 ASIN 查询，所以此方案**必须先解决 asin 关联问题**。

**两种实现路径**：

**B-1：通过 ai_recommend_log 间接获得 asin**（推荐）

`ai_recommend_log` 表（见 `02-系统结合方案.md §4.4`）记录了 AI 推荐时的 `asin`。  
如果用户采纳了某条 AI 推荐 → `selection_products` 写入 → 推入 `final_drafts` 时，**把对应的 `asin` 一起写入 `final_drafts`**。

实施步骤：
1. 给 `final_drafts` 加字段：`source_asin VARCHAR(20)`（推荐来源的 asin，不要求唯一）
2. 用户从 AllSelection 推入 final_drafts 时，后端通过 `ai_recommend_log` 找到对应 asin 写入
3. 反查时遍历 `final_drafts WHERE source_asin IS NOT NULL AND create_time > 60天`

**B-2：通过 SKU 反查**（兜底方案）

现有 `final_drafts.sku` 是用户自填的产品 SKU。  
如果用户填写 SKU 时遵循某种规则（如 `B0XXXX-变体`），可能从中解析出 ASIN。  
**但此方案脆弱**，不推荐。

**反查流程**（以 B-1 为准）：
```
每月1号自动任务:
  遍历 final_drafts 中 create_time > 60天 且 source_asin IS NOT NULL 的产品
  → 调卖家精灵API查询最新数据（复用 SellerspriteApiService）
  → 对比选品时数据 vs 现在数据：
    - BSR变化：升了还是降了？
    - 销量变化：月销从多少涨到多少？
    - 价格变化：有没有被卷价格？
    - 评论变化：评分上升还是下降？
  → 自动计算"选品准确率"
```

**反查数据落入新表 `draft_outcomes`**：
```
draft_outcomes
  draft_id          -- 关联final_drafts
  asin              -- 来自 final_drafts.source_asin
  checked_at        -- 反查时间
  original_bsr      -- 选品时BSR
  current_bsr       -- 当前BSR
  bsr_change_rate   -- BSR变化率
  original_price    -- 选品时价格
  current_price     -- 当前价格
  price_change_rate -- 价格变化率
  original_rating   -- 选品时评分
  current_rating    -- 当前评分
  outcome_label     -- auto_success/auto_watch/auto_fail
```

> **关键改动**：实施 B 方案前必须先做：
> 1. `final_drafts` 表加 `source_asin` 字段（SQL 迁移）
> 2. FinalDraft 推送逻辑：从 AllSelection 推入时携带 asin
> 3. 上述两项工作量小（约 1-2 小时），不构成阻塞

#### 方案C：对接领星ERP（最完整，后期考虑）

> **现状**：`backend/app/api/v1/lingxing.py` 已存在，**但仅做 COS 上传**，未对接领星的销售/订单数据 API。  
> 要实现真正的"结果反馈"需调用领星 `OrderList`/`ProductList` 等接口，**属于 P3 长期工程**。

### 1.4 "智能优化"环节：反馈如何改善推荐

#### 品类级命中率统计

```sql
-- 每个品类的历史选品命中率
SELECT 
  cr.category,
  COUNT(*) AS total_drafts,
  SUM(CASE WHEN do.outcome_label = 'success' THEN 1 ELSE 0 END) AS success_count,
  SUM(CASE WHEN do.outcome_label = 'success' THEN 1 ELSE 0 END) / COUNT(*) AS hit_rate
FROM draft_outcomes do
JOIN final_drafts fd ON do.draft_id = fd.id
JOIN category_ratings cr ON fd.category = cr.category
WHERE do.checked_at IS NOT NULL
GROUP BY cr.category
```

**输出示例**：
```
Kitchen & Dining:  总定稿 28个, 成功 15个, 命中率 53.6%
Pet Supplies:      总定稿 12个, 成功 9个,  命中率 75.0%
Phone Accessories: 总定稿 35个, 成功 8个,  命中率 22.9%
```

**如何影响下次推荐**：
```
品类推荐权重 = 品类静态评分 × 0.7 + 品类历史命中率 × 0.3

Pet Supplies: 静态85分 × 0.7 + 命中率75% × 0.3 = 59.5 + 22.5 = 82 → 推荐
Phone Accessories: 静态60分 × 0.7 + 命中率23% × 0.3 = 42 + 6.9 = 48.9 → 不推荐
```

#### 模式级命中率统计

```
"快速起量"模式: 总推荐 45个, 成功 29个, 命中率 64.4% → 高权重模式
"低配高卖"模式: 总推荐 32个, 成功 22个, 命中率 68.8% → 高权重模式
"FBM可行"模式:  总推荐 18个, 成功 5个,  命中率 27.8% → 降低权重
```

**发现**：某些模式在你的业务场景下特别有效，某些模式理论上好但实际命中率低。
**这些是只有历史数据才能告诉你的信息。**

## 二、三种选品来源的差异化AI策略

### 2.1 三种来源的本质差异

| 来源 | product_type | 数据特点 | 选品逻辑 |
|------|-------------|---------|---------|
| **新品榜** | new | 来自八爪鱼新品榜数据，都是近期上架的新品 | 找"新趋势"——什么品类的新品多且卖得好 |
| **竞品店铺** | reference | 来自指定竞品店铺的产品，已知卖家 | 找"对标品"——竞品卖什么我也做什么 |
| **整店导入** | zheng | 某个店铺的全部产品 | 找"整店复制"机会——这个店铺整体值得学 |

### 2.2 新品榜(new)的AI策略

**核心问题**：新品榜数据量大（可能几千个），怎么快速找到值得关注的新品？

**AI增强思路**：

```
Step 1: 新品品类热度分析
  新品榜数据按main_category_name聚合
  → 哪个品类的新品数量最多？（说明品类在升温）
  → 哪个品类的新品平均销量最高？（说明新品存活率高）
  → 哪个品类的新品BSR增长最快？（说明市场在扩张）

Step 2: 新品"先行者"识别
  在新品中找：上架<30天 + 销量已进入品类前20%
  → 这些是"快速起量的新品"，说明品类需求在
  → AI建议：关注这些新品所属的品类

Step 3: 新品-老品对比
  将新品数据与竞品池(competitor_products)中同品类老品对比
  → 新品的价格比老品低？（说明新品在打价格战）
  → 新品的Listing质量比老品高？（说明品类在升级）
  → AI给出品类趋势判断
```

**前端呈现**：在AllSelection的"新品榜"tab中，增加品类热度排序和新品趋势标签。

### 2.3 竞品店铺(reference)的AI策略

**核心问题**：竞品店铺有几百个产品，哪些值得跟进？

**AI增强思路**：

```
Step 1: 竞品店铺画像
  分析该店铺：
  - 产品数量、品类分布
  - 平均价格、平均销量、平均评分
  - 头部产品（销量前10）vs 尾部产品
  - 最近30天上新了哪些产品？（说明店铺在往哪个方向扩展）

Step 2: 可跟进品识别
  在竞品店铺产品中，筛选出：
  - 该竞品在卖、我们还没在做的品
  - 竞品的新品（上架<60天）→ 说明竞品在押注的方向
  - 竞品的FBM产品 → 可能利润率更高，更值得跟进
  
Step 3: 差异化建议
  AI分析竞品的Listing质量：
  - 竞品没有A+？→ 我们做A+就能超越
  - 竞品没有视频？→ 我们做视频就能超越
  - 竞品评分<4.0？→ 改进品质就能超越
  - 竞品价格偏高？→ 同品质低价就能抢市场
```

**前端呈现**：在AllSelection的"竞品店铺"tab中，按店铺分组展示，每个店铺显示画像摘要。

### 2.4 整店导入(zheng)的AI策略

**核心问题**：整店几百个产品，这个店值不值得学？哪些品类值得跟进？

**AI增强思路**：

```
Step 1: 店铺整体评估
  - 店铺产品总数、品类集中度（做1个品类还是多品类？）
  - 店铺平均评分（整体运营水平）
  - 店铺头部产品占比（靠1-2个爆款还是均衡分布？）
  
Step 2: 店铺品类地图
  按品类分组，标注每个品类的：
  - 产品数（店铺在这个品类投了多少SKU）
  - 平均销量（这个品类卖得怎么样）
  - 上架时间分布（最近上新的是什么品类）
  
Step 3: 整店复制可行性
  AI判断：
  - 店铺成功是因为供应链优势？（大量SKU铺货）
  - 还是因为产品差异化？（少量精品）
  - 我们能复制哪些？不能复制哪些？
```

### 2.5 AI策略与品类分析的融合

三种来源的AI策略最终都汇合到**品类分析**这个共同基础上：

```
新品榜AI → 发现"哪些品类在升温"
竞品店铺AI → 发现"竞品在哪些品类布局"
整店AI → 发现"成功店铺聚焦哪些品类"

        ↓ 三者共同输出

    品类分析层（统一的六层分析）
    
        ↓ 统一输出
    
    品类评级 + 机会产品 + 推荐报告
```

**这意味着品类分析是AI系统的"中枢"，三种来源是"探针"。**

## 三、历史数据智能

### 3.1 系统积累的数据资产

随着系统使用，会积累以下数据：

| 数据 | 来源 | 价值 |
|------|------|------|
| **每月竞品数据** | competitor_products | 品类趋势、价格变化、新卖家进入 |
| **每月选品记录** | selection_products + week_tag | 用户选了什么、没选什么 |
| **淘汰黑名单** | skip_asins | 什么产品被系统判定为"不可做" |
| **选品回收站** | selection_recycle | 用户主动删除了什么选品 |
| **定稿记录** | final_drafts | 用户最终决定做什么 |
| **定稿结果** | draft_outcomes（新增） | 做了什么、结果好不好 |
| **品类评级历史** | category_ratings | 品类评分随时间的变化 |

### 3.2 "淘汰黑名单"的AI利用

**现状**：`skip_asins`表记录了被精筛淘汰的产品，有`filter_reasons`字段。但这些数据只是"存着"，没有进一步利用。

**AI增强**：

```
场景1：淘汰原因分析
  SQL聚合：各淘汰原因的占比
  PRICE_FAIL: 35% → 说明数据源价格偏高的多
  REVIEW_FAIL: 20% → 说明评论数太多的多
  BSR_FAIL: 25%
  WEIGHT_FAIL: 10%
  DEAD_PRODUCT: 10%
  
  AI解读："本批数据有35%因价格超限被淘汰。
  如果将priceMax从19.99调至25，可多获取约280个候选。
  但历史上£20-25区间的选品命中率仅为18%（低于平均45%），
  不建议放宽价格上限。"

场景2：黑名单ASIN追踪
  某些ASIN在黑名单里，但如果品类分析认为该品类很好，
  AI可以提醒："ASIN B0XXXXX 上月因BSR>50000被精筛淘汰，
  但所属品类Kitchen&Dining本月评级为A级。
  建议复查该ASIN最新数据，可能BSR已改善。"
```

### 3.3 "选品回收站"的AI利用

**现状**：`selection_recycle`存放用户删除的选品。用户删除 = 用户不看好。

**AI增强**：

```
分析用户删除行为：
  - 被删除产品的品类分布 → 用户不感兴趣的品类
  - 被删除产品的价格分布 → 用户不考虑的价格带
  - 被删除产品的grade分布 → 用户觉得哪些等级不值得做
  
对比保留 vs 删除：
  保留的产品: 平均价格£14, 平均grade B, 品类集中在Kitchen
  删除的产品: 平均价格£8, 平均grade C, 品类集中在Phone Accessories
  
→ AI学习: 用户偏好中档价位、Kitchen品类的产品
→ 下次推荐时: Kitchen品类的权重+20%, Phone Accessories权重-30%
```

### 3.4 "月度品类评级"的纵向对比

品类评级不是一次性的，每月都会重新分析。这就有了**时间序列数据**：

```
Kitchen & Dining 品类评级变化:
  2026-01: C级 (52分) — 品类一般
  2026-02: C级 (55分) — 略有上升
  2026-03: B级 (68分) — 明显升温，新品增多
  2026-04: A级 (82分) — 品类爆发，多个新品快速起量
  2026-05: A级 (85分) — 保持强势
  2026-06: B级 (71分) — 开始降温，CN卖家大量涌入

AI洞察:
  "Kitchen & Dining 品类从1月到5月持续升温，
  但6月CN卖家比从35%飙升到58%，内卷指数上升。
  品类评级从A降为B。
  如果此时进入，将面临更激烈的竞争。
  建议：要么快速进入抢占位置，要么等价格战结束后再进入。"
```

**这就是"品类分析六层"中第5层风险评估的"时间维度"。**

### 3.5 用户偏好画像的渐进构建

不是要求用户填写偏好，而是从行为中**推断**：

```
用户偏好画像 (user_preference_profile):
{
  "price_preference": {
    "sweet_spot": [12, 22],      // 用户最常选的价格区间
    "hard_floor": 5,              // 从不选低于£5的
    "hard_ceiling": 35            // 从不选高于£35的
  },
  "category_preference": {
    "preferred": ["Kitchen & Dining", "Pet Supplies"],
    "avoided": ["Phone Accessories", "Clothing"]
  },
  "grade_tolerance": {
    "min_acceptable": "C",        // 用户从不选D级产品
    "preferred": "A"              // 大多数选品是A级
  },
  "pattern_preference": {
    "most_selected": ["快速起量", "低配高卖"],
    "least_selected": ["FBM可行"]
  },
  "risk_tolerance": "medium",     // 从不选高风险品类，但会选中风险
  "selection_velocity": 8.5,      // 平均每次选品周期选8.5个产品
  "source_preference": {
    "new": 0.3,                   // 30%的选品来自新品榜
    "reference": 0.5,             // 50%来自竞品店铺
    "manual": 0.2                 // 20%手动添加
  }
}
```

**画像更新规则**：
- 每次选品周期结束后重新计算
- 最近3次选品权重0.6，更早的权重0.4（偏好会变）
- 至少3次选品周期后才开始应用画像（数据不足时不瞎推荐）

### 3.6 "选品→定稿"转化漏斗分析

系统可以追踪完整的转化漏斗：

```
2026年6月选品漏斗:
  
  数据导入:     5000 ASIN
     ↓ (初筛 35%通过)
  初筛通过:     1750 ASIN
     ↓ (API调用 + 精筛 17%通过)
  精筛通过:     300 (MODE1: 180, MODE2: 120)
     ↓ (AI推荐 10%)
  AI推荐选品:   30 → 写入selection_products
     ↓ (用户选择 50%)
  用户选中:     15 → 用户在AllSelection中保留的
     ↓ (推入定稿 60%)
  推入定稿:     9 → 进入FinalDraft
     ↓ (生产 80%)
  实际生产:     7
     ↓ (60天后验证)
  选品成功:     4 (命中率 57%)
```

**漏斗分析的价值**：
- 如果"AI推荐→用户选中"转化率持续很低（<30%），说明AI推荐不符合用户偏好 → 调整推荐策略
- 如果"用户选中→推入定稿"转化率很低，说明用户在选品池里犹豫不决 → 需要更好的辅助决策
- 如果"实际生产→选品成功"命中率低于40%，说明选品标准需要校准 → 回溯调整品类评分权重

## 四、AI介入的"节奏"设计

### 4.1 不是所有时候都需要AI

用户的工作节奏：

```
每周一：导入上周的八爪鱼数据 → 需要AI品类分析 + AI推荐
每月中：回看本月选品结果 → 需要AI结果反馈 + 趋势分析
每季度：总结选品成效 → 需要AI偏好学习 + 策略调整
```

### 4.2 AI触发的三种模式

**模式1：事件触发（自动）**
```
导入完成 → 自动触发品类分析 → 15秒后生成报告 → 推送通知
精筛完成 → 自动触发机会产品识别 → 推荐列表就绪
```

**模式2：手动触发（用户主动）**
```
用户点击"AI推荐选品" → 运行推荐逻辑
用户点击"品类分析" → 重新分析品类数据
用户点击"AI建议" → 获取阈值建议
```

**模式3：周期触发（定时任务）**
```
每月1号 → 反查定稿产品最新数据 → 更新结果反馈
每周一 → 自动更新品类评级（如果竞品池数据有更新）
```

### 4.3 通知策略

AI分析完成后不应该打扰用户，而是：

```
品类分析完成 → 页面右上角小红点提示
  "品类分析已完成：发现3个A级品类，点击查看"

AI推荐就绪 → 选品页面顶部横幅
  "AI已为您推荐30个产品，基于本次导入的300个竞品"

定稿反查完成 → 定稿页面提示
  "6个定稿产品已有最新数据，命中率58%，查看详情"
```

## 五、从"选品"到"做品"的桥梁

### 5.1 当前断层

选品(Selection)和定稿(FinalDraft)之间有一个**认知断层**：

- 选品池里看到的是"竞品长什么样"
- 定稿需要的是"我要做什么设计/元素/载体"

用户需要自己想："这个竞品不错，我应该做什么元素的产品来竞争？"

### 5.2 AI辅助"做品决策"

在用户准备从选品推入定稿时，AI可以提供：

```
AI做品建议:

"这个竞品(Kitchen Timer, £15.99)分析：
 
 1. 品类特征: 功能性强、外观差异化空间大
 2. 现有竞品: 大部分是简约风格，没有复古风格
 3. 建议元素: 复古厨房/烘焙主题
 4. 建议载体: 马克杯/围裙/餐垫
 5. 定价建议: £12-18区间（品类甜蜜价格带）
 6. 差异化方向: 现有竞品Listing质量低（无A+/无视频），
    做好Listing即可超越"
```

这个建议不需要LLM逐产品生成。**品类分析已经包含了价格带、Listing质量、竞争格局等信息。** 只需要在用户点击"推入定稿"时，把品类分析结果翻译成"做品建议"。

### 5.3 品类→元素/载体的映射

系统已有**素材库(MaterialLibrary)**和**载体库(CarrierLibrary)**。

AI可以建立品类→元素/载体的推荐映射：

```
Kitchen & Dining品类:
  推荐元素: 厨具图案、食材图案、烘焙工具、复古厨房
  推荐载体: 马克杯、围裙、餐垫、厨房毛巾
  （基于历史定稿数据 + 品类特征推断）

Pet Supplies品类:
  推荐元素: 猫狗图案、宠物肖像、搞笑宠物
  推荐载体: 马克杯、帆布包、抱枕、T恤
```

这些映射从`final_drafts`的历史数据中统计学习：
- 过去Kitchen品类的定稿用了什么元素？什么载体？
- 哪些元素/载体组合的"结果反馈"最好？

## 六、品类分析的"时机"维度

### 6.1 品类生命周期

每个品类都有生命周期，AI需要判断品类处于哪个阶段：

```
萌芽期 → 新品开始出现，但总数少（<5个通过筛选）
         AI建议: 观望，等数据更充分

成长期 → 新品数量月增30%+，BSR普遍下降（排名上升）
         AI建议: 最佳进入时机，先发优势大

成熟期 → 产品数量稳定，头部格局固定，评论壁垒高
         AI建议: 需要差异化策略才能进入

衰退期 → 新品减少，BSR普遍上升（排名下降），价格开始走低
         AI建议: 不建议进入，除非清库存

内卷期 → CN比飙升，价格持续下降，利润率被压缩
         AI建议: 危险，除非有成本优势
```

**如何从数据判断阶段**（不需要LLM）：

```python
if monthly_new_products < 5:
    stage = "萌芽期"
elif month_over_month_growth > 0.3 and avg_bsr_trend == "down":
    stage = "成长期"
elif product_count_stable and top3_share > 0.5 and avg_ratings > 200:
    stage = "成熟期"
elif month_over_month_growth < -0.2 and avg_price_trend == "down":
    stage = "衰退期"
elif cn_ratio_trend == "up" and avg_price_trend == "down":
    stage = "内卷期"
```

### 6.2 品类时机与选品时机的关系

品类处于"成长期" + 产品匹配"快速起量"模式 = **最佳选品时机**

品类处于"成熟期" + 产品匹配"低配高卖"模式 = **有机会但需要投入**

品类处于"内卷期" + 产品匹配"高溢价"模式 = **逆流而上，风险大**

**时机判断直接影响推荐的权重。**
