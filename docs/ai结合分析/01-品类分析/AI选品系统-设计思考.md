# AI 选品系统 — 深度设计思考

> 核心命题：从几千个筛选后的产品中，快速定位值得做的几个。
> 核心方法：以品类为分析单位，脚本做量，AI做质。

> **本文档定位**：品类分析方法论总纲。  
> 六层每层的深度细节见同目录《AI选品类分析六层-深度补充.md》。  
> AI如何接入现有系统见 `02-系统结合/`。  
> 数据存储/字段设计以 `02-系统结合/AI选品×系统深度结合方案.md` 为准（更贴近实际表结构）。

> **重要：数据源约束**（与实际代码对齐）  
> 本文档所有品类分析的数据源是 **`competitor_products` 表**（Java 端 `sjzm-product` 模块），因为只有它具备品类分析所需的全部字段：
> - `node_label_path`（3 级品类路径，如 `Home & Kitchen:Kitchen & Dining:Small Appliances`）
> - `brand`, `seller_name`, `seller_nation`（品牌/卖家/国籍）
> - `ebc`, `video`（Listing 质量：A+/视频）
> - `month`, `week_tag`（时间维度）
> - `score`, `grade`, `filter_mode`（筛选与评分）
>
> `selection_products`（Python 端）**不**作为品类分析数据源。它是用户在 AllSelection 中选中的结果表，只含 `main_category_name`（榜单大类名），且缺上述关键字段。
>
> **AI 推荐结果**通过新建的 `ai_recommend_log` 轻量表（见 `02-系统结合/`）传递给 `selection_products`，不污染主表。

## 一、现有系统的瓶颈在哪

### 当前链路

```
Excel上传(5000+) → 初筛(价格/评论/去重) → ~800个PASS
→ 调卖家精灵API(800个,20批) → 精筛(模式一+模式二)
→ ~300个通过(MODE1+MODE2) → 评分(S/A/B/C/D)
→ 用户手动翻看 → 选几个
```

### 瓶颈不是筛选，是"发现"

规则筛选做到了"淘汰不合适的"，但没做到"发现好的"。

300个MODE1通过的产品，score 从90到50都有，用户面对的是一个列表，不是决策。

**根本原因：规则只能做数值比较，不能理解"产品"本身。**

两个产品数值一模一样（价格15镑、BSR 3000、上架60天），但一个是手机壳（红海），一个是宠物喂水器（蓝海），规则分不出来。

### 缺失的能力

| 缺失 | 说明 |
|------|------|
| 品类级判断 | 这个品类整体适不适合做？ |
| 竞争格局感知 | 品类内头部是谁？集中度如何？ |
| Listing质量差距 | 现有卖家运营水平如何？有没有优化空间？ |
| 价格带空白 | 哪个价格区间没有好产品？ |
| 风险识别 | 季节性、侵权、合规风险 |
| 跨品类关联 | 几个品类能不能共享供应链？ |
| 机会模式识别 | 哪些产品有"快速起量""低配高卖"等特征？ |

## 二、核心设计理念

### 原则1：品类是分析单位，不是产品

人做选品的真实思路：
1. "最近宠物用品好像不错" → 先看品类
2. "这个品类里什么价格带好卖？" → 再看价格带
3. "头部卖家强不强？我能不能超越？" → 看竞争格局
4. "具体哪几个产品值得参考？" → 最后才看产品

**AI应该模拟这个思路，而不是反过来从产品往上堆。**

### 原则2：脚本做量，AI做质

| 任务 | 工具 | 处理量 |
|------|------|--------|
| 数值筛选 | SQL规则引擎 | 5000→300 |
| 品类聚合 | SQL GROUP BY | 300→30个品类 |
| 品类指标计算 | Python脚本 | 30个品类，毫秒级 |
| 品牌侵权检测 | Python关键词匹配 | 300个产品，毫秒级 |
| 机会模式识别 | Python模式匹配 | 300个产品，毫秒级 |
| **品类评估** | **LLM** | **30段品类描述** |
| **机会产品解读** | **LLM** | **10-15个候选** |
| 品类评级回写 | SQL JOIN | 秒级 |
| 最终排序推送 | Python + SQL | 秒级 |

LLM总共调用2-3次，处理40-50段文本。

### 原则3：AI输出的是决策，不是数据

用户不想看"品类A的brand_concentration=0.91"。
用户想看"品类A品牌很分散，新品牌容易进"。

**AI的价值是把数据翻译成判断。**

## 三、品类分析 — 六层深度拆解

### 第1层：品类画像（SQL聚合，秒级）

对精筛通过的产品，按 `node_label_path` 一二级品类做 GROUP BY。

**一条SQL出品类画像，包含以下维度：**

| 维度 | SQL字段 | 含义 |
|------|---------|------|
| 规模 | COUNT(DISTINCT parent_asin) | 独立品数量 |
| 卖家 | COUNT(DISTINCT seller_name) | 独立卖家数 |
| 品牌 | COUNT(DISTINCT brand) | 独立品牌数 |
| 价格 | MIN/AVG/MAX(price) | 价格分布 |
| 销量 | AVG(units), SUM(units>100) | 销量水平和高销量占比 |
| BSR | AVG/MIN(bsr) | 排名水平 |
| 评论 | AVG(ratings) | 竞争成熟度 |
| 上架 | AVG(listing_days) | 品类新旧度 |
| 国籍 | SUM(seller_nation='CN') | CN卖家占比 |
| 配送 | SUM(fulfillment='FBA'/'FBM') | 配送分布 |
| 评分 | SUM(grade IN 'S','A'), AVG(score) | 高评分占比 |
| Listing质量 | SUM(ebc=1), SUM(video=1) | 运营投入水平 |

**过滤条件：至少3个独立品才值得分析。实际产出20-50个品类。**

### 第2层：品类指标计算（Python脚本，毫秒级）

从SQL原始数据衍生出可量化的品类评分指标：

**7个核心品类指标：**

1. **品牌集中度** = 品牌数 / 独立品数
   - 0.8+ = 极度分散，新品牌容易进
   - 0.3以下 = 头部品牌垄断，难以进入
   
2. **内卷指数** = CN卖家数 / 总卖家数
   - 0.7+ = 严重内卷，价格战不可避免
   - 0.3以下 = 本地卖家为主，竞争理性
   
3. **评论壁垒** = 平均评论数
   - <50 = 低壁垒，新品容易追赶
   - >200 = 高壁垒，老品护城河深
   
4. **市场活跃度** = 高销量产品(>100)占比
   - 0.3+ = 多个产品卖得好，市场容量大
   - 0.1以下 = 只有头部能卖，赢家通吃
   
5. **价格带宽比** = (最高价-最低价) / 均价
   - >1.0 = 价格带宽，有差异化空间（做高端或做低端）
   - <0.5 = 价格趋同，只能卷价格
   
6. **品类新鲜度** = 1 - min(平均上架天数/365, 1)
   - >0.7 = 新品活跃，新品能活
   - <0.3 = 老品把持，新品难出头
   
7. **Listing运营水平** = (有A+的产品占比 + 有视频的产品占比) / 2
   - <0.3 = 现有卖家运营水平低，优化Listing就能超越
   - >0.7 = 对手很专业，进入成本高

### 第3层：价格带地图（SQL + Python，秒级）

在每个品类内部，按价格带分组：

```
价格带: 0-10 / 10-15 / 15-20 / 20-30 / 30-50 / 50+
每个价格带统计: 产品数、平均销量、平均BSR、平均评论数、高评分占比
```

**价格带地图的价值：发现"空白带"**

- 某品类15-20镑只有2个产品，但平均销量89 → **空白带，需求存在但供给不足**
- 某品类10-15镑有18个产品，平均销量只有8 → **拥挤带，供给过剩**

这是LLM特别擅长判断的：看到数字后说出"这个价格带有机会"。

### 第4层：卖家力量分析（SQL聚合，秒级）

品类内的卖家格局：

```sql
-- 每个品类内，卖家拥有多少通过筛选的产品
SELECT category, seller_name, COUNT(*) AS product_count
FROM competitor_products
WHERE filter_mode IN ('MODE1','MODE2')
GROUP BY category, seller_name
```

衍生指标：
- **头部卖家占比**：拥有3+产品的卖家的产品数 / 总产品数
  - >50% = 头部垄断，危险
  - <20% = 极度分散，好进入
- **最大卖家产品数**：如果某个卖家在品类内有10+产品，说明有供应链优势

LLM判断：
- "Pet Supplies 品类23个产品分布在19个卖家 → 极度分散，没有霸主"
- "Phone Accessories 品类45个产品中15个来自同一卖家 → 该卖家有供应链壁垒"

### 第5层：品类风险评估（LLM判断）

有些风险无法从数值算出来，需要LLM的"常识"：

| 风险类型 | LLM判断依据 |
|---------|-----------|
| **季节性** | 品类名含Christmas/Halloween/Summer → 季节依赖 |
| **侵权高发** | 品类内品牌字段出现Disney/Nike/Apple/乐高相关 → IP雷区 |
| **合规门槛** | Supplements/Baby/Electrical → 需要认证(FDA/CE等) |
| **退货率** | 服装/Apparel/电子配件 → 天然高退货 |
| **价格战趋势** | CN比>60% + 均价低于£10 → 正在打价格战 |
| **亚马逊自营威胁** | 品类标准化程度高(手机壳/数据线) → 亚马逊随时自己做 |
| **物流限制** | 品类含液体/电池/粉末 → 物流受限，FBA可能拒收 |

这些判断在品类级做，不需要逐产品。**LLM看品类名+品类数据就能判断。**

### 第6层：跨品类关联发现（LLM独有能力）

LLM看完所有品类数据后，能发现人类不容易注意到的模式：

**关联类型1：特征相似品类**
> "Kitchen Gadgets、Desk Organizers、Garden Tools 三个品类特征高度相似：
> 都是功能性小件、均价£10-20、CN比30-45%、评论壁垒<80
> → 可能共享供应链，建议一并调研"

**关联类型2：互补品类**
> "Pet Feeding 和 Pet Grooming 的卖家重叠度60%
> → 如果做宠物喂食器，可以同时考虑宠物美容工具，复用供应商关系"

**关联类型3：趋势信号**
> "本月 Home & Kitchen 品类通过筛选的产品比上月增加40%
> → 可能说明这个品类正在升温，值得重点关注"

## 四、品类内的产品机会识别

品类评级出来后，不是所有产品都值得看。要在**推荐品类**内识别**特定模式的产品**。

### 6种机会产品模式（Python脚本识别，批量处理）

**模式1：快速起量**
- 条件：上架 < 60天 且 BSR < 2000
- 含义：市场认可度高，短时间内就卖起来了
- 价值：说明需求真实且强劲

**模式2：低配高卖**
- 条件：无A+、无视频、评论<50，但销量>50
- 含义：Listing运营水平差但产品本身有需求
- 价值：优化Listing就能超越，最大机会

**模式3：FBM可行**
- 条件：fulfillment='FBM' 且 销量>30
- 含义：不用FBA也能卖，说明产品不需要Prime流量加持
- 价值：物流成本低，利润率更高

**模式4：高溢价仍能卖**
- 条件：价格 > 品类均价×1.4 且 销量>20
- 含义：消费者愿意为品质/设计付溢价
- 价值：品质驱动型品类，不卷价格

**模式5：评分洼地**
- 条件：rating < 4.0 且 销量>30
- 含义：产品有问题但需求在，消费者在忍受
- 价值：改进产品质量即可抢占市场

**模式6：无品牌品类**
- 条件：brand为空/generic/unbranded 且 品类内50%+产品无品牌
- 含义：消费者不认品牌，白牌就能进
- 价值：不需要品牌建设，门槛最低

### 模式组合的价值

单个模式有价值，**模式组合**价值更大：

- "快速起量 + 低配高卖" = 最好的机会，需求强且Listing差
- "FBM可行 + 无品牌品类" = 最低门槛进入
- "高溢价 + 评分洼地" = 做品质升级版就能吃掉市场

Python脚本在推荐品类内批量匹配这些模式，识别出10-20个候选产品。

## 五、LLM 的两次调用设计

> **前置条件**：需先扩展 LLM 服务能力。  
> 现状：`backend/app/services/tencent_llm_vision_service.py` 仅封装了**图像理解**接口（`hunyuan-vision` 模型）。  
> 需求：新增**纯文本** LLM 调用方法，建议在同文件新增 `analyze_text(prompt) -> str`：
> - 复用现有 `AsyncOpenAI` client（OpenAI 兼容接口）
> - 调用 `model="hunyuan-pro"` 或 `"hunyuan-standard"`（非 vision 模型）
> - 文本 prompt 解析 + JSON 提取复用现有 JSON 解析逻辑  
> 完成此扩展后，以下两次调用才能落地。

### 第1次调用：品类批量评估

**输入**：20-50个品类的结构化描述（每个品类约10行数据）

**Prompt结构**：
```
你是跨境电商选品专家。以下是亚马逊UK站最新一批通过筛选的品类数据。

请对每个品类评估：
1. 市场机会（1-5分）
2. 进入难度（1-5，5=最难）
3. 竞争烈度（1-5，5=最卷）
4. 综合推荐度：推荐 / 中性 / 不推荐
5. 一句话理由
6. 风险标签（如有）

同时请发现：
- 哪些品类之间有共性，可以共享供应链？
- 有没有特别值得注意的趋势？

品类数据：
[品类1] ...
[品类2] ...
...
```

**输出解析**：JSON结构化结果，存入 `category_ratings` 表。

### 第2次调用：机会产品深度解读

**输入**：10-15个被识别为机会产品的候选（每个约5行数据+模式标签）

**Prompt结构**：
```
基于品类分析，以下产品被识别为高潜力候选。请逐个判断：

1. 是否值得做？（值得 / 观望 / 不值得）
2. 核心优势是什么？
3. 最大风险是什么？
4. 如果要超越现有竞品，需要做什么？
5. 综合推荐度排名

最后给出Top 5推荐清单和总结建议。

产品数据：
[产品1] 品类: Kitchen Gadgets(推荐) | 模式: 快速起量+低配高卖 | ...
[产品2] ...
```

**输出**：结构化推荐报告，推送给用户。

## 七、AI选品报告的输出结构

每次选品生成的报告不是产品列表，而是**结构化的决策文档**：

### 报告结构

```
══════════════════════════════════════
   [日期] [站点] 选品分析报告
══════════════════════════════════════

一、品类全景
   分析品类数: XX | 推荐: X | 中性: X | 不推荐: X
   
二、推荐品类详情（每个品类一页）
   品类名 / 评级 / 三维评分
   核心数据（独立品数/均价/CN比/评论壁垒）
   价格带地图（哪个价格带有空白）
   卖家格局（分散/集中，头部是谁）
   风险标签
   AI一句话判断
   
三、重点机会产品（Top 15-30）
   每个产品：
   - 所属品类 + 品类评级
   - 产品核心数据
   - 匹配的机会模式
   - AI推荐理由
   - AI风险提示
   
四、风险品类/产品提醒
   不推荐的品类和原因
   有风险标签的产品

五、跨品类洞察
   共享供应链的可能性
   趋势信号
   整体市场判断
══════════════════════════════════════
```

### 报告的使用方式

用户拿到报告后：
1. 先看"品类全景" → 决定关注哪几个品类
2. 看推荐品类的"价格带地图" → 决定做哪个价格带
3. 看"机会产品" → 选几个深入研究
4. 看"风险提醒" → 避开雷区

**整个决策时间从"翻看几百个产品列表"变成"读一份2-3页的报告"。**

## 八、触发方式与自动化

### 方式1：导入后自动触发

现有的 ASIN 导入流程（`AsinImportService.executeApiCalls`）完成后，自动触发品类分析。

```
导入完成(DONE) → 自动触发品类分析 → 生成报告 → 推送通知
```

用户不需要手动操作，导入完就能看到AI选品报告。

### 方式2：手动触发对已有数据重新分析

改完筛选配置、重新评分后，手动触发品类分析。

```
改配置 → 重新筛选 → 重新评分 → 手动触发品类分析 → 新报告
```

### 方式3：跨月趋势分析

每月数据导入完后，对比上月品类数据，发现趋势变化。

```
本月数据 vs 上月数据 → 品类增长/衰退 → 趋势报告
```

## 十一、关键设计决策

### 决策1：品类分析粒度

**选择：一二级品类（如 Home & Kitchen > Kitchen & Dining）**

理由：
- 一级品类太少（20-30个），粒度太粗
- 三级品类太多（可能上千个），且每个品类产品数不够
- 一二级交叉（如 Home & Kitchen > Kitchen & Dining）大概50-200个，筛选后有产品的约20-50个
- 这个粒度正好匹配人类认知："厨房用品""宠物喂食""园艺工具"

### 决策2：LLM选择

**选择：复用现有腾讯混元（OpenAI兼容接口），后续可替换**

约束：
- 必须先在 `tencent_llm_vision_service.py` 新增 `analyze_text()` 方法（现有服务只支持图像）
- 文本模型用 `hunyuan-pro` 或 `hunyuan-standard`，**不能用 `hunyuan-vision`**
- API Key、base_url、client 初始化已具备，只需添加新方法

理由：
- 已有 `TencentLLMVisionService` 的基础设施
- OpenAI兼容接口意味着换模型只改配置
- 品类分析不需要视觉能力，纯文本即可
- 建议后续接入 Claude/GPT 以获得更好的结构化输出

### 决策3：品类评级有效期

**选择：按月标记，每月重新分析**

理由：
- 品类格局不会每周大变，月度频率足够
- 每月新数据导入后自动重新分析
- 历史品类评级保留，可做趋势对比

### 决策4：机会产品识别用脚本还是AI

**选择：模式识别用脚本，模式解读用AI**

理由：
- 6种模式的条件是明确的数值判断，脚本更快更可靠
- 模式组合的价值判断需要上下文理解，AI更合适
- 脚本先过滤出10-20个候选，AI只对候选做深度解读

### 决策5：是否阻塞导入流程

**选择：不阻塞，异步执行**

理由：
- 品类分析需要LLM调用，可能耗时20-30秒
- 不应阻塞导入流程的完成回调
- 用异步任务（Celery或独立线程）在导入完成后触发
- 分析完成后推送通知
