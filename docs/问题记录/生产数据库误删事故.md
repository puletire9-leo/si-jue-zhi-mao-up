# 生产数据库误删事故

**日期**: 2026-06-04
**严重级别**: P0 - 生产数据丢失
**恢复状态**: 已恢复（从旧卷 sijuelishi-prod_prod-mysql-data 复制）

---

## 事故经过

1. Docker 容器全部停止，执行 `docker compose -f docker-compose.prod-simple.yml down` + `up -d`
2. `down` 删除了旧容器，`up -d` 创建了新容器和**新数据卷**
3. 旧生产环境用的是另一个 compose 文件（项目名 `sijuelishi-prod`），数据卷叫 `sijuelishi-prod_prod-mysql-data`
4. `docker-compose.prod-simple.yml` 创建的是 `si-jue-zhi-mao-up_prod-mysql-data`，空卷
5. 新 MySQL 启动后初始化了空数据库，**生产数据丢失**

## 根因

- **`docker compose down` 会删除容器**，新 `up -d` 会按 compose 文件中的卷名创建新卷
- 没有确认当前生产数据在哪个卷里就执行了 down/up
- 两个 compose 文件的项目名不同，导致卷名不同

## 教训（铁律）

1. **生产环境禁止 `docker compose down`** — 只用 `docker compose restart` 或 `docker stop/start`
2. **操作前必须确认数据卷归属** — `docker volume ls` + `docker inspect prod-mysql`
3. **切换 compose 文件前必须备份数据库**
4. **`down` 和 `up -d` 不是无损重启** — 容器会被销毁重建，卷可能丢失

## 恢复过程

1. 发现 `zhangzixuan` 登录失败（Total: 0），确认数据丢失
2. `docker volume ls` 发现旧卷 `sijuelishi-prod_prod-mysql-data`（2.4GB）
3. 用临时 MySQL 容器挂载旧卷，确认数据完整（binlog 最后写入 7:07 AM）
4. `docker run --rm -v old:/src -v new:/dst alpine cp -a /src/* /dst/` 复制数据
5. 重启 MySQL，验证 users=15, competitor_products=121906
