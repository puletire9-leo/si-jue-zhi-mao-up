# 大量商品数据导致页面卡死

- **记录日期**：2026-07-21 至 2026-07-24
- **影响范围**：总选品管理、新品榜、店铺选品、店铺画像、卖家精灵请求中心
- **核心结论**：这不是一个单点 SQL 问题，而是数据库扫描、后端大对象加载、前端重组件挂载、KeepAlive 内存常驻和大任务轮询叠加后的系统性问题。排查必须按“数据库 → API → 组件渲染 → 页面生命周期 → 浏览器内存”逐层拆开。

---

## 一、用户症状与对应层级

| 症状 | 主要层级 | 直接表现 |
|------|----------|----------|
| 打开更多筛选后长时间转圈 | 数据库/API | `shop_products` 大表排序、过滤、COUNT 全量扫描 |
| 数据已经返回但卡片滚动卡 | 前端渲染 | 一页同时挂载大量 `UniversalCard` 和 Element Plus 子组件 |
| 打开店铺选品后切到任何页面都卡 | 页面生命周期/内存 | 图片密集页面被无差别 KeepAlive，DOM、图片和响应式状态常驻 |
| 请求中心打开 3000+ 店铺任务详情后卡死 | 网络/前端状态 | 数千子项一次性返回、深度代理、整表轮询和整表重渲染 |
| 店铺筛选抽屉打开慢，零结果筛选再次变慢 | 聚合查询 | 每次执行 7 层 CTE、窗口函数和 3D 派生计算 |

不要把这些症状统称为“前端慢”。同一页面可能同时存在多个瓶颈，但修复和验收必须分别验证。

## 二、店铺商品分页：数据库与 API 热点

### 2.1 生产实测根因

`ShopCollectionService.selectionProducts()` 原先使用 MyBatis-Plus `selectPage` 和 `SELECT *`：

1. 默认 `ORDER BY updated_at DESC` 后又固定追加 `asin ASC`，排序方向冲突，索引无法直接产出有序结果，16.6 万行全量 filesort 约 **2711 ms**。
2. 价格、销量、上架天数、BSR、重量等筛选列没有合适的复合索引，只能先按低基数 `marketplace` 扫描大分区；带筛选列表约 **494 ms**，COUNT 约 **267 ms**。
3. `SELECT *` 将 `raw_json` 等 70 多列和大字段带入 JVM，查询结果本身变重。
4. `productWall` 需要按销售等级在内存中分组，不能简单在 SQL 侧 LIMIT；若直接拉全字段，会放大 JVM 内存和 GC 压力。

### 2.2 已落地修改

| 位置 | 修改 | 目的 |
|------|------|------|
| `java-backend/sql/add_shop_products_selection_indexes.sql` | `idx_shop_sel_default (marketplace, updated_at)` | 默认排序走反向索引扫描，历史实测 2711 ms → 2.2 ms |
| 同上 | `idx_shop_sel_metrics (marketplace, units, price, listing_days)` | 高频筛选走范围扫描，历史实测 494 ms → 105 ms |
| `ShopCollectionService.selectionProducts()` | 只选择卡片需要的约 31 个字段 | 排除 `raw_json` 等大字段 |
| `ShopCollectionService.selectionProducts()` | 次级排序改为与主排序同方向的 `id` | 保持索引有序扫描，避免再次 filesort |
| 同上 | 前后端页大小上限统一为 200 | 避免 500 张重卡片一次性进入渲染层 |
| 同上 | total COUNT 与 list 查询分离并缓存 | 翻页期间复用 total，避免每页重复 COUNT |
| `ShopCollectionService.productWall()` | 只查询商品墙实际需要的 11 个字段 | 不能 LIMIT 时优先降低单行体积 |
| 批次筛选 | 使用已写入的 ISO `batch_code`，兼容 `batch_date` | 避免每行执行 `STR_TO_DATE`/`DATE_FORMAT` |

历史记录中的 SQL 实测是查询计划优化前后的对比，不等同于所有环境的固定 SLA；上线后仍应通过 `EXPLAIN` 和接口耗时复核。

### 2.3 商品详情和快照类查询

`productWall`、`compare`、`insight` 都按 `source_run_id` 过滤，原有 `(marketplace, seller_name, batch_date)` 索引无法覆盖。因此新增幂等迁移：

```text
java-backend/sql/add_shop_products_source_run_index.sql
idx_shop_products_source_run (marketplace, seller_name, source_run_id)
```

审查时删除了没有执行计划证据的 `idx_shop_products_dedup` 方案。窗口去重实际使用 `COALESCE(NULLIF(parent_asin,''), asin)`，一个普通五列索引不能自动覆盖表达式和完整排序键；大表索引必须先有 `EXPLAIN ANALYZE` 证据再建。

## 三、店铺分类、批次和 total 聚合

`selectionCategories` 和 `selectionBatches` 都可能扫描几十万行：

- 分类使用 `TRIM(node_label_path)` 分组，普通列索引不能直接匹配表达式。
- 批次按 `marketplace` 过滤、按 `batch_date` 分组，原索引中间夹着 `seller_name`，不能有效支持该访问模式。
- 重复打开筛选抽屉会重复执行相同聚合。

已增加：

```text
java-backend/sql/add_shop_products_aggregate_indexes.sql
idx_shop_sel_cat_trim  ((TRIM(node_label_path)))
idx_shop_sel_batch      (marketplace, batch_date)
```

`ShopCollectionService` 使用共享的 `categoryCache` 缓存分类、批次和 total，并在店铺商品写入后按站点精确失效。缓存键采用长度前缀编码，标题、店铺名、Amazon 类目中包含 `|` 或逗号时不会发生碰撞：

```text
长度:内容;长度:内容;
```

### 生产 DDL 踩坑

MySQL 8.0.46 对函数索引内部的隐藏虚拟列不支持 `LOCK=NONE`。第一次执行聚合索引脚本时报：

```text
ERROR 1846: LOCK=NONE is not supported ... ADD COLUMN ... VIRTUAL
```

最终脚本保留普通联合索引的 `ALGORITHM=INPLACE, LOCK=NONE`，函数索引改用 `LOCK=SHARED`。函数索引执行期间会阻塞写入，生产必须先暂停访问 `shop_products` 的应用和导入任务。`information_schema` 守卫保证脚本重复执行安全，但预检和 SchemaGuard 都不会检查索引，索引必须单独查询 `information_schema.statistics`。

## 四、店铺聚合画像：从实时 CTE 到物化快照

### 4.1 原始问题

店铺画像列表每次打开都要执行多层 CTE、`ROW_NUMBER()`、等级计算、分类排名和 3D 派生字段。几十万商品行下，即使列表只展示少量店铺，也会先做大范围聚合。特别是筛选结果为零时，旧逻辑仍会回退执行整套实时 SQL。

### 4.2 物化快照方案

新增：

```text
java-backend/sql/create_shop_seller_summary.sql
ShopSellerSummary
ShopSellerSummaryMapper
ShopSellerSummarySnapshotWriter
```

粒度是一行 `(marketplace, seller_name)`，保存 `ShopProfileSummary` 的标量字段、批次日期和 3D 解释。常规店铺列表优先读取单表快照，只有快照尚未初始化时才回退实时计算。

刷新分为两部分：

1. 事务外执行完整实时计算，避免长时间占用写事务。
2. 独立事务内按站点删除旧快照并批量插入新快照，避免读到半套数据或失败后留下残缺快照。

请求中心店铺批任务不再“每处理一家店就刷新一次全站画像”：

- 单店直抓仍即时刷新。
- 批量请求只失效商品筛选缓存。
- 请求中心任务进入终态后按站点统一刷新一次 `shop_seller_summary`。

### 4.3 发现并修复的两个上线问题

**实体字段命名映射**：Java 属性 `newABCCount`、`newABCRatio`、`topABCCategory`、`shopProfile3dType`、`shopProfile3dExplanation` 被默认命名策略拆成了错误列名。`SchemaGuard` 首次启动时拦截了该问题。最终在 `ShopSellerSummary` 上增加显式 `@TableField` 映射，保持数据库列名和既有 SQL 口径一致，不能通过关闭 SchemaGuard 绕过。

**全量刷新被 1000 行上限截断**：页面查询上限 1000 不能复用到快照刷新。DE 首次刷新恰好返回 1000 行，实际应为 2382 行。现在 Mapper 只在 `limit` 为正数时生成 `LIMIT`，刷新传空上限；相关 15 个定向测试全部通过。

### 4.4 生产验证

2026-07-24 生产快照精确行数：

| 站点 | 快照行数 | 去重店铺数 | 正常列表验证 |
|------|----------|------------|--------------|
| UK | 849 | 849 | 初始化接口 200 |
| DE | 2382 | 2382 | 初始化接口 200；`limit=100` 约 85 ms |
| US | 990 | 990 | 初始化接口 200 |

DE 不存在的店铺筛选返回 200/0 行约 20 ms，证明“已初始化快照 + 当前过滤无结果”不会再次回退 7 层实时 CTE。

## 五、前端卡片流：不要把数据库分页误当成渲染虚拟化

### 5.1 高度测量的 O(N²) 问题

`AllSelection/index.vue` 中，每张卡片的 `ResizeObserver` 回调都复制整个 `cardBaseHeights` 对象并触发响应式更新。N 张卡片同时首屏时会产生 N 次全量拷贝和重渲染，近似 O(N²)。

当前实现：

- `pendingHeightUpdates` 收集同一帧的高度变化。
- `requestAnimationFrame` 每帧只合并写入一次。
- 翻页/筛选后只保留当前页高度，忽略旧页面迟到回调。
- `onUnmounted` 取消未执行的 rAF 和 ResizeObserver。

### 5.2 当前最终渲染策略

当前工作区不是 JS 行虚拟列表：

- 页大小前后端统一限制为 200，前端选项是 60/100/200。
- `productList` 使用 `shallowRef`，选中态使用 `Set` 做 O(1) 命中。
- 选中用户信息异步补齐，不阻塞首屏列表就位。
- `.product-card-scale-wrapper` 使用 `content-visibility: auto` 和 `contain-intrinsic-size`，浏览器可跳过离屏卡片的布局/绘制。
- 组件和 DOM 仍会创建，`content-visibility` 不是完整虚拟列表。

历史上曾尝试自研变高网格行虚拟化，但行高测量、缩放和真实内容高度不稳定，会造成滚动抖动甚至 `scrollTop` 被钳住、无法滚到底。因此当前保留浏览器原生滚动语义，优先使用页大小限制、列裁剪、合帧和 CSS 离屏优化；若未来仍需更大页，应先做真实用户滚动基线，再引入成熟的变高虚拟列表。

### 5.3 KeepAlive 导致的全局卡顿

症状是离开店铺选品后整个系统仍卡，且等待一段时间会恢复；这不是单页查询问题。旧布局无条件缓存最多 30 个页面，图片密集的选品页面把完整 DOM、图片和响应式状态长期留在内存中。

`lay-content/index.vue` 现在只缓存显式 `route.meta.keepAlive` 页面，缓存上限从 30 降为 10；未标记页面离开即销毁，释放卡片、图片、Observer 和定时器。副作用是未标记页面切回会重新加载，这是预期取舍。

## 六、请求中心大任务详情

一次任务可包含 3000+ 家店铺，旧实现同时触发三个放大器：

1. 子项接口一次返回全部记录。
2. `el-table` 一次挂载数千行 DOM。
3. 每 3 秒轮询重新拉整表，Vue `ref` 对大数组深度代理并触发 GC。

现在的链路：

- `SellerspriteRequestCenterService.listItems` 默认分页 20、上限 200，按 `seq` 升序。
- 前端 `items` 改为 `shallowRef`，只保留当前页。
- 轮询只刷新任务汇总，不重拉子项表。
- 翻页、切任务、快速重试使用请求序号、`runId` 和页码校验，旧响应不能覆盖当前页。
- 子项状态的实时性取舍：轮询期间只更新汇总，翻页或重试时才刷新当前子项页。

这类问题的通用原则是：分页不仅是数据库 LIMIT，也必须同时限制 API 响应、响应式代理范围和 DOM 数量。

## 七、部署与验收经验

本次生产变更顺序：

1. 使用 `--single-transaction --no-tablespaces` 生成全库压缩备份，宿主机与容器文件 SHA-256 一致；backend 镜像当时缺少 `mysqldump` 且备份目录无持久卷，因此没有把不可验证的 API 备份当作保护措施。
2. 暂停 Java、Gateway、Python、Celery 和前端应用，只保留 MySQL/Redis/Nacos，执行建表和在线索引。
3. 执行 `scripts/deploy/prod_preflight_check.ps1 -Env prod`，再构建和重建 Java/前端。
4. 检查 `prod-java-product` 日志中的 `SchemaGuard` 和 `/actuator/health`。
5. 通过前端/Gateway 认证后，UK、DE、US 依次初始化快照。
6. 用精确 COUNT、接口响应、容器状态和错误日志进行验收。

生产纪律：

- 不使用 `docker compose down -v`。
- 不给现网默认项目名随意追加 `-p`，避免容器名冲突。
- 变更 `env_file` 后必须 `up -d --force-recreate`，`restart` 不会重新读取环境变量。
- 大表 DDL 前备份、查磁盘、查长事务和活动任务；在线 DDL 的 `LOCK=NONE` 不是所有索引类型都支持。
- 预检只检查实体表和 Java 路由；SchemaGuard 检查实体表/列；两者都不检查业务索引，索引必须单独核对。
- 全量快照刷新不能继承页面 LIMIT；所有“页面上限”都要和“后台重建上限”分开定义。

## 八、遗留项与后续判断

1. 带筛选的精确 COUNT 仍可能是主要数据库耗时，当前采用缓存和批次筛选降低重复计算；若继续优化，应评估定制 COUNT 或“加载更多”，不要盲目添加 FORCE INDEX。
2. `content-visibility` 仍会创建 Vue 组件和 DOM，页大小 200 以上需要真实滚动、内存和长任务基线，不应仅凭 SQL 变快宣布页面不卡。
3. 多层 CTE 的窗口去重仍是高风险热点，没有 `EXPLAIN ANALYZE` 证据前不要重写生产 SQL。
4. 全仓库 TypeScript 类型检查和 Java 全量测试可能被其他既有改动阻塞；本次店铺快照相关 15 个定向测试已通过，生产主代码编译、SchemaGuard 和端到端接口已验证。
