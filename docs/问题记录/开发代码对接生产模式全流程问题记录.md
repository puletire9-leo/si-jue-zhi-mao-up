# 开发代码对接生产模式全流程问题记录

**日期**: 2026-06-04
**严重程度**: 高（生产环境多项功能不可用）
**影响范围**: 店铺评级模块、定稿图片加载、filter-presets、click-logs 等需要认证的接口

将 `9251f77 feat: 前端模块化架构 + 店铺评级模块` 提交的代码部署到 Docker 生产环境（`docker-compose.prod.yml`）。该提交包含：

部署过程中遇到 **7 个独立问题**，逐一排查修复。

## 问题 1：前端构建产物未正确同步

**现象**: 浏览器访问 `/zheng-shop-overview`，调用的是旧端点 `/api/v1/selection/stores/grades`（404），而非新端点 `/api/v1/modules/shop-rating/candidates`。

**根因**: `npm run build` 每次生成的 JS 文件名带 hash（如 `index-5VpT0Cen.js`、`index-BPdBgUAX.js`、`index-DZVz29lW.js`）。构建输出到 `static/vue-dist/`，但 `index.html` 仍引用旧的 JS 文件名。旧 JS 不含新模块代码，所以走旧逻辑。

**排查过程**:
1. Grep 发现新模块代码调用 `/api/v1/modules/shop-rating/`（正确）
2. 但浏览器日志显示调用 `/api/v1/selection/stores/grades`（旧端点）
3. 检查 `static/vue-dist/index.html` → 引用 `index-5VpT0Cen.js`（旧）
4. 检查 `index-5VpT0Cen.js` → 不含 `modules/shop-rating`
5. 检查 `index-BPdBgUAX.js` → 含 `modules/shop-rating`（新）
6. **结论**: `index.html` 未更新，浏览器加载了旧 JS

**修复**: 重新执行 `npm run build -- --minify false`，确认 `static/vue-dist/index.html` 引用新 JS 文件名。

**教训**: 每次前端构建后必须验证 `index.html` 引用的 JS 文件名是否已更新。Vite 构建的文件名带 content hash，旧文件不会被覆盖。

## 问题 2：COS_BUCKET 配置错误导致图片加载失败

**现象**: 生产环境定稿页面所有图片显示占位 SVG（420 字节），开发环境正常。

**根因**: `docker-compose.prod.yml` 中 `backend` 服务的 `COS_BUCKET` 使用 `${COS_BUCKET}` 从宿主机环境变量读取，值为 `sijuelishi-dev-1328246743`（带 `-dev` 后缀）。但图片实际存储在 `sijuelishi-1328246743`（无 `-dev`），两个是不同的 COS 存储桶。

| 配置来源 | COS_BUCKET | 结果 |
|---------|-----------|------|
| 宿主机 `.env` | `sijuelishi-dev-1328246743` | NoSuchKey |
| `celery-download` 硬编码 | `sijuelishi-1328246743` | 正确 |
| 数据库中图片 URL | `sijuelishi-1328246743` | 正确 |

**排查过程**:
1. 前端图片显示占位图，测试代理接口 `/api/v1/image-proxy/proxy` → 返回 200 但只有 420 字节
2. 查看 Python 后端日志 → `COS SDK 获取失败: NoSuchKey`
3. 关键线索：日志中 COS URL 为 `sijuelishi-dev-1328246743`，数据库中图片 URL 为 `sijuelishi-1328246743`
4. 对比 `docker-compose.prod.yml` 中各服务的 COS 配置，发现 `backend` 引用 `${COS_BUCKET}`（带 `-dev`），`celery-download` 硬编码正确值

**修复**: 将 `backend` 服务的 `COS_BUCKET` 从 `${COS_BUCKET}` 改为硬编码 `sijuelishi-1328246743`。

**教训**: 生产环境配置不应引用宿主机环境变量（宿主机 `.env` 通常是开发配置）。同一项目的不同服务配置应保持一致。参考 [[feedback_cos_bucket_mismatch]]。

## 问题 3：前端调用不存在的旧端点

**现象**: 店铺页面仍调用 `/api/v1/selection/stores/grades`（404），即使问题 1 已修复（新 JS 已加载）。

**根因**: 新模块 `index.vue` 中 `loadSelectionStores()` 函数调用 `selectionApi.getStoresWithGrades()`，该函数请求 `/api/v1/selection/stores/grades`。但 Python 后端只有 `/api/v1/selection/stores`，没有 `/stores/grades` 端点。

**排查过程**:
1. 问题 1 修复后，浏览器加载了新 JS，但仍调旧端点
2. Grep 新模块 `index.vue` → 第 453 行调用 `selectionApi.getStoresWithGrades()`
3. 检查 `selection.ts` → `getStoresWithGrades()` 请求 `/api/v1/selection/stores/grades`
4. 检查 Python 后端 → 只有 `/stores` 端点，无 `/stores/grades`
5. **结论**: 旧端点从未实现或已被删除

**修复**: 将 `loadSelectionStores()` 改为调用 `selectionApi.getStores()`（`/api/v1/selection/stores`），更新数据映射（`store_name` → `storeName`，`count` → `productCount`）。

**教训**: 模块化开发时，引用的 API 函数必须确认后端已实现。前后端接口契约应有文档或类型检查。

## 问题 4：Nginx 绕过 Gateway 导致认证缺失

**现象**: `/api/v1/filter-presets` 和 `/api/v1/click-logs/my-selections` 返回 500，Java 后端日志报 `MissingRequestHeaderException: Required request header 'X-User-Id'`。

**根因**: Nginx 将 Java API 请求直接转发到 `prod-java-product:8002`，绕过了 `prod-gateway:9000`。Gateway 负责解析 JWT token 并注入 `X-User-Id` 请求头，绕过后 Java 后端拿不到用户信息。

**架构对比**:

```
错误链路（绕过 Gateway）:
  前端 → Nginx → java-product:8002（无 X-User-Id）→ 500

正确链路（通过 Gateway）:
  前端 → Nginx → gateway:9000（解析 JWT，注入 X-User-Id）→ java-product:8002 → 200
```

**排查过程**:
1. 前端日志显示 `/api/v1/filter-presets` 500
2. Java 后端日志 → `MissingRequestHeaderException: Required request header 'X-User-Id'`
3. 检查 nginx 配置 → 所有 Java 路径直接 `proxy_pass http://prod-java-product:8002`
4. 检查 gateway 配置 → 有完整的路由规则 + JWT 认证
5. **结论**: Nginx 绕过了 gateway，Java 后端无法获取认证信息

**修复**: 将 nginx 中所有 Java API 路径合并为一个正则 location，统一转发到 `prod-gateway:9000`：

```nginx
# 修改前（多个 location 直接到 java-product）:
location ~ ^/api/v1/filter-presets(/.*)?$ {
    proxy_pass http://prod-java-product:8002;  # 绕过 Gateway
    ...
}
location ~ ^/api/v1/click-logs(/.*))?$ {
    proxy_pass http://prod-java-product:8002;  # 绕过 Gateway
    ...
}
# ... 十多个类似 location

# 修改后（统一走 Gateway）:
location ~ ^/api/v1/(auth|users|filter-config|filter-presets|scoring|asin-import|competitor|click-logs|sellersprite-config|deng-zong-shop|modules|products|selections|product-sales|final-drafts|materials|carriers|images|image-proxy)(/.*)?$ {
    proxy_pass http://prod-gateway:9000;
    ...
}
```

Python 后端路径（`/api/v1/selection/`、`/api/v1/material-library/` 等）不在此正则中，走 `/api/v1/` catch-all 直接到 `prod-backend:7090`。

**教训**: 生产环境的请求链路必须经过 Gateway 认证层。Nginx 不应绕过 Gateway 直接访问微服务。架构上应统一：前端 → Nginx → Gateway → 微服务。

## 问题 5：Gateway JAR 未更新

**现象**: Gateway 不认识 `/api/v1/modules/**` 路由，返回 404。

**根因**: Gateway JAR 文件日期为 5/28，未包含最新的路由配置（`/api/v1/modules/**` 已添加到 `application.yml`，但 JAR 未重新构建）。

**修复**: 重新构建 gateway JAR：
```powershell
cd java-backend/sjzm-gateway
mvn package -DskipTests
```
然后重建容器。

**教训**: Java 微服务修改后必须重新构建 JAR 并更新 Docker 容器的挂载文件。Volume 挂载 `:ro` 模式下，替换宿主机 JAR 文件后需 `docker compose down && up` 重建容器。

---

## 问题 6：Nginx 缺少 `/api/v1/modules/` 路由

**现象**: `/api/v1/modules/shop-rating/candidates` 请求被 `/api/v1/` catch-all 捕获，转发到 Python 后端，返回 404。

**根因**: Nginx 没有为 `/api/v1/modules/` 配置专用的 location 块，请求落入最后的 `/api/v1/` catch-all（Python 后端）。

**修复**: 添加 location 块路由到 Java 后端（后在问题 4 中合并为统一正则）。

**教训**: 新增 API 路径时，必须同步更新 nginx 配置和 gateway 路由。

---

## 问题 7：Java 编译错误（缺少 category 参数）

**现象**: `mvn package` 编译失败，`CompetitorService` 和 `DengZongShopController` 中 mapper 方法调用参数不匹配。

**根因**: Mapper XML 新增了 `category` 筛选参数，但 Java 代码中的调用处未同步更新。

**修复**: 在 `CompetitorService`、`DengZongShopController`、`CompetitorQueryRequest` 中补充 `category` 参数。

**教训**: 修改 Mapper XML 参数后，必须同步更新所有 Java 调用处。IDE 的类型检查可以提前发现此类问题。

## 完整部署检查清单

每次将开发代码部署到生产环境，应按以下顺序检查：

### 前端
- [ ] `npm run build -- --minify false` 成功
- [ ] `static/vue-dist/index.html` 引用的 JS 文件名已更新
- [ ] 新增 API 路径在前端代码中使用正确（grep 确认无旧端点引用）
- [ ] 浏览器强制刷新（Ctrl+Shift+R）验证

### Nginx
- [ ] 新增 API 路径有对应的 location 块
- [ ] Java API 路径走 Gateway（`prod-gateway:9000`），不直接走微服务
- [ ] Python API 路径走 Python 后端（`prod-backend:7090`）
- [ ] `docker exec prod-frontend nginx -s reload` 无报错

### Gateway
- [ ] `application.yml` 的 routes 包含所有 Java API 路径
- [ ] JAR 已重新构建（`mvn package -DskipTests`）
- [ ] 容器已重建（`docker compose down && up`）

### Java 微服务
- [ ] 编译无错误（`mvn package -DskipTests`）
- [ ] Mapper XML 参数与 Java 调用一致
- [ ] JAR 已替换到宿主机挂载路径
- [ ] 容器已重建

### Python 后端
- [ ] 环境变量与 `docker-compose.prod.yml` 一致（特别是 COS_BUCKET）
- [ ] 不引用宿主机 `${VAR}`，直接写死生产值
- [ ] 容器已重建（`docker compose up -d backend`）

### 端到端验证
- [ ] 前端页面正常加载（无 JS 报错）
- [ ] API 请求返回 200（非 404/500）
- [ ] 图片代理正常返回图片（非占位 SVG）
- [ ] 认证相关接口有 `X-User-Id`（通过 Gateway 注入）
