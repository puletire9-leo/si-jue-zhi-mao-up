# 模块化开发踩坑记录

> 日期：2026-06-03 ~ 2026-06-04
> 功能：前端模块化架构 + 后端店铺评级模块
> 总结：本次开发暴露了多个"改了但没生效"的问题，根因是对 Docker 开发环境的运行机制理解不透彻。

---

## 一、前端模块化改造

### 1.1 router 硬编码路由误删

**问题：** 改造 `router/index.ts` 时，用模块路由替换了整个 `children` 数组，导致所有未迁移的路由（all-selection、asin-import 等）被删除。sidebar 的 legacyGroups 指向的路由全部 404。

**根因：** 一次性替换过大，没有保留旧路由作为过渡。

**修复：** 恢复所有旧路由，在末尾追加 `...moduleRoutes`。模块路由和 legacy 路由共存，逐步迁移。

**教训：** 渐进式改造，不要一步到位删旧代码。新旧共存 → 逐个迁移 → 最后清理。

### 1.2 sidebar iconCache 缺少 new

**问题：** `const iconCache = Map<string, any>` 写成了类型声明而不是实例化，运行时报错。

**根因：** 手写代码时遗漏了 `new` 关键字。

**修复：** 改为 `const iconCache = new Map<string, any>()`。

**教训：** 写完代码立刻跑 type check，不要等到最后。

### 1.3 sidebar findItem 参数类型不匹配

**问题：** `findItem(menuItems, index)` 中 `menuItems` 是 `ComputedRef<MenuItem[]>`，但 `findItem` 期望 `MenuItem[]`。Vue 模板中自动 unwrap，但 script 中不会。

**根因：** Vue 3 `<script setup>` 中 computed 返回的是 ref，脚本代码中需要用 `.value`。

**修复：** 改为 `findItem(menuItems.value, index)`。

**教训：** 在 script 中使用 computed 变量时，始终用 `.value`。模板中才自动 unwrap。

### 1.4 manifest menuGroup 重复

**问题：** 郑总店铺模块 manifest 设置了 `menuGroup: '选品中心'`，但 sidebar 的 legacyGroups 已经有同名分组，导致侧边栏出现两个"选品中心"。

**根因：** 模块化和 legacy 共存时，menuGroup 命名冲突。

**修复：** 去掉 manifest 的 menuGroup，让模块作为独立顶级菜单项。

**教训：** 模块和 legacy 共存期间，新模块不要使用 legacy 已有的 menuGroup 名。

## 二、后端模块化

### 2.1 @MapperScan 范围扩大导致启动失败（严重）

**问题：** 为了扫描模块 Mapper，把 `@MapperScan("com.sjzm.product.mapper")` 改成 `@MapperScan("com.sjzm.product")`，导致 MyBatis 尝试把 Controller、Service、Entity 都当 Mapper 实例化，启动报错。

**根因：** `@MapperScan` 会递归扫描指定包下所有接口。`com.sjzm.product` 包含了所有类。

**修复：** 改回 `@MapperScan("com.sjzm.product.mapper")`。模块 Mapper 放在 `com.sjzm.product.mapper` 包下（而不是 `modules.xxx.mapper`），利用现有的扫描范围。

**教训：** 模块化不能破坏现有的包扫描约定。Mapper 统一放 `mapper/` 包，Controller/Service/Entity 放 `modules/` 包。两者被不同的机制扫描。

### 2.2 模块 Mapper 放错包

**问题：** 最初设计模块 Mapper 放 `com.sjzm.product.modules.xxx.mapper`，但这个包不在 `@MapperScan("com.sjzm.product.mapper")` 范围内，不会被扫描到。

**根因：** `@MapperScan` 不会扫描子包的子包，只扫描指定包及其子包。

**修复：** 约定模块 Mapper 统一放 `com.sjzm.product.mapper` 包下。Controller/Service/Entity 放 `modules/xxx/` 下（被 `scanBasePackages` 覆盖）。

## 三、Docker 开发环境

### 3.1 网关配置改了但没生效（严重）

**问题：** 修改了 `sjzm-gateway/src/main/resources/application.yml`，重启网关容器后配置没变。

**根因：** 网关命令是 `mvn install && java -jar app.jar`。配置在 `mvn install` 时被打包进 JAR。重启容器不会重新 `mvn install`，所以 JAR 里的配置还是旧的。

**修复：** 把网关命令改为 `spring-boot:run`（和 java-product 一致），从源码直接读配置，重启即生效。

**教训：**
- `java -jar` 模式：配置打包进 JAR，改配置需要重新 `mvn install`
- `spring-boot:run` 模式：直接读源码，改配置重启就生效
- 开发环境一律用 `spring-boot:run`

### 3.2 Vite 代理未配置新 API 路径

**问题：** 新增 `/api/v1/modules/shop-rating/` 接口，前端请求 404。

**根因：** `vite.config.js` 的 proxy 配置是逐路径声明的。新路径没有配置代理规则，请求走了默认 target（Python 后端），Python 后端没有这个路由。

**修复：** 在 `vite.config.js` 添加 `/api/v1/modules` 代理规则，指向 `javaTarget`。

**教训：** 新增后端 API 路径时，必须同步更新：
1. `vite.config.js` 的 proxy 配置
2. `sjzm-gateway/src/main/resources/application.yml` 的路由 predicates
3. 网关需要重启（开发环境改用 `spring-boot:run` 后只需重启容器）

### 3.3 Vite 配置修改需要重启

**问题：** 修改 `vite.config.js` 后，HMR 不会自动生效。

**根因：** Vite 的 HMR 只处理 Vue/TS/CSS 文件。`vite.config.js` 是构建配置，修改后需要重启 dev server。

**修复：** `docker restart dev-frontend`。

**教训：** `vite.config.js`、`tsconfig.json`、`package.json` 这类配置文件修改后，必须重启前端容器。

## 四、前端问题

### 4.1 request 拦截器返回值误用

**问题：** 评级接口返回 200，但前端报"启动评级失败"。

**根因：** `utils/request.ts` 的响应拦截器已经 `return response.data`（即 API 响应体 `{code, message, data}`）。组件里 `res` 就是这个对象，`res.data` 才是业务数据。但代码写成了 `res.data?.data?.taskId`，多了一层 `.data`。

**修复：** 改为 `res.data?.taskId`。

**教训：** 搞清楚 `request` 封装层返回的是什么：
- `axios` 原始返回：`response.data` = API 响应体
- 本项目的 `request` 拦截器：直接返回 `response.data`，所以 `res` = API 响应体
- 访问业务数据：`res.data.xxx`（不是 `res.data.data.xxx`）

## 五、Java 代码问题

### 4.1 @Async 不生效（严重）

**问题：** `evaluate()` 方法内直接调用 `this.doEvaluate()`，`@Async` 注解不生效，任务同步执行，阻塞 HTTP 请求线程。

**根因：** Spring 的 `@Async` 基于 AOP 代理。同一个类内部调用 `this.method()` 绕过了代理，注解失效。

**修复：** 通过 `ApplicationContext.getBean(ShopRatingService.class).evaluateAsync()` 调用，走 Spring 代理。

**教训：** Spring AOP 的经典坑。`@Async`、`@Transactional`、`@Cacheable` 等注解在同类内部调用时都会失效。解决方案：
- 注入自身代理（`@Lazy` self-injection）
- 通过 `ApplicationContext.getBean()` 获取代理
- 抽到另一个 Service 类

### 4.2 scoreOneShop 重复查全量 DB

**问题：** 每个候选店铺评分时，都调用 `selectRatingData(marketplace)` 拉取该站点全部商品，然后过滤出目标店铺。15 个候选 = 15 次相同 SQL。

**根因：** 没有复用基准构建时已经加载的数据。

**修复：** 新增 `selectRatingDataBySeller(marketplace, sellerName)` 方法，只查单店数据。每个候选店铺只执行一次精确查询。

### 4.3 Redis JSON 手动拼接不安全

**问题：** `"{\"status\":\"FAILED\",\"error\":\"" + e.getMessage() + "\"}"` 中，如果 `getMessage()` 包含 `"` 或 `\`，JSON 会损坏。

**根因：** 手动拼接 JSON 没有转义特殊字符。

**修复：** `e.getMessage().replace("\"", "'")` 兜底。

**教训：** 手动拼 JSON 只适合简单场景。复杂结构考虑用 Jackson 或 Gson。

### 4.4 parseResults 丢失嵌套对象

**问题：** `parseResults()` 用 `extractField()` 解析 JSON，但 `extractField()` 遇到 `{` 直接返回 null，导致 `detail` 嵌套对象始终为 null。

**根因：** `extractField()` 只处理基本类型（字符串、数字），不处理嵌套对象。

**修复：** 新增 `extractJsonObject()` 方法，用括号匹配提取嵌套 JSON 字符串，再逐字段解析。

### 4.5 TaskStatus DTO 字段名不一致

**问题：** DTO 定义了 `progress/total`，代码实际用 `currentStep/totalSteps`。前端也用 `currentStep/totalSteps`。反序列化时字段对不上。

**根因：** DTO 和实现不同步。

**修复：** DTO 改为 `currentStep/totalSteps`，与实际使用一致。

## 五、开发流程优化清单

### 新增后端 API 的检查清单

- [ ] Controller 放在正确包下（`modules/xxx/controller/` 或 `controller/`）
- [ ] Mapper 放在 `com.sjzm.product.mapper` 包下（不是 `modules/xxx/mapper/`）
- [ ] `vite.config.js` 添加代理规则
- [ ] `application.yml`（gateway）添加路由 predicates
- [ ] 重启 gateway（开发环境用 `spring-boot:run`，重启容器即可）

### 新增前端模块的检查清单

- [ ] `manifest.ts` 的 menuGroup 不与 legacy 分组冲突
- [ ] `icon` 字段用字符串名，不用 import 的组件
- [ ] router 中保留旧路由，不要删除未迁移的路由
- [ ] sidebar 中 legacyGroups 和动态模块共存
- [ ] 修改后跑 `vue-tsc --noEmit` 确认无类型错误

### Spring 注解使用注意

- [ ] `@Async`、`@Transactional` 同类内部调用会失效
- [ ] 解决：通过 `ApplicationContext.getBean()` 获取代理调用
- [ ] 或者抽到独立的 Service 类

### Docker 开发环境注意

- [ ] Java 服务用 `spring-boot:run`，不用 `java -jar`（配置修改重启即生效）
- [ ] `vite.config.js` 修改后需要 `docker restart dev-frontend`
- [ ] 网关配置修改后需要重启 gateway 容器
- [ ] 容器间通信用容器名（`java-product`、`dev-backend`），不用 `localhost`
