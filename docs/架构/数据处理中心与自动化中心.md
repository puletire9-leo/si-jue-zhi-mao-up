> 2026-08-14 建立。运营物流已作为第一条正式业务链路接入。
>
> 财务与运营两条链路的当前完整实施状态、数据口径、算法、前端、RDS、测试和部署收口，统一见 [财务与运营自动化任务完整实施记录](财务与运营自动化任务完整实施记录.md)。

## 一、总体结构

```text
外部连接器 -> 来源事实表 -> 数据处理中心 -> 业务标准表 -> 自动化中心 -> 外部目标
```

| 层 | 职责 | 当前例子 |
|---|---|---|
| 外部连接器 | 鉴权、请求、限流、翻页、原始落库 | 领星、卖家精灵、八爪鱼、飞书 |
| 数据处理中心 | 标准化、校验、去重、关联、计算、物化 | 后续运营物流进度管线 |
| 自动化中心 | 调度、编排、互斥、重试、运行审计、目标绑定 | 后续领星采购进度同步飞书 |

依赖方向固定：

```text
automation -> dataprocessing
automation -> lingxing / feishu 等连接器

lingxing、feishu、dataprocessing 不反向依赖 automation
```

## 三、当前实现

数据处理中心：

```text
com.sjzm.product.modules.dataprocessing
```

自动化中心：

```text
com.sjzm.product.modules.automation
```

领星请求中心与自动化中心的调用边界：

```text
自动化请求注册表 -> 领星请求任务队列 -> LingxingClient
       排期/错峰          单线程执行/审计       唯一领星 HTTP 出口
```

需要领星 API 的自动化必须先在
`lingxing_automation_request_registry` 登记。注册表支持每日、每周、固定延迟、
手动四种周期，并用槽位顺序和最小间隔错开同组请求；到期后只入队，不在调度线程
直接请求领星。现有 `lingxing_request_task` 仍是每一次真实请求的唯一执行记录。

SQL：

```text
java-backend/sql/create_data_processing_automation_center.sql
```

当前已注册：

- 数据管线 `LOGISTICS_PURCHASE_PROGRESS`
- 自动化任务 `OPERATIONS_LOGISTICS_PURCHASE_PROGRESS`

运营物流 `automation_job` 只保留业务编排能力并设为 `MANUAL`，实际周期由领星自动化
请求注册表控制。默认注册项 `OPS_LOGISTICS_DAILY` 保持关闭，配置飞书目标并人工验证后
只启用该注册项，避免两套调度重复触发。

两个中心的管理 API 统一经过网关权限 `automation:manage`，当前仅 `admin/管理员` 通配角色默认具备该权限。

## 四、迁移原则

1. 新的数据处理逻辑必须进入数据处理中心。
2. 旧逻辑不做一次性大搬迁，只在业务修改时逐步迁移。
3. 来源模块保留协议级清洗；跨来源和业务状态计算进入数据处理中心。
4. 自动化任务只读取来源事实或业务标准表，不直接消费未整理的第三方 JSON。
5. 飞书仅作为协作输出，不作为系统唯一事实来源。
6. 长任务未来可接入统一消息队列，但任务契约、运行表和绑定表保持不变。

## 五、第一条业务链路

运营物流按以下顺序执行：

```text
按 startDate/endDate 同步领星采购单
-> 按更新时间范围分页同步实际 SP
-> 从实际 SP 提取 RP 批次并反查完整发货计划
-> 按同时间窗内已到仓采购 SKU 补查尚无实际 SP 的发货计划
-> 运营物流采购进度处理管线
-> 业务标准表
-> OPERATIONS_LOGISTICS_PURCHASE_PROGRESS 自动化任务
-> 飞书采购单进度表批量新增/更新
```

一个采购单可能包含多个 SKU，业务唯一键必须使用采购子项稳定 ID，不能只使用采购单号或 SKU。

三状态规则：

```text
存在关联的有效 SP（shipment_status in (1,2)，且分配数量 > 0） -> 已发货
不存在有效 SP，采购子项 received_quantity < purchase_quantity -> 待到货
不存在有效 SP，采购子项 received_quantity >= purchase_quantity -> 待发货
```

有效 SP 是已发生 FBA 出库的业务事实。状态判定不比较采购量、入库量和 SP
实发量是否完全覆盖；只要采购子项关联到任意有效 SP，就进入 `已发货` 终态。
到货状态必须按采购子项/SKU 判断，不能把采购单整体“部分到货”状态套给所有 SKU。

飞书采购进度表的主标识为“创建批次号”，值取
`lingxing_purchase_plan.ppg_sn`。`PO...` 是采购执行单，`PP...` 是采购计划号，
两者均不能代替 `PPG...` 创建批次号。采购计划同步的领星时间参数必须传
`yyyy-MM-dd`，不能传带时分秒的字符串。

配置：

```text
OPERATIONS_LOGISTICS_FEISHU_APP_TOKEN
OPERATIONS_LOGISTICS_FEISHU_TABLE_ID
```

数据库迁移：`java-backend/sql/create_operations_logistics_purchase_progress.sql`。

补齐艾为完整 SP 字段的可重跑迁移：

```text
java-backend/sql/expand_lingxing_shipment_tables_full_fields.sql
```

### 时间窗参数

首次或人工测试必须显式传入统一时间窗，采购同步、SP 同步、状态计算和飞书投递使用同一范围：

```json
{
  "syncShipments": true,
  "startDate": "2026-08-01 00:00:00",
  "endDate": "2026-08-14 23:59:59"
}
```

### 历史批次关联

领星发货计划和实际 SP 不直接返回采购单号，因此历史关联使用思觉历史自己的两条领星事实链：

1. `getBatchDetailList` 返回 `purchase_order_sns + plan_sn + purchase_in_time`，用于确认采购批次及真实入本地仓时间。
2. `getInboundShipmentList` 返回有效 SP、实际发货数量和实际发货时间。
3. 数据处理中心按 `SKU + 本地仓` 建立库存队列，在本次同步的统一业务时间窗内，
   按采购批次真实入库时间执行 FIFO 数量分配；同一 SP 数量只分配一次。禁止把
   时间窗外的历史采购批次放进队列，否则在历史 SP 未全量同步时会抢占当前 SP。
4. FIFO 仅用于确认 SP 应归属哪个采购批次；一旦分配数量大于 0，该采购子项立即进入 `已发货`，不要求 SP 数量覆盖全部入库量。

该机制不是按 SKU 单独认亲：采购单号、仓库、入库时间、SP 时间和数量守恒共同参与归属。缺少采购批次入库时间的记录不进入自动分配，避免跨批误判。

### 飞书权限

后台应用身份至少需要以下任一权限才能自动写入：

```text
bitable:app
base:record:create
```

任务默认保持关闭。人工代写飞书后，必须同步写入 `automation_record_binding`，否则应用权限开通后会重复创建。
