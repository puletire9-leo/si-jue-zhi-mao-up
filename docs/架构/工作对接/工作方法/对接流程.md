# 架构师对接工作方法（升级版）

> 融合 TOGAF ADM、BIZBOK 业务能力与价值流、Continuous Discovery、Gregor Hohpe「架构师电梯」及国内企业级业务架构实践，形成可落地、可复用的中间层工作方法。

## 核心角色定位

你是**翻译官**（业务语言 ↔ 技术语言）、**协调者**（组织会议推动决策）、**决策者**（技术选型与优先级）。

**关键原则**：
- 永远不要让 IT 直接找业务，你是唯一中间层。
- 给业务看流程图、能力地图、原型；给 IT 看架构图、接口文档、差距分析。
- 用「业务能力 + 价值流」作为双方的通用语言。
- 持续发现（Discovery）与交付（Delivery）并行，而不是瀑布式一次性做完。

## 三步走（建议总时长 3–4 周，可按项目规模调整）

### 第1步：理解业务与建立共同语言（1–1.5 周）

**目标**：把业务真实场景、痛点、优先级翻译成业务与 IT 都能理解的结构化语言。

**关键动作**：
1. **业务访谈（Business Scenario 风格）**  
   逐个访谈运营 / 美工 / 采购 / 财务 / 核心决策者。  
   重点问实际场景，而非抽象描述：
   - 一天处理多少工作量？关键决策依据什么数据？
   - 最痛的环节是什么？期望系统解决什么？
   - 当前手工/半手工流程是怎样的？失败时怎么处理？
   - 成功标准是什么？（量化指标优先）

2. **构建业务能力与价值流**  
   - 画出**价值流**（端到端客户/业务价值交付过程）  
   - 识别支撑价值流的**业务能力**（Capability）  
   - 标注痛点与当前成熟度（热力图）

3. **输出物**（必须完成）：
   - 业务流程图 / 价值流图
   - 痛点清单（含影响程度）
   - 业务能力地图（简版）
   - 功能优先级（P0 必做 / P1 重要 / P2 可延后）
   - 初步成功标准与量化指标

**工具建议**：访谈纪要模板 + 价值流/能力图（可用 Miro / FigJam / 飞书白板）。

---

### 第2步：对接 IT 与定义目标架构（1–1.5 周）

**目标**：把业务需求翻译成技术可执行的语言，明确现状与目标差距，确定接口与排期。

**关键动作**：
1. **IT 启动会**  
   用大白话讲业务（「就像淘宝选货」），解释关键概念（SKU / Listing / ASIN / 领星等）。  
   说清楚现有系统（刘淼 / 刘颖豪 / 赵燎等）与新系统的关系。

2. **技术讨论与差距分析**  
   - 确定整体架构风格（推荐：数据中心型，各板块可并行）  
   - 技术栈建议（Java + Vue 或其他已验证栈）  
   - 接口规范：JSON 格式、Token 鉴权、幂等、失败重试、错误码、监控告警  
   - 做 **Baseline（现状）vs Target（目标）** 差距分析

3. **接口对接专项会议**  
   分别与各现有系统负责人开会，明确：
   - 数据推送格式与字段映射
   - 频率与触发条件
   - 失败重试与补偿机制
   - 数据量级预估与性能要求

4. **输出物**（必须完成）：
   - 技术架构文档（含现状 vs 目标）
   - 接口规范文档
   - 业务-IT 映射矩阵（能力 ↔ 系统/服务）
   - 开发排期与里程碑（含 MVP 范围）
   - 风险清单

**工具建议**：架构图（C4 / 简单分层图）、接口文档模板、差距分析表。

---

### 第3步：原型验证与假设驱动迭代（1 周）

**目标**：用最低成本验证最关键假设，而不是一次性做完整系统。

**关键动作**：
1. **用 Figma 做高保真原型**  
   重点聚焦运营决策工作台（候选品列表 / 筛选 / 详情 / 决策按钮）。  
   明确标注「假设」与「已验证」部分。

2. **联合评审**（业务 + IT）  
   记录「必须改」与「可选」意见。  
   使用假设清单：每个关键功能背后的假设是什么？如何用最小实验验证？

3. **小实验优先**  
   高风险假设先用原型测试 / 数据验证 / 手工模拟，再进入正式开发。

4. **输出物**：
   - 可交互原型
   - 评审意见清单（必须改 / 可选）
   - 验证通过的假设与仍存风险的假设
   - 更新后的 MVP 范围与排期

**工具建议**：Figma + 假设清单表 + 评审会议模板。

## 实用工具箱

### 1. 术语对照表（持续维护）
| 业务语言          | 技术语言                  |
|-------------------|---------------------------|
| 候选品            | candidate_product         |
| SKU 决策          | sku_confirmation          |
| 竞品 ASIN         | competitor_asin           |
| 业务能力          | Capability                |
| 价值流            | Value Stream              |
| 现状架构          | Baseline Architecture     |
| 目标架构          | Target Architecture       |

和业务说左边，和 IT 说右边。

### 2. 会议模板（固定结构）
每次会议强制执行：
1. 目标（1 分钟）
2. 议程
3. 讨论
4. 行动项确认（谁、做什么、截止时间）
5. 24 小时内发会议纪要

### 3. 决策矩阵
| 业务价值 | 技术复杂度 | 决策          |
|----------|------------|---------------|
| 高       | 简单       | 优先做        |
| 高       | 复杂       | MVP 简化做    |
| 低       | 任意       | 不做 / 延后   |

### 4. 每周风险自检（强制）
每周问自己 4 个问题：
- 需求变了吗？是否走了变更流程？
- 进度延期吗？原因是什么？
- 接口阻塞吗？谁在负责？
- 技术难点未解决吗？有替代方案吗？

### 5. 变更管理流程（轻量）
1. 提出变更（业务或 IT）
2. 影响评估（范围 / 排期 / 成本）
3. 决策（你 + 关键干系人）
4. 更新文档与排期
5. 通知所有相关方

## 典型问题处理手册

| 问题                  | 应对方式                                                                 |
|-----------------------|--------------------------------------------------------------------------|
| 需求频繁变化          | 固定 MVP 范围，建立正式变更流程，超出范围的进 P2 或下个迭代              |
| IT 说「做不到」       | 追问具体难点（技术/资源/时间），一起探讨替代方案或简化方案               |
| 业务说「不好用」      | 追问具体场景与数据，区分「真不好用」与「不习惯」，用原型快速验证         |
| 进度延期              | 砍功能（按决策矩阵）、加资源或调整预期，并同步所有干系人                 |
| 接口联调卡住          | 立即升级到负责人，准备临时 mock 或手动方案，避免阻塞主路径               |
| 业务与 IT 互相推诿    | 你作为中间层强行拉会，用能力-系统映射矩阵把责任边界说清楚                |

## 成功标准（可量化）

- 业务方能独立、清晰地讲出 MVP 范围与优先级
- IT 完全理解业务背景与关键决策逻辑
- MVP 范围达成共识，并有明确时间表与责任人
- 建立了定期沟通机制（周会 + 随时升级通道）
- 产出完整文档：能力/价值流图、架构文档、接口规范、原型、排期
- 关键假设已通过原型或小实验验证
- 变更有流程，风险有清单

---

## 进阶建议（可选）

1. **长期沉淀**：把能力地图与价值流做成组织资产，后续项目可复用。
2. **双轨并行**：Discovery（发现）与 Delivery（交付）持续并行，而不是三周结束后就结束。
3. **架构师电梯**：定期在业务战略层与 IT 执行层之间「坐电梯」，保持双向信息流通。
4. **复盘机制**：三周结束后做一次快速复盘（什么有效、什么需改进），沉淀进下一版方法。

方法是工具，判断力是核心。  
当业务与 IT 产生冲突时，优先回到「业务价值」和「最小可行验证」，而不是陷入技术或流程争论。

价值流（Value Stream） 是业务架构里非常核心的一个概念，简单说就是：
从客户（或业务干系人）视角出发，端到端地描述「价值是如何被创造和交付」的完整过程。
它不是普通的「业务流程」，而是站在价值交付的高度看问题。

和普通流程图的区别



































对比维度普通业务流程（Process）价值流（Value Stream）视角内部怎么做（部门/系统视角）客户/业务真正得到什么价值（外部视角）关注点步骤、责任人、系统操作价值如何一步步被创造和交付范围通常只覆盖某个部门或系统内部端到端（跨部门、跨系统）目的规范操作、提高效率发现价值断点、优化整体交付、对齐IT输出流程图、SOP价值流图 + 支撑能力 + 痛点热力图
一句话区分：

流程图回答「我们怎么做」
价值流回答「客户最终得到了什么，中间哪里卡住了」


举例（结合你原来的选品场景）
假设业务是「选品并上架」：
普通流程图可能是：
运营提需求 → 美工做图 → 采购询价 → 财务审核 → 上架……
价值流则会这样描述：
价值流名称：候选品决策与上架

识别机会（发现有潜力的商品）
评估与决策（运营根据数据决定是否做）
准备内容（图片、文案、SKU信息）
确认供应（采购确认货源与价格）
正式上架（系统上架并开始销售）
监控反馈（看销售数据，决定是否继续）

在这个价值流里，你可以看到：

每个阶段真正交付给「业务决策者」或「客户」的价值是什么
哪里有等待、返工、信息断层（痛点）
哪些业务能力在支撑这些阶段（比如「竞品分析能力」「库存可用性查询能力」）
这些能力目前由哪些系统支撑，哪里需要新建或改造


为什么架构师要画价值流？

统一语言：业务说「我要好用的选品工具」，IT说「我要接口和表结构」。价值流把两边拉到同一个画面上。
发现真痛点：很多「功能需求」其实是价值流某个环节卡住了。
指导优先级：高价值、高痛点的环节优先做（对应你文档里的决策矩阵）。
对齐IT架构：价值流阶段 → 业务能力 → 应用/服务 → 数据，形成清晰映射。


怎么画（实用建议）

先问业务：「从开始到最终产生业务结果，中间客户/决策者依次经历什么？」
把完整过程拆成 5–9 个阶段（不要太细）。
每个阶段标注：
主要参与角色
当前主要痛点
需要什么信息/能力

用简单的横向泳道或阶段条画出来即可（不需要复杂工具）。
