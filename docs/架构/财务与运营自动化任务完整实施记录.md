## 2. 总体架构与职责边界

```text
领星 OpenAPI / 领星 MCP           飞书 OpenAPI
           ↓                            ↑
      领星运行中心                飞书对接中心
           ↓                            ↑
      RDS 来源事实表 → 数据处理中心 → 业务标准表
                                      ↑
                              自动化任务中心
```

固定边界：

1. 领星运行中心是所有领星 OpenAPI 批量任务的排队和审计入口。
2. `LingxingClient` 是领星 HTTP 唯一客户端出口，负责签名、令牌、节流和限流重试。
3. 数据处理中心只做标准化、关联、计算和业务表物化，不管外部密钥。
4. 自动化中心负责排期、编排、互斥、运行审计、阶段耗时和投递幂等，不直接解析第三方原始 JSON。
5. 飞书是协作输出，不是系统唯一事实源；飞书失败不得覆盖 RDS 事实。
6. 自动化任务可阶段化运行，不强制每次执行整条链路。

## 3. 共用基础能力

### 3.1 RDS 主数据源与批处理写入

新增 `RdsDataSourceConfig`、`LingxingRdsMapperScanConfig`和 `rds` 包边界，将领星、财务、运营相关 Mapper 绑定到远程 MySQL RDS。

`RdsBatchWriteService` 提供：

- `execute`：使用 MyBatis `ExecutorType.BATCH`，在同一 RDS 连接和事务中分批 flush。
- `insert`：MyBatis-Plus 实体批量新增。
- `saveOrUpdate`：根据已有业务键批量新增/更新。
- `executeOne`：单条集合 SQL、状态更新或需要原子提交的操作。

强制规则：

- 业务 Service 禁止直接提交 RDS Mapper 写操作。
- 禁止对 RDS 实体使用 `Db.saveBatch` / `Db.saveOrUpdateBatch`。
- 常规结构化行批次建议 500，较大行默认 200。
- 中心统一记录 Mapper、行数、flush size 和耗时。

### 3.2 领星请求中心

```text
lingxing_automation_request_registry
  → lingxing_request_task
  → LingxingTaskHandlerRegistry
  → 具体处理器
  → LingxingClient
```

- 注册表支持 `MANUAL / DAILY / WEEKLY / FIXED_DELAY`。
- 同组通过 `slot_order * minimum_gap_seconds` 错峰。
- worker 单线程，按 `priority DESC, id ASC` 取任务。
- 领星账号级串行门禁，不允许财务和运营同时打同一账号。
- 任务可在前端手动入队、停止和恢复异常中断队列。
- 周产品表现和每日库存批次属于领星基础数据任务，显示在领星中心，不占用“财务/运营”两个跨系统业务任务名额。

当前领星节流：

- 普通请求最小间隔 500ms。
- 产品表现正式分页链路保持响应完成后 10s 节奏。
- 命中 `103/3001008` 后采用 2s 短退避，已取消 30/60/90s 固定递增等待。
- 小页探针实测 12s 仍可限流、13s 可连续成功；探针只用于诊断，不直接替换正式 1000 行分页参数。

### 3.3 自动化中心与耗时审计

新增三类主表：

- `automation_job`：任务配置。
- `automation_run`：每次执行的请求、结果、数量、错误和时间审计。
- `automation_record_binding`：业务键与飞书 record_id 等外部记录的幂等绑定。

`AutomationStageTimer` 将每个阶段耗时写入 `automation_run.result_json.stageDurationsMs`。前端展示总耗时及阶段明细，用于定位 44 分 40 秒等长任务的真实耗时分布。

### 3.4 飞书对接中心

- `FeishuConfigService`：环境变量为主，`api_config` 可覆盖。
- `FeishuClient`：缓存 `tenant_access_token`，失效时强制刷新并最多重发一次。
- 支持多维表格的表列表、记录查询、批量新增和批量更新。
- 前端可维护 App ID/App Secret、做 token 自检和业务资源自检；App Token 和 Secret 只显示掩码。
- 应用至少需要 `bitable:app` 或 `base:record:create` 等对应资源权限。

### 3.5 人员维度中心

`person_roster` 增加 `effective_from` / `effective_to`，并新增管理前端。

- 财务日报使用报表日期对人员配置做时态过滤。
- 一条 ASIN 严格只允许归属一个开发和一个运营。
- 未登记或多人匹配的 ASIN 仍保留在“总”指标，但不随机归到人员维度，同时写告警日志。
- 新人员后续直接在前端增加，财务动态行会在当天真实命中数据时自动出现。

## 4. 财务日报自动化

### 4.1 当前有效流程

```text
每日 10:00 / 手动触发
→ FINANCE_DAILY_REPORT_DAILY 生成领星队列任务
→ FinanceDailyReportLingxingTaskHandler
→ AutomationCenterService.trigger("FINANCE_DAILY_REPORT")
→ 校验飞书目标（需投递时）
→ 非破坏刷新目标 Listing（可独立开关）
→ 读取 UK/DE 统一表白名单和店铺 SID
→ 请求目标日 UK/DE 产品表现，currency_code=GBP
→ 只保留各站点白名单 ASIN
→ RDS 日事实表首次成功幂等落库
→ UK/DE 日事实按 ASIN 合并
→ 使用 Listing.open_date 补足产品表现接口缺失的上架日期
→ 加载目标日有效开发/运营配置
→ 计算 16 个指标和 5 类动态维度行
→ 发布质量门禁
→ 飞书 5 张表每批最多 200 条幂等新增/更新
→ AutomationRun 记录数量、错误和全部阶段耗时
```

### 4.2 数据范围和币种

当前生产代码口径：

- 领星产品表现保持 UK+DE 完整请求，不在 API 层只拉 UK。
- 每个站点分别用 `lingxing_product_unified_marketplace` 白名单过滤。
- RDS 保留 `marketplace`，用于范围、审计和后续拆分。
- 金额在领星请求阶段统一为 GBP，不在系统内自行伪造汇率转换。
- 加工层去重键与统一表一致：国家+ASIN。同一 ASIN 在 UK、DE 各计 1。
- 自动化流程：领星日数据拉取 → RDS 日事实落库 → **按当天日事实重算统一表日快照（国家+ASIN）** → 财务指标计算 → 飞书。
- SKU 总量等于该日快照行数。重算时也从 RDS 日事实重建该日快照，不用最新统一表覆盖历史日。
- 飞书仍接收 `marketplace=ALL, currency=GBP` 的合计行。

历史上曾实现过 `PRODUCTION_UK` 严格 UK-only 口径，后续业务确认改为 UK+DE 统一 GBP；旧案例同样是 UK+DE 合并后显示 GBP。因此 UK-only 只是历史方案，不得再作为当前生产验收口径。

### 4.3 日事实、周数据与统一表

- 旧模型仍使用周产品表现，周请求、周加工、统一表和旧模型查询流程保持不变。
- 周数据和相关统一表流程已转为从 RDS 读写，本地库仅保留。
- 日产品表现是财务日报的新增事实源，完整结构化落库，并保留请求中的完整原始行 JSON 用于审计。
- 日事实在入库前已按统一表各站点 ASIN 白名单过滤，不保留团队范围外的大量产品表现行。
- 统一表不再按“开发人硬编码名单”过滤，团队范围以标签/白名单口径为准。

### 4.4 Listing 事实

- 产品表现 `product_create_time` 可能为空，上架日期改从领星 Listing 的 `open_date` 取得。
- 财务完整流程在日事实前刷新目标 Listing。
- 刷新按统一表 ASIN 反查实际 SID，分页请求，仅 upsert 本次返回行。
- 财务任务禁止清空 `lingxing_listing`，历史行必须保留。
- 历史重算必须 `pullFromLingxing=false, refreshListing=false`，不得为了复算重拉 Listing。

### 4.5 财务算法

每个 ASIN 生成 6 个状态指标和 10 个经营指标。

| 指标 | 当前公式/来源 |
|---|---|
| 淘汰 SKU | 标签包含“淘汰”且不包含“待淘汰” |
| 季节性 SKU | 标签包含“季节性” |
| SKU 总数量 | 该日统一表快照的 UK+DE「国家+ASIN」行数（由当天日事实重建）。同一 ASIN 英美各算 1 |
| 动销＞90 天的 SKU | `FBA可售 > 0 AND (当日销量 = 0 OR FBA可售 / 当日销量 > 90)`；代码等价实现为 `fba > 0 && (volume == 0 || fba > 90 * volume)` |
| 未上架 SKU | `FBA=0 AND 不是断货候选 AND 不是淘汰/待淘汰 AND 不是侵权下架` |
| 断货 SKU | `FBA=0 AND (目标日前历史曾出单 OR 当日销量>0)`，再排除淘汰/待淘汰、侵权下架和季节性 |
| 销量/订单量/展示/点击 | 产品表现日事实直接求和 |
| 销售额/广告销售额/广告花费/退款金额 | 领星已统一 GBP 的日事实求和，输出保留 2 位小数 |
| 广告订单量 | 产品表现日事实求和 |
| 可用库存 | FBA 可售数量求和 |

历史曾出单的证据来自目标日前 RDS 周事实和日事实，不再只继承“上一日是否断货”。这修复了“历史出过单、中间恢复库存、当日再次归零且当日无销量”的漏算。

### 4.6 两套计算口径

- `LEGACY_CASE`：只用于财务案例回归。UK+DE 输入按 ASIN 合并，使用案例的 7 个开发和 5 个运营名单，不请求领星、不写 RDS、不投递飞书。
- `PRODUCTION_GBP`：当前生产口径。UK+DE 分站点白名单过滤，按国家+ASIN 去重（与统一表一致），人员按报表日期动态配置，输出 ALL/GBP。

### 4.7 动态输出结构

不再固定 17 行。固定基础行为 4 行：

- 总：1 行。
- 非标品：1 行。
- 上架时间：2 行（`5月以前上架`、`5月及以后上架`）。
- 运营/开发：只输出目标日有效且真实命中数据的人员。

案例 08-01 为 8 行，08-02—08-03 为 9 行，08-04—08-11 为 16 行；生产已按相同的“基础行 + 实际人员”逻辑生成。

### 4.8 阶段化运行参数

| 参数 | 作用 | 默认 |
|---|---|---|
| `pullFromLingxing` | 是否请求领星目标日产品表现 | `true` |
| `refreshListing` | 是否先非破坏刷新 Listing | 跟随 `pullFromLingxing` |
| `persistFacts` | 是否将新拉取事实写入 RDS | 跟随 `pullFromLingxing` |
| `persistStatusSnapshot` | 是否保存本次状态审计快照 | `false`，当前不冻结 |
| `allowRepull` | 已有目标日事实时是否允许显式诊断性重拉 | `false` |
| `publishToFeishu` | 是否投递飞书 | `true` |

常用组合：

- 完整日任务：拉取 + Listing + 落库 + 计算 + 飞书。
- 只拉取验证：`publishToFeishu=false`。
- RDS 纯复算：`pullFromLingxing=false, refreshListing=false, persistFacts=false, publishToFeishu=false`。
- RDS 重新投递：上述基础上将 `publishToFeishu=true`。

目标日已有日事实时，默认在发出领星 HTTP 前拒绝重复拉取。

### 4.9 飞书幂等与发布门禁

- 5 张表：总、运营、开发、非标品、上架时间。
- 业务键：`reportDate|marketplace|dimension|dimensionValue`。
- `automation_record_binding` 保存业务键与飞书 record_id，后续执行批量更新而不是重复新增。
- 飞书每批最多 200 条。
- 发布前强制校验：固定维度数量、人员范围、业务行去重、`ALL/GBP`、上架时间分组与 SKU 总量等。
- 投递可以失败并在运行审计中记录，不得回滚或覆盖已完成的 RDS 日事实。

### 4.10 自动时间

`seed_finance_daily_report_automation.sql` 当前目标状态：

- 每日 `10:00:00`，时区 `Asia/Shanghai`。
- 默认 `reportDate=null`，Job 取昨天。
- 优先级 90，独立槽位组 `FINANCE_REPORT`。
- SQL 中目标 `enabled=1`；生产库实际启停状态必须以领星运行中心或 RDS 当前记录为准。

## 5. 运营物流采购进度自动化

### 5.1 当前流程

```text
手动触发 / OPS_LOGISTICS_DAILY 注册项入队
→ 按 startDate/endDate 同步领星采购计划与采购单
→ 按更新时间范围分页同步实际 SP
→ 从实际 SP 提取 RP 批次并反查完整发货计划
→ 对窗口内已到仓但暂无实际 SP 的采购 SKU 补查发货计划
→ 数据处理中心按 SKU+本地仓+时间和数量做 FIFO 分配
→ operations_logistics_purchase_progress 批量 upsert
→ 飞书采购进度表幂等新增/更新
→ AutomationRun 审计结果和阶段耗时
```

### 5.2 数据范围

- 历史人工测试范围为 2026 年 8 月，请求、处理和飞书投递必须使用同一 `startDate/endDate`。
- 默认处理窗口为当月 1 日至当前；正式补数或验证必须显式传时间窗。
- 领星采购计划时间参数传 `yyyy-MM-dd`，禁止将带时分秒的字符串直接传给该接口。

### 5.3 关联和三状态公式

领星发货计划/实际 SP 不直接返回采购单号，因此使用：

1. `getBatchDetailList` 返回的 `purchase_order_sns + plan_sn + purchase_in_time`。
2. `getInboundShipmentList` 返回的有效 SP、实际发货数量和发货时间。
3. 按 `SKU + 本地仓` 建立采购入库队列，按真实入库时间做 FIFO 数量分配；同一 SP 数量只分配一次。
4. 时间窗外的历史采购批次不参与本次分配，避免历史 SP 不完整时抢占当前数量。

状态：

| 条件 | 输出 |
|---|---|
| 关联任意有效 SP，`shipment_status in (1,2)` 且分配数量 > 0 | 已发货，终态 |
| 无有效 SP，`received_quantity < purchase_quantity` | 待到货 |
| 无有效 SP，`received_quantity >= purchase_quantity` | 待发货 |

一旦分配到有效 SP 数量，当前采购子项立即进入“已发货”，不要求 SP 数量完全覆盖采购量或入库量。到货状态必须按采购子项/SKU 判断，不能使用采购单整体的部分到货状态。

### 5.4 业务键和飞书

- 一张采购单可有多个 SKU，业务唯一键必须使用采购子项稳定 ID，不能只用采购单号或 SKU。
- 飞书主标识“创建批次号”使用 `lingxing_purchase_plan.ppg_sn`。
- `PO...` 是采购执行单，`PP...` 是采购计划号，都不能替代 `PPG...` 创建批次号。
- 投递使用 `automation_record_binding` 幂等绑定；已发货可标记终态，不再常规刷新。
- 曾经人工代写的飞书记录必须回填绑定表，否则应用权限恢复后会重复创建。

### 5.5 排期状态

- `automation_job` 中任务编码为 `OPERATIONS_LOGISTICS_PURCHASE_PROGRESS`，业务 Job 保持 `MANUAL`，避免两套调度。
- 领星注册项为 `OPS_LOGISTICS_DAILY`，SQL 默认目标为每日 02:10、优先级 100。
- 该注册脚本仍以 `enabled=0` 作安全默认；生产实际是否已启用，必须以当前注册表记录为准。

## 14. 不可破坏的生产约束

1. 已存在的产品表现日事实默认不重拉、不覆盖。
2. 历史财务复算必须设置 `pullFromLingxing=false, refreshListing=false`。
3. 财务任务禁止清空 Listing。
4. 当前不冻结财务状态快照，`persistStatusSnapshot` 默认为 `false`。
5. 报表算法以目标日事实为准；上架日期使用当前刷新的 Listing 事实，不从上一日快照或统一表空值补造。
6. 所有 RDS 写入必须通过 `RdsBatchWriteService`。
7. 领星大规模批量任务必须进领星运行中心，不得由新自动化单独新建一套请求节奏。
8. 飞书投递必须幂等，不得因为权限失败而重新拉取领星数据。
9. 一条 ASIN 不得同时归属多个开发或多个运营。
10. 旧案例只用于公式和结构回归；案例输入与最终表格不是同一冻结时点时，禁止通过硬编码常数对齐。
