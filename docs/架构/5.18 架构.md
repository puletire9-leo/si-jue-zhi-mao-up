  竞品 API 在微服务体系中的定位

  卖家精灵 competitor_lookup 本质是数据获取层，在微服务体系里应该这样分层：

  ┌─ 前端 Vue ─────────────────────────────────────┐
  │  输入 ASIN → 展示竞品完整数据                      │
  └────────────────┬───────────────────────────────┘
                   │ HTTP (OpenFeign → Gateway)
  ┌─ sjzm-gateway ─────────────────────────────────┐
  │  路由: /api/v1/competitor/** → sjzm-product     │
  └────────────────┬───────────────────────────────┘
                   │
  ┌─ sjzm-product (8002) ──────────────────────────┐
  │  CompetitorController                           │
  │    ├── POST /lookup       按ASIN批量查竞品       │
  │    ├── POST /search       按关键词/品牌搜索      │
  │    └── GET  /cache/{asin} 读取本地缓存          │
  │                                                 │
  │  CompetitorService                              │
  │    ├── 调用 卖家精灵 API (secret-key 签名)       │
  │    ├── 数据转换 (API model → 内部 model)         │
  │    ├── 写入 selection_products 表做本地缓存      │
  │    └── 合并历史对比数据 (DB数据 + API新鲜数据)   │
  │                                                 │
  │  熔断: Resilience4j (已预配置 selectionService)  │
  │  缓存: Caffeine 本地 + Redis (已配置双层缓存)    │
  │  限流: Guava RateLimiter (保护卖家精灵 API 额度)  │
  └────────────────────────────────────────────────┘

  当前框架需要补充的关键组件

  要从"Spring Boot 骨架"推进到"可部署的微服务"，缺以下核心件：

  第一优先级：必须有才能拆微服务

  ┌───────────────────────────┬───────────────────────────────────────┬──────────┐
  │           组件            │                 作用                  │ 当前状态 │
  ├───────────────────────────┼───────────────────────────────────────┼──────────┤
  │ Nacos (服务发现+配置中心) │ 5 个服务互相发现、动态配置            │ 未引入   │
  ├───────────────────────────┼───────────────────────────────────────┼──────────┤
  │ Spring Cloud Gateway      │ 统一入口、路由分发、鉴权              │ 未引入   │
  ├───────────────────────────┼───────────────────────────────────────┼──────────┤
  │ OpenFeign                 │ 服务间调用（product 调 image 服务等） │ 未引入   │
  └───────────────────────────┴───────────────────────────────────────┴──────────┘

  第二优先级：竞品 API 直接依赖

  ┌────────────────────────────┬────────────────────────────────────┬───────────────────────────┐
  │            组件            │                作用                │         当前状态          │
  ├────────────────────────────┼────────────────────────────────────┼───────────────────────────┤
  │ MyBatis-Plus Entity/Mapper │ 扩展现有表或新建缓存表             │ 已配置框架，缺代码        │
  ├────────────────────────────┼────────────────────────────────────┼───────────────────────────┤
  │ Resilience4j               │ 调用卖家精灵 API 超时/熔断保护     │ 已预配置 selectionService │
  ├────────────────────────────┼────────────────────────────────────┼───────────────────────────┤
  │ Caffeine/Redis 双层缓存    │ 竞品数据缓存（API 调用有额度限制） │ 已配置                    │
  └────────────────────────────┴────────────────────────────────────┴───────────────────────────┘

  竞品 API 特有需求

  - API 额度管理：卖家精灵按调用次数计费，需要 Redis 计数器做频控
  - secret-key 安全存储：不能暴露到前端，由后端代理调用
  - 批量限制：API 最多一次 40 个 ASIN，需要在 Service 层做分批逻辑

  ---
  务实建议：分阶段推进

  考虑到 Java 端业务代码为零，而 Python 端仍在全量运行，我建议：

  阶段 A — 先在 Python 快速验证（1-2天）
  直接在现有 Python 后端新增 sellersprite_service.py 和 /api/v1/competitor/lookup 端点，快速打通数据链路，验证 API 返回数据是否符合预期。Python    
  调用外部 API 已有成熟模式（aiohttp + 腾讯云），代码量小。

  阶段 B — Java 微服务框架补齐（3-5天）
  引入 Spring Cloud Gateway + Nacos + OpenFeign，把 Java 从单体变成真正的微服务体系。这是所有后续 Java 业务开发的前提。

  阶段 C — 竞品模块迁入 Java（2-3天）
  在 sjzm-product 服务中实现 CompetitorController/Service/Mapper，此时熔断/缓存/限流基础设施已就绪，直接复用。

  阶段 D — 前端切换数据源
  Vue 前端从调 Python API 切换到调 Gateway → Java 微服务。
