## 三、核心架构原则

### ⭐ 轻量化板块并行架构

**关键设计理念：**
> "必须是较为轻量的各板块并行关系，而不是一条线，少一块就用不了了"

**这意味着：**

### ❌ 错误的线性依赖架构
```
数据采集 → 初筛 → 决策 → 任务分发 → 执行 → 反馈
   ↓        ↓      ↓        ↓        ↓      ↓
 断一环整个系统停摆
```

### ✅ 正确的并行板块架构
```
        ┌────────────┐
        │  核心数据层  │
        └─────┬──────┘
              │
    ┌─────────┼─────────┬─────────┬─────────┐
    ↓         ↓         ↓         ↓         ↓
┌────────┐┌────────┐┌────────┐┌────────┐┌────────┐
│ 板块1  ││ 板块2  ││ 板块3  ││ 板块4  ││ 板块5  │
│ 运营决策││Listing ││ 美工   ││ 采购   ││ 财务   │
└────────┘└────────┘└────────┘└────────┘└────────┘
   ↕          ↕         ↕         ↕         ↕
 独立工作   独立工作   独立工作   独立工作   独立工作

特点：
- 每个板块可独立使用
- 板块间松耦合
- 某板块故障不影响其他板块
- 数据通过中心层共享
```

## 五、板块设计原则

### 原则1：板块独立可用
每个板块可以独立启动和使用，不强依赖其他板块

**示例：**
- 运营决策板块：即使Listing板块未启动，运营仍可查看候选品、做决策
- Listing板块：即使采购板块未启动，运营仍可撰写Listing
- 财务板块：即使其他板块都停了，财务仍可查看历史数据、生成报表

### 原则2：数据中心共享
所有板块通过统一的数据中心层读写数据，而非板块间直接调用

**架构：**
```
板块A → 数据中心 ← 板块B
板块C → 数据中心 ← 板块D

而非：
板块A → 板块B → 板块C → 板块D (串行依赖)
```

### 原则3：松耦合通信
板块间通过事件/消息通信，而非同步调用

**示例：**
- 运营决策完成 → 发布"SKU已确认"事件
- Listing板块订阅该事件 → 自动创建Listing任务
- 如果Listing板块未启动 → 事件暂存，等板块启动后处理

### 原则4：降级可用
关键功能支持降级模式

**示例：**
- AI写Listing失败 → 降级为手工撰写
- 自动任务分配失败 → 降级为手工分配
- 数据同步失败 → 显示缓存数据 + 提示同步异常

## 六、新系统核心板块

### 板块1：数据汇聚与展示
**定位：** 数据接收中心

**功能：**
- 接收刘淼系统推送的候选品数据
- 接收刘颖豪系统推送的设计稿
- 接收领星ERP推送的销售数据
- 统一数据格式与存储

**独立性：** ⭐⭐⭐⭐⭐
- 纯数据层，不依赖任何业务板块
- 其他板块故障不影响数据接收

---

### 板块2：运营决策工作台（核心）
**定位：** 运营SKU决策的核心界面

**功能：**
- 候选品列表（从数据中心读取）
- 多维度筛选（价格/销量/竞争度/利润预估）
- 竞品对比分析
- 决策操作（确认开品/拒绝/待定）
- 决策记录与追踪

**独立性：** ⭐⭐⭐⭐⭐
- 只依赖数据中心
- 可独立使用，不依赖后续板块

**关键设计：**
- 运营可以只做决策，不管后续流程
- 决策后发布事件，其他板块自行响应
- 如果后续板块未启动，决策结果仍然保存

---

### 板块3：Listing管理
**定位：** Listing撰写与管理

**功能：**
- 接收已决策SKU（订阅"SKU已确认"事件）
- Listing撰写（AI辅助 + 人工编辑）
- 审核流程
- 版本管理

**独立性：** ⭐⭐⭐⭐
- 运营可以直接进入该板块撰写任意SKU的Listing
- 不强制要求SKU必须先经过决策板块
- 支持手工创建Listing任务

---

### 板块4：美工协作
**定位：** 与美工系统对接，任务跟踪

**功能：**
- 创建美工任务（可手工创建）
- 接收刘颖豪系统推送的设计稿
- 设计稿预览与审核
- 与SKU关联

**独立性：** ⭐⭐⭐⭐⭐
- 刘颖豪系统独立运行，不影响本板块
- 本板块可独立管理美工任务
- 设计稿可通过API推送或手工上传

---

### 板块5：采购管理
**定位：** 采购计划与跟踪

**功能：**
- 采购计划创建（自动 + 手工）
- 批次管理
- 供应商管理
- 采购订单
- 入库登记

**独立性：** ⭐⭐⭐⭐⭐
- 可独立使用，不依赖其他业务板块
- 支持手工创建采购计划
- 即使前置流程未完成，仍可独立采购

---

### 板块6：发布与上架
**定位：** 与领星ERP对接

**功能：**
- 发布检查清单
- 领星API对接
- 上架状态跟踪

**独立性：** ⭐⭐⭐⭐
- 可手工触发上架
- 不强制要求完整流程

---

### 板块7：数据分析与财务
**定位：** 销售数据分析与财务报表

**功能：**
- 销售数据同步
- SKU表现分析
- 财务日报生成
- 数据反馈到决策板块

**独立性：** ⭐⭐⭐⭐⭐
- 纯数据分析板块
- 可独立查询历史数据
- 不依赖其他业务板块

## 七、数据流设计

### 外部数据输入

```
刘淼系统 ────→ [数据汇聚层] ←──── 刘颖豪系统
                    ↓
                [数据中心]
                    ↓
    ┌───────────────┼───────────────┐
    ↓               ↓               ↓
[运营决策]      [Listing]       [美工协作]
    ↓               ↓               ↓
    └───────────────┼───────────────┘
                    ↓
              [统一数据湖]
```

### 板块间通信

**方式：事件驱动**
```
运营决策板块：
  - 发布事件："SKU已确认"
  
Listing板块：
  - 订阅 "SKU已确认"
  - 自动创建Listing任务
  - 如果板块未启动，事件暂存
  
美工板块：
  - 订阅 "Listing已完成"
  - 提示需要作图
  - 如果板块未启动，不影响Listing
```

**关键特性：**
- 异步通信
- 消息持久化
- 支持补偿
- 板块启动后自动处理积压消息

## 八、与现有系统的关系

### 与刘淼系统（系统A）
**集成方式：** 单向数据推送

**接口设计：**
```
刘淼系统 → POST /api/v1/candidates/import
```

**数据内容：**
- 候选品基础信息
- 竞品ASIN列表
- 市场数据

**解耦策略：**
- 刘淼系统完全独立，按自己节奏采集
- 新系统只是数据接收方，不反向调用
- 如果新系统故障，刘淼系统不受影响（数据可重推）

---

### 与刘颖豪系统（系统M）
**集成方式：** 单向数据推送

**接口设计：**
```
刘颖豪系统 → POST /api/v1/designs/import
```

**数据内容：**
- SKU关联
- 设计稿链接
- 审核状态

**解耦策略：**
- 刘颖豪系统完全独立，美工在自己系统工作
- 新系统可选择是否使用推送的设计稿
- 也可以在新系统手工上传设计稿

---

### 与赵燎系统（系统B）
**集成方式：** 暂不集成，并行使用

**过渡策略：**
1. **短期（1-3个月）** - 两系统并存
   - 运营可能同时用两个系统
   - 新系统逐步完善功能
   
2. **中期（3-6个月）** - 功能对比
   - 识别重叠功能
   - 评估哪些功能新系统做得更好
   - 运营逐步迁移到新系统
   
3. **长期（6个月+）** - 决策保留或迁移
   - 如果赵燎系统有独特价值功能 → 保留
   - 如果新系统完全覆盖 → 迁移
   - 评估集成成本 vs 独立维护成本

## 九、轻量化实现策略

### 策略1：模块可插拔
**技术实现：**
- 每个板块独立微服务/模块
- 通过配置启用/禁用
- 前端动态加载板块

**示例配置：**
```yaml
modules:
  decision: enabled
  listing: enabled
  design: disabled  # 可选禁用
  purchase: enabled
  finance: disabled  # 初期可不启用
```

### 策略2：功能最小化
**MVP原则：**
- 每个板块只做最核心功能
- 不追求完美，追求可用
- 后续迭代补充

**示例：**
- 运营决策板块：第一版只有"确认"和"拒绝"两个按钮
- Listing板块：第一版只有纯文本编辑器
- 美工板块：第一版只有图片上传

### 策略3：降级友好
**设计原则：**
- 自动化失败 → 降级为手工
- 复杂功能故障 → 降级为简单功能
- 实时同步失败 → 降级为定时批量
