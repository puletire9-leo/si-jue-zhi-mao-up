# 店铺选品链路全流程 & 卡顿节点分析

> 目标：把"店铺选品"（`/reference-products`）从 **MySQL → 后端 → 前端渲染** 的完整链路走通，定位几十万商品下的卡顿节点。
>
> 核心认知：**本项目不大也不复杂，是业务主导系统。唯一的性能矛盾 = 商品数据量大（单站点 ~23 万行）。** 几十万行对 MySQL 不算什么，真正的瓶颈在「数据从 DB 搬到前端、再渲染成卡片」这条链路上的放大效应。

## 二、后端链路（DB → 接口）

### 2.1 关键文件
| 环节 | 位置 |
|------|------|
| 接口入口 | `ShopCollectionController.java:133` `POST /selection-products` |
| 查询实现 | `ShopCollectionService.selectionProducts:649` |
| WHERE 构造 | `buildSelectionProductFilter:701` |
| 批次归一 | `normalizeSelectionBatchScope:848` |
| 表/实体 | `entity/ShopProduct.java`（~65 字段，含 raw_json 大字段）|

### 2.2 后端已做的优化（相当到位）
| 优化 | 效果 |
|------|------|
| **列裁剪** 30 字段 vs 65，排除 raw_json(数十 KB/行) | 降网络+JVM 内存 |
| **count/list 分离 + Caffeine 缓存** | 翻页跳过 COUNT(*) |
| **分类聚合缓存** 60-90min TTL | GROUP BY 不重复打 DB |
| **批次归一** 浏览限 2 批 / 兜底最新 1 批 / 搜索清空 | ★杜绝无条件全表扫 |
| **idx_shop_sel_default** (marketplace, updated_at) | 默认排序 2711ms→2.2ms |
| **idx_shop_sel_metrics** (marketplace, units, price, listing_days) | 筛选+排序 494ms→105ms |
| **次级排序键=主键同方向** | 消除旧 asin ASC 的全量 filesort（曾是首屏 2.7s 主因）|
| **page size 硬上限 200** | 限单次返回行数 |

### 2.3 后端仍存在的瓶颈（次要，非当前卡顿主因）
1. **batch_date IN + 排序 的索引断层**：无 `(marketplace, batch_date, 排序列)` 复合索引，批次过滤后排序可能退化 filesort。
2. **搜索场景无索引**：`LIKE '%关键词%'` 天然无法走索引，清空批次后是全站点扫描——但搜索结果集通常小，可接受。
3. **M01/M03 方法卡 OR 分档**：复杂 OR（30/60/90天+BSR兜底）优化器难选最优索引。
4. **非 units 排序**（price/bsr/listingDate）时 `idx_shop_sel_metrics` 有序性失效，仍需 filesort。

> **结论：后端不是当前卡顿的主战场。** MySQL 查一页 ≤200 行、30 字段，走索引在毫秒级。真正的卡在前端。

### 3.4 前端尚未实现的优化
- ❌ 无成熟虚拟化库（vue-virtual-scroller），自研方案对高度动态变化敏感
- ❌ productList 无 `shallowRef` / `v-memo` 浅响应式（每条商品对象全深度响应式，几百条 × 30 字段 = 大量 reactive 代理）
- ❌ 无分片渲染（requestIdleCallback 分批挂载）
- ❌ 无 Web Worker 卸载数据转换

## 四、卡顿根因诊断结论

**一句话：卡顿不在 MySQL，不在网络，在「前端把每条商品做成全响应式对象 + 每张卡 30 个 computed + 高度动态观测的三重放大」。**

数据量放大链条：
```
DB 200 行(毫秒级)
  → 前端 200 个深响应式对象(reactive 代理开销)
  → sortedProductList/virtualRows 全量 computed 遍历
  → 可视区 ~20 张卡 × 30 computed 实例化
  → ResizeObserver × 可视卡 → 回调风暴 → computed 链重算
```
当 page size 从 60 拉到 200/500，上述每一环线性甚至超线性放大 → 卡死。

**当前已通过「后端批次限流 + page size 上限 200 + 自研虚拟滚动」缓解了最坏情况**，但前端响应式与 computed 的结构性开销仍在。

## 六、本轮实施与实测（2026-07-29）

### 6.1 实际根因（用 CDP profiler 逐一实测锁定，纠正了第三节的部分推测）

| 现象 | profiler 实测根因 | 修复 |
|------|------|------|
| 打开「更多筛选」卡死 **11s** | 抽屉卖家下拉 `filterable` el-select 灌入 limit:1000 卖家，Element Plus 给每 option 建响应式 effect → `vue get` getter 风暴 | **删除卖家下拉**，按店铺名改用顶部搜索框（跨批次全库搜）|
| 200/页滚不动、卡中途 | 虚拟化 padTop 用估算行高撑空间，与实际错配 | VIRT_MIN_COUNT→600 全量渲染 |
| 200/页越滚越卡最后卡死 | 全量 200 张卡的 canvas 被 ResizeObserver 观测，滚动进出视口触发回调风暴 → cardBaseHeights 写入 → computed 链全量重算 | **删除整套高度观测机制**（cardBaseHeights/cardHeightObserver/updateCardBaseHeight/cardWrapperStyle），卡片改 transform:scale + 固定高度 |

### 6.2 卡片缩放方案的踩坑记录（重要）
卡片需缩放显示，CSS 有三条路，实测取舍：
- **transform:scale + absolute**（原方案）：缩放视觉正确，但 absolute 不撑父高 → 必须 JS 测高回填 → ResizeObserver 回调风暴（卡死主因）。
- **zoom**：真实改变占用空间、无需测高，但 **Chrome 对 zoom 元素滚动重绘有严重性能问题**——实测滚动 JS 忙 37s，比原方案更糟。**已否决。**
- **transform:scale + 固定高度**（最终方案）：wrapper 用 `--selection-card-fallback-height`（=BASE_CARD_HEIGHT×scale，实测与真实高度误差仅 3%），canvas absolute + scale。等高卡片选品场景可接受。**零 JS 测量、零 zoom，滚动走浏览器原生。**

> 注：BASE_CARD_HEIGHT=560 是 scale=1 的真实高度（实测 canvas 545），并非早期误判的「2.5 倍虚高」——224 是 560×0.4(默认scale) 缩放后值。

### 6.3 实测结果
| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 打开筛选抽屉 | 11225ms 阻塞 | ~170ms |
| 200/页真实滚轮滚动 JS 忙 | 卡死 | **31ms** |
| 类目聚合（6万数据，冷）| 4.2s + 上千 option | 132 大类；缓存后 4ms |
| 空闲 JS | — | 1ms（无后台占用）|

> 测试陷阱记录：用 `dispatchEvent(new Event('scroll'))` 手动派发滚动会同步触发 onGridScroll 回调，循环派发造成 37s 假象；真实 `mouse.wheel` 滚动才是 31ms。定位性能务必用真实交互测。

### 6.4 仍待办
- **单卡 ~30 个 computed**（N1）：全量渲染下仍是翻页/换数据时的主要开销，未动。可将纯展示派生值下沉到数据规整层。
- 5 秒轮询 `refreshSelectionUsers`（N5）+ `selection-users` 接口 500 错误（独立 bug）。
- 正确的「固定/准确行高虚拟化」后可下调 VIRT_MIN_COUNT，进一步降大列表 DOM 数。
