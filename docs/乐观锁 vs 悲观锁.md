乐观锁 vs 悲观锁
     
  ┌────────┬─────────────────────────────────────────────────────────┬────────────────────────────────────────────────┐
  │        │                         悲观锁                          │                     乐观锁                     │
  ├────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ 思路   │ "肯定有人抢，我先锁住"                                  │ "应该没人抢，我先做再检查"                     │  
  ├────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ 类比   │ 进厕所先锁门，外面的人等着                              │ 进去用，出来发现有人改了门牌号，自己重来       │    ├────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ 实现   │ Java synchronized、DB SELECT FOR UPDATE、Redis 分布式锁 │ 版本号 version，更新时比对 WHERE version = old │
  ├────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤
  │ 适合   │ 冲突频繁、操作代价高                                    │ 冲突少、操作轻量                               │  
  ├────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤  
  │ 不适合 │ 锁等待时间长 → 死锁风险                                 │ 冲突多了 → 大量重试，浪费资源                  │  
  ├────────┼─────────────────────────────────────────────────────────┼────────────────────────────────────────────────┤  
  │ 本例   │ ✅ 一个任务跑几分钟，不值得让另一个等                   │ ❌ API 调一次十几秒，等全做完再检查太晚了      │  
  └────────┴─────────────────────────────────────────────────────────┴────────────────────────────────────────────────┘  

  适用于此场景：悲观锁 — 在 executeApiCalls 开头检查是否已有任务在跑，有就直接拒绝，不排队等。
