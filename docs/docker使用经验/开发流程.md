# 开发流程

## 核心原则

```
宿主机编译 Java → Docker 运行已编译代码 → DevTools 监听 class 变化自动重启
```

Docker 是运行环境，不是编译环境。Java 编译在宿主机完成，Docker 只负责 `mvn spring-boot:run`。

## 当前开发模式事实

`docker-compose.dev.yml` 是开发环境唯一入口。当前默认服务集为：

| 服务 | 容器名 | 宿主机端口 | 容器内端口 |
|------|--------|------------|------------|
| 前端 Vite | `dev-frontend` | 6175 | 5175 |
| Python 后端 | `dev-backend` | 18090 | 8090 |
| Celery Worker | `dev-celery-worker` | 无 | 无 |
| Java product | `java-product` | 18002 | 8002 |
| Java user | `java-user` | 18001 | 8001 |
| MySQL | `dev-mysql` | 13338 | 3306 |
| Redis | `dev-redis` | 6379 | 6379 |

当前 compose 文件没有 `gateway` / `nacos` profile。需要联调网关或注册中心时，先补齐对应 compose 服务定义，再把本文件同步更新。

**Windows 端口注意**：不要再把开发服务映射到 8001/8002/8090/8179/8180 这类宿主端口。当前机器的 Windows excluded port range 覆盖 `7998-8197`，Docker 绑定这些端口会报 `ports are not available` / `bind: An attempt was made to access a socket in a way forbidden by its access permissions`。容器内部仍使用原端口，容器间通信不受影响。

## 服务热更新

| 服务 | 代码位置 | 热更新机制 | 生效时间 | 备注 |
|------|----------|-----------|---------|------|
| 前端 | `frontend/` | Vite 轮询 | 1-2s | WSL2 下必须用 `usePolling: true`，文件事件不穿透 |
| Python 后端 | `backend/app/` | uvicorn --reload | 即时 | |
| Java product | `java-backend/sjzm-product/` | DevTools 重启 | ~15-30s | |
| Java user | `java-backend/sjzm-user/` | DevTools 重启 | ~15-30s | |
| Java gateway | `java-backend/sjzm-gateway/` | DevTools 重启 | ~15-30s | 仅联调网关时启动 |

## 首次启动

```bash
# 1. 本地安装 Java 依赖（只需执行一次）
cd java-backend
mvn install -DskipTests

# 2. 启动默认开发集（更快，不含 gateway / nacos）
docker compose -f docker-compose.dev.yml up -d
```

## 日常开发

### Java 后端

```bash
# 修改 Java 代码后，在宿主机编译
cd java-backend
mvn compile -DskipTests

# DevTools 自动检测 class 变化，自动重启服务，无需手动重启容器
# 查看重启日志：
docker logs -f java-product
```

**关键**: 不要等到报错才编译。改完代码就 `mvn compile`，DevTools 会自动热重启。

### Python 后端

改代码保存即生效，uvicorn `--reload` 自动重载。代码挂载在 `backend/app/`。

### 前端

改代码保存即生效，Vite 轮询模式检测文件变化自动 HMR（1-2 秒延迟）。

**注意**: 修改 `vite.config.js` 后不会热更新，需要重启前端容器：
```bash
docker compose -f docker-compose.dev.yml restart frontend
# 或 docker restart dev-frontend
```

## 数据库与路由门禁（dev/prod 统一）

现在开发和生产共用同一套防线，目标是把“缺表/缺字段/路由漏配”挡在启动或部署前，不再等到页面弹 500 才发现。

| 防线 | 覆盖问题 | 生效位置 |
|------|----------|----------|
| SQL 迁移文件 | 新表、新字段、索引、唯一键 | `java-backend/sql/*.sql` |
| SchemaGuard | `@TableName` 对应表、实体字段对应列 | Java product 启动期 |
| preflight 脚本 | 实体表是否存在、Java API 是否被 Vite/nginx 代理 | `scripts/deploy/prod_preflight_check.ps1` |

### 新增/修改数据库表的固定流程

1. 先写实体/Mapper/Service 代码。
2. 同步新增幂等 SQL 到 `java-backend/sql/`，文件名说明清楚用途，例如 `create_xxx.sql`、`add_xxx_column.sql`。
3. 在开发库执行 SQL，再编译 Java：

```powershell
$env:MYSQL_PASSWORD = "sijue123456"  # 或使用 config/secrets/dev.env 中的值
Get-Content -Raw -Encoding UTF8 java-backend/sql/xxx.sql | docker exec -i -e MYSQL_PWD="$env:MYSQL_PASSWORD" dev-mysql mysql -usijue sijuelishi_dev
cd java-backend
mvn compile -DskipTests
```

4. DevTools 重启后看 `java-product` 日志，必须出现 SchemaGuard 通过或没有 SchemaGuard 错误：

```powershell
docker logs java-product --since 5m | findstr SchemaGuard
```

5. 跑开发预检：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy/prod_preflight_check.ps1 -Env dev
```

开发容器未启动但只想检查路由时：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy/prod_preflight_check.ps1 -Env dev -SkipDatabase
```

### 新增 Java API 的固定流程

1. 新增 `@RequestMapping("/api/v1/xxx")` 后，先确认该 API 属于 Java product、Java user 还是 Python。
2. Java product 新路由必须同步两处：
   - 开发：`frontend/vite.config.js`
   - 生产：`frontend/nginx.conf`
3. 跑预检确认 Vite 和 nginx 都覆盖：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy/prod_preflight_check.ps1 -SkipDatabase
```

4. 如果改了 `vite.config.js`，重启前端容器：

```powershell
docker restart dev-frontend
```

### 生产迁移前固定检查

生产部署前必须先执行 SQL 迁移，再跑完整预检：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy/prod_preflight_check.ps1 -Env prod
```

生产 Java product 启动时 SchemaGuard 默认 `fail-fast=true`。如果 SQL 漏执行，服务会启动失败，这是预期行为：宁可启动期暴露，也不要线上功能运行到一半才 500。

只有临时排障时才允许短时间关闭：

```bash
SCHEMA_GUARD_ENABLED=false
```

关闭后必须恢复，不能作为常规开发或部署手段。

## ⚠️ 路由归属：开发默认看 Vite proxy，联调网关时再同步两处

当前开发环境默认 `VITE_USE_GATEWAY=false`，浏览器请求先走 `frontend/vite.config.js` 的 proxy，直接转发到 Java / Python / selection-agent。

只有在以下场景才需要同时修改网关和前端两处路由表：
- 打开 `VITE_USE_GATEWAY=true` 联调网关
- 验证生产链路
- 维护直接访问 `localhost:9000` 的端点

| 路由表 | 文件 | 生效环境 |
|--------|------|---------|
| 网关路由 | `java-backend/sjzm-gateway/src/main/resources/application.yml` | prod；以及 dev 显式开启 `VITE_USE_GATEWAY=true` 时 |
| Vite dev proxy | `frontend/vite.config.js` 的 `proxy` | **仅 dev server(宿主 6175 → 容器 5175)** |

**关键陷阱**：开发和生产是两张路由表。开发浏览器请求先过 `vite.config.js`，生产请求先过 `frontend/nginx.conf` 再进 gateway。新增 Java Controller 时，只改后端代码不够；Vite/nginx 任意一边漏配，都会出现“直连服务 200、页面 404/500”的错觉。

`/api/v1/product-line/*` 曾经有 Java/Python 分流历史，当前 `vite.config.js` 已把 `/api/v1/product-line` 指向 Java。以后如果重新引入 Python 分流，必须在本文件和 `scripts/deploy/prod_preflight_check.ps1` 同步更新规则。

**踩坑实例**：网关路由从废弃的 `/all-categories` 改成 `/tree`，漏改 `vite.config.js`。`/product-line/tree` 落到兜底 → 转发到 8011(无此端点)→ 404 →"品线树加载失败"。curl 网关 9000 一直 200，命令行测不出来，只有浏览器(6175)复现。

**新增/改动 product-line 端点检查清单**：
- [ ] `vite.config.js`：Java 端点加显式 `proxy` 条目指向 `javaTarget`，**排在 `/api/v1/product-line` 兜底之前**
- [ ] 改完 `vite.config.js` 后 `docker restart dev-frontend`（proxy 不走 HMR）
- [ ] 验证：`curl http://localhost:6175/api/v1/<新端点>`（**走 dev server，不是 9000**）确认非 404
- [ ] 如果 dev 开了 `VITE_USE_GATEWAY=true` 或要走生产链路，再同步网关 `application.yml`

## 容器内命令说明

Java 服务全部使用 `mvn spring-boot:run`（不是 `java -jar`），且启动前不做 Docker 内编译:

```yaml
java-product:
  command: >
    sh -c "cd sjzm-product &&
    mvn spring-boot:run -DskipTests
    -Dspring-boot.run.jvmArguments='-Xms256m -Xmx1024m'
    -Dspring-boot.run.arguments='--server.port=8002'"
```

- 不设 `restart: unless-stopped`（防止 bug 导致反复重启刷爆日志）
- DevTools 依赖已在各模块 `pom.xml` 中配置

## 新增功能模块（即插即用）

新功能页面用模块化方式，**不改 router/sidebar**，放文件夹自动生效：

```
1. 前端：src/modules/xxx/manifest.ts + index.vue
2. 后端：com.sjzm.product.modules.xxx/（Controller/Service/Entity）
3. 后端 Mapper 放 com.sjzm.product.mapper/（被 @MapperScan 覆盖）
```

详见 [frontend/CLAUDE.md](../frontend/CLAUDE.md) 和 [java-backend/CLAUDE.md](../java-backend/CLAUDE.md) 的模块化规则。

## 注意事项

- Docker 仅作运行环境，Java 编译在宿主机完成
- Docker 内不执行 `mvn install`，依赖已在宿主机通过 `mvn install` 安装到 `~/.m2`
- Java 后端依赖 Maven 缓存卷 `java-m2`，首次启动需先在宿主机 `mvn install`
- 容器间通信用 Docker 容器名（如 `backend`、`java-product`、`gateway`）
- Vite 代理配置在 `frontend/vite.config.js`，优先匹配 Java 路由，`^/api` 兜底到 Python（改端点归属时务必同步网关路由，见上文「双路由表」小节）
- 排查运行时 bug（404/500/数据异常）先看 docker 日志 + 逐层直连端点复现，别读源码猜：`docker logs <容器> --since 30m | grep ...`，再逐层 curl `6175`(浏览器/Vite)→`18002/18090`(宿主机直连服务)定位故障层

## Git 分支与 PR 流程

```bash
# 1. 从 master 创建功能分支
git checkout -b feat/xxx master

# 2. 开发并提交
git add <files>
git commit -m "feat: 功能描述"   # 或 fix:/docs:/refactor:

# 3. 提交前生成 CHANGELOG
git-cliff --output CHANGELOG.md

# 4. 推送分支
git push -u origin feat/xxx

# 5. 在 GitHub 创建 PR → 审查 → 合并到 master

# 6. 打 tag 发版（合并后在 master 上）
git checkout master && git pull
git tag v0.4.0
git push --tags
```

### 提交规范（Conventional Commits）

| 前缀 | 用途 | CHANGELOG 分类 |
|------|------|---------------|
| `feat:` | 新功能 | 新增 |
| `fix:` | Bug 修复 | 修复 |
| `docs:` | 文档 | 文档 |
| `refactor:` | 重构 | 重构 |
| `perf:` | 性能优化 | 性能优化 |

### 铁律

- **分支必须先开发测试通过后才能 PR 合并 master**
- 禁止 `temp_*.py`、`test_*.py` 等临时文件提交（已在 `.gitignore` 排除）
- 禁止 `git push --force` 到 master
