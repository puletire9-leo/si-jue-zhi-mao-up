# 精铺测品模型层级与字段口径

> 版本：v1.0  
> 创建日期：2026-07-10  
> 状态：对齐文档，后续按此结构改代码

---

## 0. 核心原则

**最细粒度 = 国家（marketplace）+ 店铺（sid）+ SKU**

同一个 SKU 在不同国家、不同店铺是**完全独立的经营对象**：

- 不同店铺由不同运营操作，首批/补货节奏不同
- FBA 库存按店铺隔离，断货/售罄信号不能跨店合并
- 采购批次按店铺下单，Q1/Q2 天然是店铺级
- cohort 归属取决于"哪个店铺什么时候上架"，不是"这个 SKU 什么时候被创建"

因此：**任何层级的聚合都从这个最细粒度向上卷，不允许反向拆分。**

---

## 1. 四层模型结构

```text
┌──────────────────────────────────────────────────────────────┐
│  Layer 4: 月度 Cohort 盈亏平衡（决策层）                       │
│  粒度: cohort_month + marketplace                              │
│  输出: store-sku R1/R2、净利润、盈亏平衡点、建议首批数量       │
├──────────────────────────────────────────────────────────────┤
│  Layer 3: 国家-SKU 聚合画像（SKU 聚合层）                      │
│  粒度: marketplace + sku                                      │
│  输出: 店铺矩阵、跨店命中、累计销量/库存/批次、SKU 出单率      │
├──────────────────────────────────────────────────────────────┤
│  Layer 2: 店铺-SKU 批次表现（批次聚合层）                      │
│  粒度: marketplace + sid + sku + batch_no                     │
│  输出: Q1/Q2、批次销量/毛利、批次状态、断货间隔                │
├──────────────────────────────────────────────────────────────┤
│  Layer 1: 店铺-SKU 周快照（事实层）                            │
│  粒度: marketplace + sid + sku + week_start                   │
│  输出: 周销量、库存、可售天数、FBA 状态                        │
└──────────────────────────────────────────────────────────────┘
```

数据流方向：**Layer 1 → Layer 2 → Layer 3 → Layer 4**，单向聚合，不反向。

UK 和 DE 是两份独立数据：Layer 3 的聚合主键必须带 `marketplace`，不允许把 GBP 与 EUR 的销量金额、利润或库存混合成一个"全球总数"。

## 2. Layer 1：店铺-SKU 周快照（事实层）

### 2.1 主键

```text
marketplace + sid + sku + week_start
```

### 2.2 字段清单

| 字段 | 来源 | 含义 | 当前状态 |
|---|---|---|---|
| `marketplace` | 周表现表 / 目标池 | 国家站点 UK/DE/FR… | ✅ |
| `sid` | 周表现表 / 目标池 | 领星店铺 ID | ✅ |
| `sku` | 周表现表 / 目标池 | 本地 SKU 编码 | ✅ |
| `store_name` | lingxing_seller | 店铺可读名（如 AM-GC-UK） | ✅ |
| `week_start` / `week_end` | 周表现表 | 观察窗口起止 | ✅ |
| `volume` | 周表现表 | 该窗口销量 | ✅ |
| `gross_profit` | 周表现表 | 该窗口毛利 | ✅ |
| `afn_fulfillable_quantity` | 周表现表 / raw_json 回填 | FBA 可售库存 | ✅ |
| `available_days` | 周表现表 | 可售天数 | ✅ |
| `fba_state` | 计算字段 | IN_STOCK / STOCKOUT / UNKNOWN | ✅ 计算器已实现 |
| `ad_cost` | 周表现表 | 广告花费 | 🟡 字段存在但未进入计算器 |
| `stock_up_num` | raw_json | 在途库存 | 🟡 |
| `operator` | 目标池/本地产品 | 运营人 | ❌ 待补 |

### 2.3 口径规则

- 同一 `marketplace + sid + sku` 的周窗口**不跨店合并**
- 同一窗口内如有多行（不同 summary_field），取 max(afn) 和 sum(volume)
- FBA 状态判断：`afn > 0` → IN_STOCK，`afn = 0` → STOCKOUT，`afn = null` → UNKNOWN
- 首次 FBA 可售周 = 第一个 `fba_state = IN_STOCK` 的周
- 首次出单周 = 第一个 `volume > 0` 的周

## 3. Layer 2：店铺-SKU 批次表现（批次聚合层）

### 3.1 主键

```text
marketplace + sid + sku + batch_no
```

`batch_no` = 按 `order_time` 排序后的序号（1 = 首批，2 = 第一次补货，…）

### 3.2 字段清单

| 字段 | 来源 | 含义 | 当前状态 |
|---|---|---|---|
| `marketplace` | 继承 Layer 1 | 国家 | ✅ |
| `sid` | 采购单 / 兜底 | 店铺 | 🟡 采购 sid 大量为 0 |
| `sku` | 采购单子项 | SKU | ✅ |
| `batch_no` | 计算字段 | 批次序号（首批=1） | ✅ 计算器已实现 |
| `order_sn` | 采购单 | 采购单号 | ✅ |
| `order_time` | 采购单 | 下单时间 | ✅ |
| `quantity_real` | 采购单子项 | **实际采购量 = Q1 或 Q2** | ✅ |
| `quantity_entry` | 采购单子项 | 到货入库量（验证用） | ✅ |
| `batch_start_week` | 计算字段 | 该批次首次观察到 FBA 可售的周 | ✅ |
| `sellout_week` | 计算字段 | 该批次首次观察到库存归 0 的周 | ✅ |
| `stockout_weeks` | 计算字段 | 从售罄到下批恢复可售的周窗口数 | ✅ |
| `batch_volume` | 聚合 Layer 1 | 该批次存续期间销量 | ✅ |
| `batch_gross_profit` | 聚合 Layer 1 | 该批次存续期间毛利 | ✅ |
| `batch_status` | 计算字段 | CURRENT / REPLENISHED / SOLD_OUT / INVENTORY_UNKNOWN | ✅ |
| `next_order_sn` | 关联 | 下一批采购单号 | ✅ |
| `next_order_time` | 关联 | 下一批下单时间 | ✅ |
| `next_active_week` | 计算字段 | 下一批首次恢复可售周 | ✅ |
| `purchase_unit_cost` | 采购单子项 | 采购单价（回本计算用） | ❌ 待接入 |
| `freight_cost` | 头程物流 | 该批次头程费用 | ❌ 待接入 |

### 3.3 口径规则

- **Q1** = batch_no=1 的 `quantity_real`
- **Q2** = batch_no=2 的 `quantity_real`
- 采购单有效性过滤：`status=9`（完成）且 `is_delete != 1`
- 采购 sid=0 时的兜底策略（优先级从高到低）：
  1. 同 SKU 在 `lingxing_local_product` 中只有唯一 sid → 直接归属
  2. 同 SKU + 同 msku 在目标池中有唯一 sid → 归属
  3. 无法确定 → 保留 `PURCHASE_SID_UNASSIGNED` 标记，不强行归属
- 批次时间窗切分：从 `batch_start_week` 到 `下一批 order_time` 前一周
- 最后一个批次的时间窗从 `batch_start_week` 到 `asOfDate`

## 4. Layer 3：国家-SKU 聚合画像（SKU 聚合层）

> **目的**：在 UK 或 DE 的单一国家内，把一个 SKU 分别在多个店铺的独立生命周期汇总为一张 SKU 经营画像。
>
> **边界**：UK 与 DE 互不干扰。`UK + 2550846` 和 `DE + 2550846` 是两个 Layer 3 对象，不生成跨币种的"全球 SKU 总计"。

### 4.1 主键

```text
marketplace + sku
```

Layer 3 的一行不是取代 Layer 1/2，而是保留其明细矩阵：

```text
UK + 2550846
  ├─ sid=4145, AM-GC-UK：一条独立生命周期、自己的 Q1/Q2、自己的库存
  ├─ sid=4200, UK-B：一条独立生命周期、自己的 Q1/Q2、自己的库存
  └─ sid=4301, UK-C：一条独立生命周期、自己的 Q1/Q2、自己的库存
```

### 4.2 现有数据能够直接得到的指标

| 指标 | 聚合规则 | 数据来源 | 口径 / 限制 |
|---|---|---|---|
| 上架店铺数 | `count(distinct sid)`，仅首次 FBA 可售非空 | Layer 1 | ✅ |
| 当前在售店铺数 | 最新观察周 `fba_state=IN_STOCK` 的店铺数 | Layer 1 | ✅ |
| 当前断货店铺数 | 最新观察周 `fba_state=STOCKOUT` 的店铺数 | Layer 1 | ✅ |
| 待观察店铺数 | 尚未出现 FBA 可售周的店铺数 | Layer 1 / SKU 映射 | ✅ |
| 国家内首次上架周 | `min(first_active_week)` | Layer 1 | ✅，精度锁定到周 |
| 国家内最近上架周 | `max(first_active_week)` | Layer 1 | ✅ |
| 累计销量 | `sum(store_sku.total_volume)` | Layer 1 | ✅，销量件数可直接相加 |
| 当前可售库存 | 同一 `as_of_week` 下 `sum(current_afn)` | Layer 1 | ✅；缺快照的店铺必须单列 `INVENTORY_UNKNOWN`，不能按 0 相加 |
| 累计观察毛利 | `sum(store_sku.total_gross_profit)` | Layer 1 | 🟡 同一国家内币种一致，但仍只是观察毛利 |
| 累计广告花费 | `sum(store_sku.ad_cost)` | Layer 1 | 🟡 需先确认广告字段和时间窗去重 |
| 已确认采购批次数 | `count(batch)`，仅店铺已归属批次 | Layer 2 | ✅ |
| 已确认累计采购量 | `sum(quantity_real)`，仅店铺已归属批次 | Layer 2 | ✅ |
| 已确认累计入库量 | `sum(quantity_entry)`，仅店铺已归属批次 | Layer 2 | ✅ |
| 当前补货中店铺数 | 最新批次状态为 `REPLENISHMENT_PENDING` 的店铺数 | Layer 2 | ✅ |
| 断货店铺和断货周数 | 保留每个 store-sku 的断货区间，不将时间错位的断货周简单相加 | Layer 2 | ✅ |
| 店铺 listing / msku 列表 | 一个 sku 下的活跃/历史 msku | §6 映射表 | 🟡 建映射表后可用 |

### 4.3 必须保留的店铺矩阵

Layer 3 的核心输出不是一个总数，而是下表。汇总指标只能作为表头摘要，不能替代明细。

| marketplace | sid | 店铺 | msku | 首次上架周 | Q1 | Q2 | 累计销量 | 当前库存 | 当前状态 | 最近补货下单 | 数据质量 |
|---|---:|---|---|---|---:|---:|---:|---:|---|---|---|
| UK | 4145 | AM-GC-UK | … | 2026-05-01 | 20 | 30 | 37 | 13 | IN_STOCK | 2026-05-26 | — |
| UK | 4200 | UK-B | … | … | … | … | … | … | … | … | … |

这张矩阵保证：同一个 SKU 的不同店铺首批、补货、库存、价格和销量都能被独立观察，任何店铺的失败不会被另一店铺的成功掩盖。

### 4.4 出单率的两个口径

Layer 3 本身表示单个 SKU，不能把它的"出单率"误称为 cohort 的 R1；需要区分：

| 名称 | 公式 | 含义 | 使用场景 |
|---|---|---|---|
| **店铺命中率** | 达到出单阈值的 store-sku 数 / 已上架 store-sku 数 | 该 SKU 在同一国家的跨店可复制程度 | SKU 画像、扩店决策 |
| **SKU 命中标记** | 至少一个 store-sku 达到出单阈值 | 该 SKU 是否至少在一个店铺跑出 | 单 SKU 状态、后续 cohort 的 SKU 级统计 |
| **Layer 4 store-sku R1** | 达到出单阈值的 store-sku 数 / 全部 store-sku 数 | 每一个店铺首批投入都计入分母 | 测品盈亏平衡 |
| **Layer 4 SKU R1** | 至少一个店铺命中的 SKU 数 / SKU 数 | 选品本身的基础命中程度 | 选品质量复盘，不能替代盈亏模型 R1 |

例：一个 SKU 上架 3 个 UK 店，只有 1 店出单：

```text
该 SKU 的店铺命中率 = 1 / 3 = 33.33%
该 SKU 的 SKU 命中标记 = HIT

在 cohort 盈亏模型中，3 个店铺都投入了首批，必须使用 store-sku R1，
不能因为这个 SKU 有一个店成功就当成 100% 成功。
```

### 4.5 当前不能可靠得到的指标

| 指标 | 原因 | 后续条件 |
|---|---|---|
| 跨国家销售额 / 毛利总计 | GBP 与 EUR 不能直接相加 | 继续保持 UK/DE 分开；如未来确需合并，新增明确的汇率日期和结算币种口径 |
| 国家内精确平均售价曲线 | 现有周表现没有确认可用的结构化价格字段 | 接入报价数据，或确认 `sales_amount / volume` 是否可作为周均成交价 |
| 全量采购量 | 采购子项 `sid=0` 时不能确认属于哪个店铺 | 通过 §5 msku 映射归属；无法归属的量单独输出，不混入店铺汇总 |
| 单 SKU 真实 ROI / 回本 | 采购成本、头程、退货、清货损失尚未齐全 | 接入批次成本和 L1/L2 费用口径 |
| 店铺间"卖得最快"的精确天数比较 | 当前固定按周观察 | 使用上架周到售罄周的周数，不伪造天精度 |

## 5. Layer 4：滚动 Cohort 生命周期模型（开发方向验证层）

### 5.1 模型目的与聚合主键

> **目的**：验证一个国家、一个上架批次、一个开发方向内的多 SKU 测品，经过首批、二批及后续补货后，是否形成稳定正利润；并定位何时整体转正、哪些 SKU 支撑利润、哪些 SKU 拖累利润。
>
> 例：`UK + 2026-05 cohort + 欧洲精铺2025`。持续观察该批对象从各自上架后的第 1 周、第 2 周……第 13 周、第 20 周及以后，而不是只在某一天计算一次 R1/R2。

**汇总主键**：

```text
marketplace + cohort_month + target_tag + observation_week
```

必要时在相同主键下增加开发板块筛选维度，例如：`category`、`developer`、`q1_bucket`、`price_band`。

- `marketplace`：UK 和 DE 永远独立计算，币种、成本和利润不混合。
- `cohort_month`：见 §5.8，按 store-sku 首次 FBA 可售周归属。
- `target_tag`：开发方向/目标标签，例如“欧洲精铺2025”。
- `observation_week`：每一个测品对象从自身首次 FBA 可售周起计算的相对观察周，`1, 2, 3, ...`。

同一个 cohort 内不要求自然上架日相同：

```text
UK + 2026-05 cohort
SKU A / UK-A：2026-05-01 首次上架 → 2026-05-01 ~ 05-07 = observation_week 1
SKU B / UK-B：2026-05-08 首次上架 → 2026-05-08 ~ 05-14 = observation_week 1
SKU C / UK-C：2026-05-28 首次上架 → 2026-05-22 ~ 05-31 窗口 = observation_week 1
```

因此，Layer 4 对齐的是**生命周期相对周**，不是把不同成熟阶段的 SKU 强行汇总到同一个自然周。

### 5.2 N 的定义（核心变更）

**旧口径（当前代码）**：N = 目标标签下的 SKU 去重数

**新口径**：N = 目标标签下的 `marketplace + sid + sku` 组合数

> 同一个 SKU 上到 UK-A、UK-B 两个店铺 → N 贡献 2，不是 1。
> 因为两个店铺是两次独立的测品投入、两份独立的首批库存。

### 5.3 字段清单

| 字段 | 来源 | 含义 | 当前状态 |

### 5.4 R1...Rn 阶段漏斗

R1/R2 不是模型的终点。每个阶段都要同时定义“进入条件”“通过条件”“观察窗口”，才能避免仅因下单就算成功。

| 阶段 | 进入条件 | 通过条件（由可配置规则定义） | 主要诊断含义 |
|---|---|---|---|
| R1：首批验证 | 有有效首批 Q1，且已完成首批观察窗口 | 达到首批销量/出单/利润阈值 | 选品、上架、价格、图片和流量是否跑通 |
| R2：二批验证 | R1 通过且已进入第二批 | 第二批达到稳定销量、毛利或周转阈值 | 首批信号是否只是偶然出单 |
| R3：三批持续经营 | R2 通过且已进入第三批 | 第三批仍达到持续销售与利润阈值 | 扩量后是否仍健康 |
| R4...Rn：后续批次 | 前一阶段通过且已进入第 n 批 | 第 n 批仍满足持续经营规则 | 是否具备长期复制价值 |

建议分别保留两种转化率，不能混用：

```text
阶段条件通过率 Rn
= 当前阶段通过的 store-sku 数 / 已进入且已成熟到当前阶段的 store-sku 数

阶段存活率 Sn
= 当前阶段通过的 store-sku 数 / cohort 初始 store-sku 数 N
```

- `Rn` 用于定位某一阶段漏斗是否坍塌。
- `Sn` 用于看最初一批测品最后还留下多少真正可持续的对象。
- 未满观察窗口的对象计入 `observing_count`，不应提前算作失败。

### 5.5 累计利润转正口径

Layer 4 的核心不是某个时点的 R1/R2，而是**这一批何时整体实现正利润，以及正利润是否稳健**。

```text
累计已实现利润(t)
= Σ[第 1 周 ... 第 t 周的已售实现利润]
- 已确认首批淘汰损失
- 已确认二批及后续批次淘汰损失
- 截至第 t 周的固定成本分摊

预测累计利润(t)
= 累计已实现利润(t)
- 当前风险库存 × 单件预计淘汰损失
```

利润输出必须同时提供两个口径：

| 口径 | 用途 | 注意事项 |
|---|---|---|
| `cumulative_realized_profit` | 财务事实复盘 | 只使用已售利润和已发生费用 |
| `projected_cumulative_profit` | 提前开发决策 | 额外扣除当前风险库存的预计损失 |

转正事件定义：

```text
first_positive_observation_week
= 最早满足 cumulative_realized_profit >= 0 的 observation_week

positive_stable
= 连续 K 个观察周 cumulative_realized_profit >= 0
```

`K` 先做配置项，建议默认 3；这样避免某一周偶然正数就被误判为已稳定转正。

### 5.6 SKU 贡献与拖累归因

每个 cohort 内的 `marketplace + sid + sku` 都需要一条贡献记录，汇总表不能只保留总利润。

| 分类 | 建议判定 | 用途 |
|---|---|---|
| `CORE_CONTRIBUTOR` | 累计净利润为正，且利润贡献达到 cohort 贡献阈值 | 找到真正支撑开品方向的 SKU |
| `POSITIVE` | 累计净利润为正，但贡献未达到核心阈值 | 健康但非核心 SKU |
| `OBSERVING` | 未达到对应阶段观察窗口 | 防止过早判定失败 |
| `UNDERPERFORMING` | 已成熟但未达到阶段销量/利润阈值，尚未淘汰 | 识别正在拖累的对象 |
| `FIRST_BATCH_ELIMINATED` | 首批失败且未进入二批 | 归因首批淘汰损失 |
| `POST_REPLENISHMENT_ELIMINATED` | 二批或后续批次失败 | 归因补货后淘汰损失 |
| `INVENTORY_AT_RISK` | 当前库存过高、销量过低，预计无法健康卖完 | 提前识别未来损失 |

Cohort 利润的可解释拆分：

```text
cohort 累计利润
= 核心贡献 SKU 利润
+ 其他正向 SKU 利润
- 首批淘汰 SKU 损失
- 二批及后续淘汰 SKU 损失
- 观察中 SKU 风险库存准备
- 固定成本
```

每个观察周至少输出四个清单：

1. 利润贡献 Top SKU
2. 亏损/拖累 Top SKU
3. 库存风险 Top SKU
4. 尚在观察但值得继续跟踪的 SKU

### 5.7 三张 Layer 4 模型表

| 表 / 输出 | 主键 | 用途 |
|---|---|---|
| `cohort_weekly_summary` | `marketplace + cohort_month + target_tag + observation_week` | R1...Rn、累计利润曲线、转正周、整体状态 |
| `cohort_store_sku_contribution` | `marketplace + cohort_month + target_tag + sid + sku` | 单个对象的阶段状态、利润贡献、拖累/风险归因 |
| `cohort_stage_transition` | `marketplace + cohort_month + target_tag + stage_no` | R1...Rn 和 S1...Sn 阶段漏斗 |

数据流：

```text
Layer 1 周曲线 + Layer 2 采购/补货批次
  → Layer 3 国家内 SKU 画像（确认横向店铺表现）
  → cohort_store_sku_contribution（每个测品对象的纵向阶段与利润）
  → cohort_weekly_summary / cohort_stage_transition
  → 开发板块看板：验证开品方向是否正确
```

### 5.8 Cohort 归属口径

```text
cohort_month = 该 marketplace + sid + sku 在 Layer 1 中首次 fba_state=IN_STOCK 所在的自然月
```

- 不再用 `lingxing_local_product.lx_create_time` 近似
- 一个 SKU 如果 UK-A 在 5 月上架、UK-B 在 7 月上架，分属两个 cohort
- 如果首次 FBA 可售周无法确定（数据缺失），标记为 `COHORT_UNKNOWN`，不参与聚合

### 5.9 观察窗口

| 窗口 | 用途 |
|---|---|
| 30 天 | 判断首批出单信号 |
| 60 天 | 判断补货后销售趋势 |
| 90 天 | cohort 经营口径（主口径） |
| 120 天 | 财务结算口径 |

## 6. SKU 关联映射（sku ↔ msku ↔ fnsku）

> 这是跨层的基础映射，Layer 1~4 都会用到。
>
> **实现前置验证**：现有周同步按 `summary_field=msku` 请求，但同一原始 `price_list` 可能含多条 listing；当前周表构建 SQL 会取 `MAX(seller_sku)`，并在发现多个 sid 时把 sid 置空。因此，不能未经验证就假定每个周表现行已天然对应唯一 msku。
>
> 必须先用历史数据校验：在同一 `marketplace + sid + sku + week_start` 下，是否出现多个活跃 msku。校验结果决定 Layer 1 的最终物理主键：
> - 若不存在：保持业务主键 `marketplace + sid + sku + week_start`，msku 作为关联属性。
> - 若存在：事实表增加 `msku`，成为 `marketplace + sid + sku + msku + week_start`；Layer 1/2 仍可向上聚合回 store-sku，但不能在原始事实层直接抹平。

### 6.1 三个 SKU 概念

| 概念 | 归属 | 唯一性 | 稳定性 |
|---|---|---|---|
| `sku`（local_sku） | 我们内部选品编码 | 全局唯一 | 一旦分配不变 |
| `msku` | 亚马逊卖家 SKU | 同一个店铺内唯一 | 换 listing 会变 |
| `fnsku` | 亚马逊仓储条码 | 每个 msku 一个 | 换 listing 会变，可空 |

**关系方向**：
- 一个 sku → 多个 (marketplace, sid, msku) 组合（每个店铺各一个 msku）
- 一个 msku → 只能指向一个 sku（反向 1:1）
- 一个 msku → 通常一个 fnsku（可空）

例：
```text
sku: 2550846
  ├─ UK-A 店铺 (sid=4145): msku = SIJIE-2550846-UK      fnsku = X001AB2CD3
  ├─ UK-B 店铺 (sid=4200): msku = SIJIE-2550846-UK-V2   fnsku = X001XY9ZW1
  └─ DE-C 店铺 (sid=5001): msku = SIJIE-2550846-DE      fnsku = X002DE1XY5
```

三条 msku 是同一个选品，但在亚马逊后台是三个独立 listing。

### 6.2 映射表设计

**表名建议**：`lingxing_sku_msku_mapping`

**主键**：`(marketplace, sid, msku)` — 因为 msku 在同一店铺内唯一

**字段清单**：

| 字段 | 含义 | 可空 |
|---|---|---|
| `marketplace` | 国家 | 否 |
| `sid` | 领星店铺 ID | 否 |
| `store_name` | 店铺名 | 否 |
| `msku` | 亚马逊卖家 SKU | 否 |
| `sku` | 本地 SKU（映射目标） | 否 |
| `fnsku` | 亚马逊仓储条码 | 是 |
| `asin` | ASIN（辅助） | 是 |
| `active` | 是否还活着 | 否 |
| `first_seen_week` | 首次出现的周（`week_start`） | 否 |
| `last_seen_week` | 最后一次出现的周 | 否 |
| `source` | 数据来源：`PERFORMANCE` / `PURCHASE` / `MANUAL` | 否 |
| `notes` | 备注（异常标记等） | 是 |

**为什么主键不带 sku**：
- msku 在同店内唯一 → `(marketplace, sid, msku)` 已经能唯一定位
- 主键带 sku 会让"同 msku 指向不同 sku"的数据冲突被隐藏在表内并存
- 冲突应该在写入时报错，不应该被主键结构容忍

### 6.3 数据来源与优先级

| 来源 | 覆盖度 | 权威性 |
|---|---|---|
| `lingxing_product_performance` | 有周同步的 store-sku 都有 | 高（周更新，有 msku+sid+marketplace） |
| 采购单子项 + 采购计划 | 采购过的 sku 才有 | 中（可能滞后于新上架） |
| 手动录入 | 边界情况 | 用于修正冲突 |

**建表 SQL 思路**：
```sql
-- 从 performance 抽出所有历史组合
SELECT marketplace, sid, msku, sku, MAX(week_start) AS last_seen, MIN(week_start) AS first_seen
FROM lingxing_product_performance
WHERE marketplace IS NOT NULL AND sid IS NOT NULL AND msku IS NOT NULL AND sku IS NOT NULL
GROUP BY marketplace, sid, msku, sku;
-- 再 UNION 采购单子项的 (sku, msku, sid)
```

主键冲突时（同一 msku 同时映射到两个 sku）→ 抛出 `MSKU_SKU_CONFLICT` 事件，人工介入。

### 6.4 刷新策略

- **触发时机**：跟随目标池每周刷新
- **写入方式**：按 `(marketplace, sid, msku)` upsert
- **`last_seen_week` 更新**：命中就更新为最新周
- **失活规则**：`last_seen_week` 距今超过 30 天 → `active = false`（不删除历史）

### 6.5 对上层的作用

| 使用场景 | 用法 |
|---|---|
| SKU 聚合层"列出该 sku 的所有 store-sku" | `WHERE sku = ? AND active = true` |
| 采购批次归属 store-sku | 采购子项拿到 msku → 查映射 → 得 (marketplace, sid) → 组装 store-sku |
| 前端 SKU 详情页"关联 listing 列表" | 按 sku 列出所有 msku + fnsku + 状态 |
| 数据质量诊断"孤儿 msku" | performance 有 msku 但映射表没有 → 数据同步遗漏 |
| 数据质量诊断"死链 sku" | sku 池有 sku 但映射表无对应 store-sku → 未上架 |

### 6.6 常见边界

| 场景 | 处理 |
|---|---|
| 同店旧 msku 淘汰、新 msku 上架 | 两条记录并存，旧的 `active=false`，新的 `active=true`，共享 sku |
| 同 msku 指向不同 sku（异常） | 主键冲突，报 `MSKU_SKU_CONFLICT`，等人工审 |
| fnsku 缺失 | 允许为空，后续可从其他来源回填 |
| 亚马逊变体（同 parent ASIN 不同 msku） | 视为独立 store-sku，各自映射到各自的 sku |
| msku 在数据里出现但没有对应 sku | 保留记录，`sku` 字段留空 + 打 `SKU_MISSING` 标记，供人工补 |

### 6.7 落地优先级

**P1**（这次一起做）：
- 建表 + 一次性历史数据回灌
- 目标池每周刷新时同步刷新映射表
- 提供按 sku 反查 store-sku 的 API

**P2**（后续）：
- 采购批次归属 store-sku 时接入映射
- SKU 聚合层的"关联 listing 列表"字段使用映射输出
- 数据质量诊断报表

## 9. 术语统一

| 术语 | 定义 | 不允许的混用 |
|---|---|---|
| 测品对象 | 一个 `marketplace + sid + sku` 组合 | 不等于"一个 SKU" |
| 首批（batch_no=1） | 该测品对象的第一个有效采购批次 | 不是"该 SKU 在任何店铺的第一次采购" |
| Q1 | 首批的 `quantity_real` | 不是库存快照的 max 值 |
| 上架时间 | 该测品对象在 Layer 1 中首次 fba_state=IN_STOCK 的周 | 不是 local_product.lx_create_time |
| cohort | 按上架月份归属的一组测品对象 | 不是按采购下单月份 |
| `R1...Rn` | 每个阶段通过数 / 当前阶段已成熟进入数 | 不能只把“发生第 n 次采购”当作通过；必须满足阶段销量、利润或周转规则 |
| `S1...Sn` | 每个阶段通过数 / cohort 初始对象数 N | 反映初始测品最终剩余多少可持续对象 |
| 累计已实现利润 | 已售实现利润 − 已确认淘汰损失 − 已发生固定成本 | 不能把 `gross_profit` 未核实费用口径直接称为真实净利润 |
| 首次转正周 | `cumulative_realized_profit >= 0` 最早成立的 observation_week | 首次为正不等于稳定为正，需同时看连续 K 周规则 |
| 稳定转正 | 连续 K 个观察周累计已实现利润为正 | K 为配置项，默认建议 3 |
| 拖累 SKU | 已成熟未达阶段规则、已淘汰或库存风险高的 store-sku | 不是简单按销量最低判定 |
| 断货 | 某测品对象在某周 fba_state=STOCKOUT 且曾经=IN_STOCK | 不是“该 SKU 在所有店铺都没库存” |

## 10. 最细粒度层可视化：单店铺单 SKU 生命周期看板

> **状态**：设计对齐中，尚未实现
> **粒度**：`marketplace + sid + sku`（不合并跨店铺同 SKU）
> **用途**：一屏看清一个测品对象的完整生命周期：上架时间、首批多少货、卖了多久、还剩多少、价格如何走、销量如何走、什么时候断货、什么时候补货

### 10.1 目标问题

这张图要能一眼回答：

- 这个 SKU 什么时候上架亚马逊
- 首批备了多少货
- 首批卖了多久卖完
- 卖完后到下一批到货中间空了多少天
- 当前还剩多少库存
- 价格曲线怎么走（有没有降价促单）
- 销量曲线怎么走（首单速度、销售峰值、断货导致的销量塌陷）
- 每次补货的时间节点在哪、补了多少

### 10.6 为什么这张图必须走"marketplace + sid + sku"最细粒度

回到 §0 的核心原则，落在这张图上：

- **库存曲线的售罄触底**只在店铺级 FBA 库存才存在。跨店合并 → UK-A 售罄那天 UK-B 有货 → 曲线永远不到 0 → **断货信号消失**
- **补货批次标记**必须落到具体店铺，因为下单是店铺级动作。跨店合并 → 出现"同一天有两个 Q1"的假象
- **价格曲线**也是店铺级：不同店铺可以设不同价，合并 = 平均掉价格策略
- **状态带**跨店混合无法解释：一个店在售一个店断货，合成什么颜色？

## 11. 时间粒度决策（已锁定）

**所有时间序列口径统一按周（`week_start`），不建日快照表。**

依据：
- 目标池约 6000 SKU × UK+DE 两站 ≈ 12000 store-sku，本身就是大数据
- 决策颗粒度是"这周补货 / 这周清货"，周已经够细
- 日粒度只会引入周内噪声（周末 vs 工作日销量不均），不提升决策质量

保留的精细度：
- 采购层 `order_time` 保留精确时间戳（顶部批次时间线可标到日）
- 首单日期可作为辅助信号（看"上架后多久出单"），但不作为上架日期字段

## 12. 后续迭代方向

1. **滚动 cohort 模型表与刷新任务**：按周生成 R1...Rn、利润曲线、转正点和贡献归因

7. **开发板块看板**：展示 cohort 转正曲线、阶段漏斗、贡献/拖累 SKU 与标签/品类/开发人方向差异
8. **跨国同 SKU 对比**：同 SKU 在不同国家的生命周期对比，只做并排对比，不合并币种与利润
