# 精铺测品二批转正模型

## 1. 模型目的

这个模型不是只看首批能不能赚钱，而是判断一批测品 SKU 是否能通过“首批测品 + 命中 SKU 补第二批”的方式实现整体正利润。

核心问题：

> 每月测一批 SKU 时，首批备货会产生测品成本。只有一部分 SKU 能出单并进入第二批。我们要判断这些出单 SKU 的首批利润和第二批利润，能不能覆盖没有跑出来的 SKU 以及二批后仍被淘汰 SKU 的损失。

因此，真正的盈亏平衡不是：

```text
首批卖完是否赚钱
```

而是：

```text
首批出单 SKU + 二批转正 SKU 的利润
- 首批淘汰 SKU 的损失
- 二批后淘汰 SKU 的损失
- 固定成本分摊
>= 0
```

## 2. 业务定义

### 2.1 首批测品

每月上新或运营一批测品 SKU，每个 SKU 先备一个较小的首批库存。

首批的作用主要是：

```text
验证市场需求
验证图片、标题、价格、广告、平台流量是否能跑通
筛选值得继续补货的 SKU
```

首批本身通常很难覆盖完整经营成本，所以不能只用首批利润判断项目是否成立。

### 2.2 二批转正

首批中能够出单、达到补货条件的 SKU，会再备第二批货。

二批的作用是：

```text
放大已经验证过的 SKU
让命中 SKU 贡献主要利润
覆盖未命中 SKU 的淘汰损失
覆盖团队、广告、软件、仓储等固定成本
```

如果二批能正常卖完或达到稳定销售状态，这类 SKU 才算真正转正。

### 2.3 淘汰 SKU

淘汰 SKU 分两类：

```text
首批淘汰 SKU：首批没有跑出来，没有达到补货标准。
二批后淘汰 SKU：首批跑出来并补了第二批，但第二批表现不达标，最终仍要清货或停止补货。
```

这两类 SKU 都需要计入亏损。

## 3. 核心变量

| 变量 | 含义 |
|---|---|
| N | 每月测品 SKU 数 |
| Q1 | 每个 SKU 首批备货数量 |
| Q2 | 进入二批后，每个 SKU 第二批备货数量 |
| R1 | 首批出单率，也就是进入二批的 SKU 比例 |
| R2 | 二批转正率，也就是进入二批后最终跑出来的 SKU 比例 |
| M | 单件真实贡献利润 |
| L1 | 首批淘汰 SKU 的单件淘汰损失 |
| L2 | 二批后淘汰 SKU 的单件淘汰损失 |
| F | 每月固定成本分摊 |

## 4. 单件真实贡献利润 M

单件真实贡献利润不是售价减采购价，而是扣完所有变动成本后的利润。

建议计算口径：

```text
M = 售价
  - 商品采购成本
  - 头程物流
  - 平台佣金
  - 支付手续费
  - 尾程/履约费用
  - 包装耗材
  - 广告成本分摊
  - 退款退货损失分摊
  - 税费
  - 汇损
```

如果不同 SKU 利润差异较大，可以先用平均单件贡献利润，也可以按品类分层计算。

## 5. 单件淘汰损失 L

淘汰损失不是简单的采购成本，而是库存清理后的真实损失。

建议计算口径：

```text
L = 商品采购成本
  + 头程物流
  + 入仓/贴标/处理费
  + 仓储费
  + 清仓折价损失
  + 销毁/移除/退仓费用
  - 清仓回收金额
```

如果首批淘汰和二批淘汰的处理方式不同，应该拆成：

```text
L1 = 首批淘汰单件损失
L2 = 二批淘汰单件损失
```

## 6. 简化版模型

适合在数据还不完整时快速判断。

假设：

```text
1. 进入二批的 SKU 都能把首批和二批卖完
2. 没进入二批的 SKU 按首批库存全部淘汰
3. 暂时不单独计算二批后淘汰
```

净利润公式：

```text
净利润 = N * R1 * (Q1 + Q2) * M
       - N * (1 - R1) * Q1 * L1
       - F
```

盈亏平衡条件：

```text
N * R1 * (Q1 + Q2) * M
- N * (1 - R1) * Q1 * L1
- F
>= 0
```

最低首批出单率：

```text
R1 >= (Q1 * L1 + F / N) / ((Q1 + Q2) * M + Q1 * L1)
```

这个公式用于回答：

```text
在首批备货 Q1、二批备货 Q2、单件利润 M、淘汰损失 L1 固定时，
最低需要多少首批出单率，整批测品才能不亏钱。
```

## 7. 二阶段真实模型

更接近实际经营，需要同时考虑：

```text
首批没有跑出来的 SKU
进入二批但二批后仍被淘汰的 SKU
真正二批转正并持续赚钱的 SKU
```

SKU 数量拆分：

```text
首批进入二批 SKU 数 = N * R1
首批淘汰 SKU 数 = N * (1 - R1)
二批转正 SKU 数 = N * R1 * R2
二批后淘汰 SKU 数 = N * R1 * (1 - R2)
```

净利润公式：

```text
净利润 =
  N * R1 * R2 * (Q1 + Q2) * M
- N * (1 - R1) * Q1 * L1
- N * R1 * (1 - R2) * Q2 * L2
- F
```

盈亏平衡条件：

```text
N * R1 * R2 * (Q1 + Q2) * M
- N * (1 - R1) * Q1 * L1
- N * R1 * (1 - R2) * Q2 * L2
- F
>= 0
```

这个版本更适合最终落地，因为它承认一个现实：

```text
首批出单不等于真正成功。
首批出单只能说明这个 SKU 值得进入二批验证。
二批转正之后，才说明这个 SKU 具备稳定利润价值。
```

## 8. 不同首批备货数量如何影响盈亏平衡

首批备货数量 Q1 会同时放大两件事：

```text
1. 命中 SKU 的首批利润空间
2. 未命中 SKU 的库存淘汰损失
```

所以 Q1 不是越少越好，也不是越多越好。

当 Q1 太少：

```text
单个命中 SKU 的利润太薄
二批还没开始前，首批几乎覆盖不了测品成本
对二批转正率要求更高
```

当 Q1 太多：

```text
未命中 SKU 的淘汰损失快速放大
要求更高的首批出单率
资金占用更大
清货压力更大
```

所以要用模型比较不同 Q1 下的最低出单率，而不是凭感觉决定首批备货数量。

## 10. 后续需要收集的数据

### 10.1 测品规模数据

| 数据 | 用途 |
|---|---|
| 每月实际上架/运营测品 SKU 数 N | 确定整批测品规模 |
| 每个 SKU 首批备货数量 Q1 | 比较不同首批备货方案 |
| 每个 SKU 第二批备货数量 Q2 | 计算二批利润能力 |
| 首批观察周期 | 定义多久内判断是否出单 |
| 二批观察周期 | 定义多久内判断是否转正 |

### 10.2 出单和转正数据

| 数据 | 用途 |
|---|---|
| 首批有出单 SKU 数 | 计算首批出单率 R1 |
| 达到补货标准 SKU 数 | 更准确地计算进入二批比例 |
| 进入二批 SKU 数 | 验证实际 R1 |
| 二批卖完 SKU 数 | 计算二批转正率 R2 |
| 二批后仍被淘汰 SKU 数 | 计算二批淘汰损失 |
| 每个 SKU 首批销量 | 判断首批是否真的跑出来 |
| 每个 SKU 二批销量 | 判断二批是否转正 |

建议先明确“出单 SKU”的标准，例如：

```text
标准 A：首批有 1 单就算出单
标准 B：首批卖出达到 30% 才算出单
标准 C：首批在 30 天内卖完才算进入二批
标准 D：首批日均销量达到指定阈值才算进入二批
```

不同标准会让 R1 差异很大，必须统一口径。

| 平台佣金 | 计算真实贡献利润 |
| 支付手续费 | 计算真实贡献利润 |
| 尾程/履约费用 | 计算真实贡献利润 |
| 包装耗材成本 | 计算真实贡献利润 |
| 广告花费 | 计算广告成本分摊 |
| 退款退货率 | 计算退款损失 |
| 折扣/优惠券成本 | 计算真实成交利润 |
| 税费 | 计算真实利润 |
| 汇率和汇损 | 跨境业务必须计入 |

### 10.4 淘汰损失数据

| 数据 | 用途 |
|---|---|
| 首批淘汰 SKU 剩余库存 | 计算首批淘汰件数 |
| 二批淘汰 SKU 剩余库存 | 计算二批淘汰件数 |
| 清仓售价 | 计算回收金额 |
| 清仓周期 | 判断资金占用和仓储成本 |
| 仓储费 | 计算淘汰损失 |
| 移除/退仓/销毁费用 | 计算淘汰损失 |
| 清仓平台费用 | 计算真实回收金额 |
| 最终回收金额 | 计算净损失 |

### 10.5 固定成本数据

| 数据 | 用途 |
|---|---|
| 团队人工成本 | 计算每月固定成本 F |
| 软件订阅成本 | 计算每月固定成本 F |
| 办公/管理成本 | 计算每月固定成本 F |
| 拍摄/修图/内容成本 | 可按 SKU 或月份分摊 |
| 样品/测试成本 | 可按 SKU 分摊 |
| 店铺固定费用 | 计算每月固定成本 F |

固定成本可以先按月分摊：

```text
F = 当月团队成本 + 软件成本 + 店铺固定成本 + 内容成本 + 其他固定费用
```

也可以折算到单个 SKU：

```text
单 SKU 固定成本 = F / N
```

## 11. 最终要看的几个指标

| 指标 | 含义 |
|---|---|
| 最低首批出单率 R1 | 首批至少要跑出多少 SKU，整批测品才可能不亏 |
| 最低二批转正率 R2 | 进入二批后至少要有多少 SKU 真正跑出来 |
| 单 SKU 盈亏平衡利润 | 每个成功 SKU 需要贡献多少利润 |
| 最大可承受淘汰率 | 最多可以淘汰多少 SKU 仍不亏 |
| 不同 Q1 下的净利润 | 比较首批备货 10、15、20、25、30 件哪个更合理 |
| 资金占用峰值 | 首批和二批合计需要占用多少现金 |

## 12. 分散补货/滚动补货更新计划

实际经营中，二批补货通常不是整批 SKU 同时发生，而是某个 SKU 卖完或接近卖完后单独补货。

因此，模型需要从：

```text
整批 SKU 统一首批 + 统一二批
```

升级为：

```text
单 SKU 生命周期记录 + 月度 cohort 汇总
```

### 12.1 为什么不能只按整批算

如果所有 SKU 都等到同一天统一补二批，公式会很简单，但这不符合真实运营。

真实情况通常是：

```text
SKU A 第 7 天卖完，马上补货
SKU B 第 15 天卖完，单独补货
SKU C 第 30 天才卖完，再决定是否补货
SKU D 一直不动，进入清货/淘汰
```

所以补货是分散的，利润也是分散产生的。

但经营复盘仍然需要一个统一口径，因此不能只看单个 SKU，也不能只看某一天补了几件货。

推荐口径：

```text
补货动作按 SKU 单独记录
经营结果按上架月份汇总
```

### 12.2 单 SKU 生命周期

每个 SKU 单独记录完整生命周期。

建议字段：

| 字段 | 含义 |
|---|---|
| SKU | 商品编码 |
| 上架日期 | SKU 开始销售的日期 |
| 首批入库日期 | 首批库存可售日期 |
| 首批数量 Q1 | 首批备货数量 |
| 首单日期 | 第一次出单日期 |
| 首批卖完日期 | 首批库存售罄日期 |
| 首批售罄天数 | 从可售到首批卖完用了几天 |
| 是否触发补货 | 是否进入下一批 |
| 第 2 批补货日期 | 下单补货日期 |
| 第 2 批到货日期 | 二批可售日期 |
| 第 2 批数量 Q2 | 二批补货数量 |
| 第 2 批卖完日期 | 二批是否卖完以及何时卖完 |
| 当前剩余库存 | 当前未售出的库存 |
| 当前累计销量 | 截止统计日总销量 |
| 当前累计利润 | 已实现利润 |
| 当前库存风险 | 如果现在淘汰，预计损失多少 |
| 当前状态 | 未出单/首批验证/已补货/转正/淘汰 |

### 12.3 时间窗口

分散补货后，需要用统一的观察周期来比较不同 SKU。

建议观察窗口：

| 时间窗口 | 用途 |
|---|---|
| 7 天 | 判断是否有快速出单信号 |
| 14 天 | 判断是否有初步市场反馈 |
| 30 天 | 判断首批是否值得补货 |
| 60 天 | 判断补货后是否继续放量 |
| 90 天 | 判断本月测品 cohort 是否整体转正 |
| 120 天 | 做最终清货和淘汰结算 |

推荐主口径：

```text
按上架月份作为 cohort，观察 90 天。
```

例如：

```text
7 月上架 120 个 SKU
不管它们分别在第几天补货
都归为 7 月测品 cohort
然后统计这 120 个 SKU 在上架后 90 天内的累计表现
```

### 12.4 滚动补货触发规则

补货不建议只等卖完再补，因为可能造成断货。

推荐用可售天数触发补货：

```text
可售天数 = 当前可售库存 / 最近 N 天日均销量
```

触发条件：

```text
如果 可售天数 <= 补货到货周期 + 安全库存天数
则触发补货
```

示例：

```text
当前库存 = 3 件
最近 7 天日均销量 = 1 件
可售天数 = 3 天

如果补货到货周期 = 15 天
安全库存天数 = 3 天
则补货触发线 = 18 天

因为 3 天 <= 18 天
所以应该立即补货，甚至已经偏晚。
```

### 12.5 分散补货下的净利润计算

分散补货后，不再强行假设只有固定 Q1 和 Q2。

应改为按每个 SKU 的实际累计批次计算：

```text
SKU 累计净利润 =
  SKU 累计已售件数 * 单件贡献利润
- SKU 当前淘汰风险库存 * 单件淘汰损失
- SKU 分摊固定成本
```

整个月度 cohort 的净利润：

```text
cohort 净利润 =
  所有 SKU 累计已售件数 * 单件贡献利润
- 所有 SKU 当前风险库存 * 单件淘汰损失
- 该 cohort 分摊固定成本
```

如果要拆得更细：

```text
cohort 净利润 =
  首批已售利润
+ 补货批次已售利润
- 首批淘汰损失
- 补货后淘汰损失
- 固定成本
```

### 12.6 分散补货后的盈亏平衡口径

分散补货后，盈亏平衡不再只问：

```text
首批 + 二批能不能赚钱
```

而是问：

```text
在 90 天或 120 天内，
这一批上架 SKU 的累计销售利润，
能不能覆盖所有未跑出来 SKU 的淘汰损失和固定成本。
```

建议保留两个口径：

| 口径 | 用途 |
|---|---|
| 90 天经营口径 | 判断这批测品是否值得继续放大 |
| 120 天结算口径 | 判断这批测品最终是否真实盈利 |

90 天口径更适合运营决策，120 天口径更适合财务复盘。

### 12.7 需要新增收集的数据

为了支持滚动补货，需要新增这些数据：

| 数据 | 用途 |
|---|---|
| SKU 上架日期 | 归属到哪个月度 cohort |
| 每批次补货日期 | 记录补货节奏 |
| 每批次到货日期 | 判断断货和补货周期 |
| 每批次补货数量 | 计算实际库存投入 |
| 每日销量 | 计算日均销量和可售天数 |
| 每日库存 | 判断何时触发补货 |
| 首单日期 | 计算首单速度 |
| 首批卖完日期 | 判断首批验证速度 |
| 每次断货天数 | 判断损失的销售机会 |
| 每个 SKU 当前状态 | 判断转正、观察、淘汰 |

### 12.8 后续落地步骤

第一步，先建立单 SKU 生命周期表：

```text
每个 SKU 一行，记录上架、首批、补货、销量、库存、状态。
```

第二步，建立补货流水表：

```text
一个 SKU 可以有多行补货记录，每一次补货单独记录数量、日期、成本、到货时间。
```

第三步，建立月度 cohort 汇总表：

```text
按上架月份汇总所有 SKU 的 30 天、60 天、90 天、120 天表现。
```

第四步，再计算不同首批备货数量下的盈亏平衡：

```text
比较 Q1 = 10、15、20、25、30 时，
在真实滚动补货规则下，
各自需要多少首批出单率、补货成功率和二批转正率。
```

第五步，形成补货决策规则：

```text
什么时候补
补多少
什么时候停止补
什么时候清货淘汰
```

## 13. 经营结论

这个模型的核心不是追求所有 SKU 都赚钱，而是判断：

```text
少数跑出来的 SKU，能不能覆盖多数没跑出来 SKU 的成本。
```

精铺测品的关键不是首批利润，而是：

```text
首批负责筛选
二批负责验证
转正 SKU 负责覆盖淘汰 SKU
```

因此，真正需要优化的是：

```text
1. 降低首批备货 Q1，减少测错成本
2. 提高首批出单率 R1，减少首批淘汰
3. 提高二批转正率 R2，避免二次误判
4. 提高单件贡献利润 M
5. 降低淘汰损失 L1 和 L2
6. 控制固定成本 F
```

最终目标：

```text
找到不同首批备货数量下，最低需要多少首批出单率和二批转正率，
才能让“首批测品 + 二批转正”整体实现正利润。
```

## 14. 当前代码落地 v1（领星数据）

后端已新增领星侧模型分析接口：

```http
POST /api/v1/modules/lingxing/sampling-model/analyze
```

第一版只读取已落库数据，不再触发领星外部接口：

| 数据表 | 当前用途 |
|---|---|
| `lingxing_local_product` | SKU 池、创建月份 cohort、产品标签、采购成本 |
| `lingxing_product_performance` | 时间窗销量、销售额、结算毛利、广告费 |
| `lingxing_profit_asin` | 逐日销量、销售额、成本、毛利，适合后续严肃财务复盘 |

当前可实算：

```text
N  = 目标标签 SKU 数
R1 = 销量 >= hitUnitsThreshold 的 SKU 数 / N
R2 = 销量 >= turnoverUnitsThreshold 且未淘汰 SKU 数 / R1 命中 SKU 数
M  = 若未手动传 unitMargin，则暂用 报表毛利 / 销量 近似
```

当前仍需作为参数输入：

```text
Q1 = 首批备货数量
Q2 = 二批备货数量
L1 = 首批淘汰单件损失
L2 = 二批淘汰单件损失
F  = 固定成本分摊
```

示例请求：

```json
{
  "source": "performance",
  "startDate": "2026-07-01",
  "endDate": "2026-07-07",
  "cohortMonth": "2026-07",
  "targetTag": "欧洲精铺2025",
  "hitUnitsThreshold": 1,
  "turnoverUnitsThreshold": 30,
  "q1": 15,
  "q2": 45,
  "unitMargin": 3.5,
  "firstBatchLoss": 2.2,
  "secondBatchLoss": 2.8,
  "fixedCost": 12000
}
```

重要口径：

```text
source=performance：数据更全，但如果同步时间窗重叠，可能重复计入。
source=profit：逐日数据更干净，适合财务复盘，但需要先把利润统计全量同步补齐。
cohortMonth：当前用领星本地产品创建时间近似，上架日期还没有结构化。
R2：当前用销量阈值 + 淘汰标签近似，后续应升级为补货流水 + 到货日期 + 90/120 天观察窗口。
```

下一轮需要补齐的数据结构：

```text
1. 单 SKU 生命周期表：上架日期、首批入库日期、首单日期、首批售罄日期、当前状态。
2. 补货流水表：每次补货日期、到货日期、数量、成本、批次类型。
3. 每日库存/销量快照：用于计算可售天数、断货、库存风险。
4. 月度 cohort 汇总表：固化 30/60/90/120 天表现，避免每次临时扫 raw_json。
```

### 14.1 SKU 池 + 每日 SKU 快照采集口径

后续模型的数据采集拆成两段：先稳定得到目标 SKU 集合，再对集合内每个 SKU 做每日经营表现快照。

#### 第一部分：每周更新 SKU 池

目标是得到 UK + DE 两国店铺中，属于 6 个目标 listing/产品标签的全部 SKU。

6 个目标标签：

```text
绿标
欧洲精铺2025非标品
欧洲精铺2025季节性断货
欧洲精铺2025待淘汰
欧洲精铺2025淘汰
欧洲精铺2025
```

推荐口径：

```text
店铺范围：从 lingxing_seller 中确认 UK / DE 店铺 sid。
主数据来源：lingxing_local_product / productList。
标签来源：先验证 raw_json.global_tags 是否覆盖 6 个目标标签；若覆盖，用它建 SKU 池。
兜底来源：若 global_tags 不稳定，则用领星后台按标签导出 + product_performance_actual 导入结果建 SKU 池。
产品表现：只负责每日经营数据，不作为稳定标签来源。
更新频率：每周全量或增量刷新一次 SKU 池。
```

执行步骤：

```text
1. 同步 UK + DE 店铺的本地产品 productList。
2. 抽样核对 raw_json.global_tags 是否能覆盖 6 个目标标签。
3. 若能覆盖，从 global_tags 中筛选目标 SKU；若不能覆盖，用 product_performance_actual 的 listing_tags 兜底。
4. 保存 SKU 池，记录 SKU、sid、国家、标签、标签来源、状态、开发人、成本、创建时间、更新时间等主数据。
5. 对比上周 SKU 池，识别新增、移除、标签变化、状态变化。
6. 新增 SKU 进入后续每日快照任务；移除 SKU 保留历史，不删除历史表现。
```

注意：产品表现接口不能直接按这 6 个标签过滤请求。官方文档里有 `tag_set` 返回字段，但当前实测同步表没有结构化 `listing_tags`，不能把它当稳定筛选条件。因此正确流程是先在本地形成 SKU 池，再按 SKU 查询每日表现。

#### 第二部分：每天更新 SKU 日表现

领星产品表现接口支持按 SKU 搜索某一天的数据，因此可以围绕目标 SKU 池做每日快照。

推荐口径：

```text
目标池：SKU 池中的约 6000 个 SKU
历史回补：2026-01-01 到 2026-07-09
日常更新：每天更新昨天或当天的单日表现
时间窗：start_date = end_date = 目标日期
汇总维度：summary_field = sku
搜索字段：search_field = local_sku
批量限制：search_value 单次最多 50 个 SKU
执行批次：6000 个 SKU 约 120 批/天/国家
```

示例请求：

```json
{
  "offset": 0,
  "length": 1000,
  "sort_field": "volume",
  "sort_type": "desc",
  "sid": [1, 109],
  "start_date": "2026-07-08",
  "end_date": "2026-07-08",
  "summary_field": "sku",
  "search_field": "local_sku",
  "search_value": ["SKU001", "SKU002"]
}
```

执行步骤：

```text
1. 从 SKU 池读取目标 SKU 清单。
2. 每 50 个 SKU 分一组。
3. UK 店铺集合先跑完，再跑 DE 店铺集合，避免抢同一个产品表现接口令牌桶。
4. 每次请求只查一天：start_date = end_date = 目标日期。
5. 将每日结果落库为独立 SKU 日快照，不复用当前 lingxing_product_performance 月更时间窗表。
6. 以 date + marketplace + sku + sid_scope + currency 做幂等键，允许重跑覆盖同一天同一批。
7. 失败批次记录任务游标，支持断点续跑。
```

这张每日快照后续应独立成表，不直接复用当前 `lingxing_product_performance` 的月更时间窗表，避免不同窗口重复覆盖和口径混淆。

每日快照主要服务：

```text
1. 单 SKU 首单速度、连续出单、日均销量
2. 可售库存、可售天数、断货判断
3. 30/60/90/120 天 cohort 复盘
4. R1/R2 从粗略阈值升级为生命周期判断
5. 补货触发和淘汰预警
```

本地产品详情接口可按 SKU 精确补充主数据，但它不是每日经营数据：

```text
productInfo / batchGetProductInfo：成本、规格、供应商、标签、开发人、状态、图片、物流关系
productPerformance/asinList：销量、销售额、毛利、广告、库存、可售天数等每日表现
```

可信性和注意点：

```text
1. SKU 池可信性取决于领星后台标签维护是否及时，需要每周记录标签变化。
2. productList 的 global_tags 和产品表现官方文档里的 tag_set 可能不是同一层级标签，不能混用为同一个标签字段。
3. 当前 lingxing_product_performance 没有 listing_tags 结构化列，标签筛选不能直接读这张表。
4. 如果 global_tags 不能稳定覆盖目标标签，SKU 池必须先用 product_performance_actual 这条后台导出链路兜底。
5. 产品表现按天查询是双闭区间 start_date=end_date，但广告、结算、退货、退款可能延迟回写，建议 T+1 首次拉取，T+3/T+7 再校准。
6. 2026-01-01 到 2026-07-09 共 190 天，6000 SKU 约 120 批/天/国家，UK+DE 约 45600 次请求；如果按多店铺 10 秒间隔执行，理论下限约 5.3 天。
7. SKU 可能跨店铺、跨 MSKU 或跨国家复用，日快照不能只用 sku 做唯一键。
8. 日快照必须幂等，重跑同一天同一批只能覆盖或 upsert，不能重复累计。
9. 当天数据适合看趋势，不适合直接做最终利润判定；严肃复盘应使用已过回写窗口的数据。
```

## 19. 2026-07-09 备货量精确口径修正

首批备货数量 Q1 不能估算，必须来自精确的备货/入仓/库存批次字段。

当前已落库的领星产品表现数据能看到库存快照，但这不是首批备货量：

```text
volume = 销量，可以用于算出单量
afn_fulfillable_quantity = FBA 可售库存快照，可以用于判断是否在售
available_inventory.available_inventory = 可用库存总计快照
stock_up_num = 实际在途快照
reserved_customerorders / reserved_fc_processing / reserved_fc_transfers = 预留/调仓快照
```

这些字段只能回答：某个时间窗查询时，这个 SKU 当前还有多少可售、在途、预留库存。它们不能直接回答：这个 SKU 首批到底备了多少件。

原因很简单：库存快照已经被销量、预留、调仓、入库、补货共同影响。比如 5 月产品表现数据中，`afn_fulfillable_quantity` 的最大值超过 300，而我们的精铺首批备货通常不可能超过 50；这说明该字段不是 Q1，而是当时库存状态。

因此模型里的 Q1 必须按下面优先级取数：

```text
1. 领星采购单/备货单/入仓单/发货批次接口中的 SKU 数量
2. 仓库库存流水或 FBA 入仓 shipment 明细中的 SKU 数量
3. 如果只有每日库存快照，最多只能做库存轨迹分析，不能当作精确 Q1
```

现有 4/5/6 月周数据仍然有价值，但用途限定为：

```text
上架周 = 第一次出现 afn_fulfillable_quantity > 0 的周
在售 SKU = 当周 afn_fulfillable_quantity > 0 的 SKU
出单量 = volume
断货/售罄信号 = 曾经 afn_fulfillable_quantity > 0，之后变成 0
```

正式计算“备货量和出单率关系”前，必须先补齐精确备货数量来源；否则只允许产出库存表现诊断，不允许产出 Q1 盈亏结论。

## 20. 2026-07-10 采购接口补齐后的 Q1/Q2 取数口径

新增领星采购接口文档后，备货量精确来源已经有明确方向：

```text
采购计划列表：POST /erp/sc/routing/data/local_inventory/getPurchasePlans
采购单列表：POST /erp/sc/routing/data/local_inventory/purchaseOrderList
```

这两个接口的作用不同，不能混用：

| 来源 | 字段 | 含义 | 模型用途 |
|------|------|------|----------|
| 采购计划 | `quantity_plan` | 计划采购量 | 计划口径、采购前预测、和采购单对账 |
| 采购计划 | `plan_sn` / `ppg_sn` | 采购计划编号 / 批次号 | 连接采购单、识别采购批次 |
| 采购计划 | `sku` / `sid` / `wid` | SKU、店铺、仓库 | 和产品表现、店铺、仓库关联 |
| 采购单 | `item_list.quantity_real` | 实际采购量 | 备货量 Q1/Q2 的主口径 |
| 采购单 | `item_list.quantity_entry` | 到货入库量 | 已确认入库口径，用于判断真实可用批次数量 |
| 采购单 | `item_list.quantity_receive` | 待到货量 | 未完成到货，不应直接计入已入库备货 |
| 采购单 | `item_list.plan_sn` / `relation_purchase_plan` | 关联采购计划 | 从计划追溯到采购单 |
| 采购单 | `order_time` / `expect_arrive_time` / `update_time` | 下单、预计到货、更新时间 | 排序批次和判断生命周期阶段 |
| 采购单 | `status` / `status_shipped` | 采购单状态 / 到货状态 | 过滤有效采购单 |

正式模型建议口径：

```text
Q1 = 该 SKU 在该店铺/国家维度下，首个有效采购批次的 item_list.quantity_real
Q1_entry = 同一批次 item_list.quantity_entry，用于验证是否实际入库
Q2 = Q1 后的下一次有效采购批次 item_list.quantity_real
```

有效采购单过滤建议：

```text
status = 9 表示完成，优先作为已完成采购单
status_shipped = 3 表示全部到货
status_shipped = 2 表示部分到货，只能按 quantity_entry 计算已到货部分
status IN (-1, 124) 作废，不进入模型
item_list.is_delete = 1 的采购单子项不进入模型
```

计划量和实际量的使用边界：

```text
quantity_plan 不是最终备货量，只能代表计划。
quantity_real 是实际采购量，适合作为 Q1/Q2 备货决策数量。
quantity_entry 是实际到货入库量，适合做已入库验证和库存链路校验。
```

和产品表现周数据的连接方式：

```text
采购批次层：sku + sid + wid + plan_sn/order_sn
经营表现层：marketplace + sid + sku + week_start/week_end
上架周：第一次 afn_fulfillable_quantity > 0 的周
首批卖完/断货：曾经 afn_fulfillable_quantity > 0 后变成 0
出单量：volume
```

注意：采购单解决的是“备了多少”的精确来源；FBA 可售库存仍然负责判断“什么时候真正上架、什么时候断货”。两类数据必须合并使用，不能互相替代。
