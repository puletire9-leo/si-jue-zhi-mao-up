# 全部选品筛选系统现状审计（2026-06-30）

> 目标：基于当前真实代码梳理 `AllSelection` 全链路筛选逻辑，找出“筛选失效 / 交叉覆盖 / 口径不一致 / 隐式默认值”问题，并给出修复建议。
>
> 范围：`frontend/src/views/AllSelection/index.vue`、`SelectionQueryForm`、`RangeFilterPanel`、`FilterPresetSelector`、`frontend/src/api/competitor.ts`、`java-backend/sjzm-product` 的 `CompetitorController` / `CompetitorService` / `CompetitorProductMapper`。

---

## 1. 当前筛选架构总览

当前“全部选品”并不是单一筛选入口，而是 4 套来源共同作用：

1. `SelectionQueryForm`
   - 负责 ASIN / 标题 / 店铺名 / 大类等搜索字段。
   - 通过 `@search` 把 `SelectionQueryParams` 交给 `AllSelection.handleSearch(...)`。

2. `unified-filter-bar`
   - 常驻在列表上方。
   - 负责站点、主栏大类、更多筛选按钮、已选标签。
   - 状态落在 `activeFilters`。

3. `FilterDrawer + RangeFilterPanel`
   - 抽屉里维护 `draftFilters` 草稿。
   - 点“确认筛选”后写回 `activeFilters`。
   - 其中范围项（价格、销量、上架天数、批次、变体数等）由 `RangeFilterPanel` 承载。

4. 方法卡 / 预设
   - M01/M02 方法卡会走独立接口分支。
   - 预设会同时回填 `queryFormRef` 和 `activeFilters`，但保存与回放字段并不完全一致。

真正发请求前的汇总器只有一个：`AllSelection.loadProducts()`。

## 2. 实际请求链路

### 2.1 普通列表（非方法卡、非郑总店铺）

前端最终请求 `/api/v1/competitor/products`，流程是：

1. 先从 `SelectionQueryForm.getQueryParams()` 取表单字段。
2. 再由 `buildApiParams()` 只映射一部分字段。
3. 然后手工把 `activeFilters.range` 里的区间筛选拼进 `competitorParams`。
4. 若没有显式选择 `createdWeeks / month / weekTag / createdAtStart`，前端会自动补“最新周批次”。

- `buildApiParams()` 只从 `queryParams` 读取 `asin/productTitle/storeName/sellerSelect/category/grade/weekTag/listingDateStart/listingDateEnd`
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1684)
- 范围筛选手工追加 `unitsMin/unitsMax/listingDaysMin/listingDaysMax/priceMin/priceMax/bsrMax/weightMax/maxVariantCount/fulfillment/grade/createdWeeks`
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1418)
- 未选周批次时自动补最新批次
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1433)

### 2.2 方法卡（M01 / M02）

方法卡不会走普通筛选接口，而是直接切到：

- `marketplace`
- `page`

对应代码：

- `size`

## 4. 已确认的问题清单

## P0：主栏大类筛选是伪生效

现象：

- UI 上主栏大类绑定的是 `activeFilters.category`。
- 变更时会触发 `loadProducts()`。
- 但真正请求参数来自 `queryFormRef.getQueryParams()`，不是 `activeFilters.category`。
- `buildApiParams()` 也没有把 `activeFilters.category` 合并回请求。

对应代码：

- 主栏大类绑定：
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:129)
- 请求汇总只读 `queryParams.category`：
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1695)

结果：

- 用户在主栏改大类，会看到列表刷新，但请求里可能根本没带新的 category。
- 这是典型的“看起来能筛，其实是空操作”。

## P0：抽屉里的卖家筛选也是伪生效

现象：

- 抽屉卖家写入 `draftFilters.sellerSelect -> activeFilters.sellerSelect`。
- 但普通请求阶段仍然只读 `queryParams.sellerSelect / storeName`。
- 抽屉确认后没有把卖家同步给 `SelectionQueryForm`。

对应代码：

- 抽屉确认仅回写 `activeFilters`：
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1963)
- 请求构造仍只读 `queryParams`
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1684)

结果：

- 抽屉卖家看似在“已选条件”里出现，但对普通列表查询不一定真的生效。

## P0：Reset 只重置了 range，没有重置其它筛选源

现象：

- 顶部 `SelectionQueryForm` 的 `重置` 按钮会触发 `handleReset`。
- 但 `handleReset` 只清空了 `activeFilters.range`。
- 不会清空：
  - `SelectionQueryForm` 自己的 `asin/title/storeName/category`
  - `activeFilters.sellerSelect`
  - `activeFilters.category`
  - `activeMethodCard`
  - 排序与站点

对应代码：

- [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1919)

结果：

- “重置”不是全局重置，而是“只清区间”。
- 很容易让用户误以为筛选都清了，实际上还有隐藏条件残留。

## P0：预设保存与预设回放字段不对称

现象：

- 保存预设时，`getCurrentFilterConfig()` 没有保存 `activeFilters.category`。
- 但回放预设时，`handlePresetApply()` 又试图把 `config.category` 回写到 `activeFilters.category`。

对应代码：

- 保存预设：
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:2118)
- 回放预设：
  - [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:2132)

结果：

- 主栏大类状态无法被可靠保存/恢复。
- 预设看似涵盖“当前筛选”，实际上丢字段。

## P1：入库批次下拉与实际列表查询口径不一致

现象：

- 批次下拉选项来自 `getCreatedWeeks(country, source)`。
- 这个接口统计的是 `competitor_products.created_at`。
- 但普通列表默认查询的是 `competitor_products_clean`，由 `useCleanTable=true` 控制。

对应代码：

- 批次下拉加载：
  - [RangeFilterPanel/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/components/RangeFilterPanel/index.vue:161)
- 批次统计 SQL：
  - [CompetitorProductMapper.java](F:/项目/si-jue-zhi-mao-up/java-backend/sjzm-product/src/main/java/com/sjzm/product/mapper/CompetitorProductMapper.java:89)
- 普通列表默认查 clean：
  - [CompetitorService.java](F:/项目/si-jue-zhi-mao-up/java-backend/sjzm-product/src/main/java/com/sjzm/product/service/CompetitorService.java:455)

进一步的口径差：

- `competitor_products_clean` 只是复制代表行，并保留那一行自己的 `created_at`
- 它不是按批次重新建一个“代表时间”字段
- 清洗脚本只是原样带出 `ranked.created_at`
  - [create_competitor_products_clean_table.sql](F:/项目/si-jue-zhi-mao-up/java-backend/sql/create_competitor_products_clean_table.sql:37)

结果：

- 批次下拉显示的是“原表每周有多少原始行”
- 实际筛出来的是“清洗表代表行 whose created_at 落在该周”
- 统计数、候选集、用户认知不在同一口径上

这就是“入库批次看着能选，但结果不稳定/不符合预期”的主要根因之一。

## P1：未显式选择批次时，前端会偷偷套一个“最新周”

现象：

- 只要没有 `createdWeeks/month/weekTag/createdAtStart`，前端就自动请求 `getCreatedWeeks(...)`，并把第一条最新周塞进 `competitorParams.createdWeeks`。

对应代码：

- [AllSelection/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/views/AllSelection/index.vue:1433)

结果：

- 用户以为自己在看“全部”，实际上默认已经带了一个“最新周”隐式筛选。
- 与“清除全部”“重置”组合后更容易让人混乱。

## P1：变体数筛选的语义与页面展示字段不一致

现象：

- 页面最终展示给用户看的变体数是 `variantCount`。
- 这个字段是后端在查完列表之后，再额外根据原表父群组统计回填的真实变体行数。
- 但筛选阶段在 `useCleanTable=true` 时，用的却是 `variations` 字段。

对应代码：

- 前端类型里就明确区分了 `variations` 与 `variantCount`
  - [competitor.ts](F:/项目/si-jue-zhi-mao-up/frontend/src/api/competitor.ts:93)
- 后端筛选用 `variations`
  - [CompetitorService.java](F:/项目/si-jue-zhi-mao-up/java-backend/sjzm-product/src/main/java/com/sjzm/product/service/CompetitorService.java:461)
- 后端展示回填用 `variantCount`
  - [CompetitorService.java](F:/项目/si-jue-zhi-mao-up/java-backend/sjzm-product/src/main/java/com/sjzm/product/service/CompetitorService.java:497)

更关键的是：

- `competitor_products_clean` 在建表/清洗时只是原样复制 `ranked.variations`
- 没有把它改造成“父群组真实变体数”
  - [create_competitor_products_clean_table.sql](F:/项目/si-jue-zhi-mao-up/java-backend/sql/create_competitor_products_clean_table.sql:48)

结果：

- 用户看到卡片上 `variantCount=7`
- 但筛选条件实际按 `variations<=N` 过滤
- 两者不是同一个语义，直接导致“变体数筛选失败”或“筛出来不符合展示数字”

这基本就是你刚提到的变体筛选问题的核心根因。

## P1：方法卡与郑总 tab 都绕开了大部分筛选体系

现象：

- M01/M02 只吃 `marketplace/page/size`
- 郑总 tab 只吃标题/卖家/排序/站点
- 其余抽屉区间、批次、变体数等都不共享

结果：

- 同一个“筛选系统”在不同 tab / 方法卡上行为完全不同。
- 用户会自然认为这些控件是全局通用的，但实际上不是。

## P2：`SelectionQueryForm` 的卖家来源和普通竞品查询来源并不一致

现象：

- 顶部卖家下拉来自 `getDengZongShopSellers(...)`
  - [SelectionQueryForm/index.vue](F:/项目/si-jue-zhi-mao-up/frontend/src/components/SelectionQueryForm/index.vue:77)
- 但普通竞品列表筛选的 `sellerName` 是筛 `competitor_products(_clean)`。

结果：

- 下拉卖家池和当前列表数据池不一定一致。
- 会增加“为什么我选了这个卖家却没有结果”的困惑。

## 5. 修复建议（按优先级）

## 第一阶段：先统一状态源，砍掉伪生效

建议目标：任何筛选项只保留一个事实来源，不再“UI 一套、请求一套”。

建议做法：

1. 定义一个统一的 `CommittedFilterState`
   - 包含搜索字段、主栏字段、抽屉字段、排序、批次、方法卡、tab 上下文。
2. `SelectionQueryForm` 不再自己持有独立事实状态
   - 改成受控组件，父组件传值、收变更。
3. `buildApiParams()` 只从统一状态组装请求
   - 不再同时读 `queryFormRef` 和 `activeFilters`。

优先修复项：

- 主栏大类
- 抽屉卖家
- Reset / 清除全部
- 预设保存/回放

## 第二阶段：统一批次口径

建议目标：批次下拉、默认批次、实际列表过滤全部基于同一语义。

两种可选方案里，我更建议方案 A：

1. 方案 A：全部改成基于 `effective_week_tag`
   - 批次下拉直接从 `competitor_products_clean.effective_week_tag` 取
   - 普通列表也按 `effective_week_tag` 过滤
   - 这样与清洗表消费口径完全一致

2. 方案 B：继续按 `created_at ISO 周`
   - 但下拉统计、列表查询、文案说明都必须明确“这是代表行入库周，不是清洗批次周”
   - 这个方案工程上能做，但业务理解会更绕

附带建议：

- 去掉“未选时自动补最新周”的隐式行为，改为 UI 上显式显示“默认最新周”或让用户自己选择。

## 第三阶段：统一变体数语义

建议目标：筛选条件和卡片展示都使用同一个字段定义。

建议做法：

1. 明确定义“变体数”就是父群组真实行数
2. 后端筛选不要再用 `variations`
3. 改为：
   - 清洗表场景也走父群组聚合子查询，或
   - 在清洗表里新增物化字段 `variant_count`
4. 前端卡片展示和筛选文案都统一用 `variantCount`

如果只追求最快止血：

- 直接把 `useCleanTable=true` 场景下的 `maxVariantCount` 过滤逻辑改成跟回填 `variantCount` 相同的 dedup 子查询逻辑。

## 第四阶段：把方法卡 / 郑总 tab 是否共享筛选讲清楚

建议目标：避免用户以为“所有筛选 everywhere 生效”。

建议二选一：

1. 方案 A：方法卡/郑总 tab 也接入统一筛选字段
2. 方案 B：明确隔离
   - 方法卡详情里直接写“当前仅支持站点 + 分页”
   - 郑总 tab 上隐藏无效筛选项

当前系统更适合先走方案 B，先把误导去掉，再决定是否扩展。

---

## 6. 推荐修复顺序

1. 先修状态统一
   - 主栏大类、抽屉卖家、Reset、预设一致性
2. 再修批次口径
   - 先决定到底按 `effective_week_tag` 还是按 `created_at ISO 周`
3. 再修变体数语义
   - 筛选与展示统一到 `variantCount`
4. 最后处理方法卡 / 郑总 tab 的共享策略

---

## 7. 结论

这次不是两个孤立 bug，而是“筛选系统当前由多套状态、多套口径、多条请求分支拼接出来”的结构性问题。

你刚发现的两个症状：

- 入库批次筛选失败
- 变体数筛选失败

都是真问题，但它们背后不是简单的字段拼错，而是：

1. 批次：下拉统计口径和实际列表查询口径不一致，还叠加了默认最新周的隐式过滤。
2. 变体：筛选用 `variations`，展示用 `variantCount`，语义本身不一致。

如果不先统一筛选状态和字段语义，继续点修单项，很容易修完一处、别处继续漂。
