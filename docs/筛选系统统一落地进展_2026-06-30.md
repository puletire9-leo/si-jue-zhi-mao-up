这一步的目的，是避免“入口看起来已经统一，但品线筛选规则在 intent builder 被静默吞掉”的隐藏分叉。

## 10. 页面查询参数状态继续收口

本轮又向前收了一步：`AllSelection` 页面现在已经建立了页面级 `queryParamsState`，不再默认通过 `queryFormRef.getQueryParams()` 回捞查询表单内部状态。

当前链路变为：

```text
SelectionQueryForm change/search
  -> queryParamsState
  -> buildSelectionFilterIntent(...)
  -> buildSelectionQueryPlan(...)
  -> resolveSelectionQueryPlan(...)
```

这意味着：

- 查询表单文本条件开始进入页面侧单一状态源
- `activeFilters / draftFilters` 与 `queryParamsState` 已经同处页面层
- 下一步若继续推进 `SelectionQueryForm` 受控化，改造面会更小、更清晰

## 11. `SelectionQueryForm` 已补上受控接口

在上一节基础上，这一轮继续把查询表单本身补成“可受控组件”：

- 新增 `modelValue`
- 新增 `update:modelValue`
- 外部同步查询参数时，表单内部会同步日期范围与紧凑搜索展示
- 外部同步 `country + sellerSelect` 时，不再被组件内部的国家切换副作用误清空

现在 `AllSelection` 已经不再依赖 `queryFormRef` 驱动查询表单状态，而是由页面级 `queryParamsState` 直接下发给组件。

## 12. 组件对外接口继续收口

本轮继续把 `SelectionQueryForm` 的对外接口往“单一语义”方向收了一层：

- `search` 事件统一发出规范化后的查询参数
- `reset` 后触发的 `search` 也统一走规范化参数
- `seller` 切换、紧凑搜索、多项精确搜索，不再混用 raw form / normalized form 两种出口
- 新增显式暴露：
  - `readQueryParams()`
  - `patchQueryParams()`
- 兼容保留旧别名：
  - `getQueryParams()` -> `readQueryParams()`
  - `setQueryParams()` -> `patchQueryParams()`

这一步的意义不是“删掉兼容层”，而是先明确当前唯一推荐语义：

```text
页面状态源 = queryParamsState
表单输出 = normalized query params
旧 imperative API = compatibility only
```

这样后续再把更多筛选入口并到统一 query intent / query plan / runtime 时，不会再因为表单组件内部存在两套参数出口而重新长出分叉。
