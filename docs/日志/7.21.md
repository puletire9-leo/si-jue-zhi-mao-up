## 导入领星：图片读取错位 + 杂图混入修复

- 现象：上传"产品汇总表"后，图片对不上 SKU 行，且 cpc段/采购数量 等非图片列的图也被读进来。用户只要"图片"列（C 列）的商品图。
- 根因一（顺序错乱）：`excelImageExtractor.ts` 解析 drawing.xml 锚点的行号正则写反了——`<xdr:from>` 内元素顺序是 `col → colOff → row → rowOff`，旧正则 `/<xdr:from>\s*<xdr:row>/` 永远匹配不到，导致 `visualOrderList` 恒空、每次都掉进"按文件名 image1/image2… 排序"的兜底，而文件名编号与行顺序、插入顺序三者都对不上。
- 根因二（杂图混入 / 真正的主因）：实测用户文件是 **WPS 单元格嵌入图片（DISPIMG）**，图片靠单元格 `=DISPIMG("ID_xxx",1)` 公式定位，drawing.xml 锚点全部堆在 A1 无位置信息。文件 18 张图分布在 C 列 9 张（要）、G 列 4 张、BA 列 5 张（都不要），旧代码走锚点无法区分列，全部混入。
- 修复：
  - 新增 WPS 单元格图片优先通道：检测到 `xl/cellimages.xml` 即走此路。映射链 单元格 `DISPIMG("ID")` → `cellimages.xml`(ID→rId) → `cellimages.xml.rels`(rId→media)，**只取图片列（C 列，索引 2）** 的 DISPIMG 单元格，按行号升序对齐同行 SKU（E 列，索引 4）。
  - 修正 drawing.xml 锚点正则（col 在 row 前）并兼容 `oneCellAnchor`，作为传统浮动图的回退；行号可信时按真实行号排序。
  - `index.vue` 上传写回增加"按 SKU 精确落行"兜底（SKU 匹配 → 锚点行号 → 视觉序号三级），并用 `usedRows` 防重复覆盖。
  - 图片列/ SKU 列索引参数化（`extractImagesFromExcel(buf, skuColIdx=4, imgColIdx=2)`）。
- 验证：用真实文件 `产品汇总表-模版 (4).xlsx` 端到端跑通——图片列命中 9 张（G/BA 列杂图全部排除），C2→SKU2610455→image3、C3→2610456→image6 …… C10→2610466→image1，行顺序与 SKU 严格对齐；`vue-tsc` 零新增错误，`npm run build` 通过。
- 部署：纯前端改动，走"只改前端"（`npm run build` + `build frontend` + `up -d --no-deps frontend`）。
- 备注：图片列固定认 C 列（表头"图片"在第 3 列）；若模版列顺序变动，改 `imgColIdx` 一个参数即可。

## 总选品管理 / 新品榜 / 店铺选品：全面性能优化

### 排查过程

对三个页面逐层排查（前端渲染 → 后端接口 → 数据库索引），关键发现：

- **总选品管理 和 新品榜 是同一组件**（`views/AllSelection/index.vue`），新品榜只是默认套了 M01 方法卡。
- 三个页面均**无"拉全量到前端过滤"的反模式**——分页、筛选、排序全部下推后端，图片已做懒加载，这几项都正常。
- 卡顿集中在以下几个真实热点：

**前端热点（AllSelection / 新品榜 / 总选品）**
1. `ResizeObserver` 批量触发时 O(N²) 开销：每张卡片高度变化时旧代码都 `{...spread}` 整体替换 `cardBaseHeights` reactive 对象，500 张卡片首屏触发 500 次全量拷贝 + 全量重渲染。
2. 无视口裁剪：`v-for` 直接渲染当前页所有卡片（最大 500 个重组件）为真实 DOM，无任何虚拟化保护。分页可选到 500 条/页（`:page-sizes="[60,100,200,500]"`）。
3. 项目已有 `VirtualList` 组件但未被 AllSelection 使用；但该组件是定高单列，不兼容变高响应式网格。

**后端热点（店铺选品）**
1. `ShopCollectionService.productWall`（line 181）：`selectList` 无 LIMIT，把整店所有商品（含 `raw_json` 大字段、70+ 列）全部拉进 JVM 再排序分组；商品墙展示只需 11 个字段。
2. `ShopScreeningMapper.xml:47–179`（未本次修改）：多层 CTE + 全表 `ROW_NUMBER()` 窗口函数 + 逐行 CASE WHEN + GROUP BY，历史数据 48 万–77 万行时全量物化中间结果，是店铺筛选列表最慢的查询；重写该 SQL 属于高风险项，本轮先加索引。

**数据库热点**
- `source_run_id` 无索引：`productWall`/`compare`/`insight` 均按此字段过滤，现有索引只覆盖 `(marketplace, seller_name, batch_date)`，命中不了。
- `ShopScreeningMapper` 的 `ranked_products` CTE 去重窗口 `PARTITION BY (marketplace, seller_name, COALESCE(parent_asin,asin)) ORDER BY batch_code DESC` 无对应覆盖索引，MySQL 须对全量产品行做内存排序。

### 本轮改动

**前端 `frontend/src/views/AllSelection/index.vue`**

1. **ResizeObserver O(N²)→O(N)**：新增 `pendingHeightUpdates` + `heightFlushHandle`，把多张卡片的高度更新累积到 pending，用 `requestAnimationFrame` 每帧只提交一次 reactive 写入；`onUnmounted` 时取消未刷帧。首屏 N 张卡片同时触发回调时，旧逻辑是 N 次全量对象拷贝+N 次响应式重渲染，新逻辑是 1 次合并写入。
2. **CSS 视口外渲染裁剪**：给 `.product-card-scale-wrapper` 添加 `content-visibility: auto` + `contain-intrinsic-size: auto <minWidth> auto <fallbackHeight>`。浏览器可跳过视口外卡片的布局和绘制，但仍会创建 Vue 组件与 DOM，因此这是第一阶段优化，不等同于完整虚拟列表。
3. **高度缓存限界**：翻页或切换筛选后只保留当前页商品高度，并忽略旧页面迟到的 `ResizeObserver` 回调，避免长会话中缓存无限增长、每帧复制成本重新放大。

**后端 `java-backend/.../shopcollection/service/ShopCollectionService.java`**

4. **productWall 列裁剪**：`selectList` 的 `LambdaQueryWrapper` 加 `.select(...)` 限定 11 个商品墙实际用到的字段（asin/parentAsin/imageUrl/title/units/salesTier/price/rating/ratings/nodeLabelPath/productUrl），排除 `raw_json` 等大字段；由于商品墙需按 tier 统计总数无法 SQL 侧 LIMIT，列裁剪是此处最安全有效的降内存手段。
5. **周批次走索引字段**：批次下拉直接按已有 ISO 周字段 `batch_code` 聚合，周筛选直接使用 `batch_code IN (...)`；日期值仍兼容 `batch_date IN (...)`，不再对每行执行 `STR_TO_DATE + DATE_FORMAT`。

**数据库 `java-backend/sql/add_shop_products_source_run_index.sql`（新增，幂等）**

6. `idx_shop_products_source_run (marketplace, seller_name, source_run_id)`：支持商品墙/快照类查询。

审查后删除原计划的 `idx_shop_products_dedup`：窗口分区实际使用 `COALESCE(NULLIF(parent_asin,''), asin)`，五列普通索引无法匹配该表达式和完整排序键，不能在没有 `EXPLAIN ANALYZE` 证据时写入生产大表。

### 未改动 / 留待下轮

- AllSelection 手写网格虚拟滚动（`content-visibility` 仅降低视口外布局/绘制成本；若组件挂载仍是热点，再单独实施真正的网格虚拟化）。

## Amazon 以图识图：US200 缩略图导致 StyleSnap 退回上传页

- 现象：选品卡生成的链接结构正确，例如 `https://www.amazon.co.uk/stylesnap?q=...`，源图直链也能正常返回图片，但打开后只显示 StyleSnap 默认的 “Upload a Photo” 页面，没有相似商品结果。
- 对照：桌面插件 `C:\Users\Admin\Desktop\亚马逊以图识图插件` 会优先读取商品页的 `data-old-hires`，其次从 `srcset` 选择最大图片，再对图片 URL 执行 `encodeURIComponent`。插件成功链接使用的是高清图；系统数据库中的部分 `image_url` 则带有 `US200` 等缩略图规格。
- 根因：当前系统直接把数据库 `image_url` 编码进 StyleSnap。类似 `71rQ0mPnEUL._AC_US200_.jpg` 或爬虫格式 `71rQ0mPnEUL.*AC_US200*.jpg` 的地址只有约 200×200，StyleSnap 对过小图片会静默放弃识图并返回默认上传页；链接结构和 `q` 参数本身没有失效。Markdown 产生的 `\_` 反斜杠也不应进入真实图片 URL。
- 修复：
  - 新增前端 `amazonImageSearch.ts`，清理 Amazon CDN 的 `US200/SX/SL1500` 等尺寸修饰符和 `\_` 转义，恢复原图地址，再按站点生成并编码 StyleSnap / Shop the Look URL。
  - `UniversalCard` 根据当前商品 `imageUrl` 即时生成识图链接，优先于数据库中可能已过期的 `similarUrl`，因此历史选品数据无需重新导入即可使用。
  - Java `ImageSearchUrlBuilder` 增加相同的原图标准化规则，`ProductFeatureProcessor` 统一调用该构造器，后续入库的 `similar_url` 不再保存未编码的小图链接。
  - `BazhuayuImageSearchService` 在启动英国八爪鱼识图任务前先转换成原图；结果表 `source_image_url` 也记录实际送入 StyleSnap 的高清地址，便于后续审计。
- 转换示例：
  - 输入：`https://images-na.ssl-images-amazon.com/images/I/71rQ0mPnEUL.*AC_US200*.jpg`
  - 原图：`https://images-na.ssl-images-amazon.com/images/I/71rQ0mPnEUL.jpg`
  - StyleSnap：`https://www.amazon.co.uk/stylesnap?q=https%3A%2F%2Fimages-na.ssl-images-amazon.com%2Fimages%2FI%2F71rQ0mPnEUL.jpg`
- 验证：前端专项 Vitest 3/3 通过，覆盖标准 Amazon 修饰符、爬虫星号格式、Markdown 反斜杠和 UK URL 编码；`npm run build` 通过；`git diff --check` 通过。全量 `vue-tsc` 仍被仓库既有类型错误阻塞，本次文件无新增类型错误。当前宿主机没有 `mvn`/`javac`，Java 单元测试已补充但未在本机执行。

## 店铺选品页卡死：真因定位与索引优化（已部署验证）

### 背景更正
前一轮"总选品/新品榜/店铺选品全面性能优化"排查方向偏了——把重心放在观察池 `ShopScreeningMapper` 的 CTE 和 `productWall` 列裁剪上。实际用户反馈卡死的是**选品页（AllSelection）的「更多筛选」**，reference 场景走 `selectionProducts()` 查 `shop_products` 表（UK 站 16.6 万行，就是页面上「共 165832 条」）。跟观察池、CTE 都无关。

### 根因（生产库 EXPLAIN + profiling 实测，非推断）
`ShopCollectionService.selectionProducts()` 用 MyBatis-Plus `selectPage` + `SELECT *`，三个问题叠加：

1. **首屏默认查询全量 filesort（主因）**：默认 `ORDER BY updated_at DESC` 且旧代码固定追加次级键 `orderByAsc(asin)`。`updated_at DESC` + `asin ASC` 方向冲突，任何索引都无法有序读取，对 16.6 万行全量 filesort。实测 **2711ms**。
2. **无复合索引覆盖筛选列**：price/units/listing_days/bsr/weight 全是无索引范围条件，只能用 `marketplace`（基数=2）前缀扫全分区，命中率 0.07%（扫 9.8 万行找 ~68 行）+ filesort。实测带筛选 **494ms**、其 count **267ms**。
3. **`SELECT *` 拉大字段**：包含 `raw_json` 等 70+ 列，单行体积大。

首屏 = list 2.7s + selectPage 的 count ~2s + 60 张带图卡片渲染 → 5 秒以上转圈。

### 本轮改动

**数据库 `java-backend/sql/add_shop_products_selection_indexes.sql`（新增，幂等，information_schema 守卫 + INPLACE/LOCK=NONE 在线 DDL）**
- `idx_shop_sel_default (marketplace, updated_at)`：默认查询 Backward index scan，2711ms → 2.2ms（SQL 层）。
- `idx_shop_sel_metrics (marketplace, units, price, listing_days)`：带筛选 range scan，494ms → 105ms（SQL 层）。
- 已在生产库执行并 `ANALYZE TABLE`，EXPLAIN 确认两查询均命中新索引、无 filesort。

**后端 `ShopCollectionService.selectionProducts()`**
- 列裁剪：`.select(...)` 只取选品卡片实际用到的 31 个字段（对齐前端 `ShopProductRow`），排除 `raw_json` 等大字段。
- 排序键修正：次级键由固定 `orderByAsc(asin)` 改为 `orderBy(tieAsc, id)`，`tieAsc` 跟随主排序方向，保证与主排序同方向 → 不破坏（反向）索引扫描、消除 filesort。

**前端 `AllSelection/index.vue`**
- 选中态解耦：`loadSelections()`（我的选品 + 多人选中）原本 `await` 串在首屏关键路径上，改为列表就位即结束 loading、选中态异步补齐。首屏不再等两个额外网络请求。
- 防竞态 `productsReqId` 为既有机制，保留。

### 部署后端到端实测（本机运维口 8025 直连 java-product，稳态）
- 首屏默认查询：2.7s+ → **34~50ms**。
- 带筛选查询：494ms → **~600ms**（仍含未优化的 count，见下）。
- 前端→Java 路由 401（未带 token，符合预期）、Python 兜底 200，nginx 无 502。

### 已知残留 / 留待下轮
- **带筛选的 count 仍 267ms**：MyBatis-Plus `selectPage` 自动生成的 count 无 ORDER BY，MySQL 优化器固执选低基数等值前缀 `uk_shop_asin_batch`（`ref` 成本被估得比 `range` 低），不主动走 `idx_shop_sel_metrics`（FORCE INDEX 可降到 89ms 但脆弱，未采用）。`ANALYZE TABLE` 无效。真实场景用户多会叠加周批次筛选进一步缩小范围，600ms 已从"卡死转圈"变为"可用"。下轮如需根治，评估：给 count 定制 index hint（需自定义 count 查询绕开 selectPage 自动 count），或前端分页改为不依赖精确 total 的"加载更多"。
- 部署方式：索引 SQL 已执行；java-product `build + up -d --force-recreate`（镜像 tag 不变，必须 force-recreate）；前端 `npm run build`（宿主）+ `build frontend` + `up -d --force-recreate frontend`。SchemaGuard 通过（56 表），`Started ProductApplication`。

## 店铺选品页卡片渲染卡顿：网格行虚拟化（已部署）

### 背景
上一节的索引 + 列裁剪解决了「筛选查询慢」，但用户反馈**卡片渲染仍卡**：页面能出数据，但滚动/展示卡顿。根因是渲染层而非查询层。

### 根因
`AllSelection/index.vue` 的 `v-for` 一次性为**当前页全部商品**（分页可选 60/100/200/500）创建 `UniversalCard` 组件实例和真实 DOM。每张卡含多个 Element Plus 重组件（`el-image`/`el-button`/`el-checkbox`/`el-icon`），500 张卡 = 数千个组件实例同时挂载，主线程长时间阻塞。既有的 `content-visibility: auto` 只能跳过视口外**绘制**，组件实例与 DOM 仍全部创建，救不了挂载阶段。

### 本轮改动（仅 `AllSelection/index.vue`，不加新依赖）
自研**网格行虚拟化**，只渲染可视区域附近的卡片：
- 按容器宽度和缩放后卡片最小宽度推算每行列数 `cols`（`recomputeGridColumns`）。
- 商品按 `cols` 切成行，行高取行内实测卡片高度最大值（缩放后），未测量用 fallback；累计每行 top 偏移（`virtualRows`）。
- 监听 `.products-grid` 滚动（rAF 节流），算出可视行区间 `[首行-buffer, 末行+buffer]`（buffer=3 行），只 `slice` 渲染区间内卡片（`virtualVisibleProducts`）。
- 用 grid 容器的 `padding-top/padding-bottom` 撑起被虚拟化掉的行空间（`virtualGridSpacerStyle`），保证滚动条高度与 grid 列布局正确。
- 复用既有 `cardBaseHeights` ResizeObserver（rAF 批量写）测量真实高度，随测量自我校正行偏移。
- `ResizeObserver` 监听容器尺寸、`watch(cardScale)` 监听缩放，两者变化重算列数；翻页/刷新回顶并重算。
- 保护阈值 `VIRT_MIN_COUNT=80`：不足 80 条直接全量渲染，避免小页面额外开销。
- `key` 仍用 `product.id`，Vue 复用组件；`content-visibility` 保留作二级保险。
