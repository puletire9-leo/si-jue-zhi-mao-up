# 7.29

## 店铺请求功能：类型分流修复（假成功 bug）

### 现象
店铺选品页（`/reference-products`）新增的「店铺请求」按钮，前端提示"请求成功"，但卖家精灵请求中心实际 FAILED。

### 根因
`SellerspriteRequestCenterService.createShopTaskOnce` **硬编码 `CANDIDATE_BATCH` 类型**。该类型执行器（`consumeNext` line 1154）强制要求每个 item 带 `triggerId(candidateId)`——从候选池按 id 抓。
- 候选池点选（`shop-candidate-pool`）带 `triggerId: row.id`，正常；
- 店铺选品页手输店铺名，**没有 candidateId** → worker 抛 `候选批量抓取 item 缺少 triggerId(candidateId)` → 任务 FAILED。
- 前端只看创建成功（HTTP 200 / queuedCount>0）就提示成功，未等异步执行结果 → **假成功**。

### 修复
`createShopTaskOnce` 按 item 是否带 triggerId 分流任务类型：
```java
boolean allHaveTriggerId = queued.stream().allMatch(item -> item.triggerId() != null);
String requestType = allHaveTriggerId ? "CANDIDATE_BATCH" : "SHOP_FULL_LOOKUP";
```
- 全带 triggerId（候选池）→ `CANDIDATE_BATCH`，原逻辑不变；
- 有不带（手输店铺）→ `SHOP_FULL_LOOKUP`，执行器落默认分支 `productSyncService.syncBySellerName` 按店铺名抓全量写 `shop_products`。

候选池零影响（仍走 CANDIDATE_BATCH）。

### 验证
直连 8025 手输 `Pavemlo uk`：`requestType=SHOP_FULL_LOOKUP` → 抓店铺全集 total=7 写库 → `status=SUCCESS`（此前 FAILED）。

## 店铺选品搜索定位（参数名不匹配排查）

排查"店铺搜不到"时发现两处历史遗留的参数名不匹配（针对 `/shop-screening` 店铺画像接口，非 `/selection-products` 商品明细接口）：
- 前端 `ShopScreeningParams` 传 `sellerName`（单数），后端 `ShopScreeningQuery` 只认 `sellerNames`（复数）/`sellerKeyword` → 店铺名筛选被忽略返回全部。
- 同理 `batchDates`（前端）vs `batchCodes`（后端）。

> 注：店铺选品页实际走 `/selection-products`（`ShopProductSelectionQuery`，认单数 sellerName + batchDates），搜索本身是好用的。上述不匹配影响的是店铺画像 `/shop-screening` 接口。用户当时"搜不到"实为批次筛选残留，清空批次后搜到。本条仅记录排查发现，`/shop-screening` 的参数对齐待后续单独处理。

## 店铺选品性能优化：限批次 + 搜索绕过批次

### 问题
`/selection-products` 查 `shop_products` 明细，单站点几十万行（UK 23万）。批次为空 = 全量扫描，是卡死主因。

### 改动
后端 `ShopCollectionService.normalizeSelectionBatchScope`（列表 `selectionProducts` + 类目统计 `selectionCategories` 共用，保证同口径）：
- **有搜索**（asin/店铺名/标题任一）→ 清空 batchDates，全库该站点搜，方便跨批次找货；
- **无搜索**（纯浏览）→ batchDates 最多取前 2 个；一个都没选则兜底回退最新 1 批（`shopProductMapper.selectMaxBatchDate`），杜绝全表扫。
- 其余筛选（价格/销量/类目/方法卡）两种路径都照常生效。

前端 `RangeFilterPanel`：`shop_batch` 场景批次下拉 `:multiple-limit="2"`（计算属性 `batchSelectLimit`，其他场景 0=不限）。

### 验证（直连 8025）
| 场景 | total | 判定 |
|------|------|------|
| 空批次浏览 | 7 | 自动限最新1批(0729)，不全表扫 |
| 传3批次 | 170863 | 只用前2个 |
| 只传2批次 | 170863 | 与传3一致，证明第3被砍 |
| 搜店铺名(无批次) | 53 | 跨批次全库搜到 |
| 搜店铺名+带不存在的0729批次 | 53 | 批次被忽略仍搜到（否则应为0）|

### 待办
- 物化表 `shop_seller_summary`（店铺画像页）UK 因单店测试抓取(0729)覆盖，画像列表塌缩成 1 家。"按最新单批次覆盖"策略缺陷，后续单独分析（可加"店铺数<阈值跳过覆盖"）。

## 基础设施

### WSL2 内存限制（治 Docker 反复卡死）
今天 Docker Desktop 后端(vmmemWSL)两次卡死、重启无效、需重启电脑。根因：16G 物理内存无 `.wslconfig`，WSL2 默认可膨胀到一半(8G)，叠加浏览器/AI 工具后宿主可用内存被榨到 0.3~0.9G，vmmem 假死。
新建 `C:\Users\Admin\.wslconfig`（纯 ASCII 注释，避免编码坏导致解析失败）：`memory=9GB` + `processors=12` + `swap=4GB` + `autoMemoryReclaim=gradual`。需 `wsl --shutdown` 生效。

### .gitignore 补充
追加 `.cache/`（Maven 本地仓库 224MB/3123文件）、`.m2/`、`**/target/`、`.playwright-mcp/`，防大文件误入 git。

## 店铺选品前端性能：系统性优化（CDP profiler 实测驱动）

核心认知：项目不复杂，唯一性能矛盾是商品数据量大（单站点几十万行）。后端毫秒级返回一页，卡在前端渲染。分析文档：`docs/架构/性能优化/店铺选品性能优化/关于店铺选品链路全流程以及卡顿的节点.md`。

### 默认批次跳过迷你批次
`normalizeSelectionBatchScope` 无搜索兜底原用 `MAX(batch_date)`，命中单店测试抓的 0729 迷你批次（1家7条）→ 打开只显示 1 家。新增 `selectLatestMeaningfulBatchDate(mp, minShops=10)`：取店铺数≥10 的最新正经批次，全是迷你批次才回退 MAX。并删 UK 0729 测试数据。

### P0：shallowRef + markRaw + v-memo
- `productList` 从 `ref` 改 `shallowRef`，赋值时每条 `markRaw`：消除几百条×数十字段的深响应式代理开销。商品是只读展示数据，全代码无就地改单条字段（都整表替换），选中态在独立 ref，安全。
- `UniversalCard` 加 `v-memo="[id, selected, mySelected, selectedUsers, selectable]"`：未变卡片跳过重渲染。
- 三页共用（新品榜/竞品/AI选品），一处改全部受益。

### 筛选抽屉卡死 11 秒 → 秒开
CDP profiler 锁定：点「更多筛选」阻塞 11225ms，全在 `vue get`(响应式 getter) + element-plus forEach computed。根因：抽屉「卖家」下拉是 `filterable` el-select，`loadDrawerSellers` 灌入 limit:1000 家卖家（批次常几百上千家），Element Plus 给每个 option 建响应式 effect → getter 爆炸。
修复：**删掉卖家下拉**（按店铺名查改用顶部搜索框，sellerName 链路跨批次全库搜，更强），停 `loadDrawerSellers` 预拉取，清死代码。11225ms → ~170ms。

### 类目聚合改「顶级大类」
`selectSelectionCategories` 原 `GROUP BY TRIM(node_label_path)`（完整路径），6万数据产生成百上千组 → 后端聚合慢(4.2s) + 前端大类下拉 option 爆炸。改 `SUBSTRING_INDEX(node_label_path,':',1)` 取第一段顶级大类，与 AI 选品口径一致。筛选口径 `buildSelectionProductFilter` 同步改第一段匹配。大类从上千降到 132 个（含少量脏数据尾巴）。冷聚合 4.2s，Caffeine 缓存后 4ms。

### 虚拟滚动错乱修复（200/页滚不动）
CDP 实测：`BASE_CARD_HEIGHT=560` 估算行高，但卡片实际渲染高 ~224px（2.5倍误差）→ padTop 撑出空间与真实内容错配 → 滚动条撑起却滚不动、卡中途。
修复：`VIRT_MIN_COUNT` 80→600，让 60/100/200 全量渲染（原生滚动无估算错配，配合 v-memo+shallowRef 性能可接受）。验证 200/页滚动精确到底。
待办：正确的固定/准确行高虚拟化后再下调阈值。

### 删除 500 每页选项
500 全量渲染会卡。前端 4 处 page-sizes（店铺选品/UniversalList/ProductManagement/CompetitorCardGrid）删 500 → `[60,100,200]`。后端 `Math.min(200,...)` 硬上限双保险。

### 已知残留（待后续）
- **200/页越往下翻越卡最后卡死**：全量渲染 200 张 UniversalCard，滚动时 ResizeObserver + 图片加载 + computed 累积压力。虚拟化是正解但需先修准行高。
- 批次"选了没商品"：实为 M01/M03 方法卡叠加（66883→2041），批次标签显示总数与实际可见数不一致的认知问题，非查询 bug。
- `selection-users` 轮询 500 错误（独立问题）。
- 物化表 `shop_seller_summary` UK 单店覆盖问题（画像页）。
