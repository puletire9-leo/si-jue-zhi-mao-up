### 已修复

1. `ShopProfileMapper.xml`
   - `selectSummaryFromShopProducts`
   - `countProductsFromShopProducts`
   - `selectProductsFromShopProducts`
   - `selectCategoriesFromShopProducts`

   以上 4 个 `shop_products` 查询全部补上 `ds.source_run_id = #{sourceRunId}` 条件，确保同一页面的画像概览、类目、商品明细都绑定同一快照。

2. `ShopCollectionService.compare`
   - 历史对比不再把 baseline/compare 两个快照全集加载到 JVM 内存后分页。
   - 新增 SQL 侧 compare CTE：按 `product_key = COALESCE(parent_asin, asin)` 去重后计算新增、消失、保留、升级、降级。
   - 五类商品列表全部按 SQL 分页返回，保留原接口返回结构。

3. 回归测试
   - `ShopCollectionServiceTest` 增加 compare 走 SQL count/page 查询的保护。
   - `ShopProfileMapperXmlTest` 增加 XML 保护，确认 4 个 `shop_products` 查询都包含 `source_run_id` 条件。

## 店铺候选池与精品店铺池完整链路计划（2026-07-08）

基于最新讨论，店铺分析主线从“方法卡命中 -> 观察池 -> 抓店铺全集 -> 画像解释”升级为更完整的作战链路：

```text
每周新品批次
  -> 方法卡筛商品
  -> 按店铺聚合候选店铺
  -> 写入店铺候选池
  -> 人工筛选 / 批量确认

  -> 抓取成功后进入正式观察 / 画像体系
  -> 从画像中筛精品店铺
  -> 精品店铺池长期维护
  -> 月度/周期复抓全集
  -> 店铺历史对比 + 多店同上分析
  -> 反哺新的选品方法卡
```

```text
docs/店铺品级/店铺候选池与精品店铺池完整实施计划.md
```

本次确认的关键点：

- 一批新品至少几万条，方法卡聚合出的店铺可能有几百到上千，前端必须有批次、方法卡、命中数、类目、状态等筛选。
- 方法卡命中的店铺先进入 `shop_candidate_pool` 候选池，不直接进入正式店铺库。
- 只有人工确认或批量确认后，才调用卖家精灵店铺名 API 抓全集，避免无意义消耗请求次数。
- 抓取成功后写 `shop_products`，并保留入库原因、来源批次、来源方法卡、抓取 run。
- 需要新增 `shop_fetch_run` 记录每次店铺全集抓取的来源、原因、请求次数、成功失败。
- 精品店铺需要独立 `shop_premium_pool`，它是可 CRUD 的长期复用池，可单个/批量新增、暂停、淘汰、修改标签和复抓频率。
- `shop_products` 不覆盖历史批次，每次全量抓取都保存不同时间段数据，便于月度对比。
- 后续重点分析：精品店本月新增商品、消失商品、销量等级变化、多家精品店同周期共同上新的商品族。
- 多店同上分析可反哺新方法卡，例如“精品店铺同周期共上法”。

当前已有基础：

- `competitor_products_clean` 支持方法卡消费。
- M01 已能按店铺聚合命中排名。
- `shop_watchlist` 已可记录观察原因。
- `shop_products` 已作为不含变体店铺全集表。
- `shop-collection` 后端和前端已有观察池与全集画像雏形。

1. 建 shop_candidate_pool，先闭合“方法卡 -> 候选店铺 -> 确认抓取”。
2. 建 shop_fetch_run，让每次抓取有来源、原因、请求次数和错误记录。
3. 建 shop_premium_pool，支持精品店铺 CRUD 与周期复抓。

## 店铺分析下一阶段：方法卡命中找店铺 + 店铺数据分表（2026-07-08，计划）

#### 1. 新品榜数据：`competitor_products` / `competitor_products_clean`

#### 2. 店铺观察池：`shop_watchlist`

定位：

```text
记录哪些店铺值得抓，以及为什么值得抓。
```

来源可以是：

- `METHOD_CARD`：如 M01 新品命中多。
- `BASELINE`：如郑总相似、自有优质店相似。
- `MANUAL`：人工加入。
- `CATEGORY`：类目专项观察。

建议字段：

```text
marketplace
seller_name
seller_id
source_type
source_code
reason
hit_count
top_category
status
last_fetch_run_id
created_at / updated_at
```

这张表回答：

```text
这家店为什么进入观察池？
它是因为哪张方法卡、哪个基线、哪个人工判断进来的？
```

#### 3. 店铺全集数据：`shop_products`

定位：

```text
专门承接卖家精灵“店铺名查询”返回的店铺商品全集。
```

关键原则：

```text
字段能力基本复制 competitor_products。
```

不是轻量表。因为店铺画像、店铺商品明细、方法卡解释、店铺上新流都需要和新品榜商品类似的完整字段能力。

建表思路：

```sql
CREATE TABLE shop_products LIKE competitor_products;
```

然后补店铺抓取专用字段：

```text
source_run_id
fetch_source
fetch_reason
watchlist_id
variation_mode
raw_json
first_seen_at
last_seen_at
```

口径：

- 卖家精灵店铺名查询固定 `variation=Y`。
- 即不含变体，直接对齐亚马逊店铺页面父体商品数量。
- 不再做 `shop_products_clean`。
- 但仍需要基础标准化：数值字段、`sales_tier`、`age_bucket/listing_days`、末级类目、`raw_json` 留底。

## 候选池/精品池完整计划审查修订（2026-07-08）

> 对照已落地代码审查 `店铺候选池与精品店铺池完整实施计划.md`，计划里所有“已实现”声明经代码核实
> 均属实（M01 父体去重、分页 fetched 判断、观察池 upsert 不覆盖 status、sales_tier 三处一致）。
> 但发现 4 个会卡实现/返工的硬伤 + 3 个设计歧义，已全部修订进两份计划文档。

### 已修订的硬伤

1. **候选池 vs 观察池职责冲突**：现有 `syncFromMethodRank` 直写 `shop_watchlist`，与计划“方法卡→候选池→
   确认→观察池”分层冲突。已定边界：方法卡命中只落候选池；观察池收敛为候选确认/人工/基线进入；
   `sync-from-method-rank` 改写候选池；METHOD_CARD 历史数据转过渡态。
2. **`batch_code` 无来源定义 + NULL 陷阱**：已定 = 复用 `ScoringService.getCurrentWeekTag()`（`yyyy-Www`，
   与 `week_tag`/M04 同源），建议提为 `WeekTagUtil` 公共工具；`source_code/batch_code` 均 `NOT NULL DEFAULT ''`
   防唯一键放行多 NULL 导致去重失效。
3. **`shop_products` 字段名对不上**：现状只有 `batch_date`(天)+`source_run_id`，计划早期写 `batch_code`+
   `fetch_run_id`。已定：补 `batch_code` 列(周粒度做历史对比归组)；run 列统一以 `source_run_id` 为准，
   `shop_fetch_run` 主键 `run_id`，各表关联列名随语义但存同一 run_id 值。
4. **`shop_fetch_run` 阶段倒置**：从阶段2 提到阶段1，与候选池同批建。否则阶段1“确认抓取”抓了记不下，
   状态机失败无法追溯。

### 已修订的设计歧义

- 删掉候选池冗余字段 `hit_product_count`（M01 hitCount 已是父体去重值，两者同数）。
- 候选池状态机定为单向不可跳级 `PENDING→SELECTED→FETCHING→FETCHED→PROMOTED`，`PROMOTED` 必须经 `FETCHED`
  （看过画像才进精品池），禁止跳过画像验证。
- 旧「店铺画像」(读 deng_zong_shop) 与新「店铺全集画像」(读 shop_products) 不合并，旧页建议改名
  「郑总基线画像」或收进基线管理，避免双入口混淆。

### 结论

计划链路本身成立，改造方向清楚。落地前只需按上述边界收口，无需推翻。仍待实测：`shop_collection`
第二/三条数据线尚未真实调用/入库验证（测试步骤见本文档前面「店铺分析第二/三条数据线」节）。

### 二审补充硬规则

再次按“准备实现阶段 1”复查计划后，补充以下规则到
`docs/店铺品级/店铺候选池与精品店铺池完整实施计划.md`：

1. **方法卡排名必须按批次过滤**：`sync-from-method-rank` 必须支持 `batchCode / effectiveWeekTag`，
   默认可取当前周，但 SQL 必须落到具体批次，不能拿全历史 `m01_active=1` 排名冒充本周候选。
2. **确认抓取顺序固定**：候选确认时先原子抢锁，再创建/更新 `shop_watchlist` 拿 `watchlist_id`，
   再创建 `shop_fetch_run`，最后抓 `shop_products`。不能抓完后才建观察池，否则商品行无法写 `watchlist_id`。
3. **失败状态补齐**：候选池新增 `FETCH_FAILED`，保留 `fetch_run_id / last_error_message / last_fetch_at`，
   允许从 `FETCH_FAILED` 重试到 `FETCHING`。
4. **批量抓取必须有原子状态锁**：只允许 `PENDING / SELECTED / FETCH_FAILED` 通过
   `UPDATE ... WHERE status IN (...)` 抢到 `FETCHING` 后调用卖家精灵，防止多人操作或重试重复消耗使用次数。
5. **候选同步不能固定 500**：候选池可能几百到上千店铺，后端必须支持分页/可配置 limit，或直接
   `INSERT SELECT` 写候选池。
6. **店铺抓取限速写入计划**：店铺名查询分页和批量抓店铺都按 2 秒/请求限速，最多约 1 分钟 30 次。
7. **前端候选池必须分页**：默认按 `hit_count DESC`，每页 50/100；命中商品图片样例只带 3-6 个，更多懒加载。
8. **统计字段口径更名**：`inserted` 不再解释成新增行，前端展示统一使用 `fetched_count / written_count / failed_count / api_calls`。
9. **同周多次抓取代表快照**：同一 `batch_code` 内多个 `batch_date/source_run_id` 时，周度画像和历史对比默认取最新成功 run，避免重复计数。

### 阶段 2+ 补充审查

继续检查精品池、画像增强、历史对比、多店同上几个后续阶段，补充以下边界：

1. **精品池状态拆分**：`shop_premium_pool.status` 只表示是否属于精品池（`ACTIVE/PAUSED/REMOVED`），
   `refresh_status` 单独表示复抓任务状态（`IDLE/RUNNING/FAILED`），避免一个字段表达两类状态。
2. **精品池软删除**：`REMOVED` 不物理删除；同一 `marketplace + seller_name` 再次加入时恢复原记录，不创建重复精品店。
3. **精品入池前置条件**：除非人工强制加入并立刻抓取，否则必须已存在成功的 `shop_products` 快照；从候选池入精品必须已 `FETCHED`。
4. **精品复抓复用同一抓取链路**：`trigger_type=PREMIUM_REFRESH`，走 `shop_fetch_run`、2 秒限速、原子抢锁和请求次数统计。
5. **复抓计划先手动**：`next_fetch_date` 第一版只是建议复抓日期和筛选条件，不先做自动定时任务，避免批量无控制地消耗使用次数。
6. **画像必须绑定快照**：店铺画像默认展示最新成功快照，但页面必须显示 `batch_code / batch_date / source_run_id`；
   切换批次时指标、商品墙、类目和明细必须同源刷新。
7. **历史对比定义固定**：以 `product_key=COALESCE(parent_asin, asin)` 判断新增、消失、保留；等级变化只在保留商品上计算。
8. **多店同上先可解释**：优先消费商品族证据；没有商品族时使用临时规则键并返回规则说明，不做不可解释黑盒相似。
9. **方法卡线索不直接落正式方法卡**：多店同上结果只能生成“市场信号/方法卡草案线索”，后续人工确认后再升级为正式方法卡。

### 八、Docker 开发模式整理（同晚）

#### 8.1 根因

ports are not available ... bind: An attempt was made to access a socket in a way forbidden by its access permissions

同时发现 `java-product` 被历史 one-off 容器占用，宿主端口为 `8400->8002`，不符合当前 `docker-compose.dev.yml`；`dev-celery-worker` 实际可 ping，但 healthcheck 查询了错误节点名 `celery@HOSTNAME`，导致长期 unhealthy。

- `docker-compose.dev.yml`：统一开发宿主端口为 `5175`、`18090`、`18001`、`18002`，容器内部端口保持 `5175/8090/8001/8002`。
- `docker-compose.dev.yml`：Celery healthcheck 改为 ping `worker@$$HOSTNAME`，匹配启动命令 `-n worker@%h`。
- `config/ports.json`、`config/public/dev.env`：同步开发端口登记、`BACKEND_PORT`、`FRONTEND_PORT`、CORS。
- `docs/docker使用经验/`、`docs/架构/端口.md`、`AGENTS.md`：同步当前开发入口，移除不存在的 gateway/nacos profile 启动说明，补充 Windows 端口保留段说明。
- 清理旧运行态：移除历史 one-off `java-product` 和失败检查容器 `java-check`，再按 compose 重建标准 Java 服务。

## 领星 6 标签 SKU 信息获取：尝试与踩坑全记录（2026-07-09 补记）

> 目标：从领星拿到打了 6 个目标 Listing 标签的 SKU 级产品表现数据。
>
> 6 个目标标签：
> `绿标`、`欧洲精铺2025`、`欧洲精铺2025非标品`、`欧洲精铺2025季节性断货`、`欧洲精铺2025待淘汰`、`欧洲精铺2025淘汰`

### 一、两条数据线，两个表

先搞清楚系统里有两条完全独立的产品表现数据线，不能混：

| 数据线 | 表 | 数据来源 | 标签字段 |
|--------|----|---------|---------|
| 领星 API 同步 | `lingxing_product_performance` | 领星 `productPerformance/asinList` 接口 | ❌ 无（接口不返回 listing_tags） |
| Markdown 导入 | `product_performance_actual` | 领星后台导出 Markdown 表格 → 解析入库 | ✅ `listing_tags` 列（第 16 列） |

`ProductPerformanceServiceImpl.importFromMarkdown` 解析 Markdown 时直接读第 16 列的标签文本：
- `containsTag(listingTags, "淘汰")` → `is_eliminated=1`
- `containsTag(listingTags, "绿标")` → `is_green=1`
- `containsTag(listingTags, "非标品")` → `archetype=CUSTOM`，否则 `STD`

这条线是**独立的手动导入链路**，和领星 API 实时同步无关。

### 二、领星 API 的硬限制：不支持按标签筛选

领星 `productPerformance/asinList` 接口的请求参数只有：

```json
{
  "sid": [店铺ID列表, 上限200],
  "start_date": "YYYY-MM-DD",
  "end_date": "YYYY-MM-DD",
  "summary_field": "asin|parent_asin|msku|sku",
  "offset": 0,
  "length": 1000,
  "sort_field": "volume",
  "sort_type": "desc",
  "currency_code": "USD|CNY"
}
```

**没有 `listing_tag`、`label`、`tag` 之类的筛选参数。** 这意味着：
- 无法直接问领星"给我所有绿标 SKU 的产品表现"
- 只能按店铺集合（sids）+ 时间窗拉全量，然后自己在本地按标签筛选
- 但领星接口返回的字段里也**没有 listing_tags**——标签信息根本不在这个接口的响应里

### 三、尝试路线与结论

#### 路线 A：Markdown 导入（已验证可用）

流程：
1. 在领星后台按 6 个标签筛选 → 导出 Markdown 表格
2. `POST /api/v1/product-performance/import` 传入文件路径
3. `ProductPerformanceServiceImpl` 解析 18 列表格，标签在第 16 列
4. 落库 `product_performance_actual`，同时做标签判断（淘汰/绿标/非标品）

**结论**：这是唯一能拿到「打了标签的 SKU + 产品表现数据」的路径。但它是手动导出→导入的离线流程，不是实时 API。

#### 路线 B：领星 API → lingxing_product_performance → 再关联标签（不可行）

想法：先用 API 拉产品表现到 `lingxing_product_performance`，再通过 ASIN/SKU 关联标签。

问题：
- 领星 API 不返回 listing_tags
- `lingxing_product_performance` 表没有标签字段
- 标签信息在领星系统里属于"本地产品"的属性，走的是 `productList` 接口（`lingxing_local_product` 表），但那也只有产品基础信息，不一定包含自定义标签
- 即使 `lingxing_local_product` 有标签，跨表 ASIN 关联也会因为一对多（一个 ASIN 多个店铺）而放大

**结论**：不可行。标签和产品表现分属两个接口，领星 API 不做 join。

#### 路线 C：先拉全量 UK+DE 产品表现，前端按标签筛选（已落地，待前端接标签）

实际执行的路线：
1. 先同步领星店铺列表 → 拿到 UK+DE 的 sid 集合
2. 调用 `productPerformance/asinList`，传全部 UK+DE 的 sids，拉全量产品表现
3. 落库 `lingxing_product_performance`（28,015 条）
4. 后续在前端"产品表现"页加标签筛选，只展示 6 个目标标签的商品

**当前状态**：第 1-3 步已完成。第 4 步标签筛选未做——因为 `lingxing_product_performance` 本身没有标签字段，标签筛选的数据源是 Markdown 导入的 `product_performance_actual` 表。

### 四、结论：两条线各司其职

| 需求 | 数据源 | 方式 |
|------|--------|------|
| 实时产品表现数据（销量/广告/利润） | `lingxing_product_performance`（API 同步） | 按店铺+时间窗拉全量，不含标签 |
| 6 标签 SKU 清单 + 产品表现 | `product_performance_actual`（Markdown 导入） | 领星后台导出→解析入库，含标签 |
| 前端"产品表现"页标签筛选 | 应读 `product_performance_actual` | 该表有 `listing_tags` 列和 `is_green`/`is_eliminated` 标记 |

### 五、同步过程中的技术踩坑

在拉取 UK+DE 全量产品表现的过程中，陆续踩了以下坑：

| # | 问题 | 根因 | 修复 |
|---|------|------|------|
| 1 | `biz_key` 超长（VARCHAR(255)） | 138 个 sid 拼成字符串超过 255 字符 | SHA-256 固定 64 字符 |
| 2 | `sid_scope` 同样超长 | 同上 | 改用行内 `raw_json.sids`（每行只归属一个店铺） |
| 3 | 同批 `saveOrUpdateBatch` 里 biz_key 冲突 | batch 内同 ASIN 多店铺汇总产生相同 biz_key | 改显式 `INSERT ... ON DUPLICATE KEY UPDATE` |
| 4 | `@Insert` 绕过 MyBatis-Plus ID 生成 | `Field 'id' doesn't have a default value` | `IdWorker.getId()` 手动生成 |
| 5 | 领星限流 `3001008` 无重试 | 令牌桶容量 1，并行 UK+DE 竞争 | `sendWithRetry`（5 次递进退避 15s×attempt） |
| 6 | `103 请勿频繁请求` | 并行跑 UK+DE 触发 | 改为串行 UK→DE，中间手动等 30s |
| 7 | 并行 UK+DE 只返回 3000 多条 | 令牌桶竞争导致部分请求被截断 | 串行后 UK 19 页 + DE 13 页 ≈ 8 分钟，数据完整 |
| 8 | 中文国家名 WHERE 匹配失败 | 领星返回中文"英国""德国" | 改用 `region='EU' AND mid=4/5` 定位 |
