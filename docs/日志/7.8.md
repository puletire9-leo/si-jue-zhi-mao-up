## 店铺分析下一阶段：方法卡命中找店铺 + 店铺数据分表（2026-07-08，计划）

### 一、当前判断

数据基础和店铺画像辅助层已经基本闭合：

- `competitor_products_clean` 已经服务新品榜方法卡筛选。
- 郑总 UK/DE clean no variants 数据已导入系统。
- `shop-profile` 店铺画像、快照、基线、定位已跑通。
- A/B/C/D 销量分级、父体口径、郑总精铺结构画像已经验证。

但最终目标不是“画像好看”，而是：

```text
找到我们需要盯的店铺。
```

因此下一阶段主线回到：

```text
新品方法卡命中商品 -> 按店铺聚合 -> 找到高价值店铺 -> 再抓店铺全集 -> 用画像解释和跟踪。
```

### 二、三条数据线确定

#### 1. 新品榜数据：`competitor_products` / `competitor_products_clean`

定位：

```text
专门承接八爪鱼新品榜数据 + ASIN 卖家精灵补数。
```

口径：

- 可以含变体。
- 后续走 `competitor_products_clean` 去变体。
- M01/M03 等新品榜方法卡优先读 clean 表。
- `m01_active` 只是 M01 当前命中的性能标记，不再扩散成一堆 `mxx_active`。

要看的文件：

- `java-backend/sjzm-product/src/main/resources/mapper/MethodCardMapper.xml`
- `java-backend/sjzm-product/src/main/resources/mapper/CompetitorProductsCleanMapper.xml`
- `java-backend/sjzm-product/src/main/resources/mapper/ShopMethodRankMapper.xml`
- `java-backend/sjzm-product/src/main/java/com/sjzm/product/modules/shoprating/service/ShopMethodRankService.java`
- `java-backend/sql/add_m01_active_flag.sql`
- `java-backend/sql/backfill_m01_active.sql`

#### 2. 店铺观察池：`shop_watchlist`

定位：

```text
记录哪些店铺值得抓，以及为什么值得抓。
```

来源可以是：

- `METHOD_CARD`：如 M01 新品命中多。
- `BASELINE`：如郑总相似、自有优质店相似。
- `MANUAL`：人工加入。
- `CATEGORY`：类目专项观察。

建议字段：

```text
marketplace
seller_name
seller_id
source_type
source_code
reason
hit_count
top_category
status
last_fetch_run_id
created_at / updated_at
```

这张表回答：

```text
这家店为什么进入观察池？
它是因为哪张方法卡、哪个基线、哪个人工判断进来的？
```

#### 3. 店铺全集数据：`shop_products`

定位：

```text
专门承接卖家精灵“店铺名查询”返回的店铺商品全集。
```

关键原则：

```text
字段能力基本复制 competitor_products。
```

不是轻量表。因为店铺画像、店铺商品明细、方法卡解释、店铺上新流都需要和新品榜商品类似的完整字段能力。

建表思路：

```sql
CREATE TABLE shop_products LIKE competitor_products;
```

然后补店铺抓取专用字段：

```text
source_run_id
fetch_source
fetch_reason
watchlist_id
variation_mode
raw_json
first_seen_at
last_seen_at
```

口径：

- 卖家精灵店铺名查询固定 `variation=Y`。
- 即不含变体，直接对齐亚马逊店铺页面父体商品数量。
- 不再做 `shop_products_clean`。
- 但仍需要基础标准化：数值字段、`sales_tier`、`age_bucket/listing_days`、末级类目、`raw_json` 留底。

### 三、后续实现顺序

1. 新增 SQL：`shop_watchlist`、`shop_products`。
2. `shop_products` 先用 `CREATE TABLE LIKE competitor_products` 保证字段不缩水，再补店铺专用字段。
3. 卖家精灵店铺名抓取服务改为写入 `shop_products`，固定 `variation=Y`。
4. 方法卡店铺排名结果写入或同步到 `shop_watchlist`，记录进入原因。
5. 店铺画像 `shop-profile` 后续从 `shop_products` 读取，而不是混读新品榜表。
6. 单店详情展示：
   - 店铺为什么进观察池。
   - 该店命中的方法卡商品。
   - 店铺全集 A/B/C/D 分布。
   - A/ABC/D 类目结构。
   - 后续新增 ASIN 上新流。

### 六、代码审查后修正（同日）

审查发现两个会导致数据偏差的问题，已从代码层面修正：

1. `ShopProductSyncService` 店铺全集分页不再用 `inserted >= total` 判断结束。
   - 旧逻辑会把 upsert 更新行也算入 inserted，重复抓或部分更新时可能提前停止。
   - 新逻辑新增 `fetched`，按实际拉取 item 数与 `total` / `pageItems < pageSize` 判断是否继续翻页。

2. `ShopMethodRankMapper.selectM01ShopRanking` 不再直接 `COUNT(*)`。
   - 旧逻辑可能把同一父体 ASIN 跨周重复命中算多次，导致观察池 `hit_count` 虚高。
   - 新逻辑先构造 `base`：按 `marketplace + seller_name + parent_asin/asin` 去重，保留最新代表行。

如果 `total > 100` 但 `apiCalls = 1`，说明分页仍有问题，需要暂停继续抓取。

调用：

```http
GET /api/v1/modules/shop-collection/summary?marketplace=UK&limit=100
```

或前端打开：

```text
店铺分析 -> 店铺全集画像
```

预期：

- 能看到抓过全集的店铺。
- 商品数、A/B/C/D、ABC 稳定盘、D 测品池有值。
- `variationMode = Y`。

数据库可辅助核对：

```sql
SELECT sales_tier, COUNT(*)
FROM shop_products
WHERE marketplace = 'UK'
  AND seller_name = '填入店铺名'
  AND batch_date = (SELECT MAX(batch_date) FROM shop_products WHERE marketplace = 'UK')
GROUP BY sales_tier;
```

#### 10. 异常处理判断

如果卖家精灵返回：

```text
Your IP address is not allowed
```

说明是 IP 白名单问题，不是代码问题。当前外网出口 IP 要加入领星/卖家精灵对应白名单。

如果抓取接口报表不存在：

```text
shop_products doesn't exist
shop_watchlist doesn't exist
```

说明第 1 步 SQL 没执行到当前库。

如果观察池有数据但画像列表为空：

```text
说明还没有抓店铺全集，或 shop_products 当前 marketplace/batch_date 没数据。
```

如果商品数明显大于亚马逊店铺父体数：

```text
检查请求是否仍为 variation=Y；不要用 variation=N。
```
