## 集中式 AI 请求中心（python-ai/ai-center）

- 背景：调研 LiteLLM（官方仓库已浅克隆到 `python-ai/litellm-official`，MIT 许可、当前 main 声明 1.95.0）。结论是完整 LiteLLM 体量约 206MB/8895 文件，还带 Postgres/Redis/UI/Prometheus 与 Rust/Prisma 构建链，且 `reasoning_effort` 只会被压成 thinking 开/关、`user_id` 无透传保证，不适合整份 vendoring 进业务仓库。改为自建轻量 FastAPI 网关，底层复用 openai SDK。
- 新建 `python-ai/ai-center/` 独立服务：对外暴露标准 OpenAI wire `/v1/chat/completions`（含 `/api/v1/ai/` 别名），非流式返回 `ChatCompletion` JSON，流式返回标准 `data:{chunk}` + `data:[DONE]`，调用方继续用 openai SDK 只切 `base_url` + `api_key`，零改造。
- 分层：`config`（全部环境变量）→ `dependencies`（Bearer 内部鉴权，常量时间比较，未配 key 时 fail-closed）→ `providers/deepseek`（AsyncOpenAI 单例，`max_retries=0` 重试交调用方）→ `services/chat`（模型白名单 + 标准字段/`extra_body` 透传 + SSE）→ `api/v1`。
- 安全边界：ai-center 独占 `DEEPSEEK_API_KEY`；调用方仅持 `AI_CENTER_INTERNAL_KEY`，两者隔离。上游 401 转 502（避免误导调用方），429 带 `Retry-After`，日志只记 request_id/service/model/status/latency/token，绝不记 prompt 与密钥。
- 密钥统一走 `config/`：上游密钥 `config/secrets/*.env` 的 `DEEPSEEK_*`；内部鉴权新增 `AI_CENTER_INTERNAL_KEY`；`config/public/*.env` 新增 `AI_CENTER_BASE_URL=http://ai-center:8012` 与模型白名单。
- 部署：dev/prod compose 接入 `ai-center` 服务，不发布宿主端口、带 `/health` healthcheck、非 root 运行；`frontend/nginx.conf` 显式 404 拒绝外部访问 `/v1/chat/completions` 与 `/api/v1/ai/`；`.gitignore` 忽略两个 litellm 研究目录并豁免 ai-center 测试文件。
- 范围界定：本轮只建独立中心，不改任何现有 Agent。`selection-agent`（v1，无外部调用方）标记 `DEPRECATED.md`；`selection-agent-v2` 仍直连 DeepSeek，待后续单独迁移。
- 验证：Python 3.11 容器（与生产一致）内 pytest 15 项全通过（鉴权 401 / 模型白名单 400 / JSON mode / `extra_body`(thinking·user_id) 透传 / SSE 帧 + usage chunk / 建流前 400 / 建流后 error 帧 / 429+Retry-After / 502）；容器冒烟 health 200、无鉴权 401、非白名单 400；dev/prod compose 均解析出 ai-center。
- 待办：`config/secrets/dev.env` 的 `sk-7641fcef...` 在 Git 历史出现过需在 DeepSeek 控制台轮换；生产部署前用 `openssl rand -hex 32` 生成 `AI_CENTER_INTERNAL_KEY` 填入 `config/secrets/prod.env`。
