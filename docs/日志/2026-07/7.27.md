# 7.27

## AI 选品：新建 ai_selection 表 + 复用全部选品框架

### 改造目标

全部选品 → `/ai-selection` 共享 AllSelection 外壳，数据源换成 `ai_selection` 持久表。
AI 投递 / 手动导入 → 从 `shop_products` / `competitor_products_clean` 查到后写入 `ai_selection` 表。
批次 → 每次投递/导入生成一个 batch_id。

### 数据库

**文件**: `java-backend/sql/create_ai_selection_table.sql`
- `CREATE TABLE ai_selection LIKE competitor_products_clean` + ALTER 追加 5 列 + 4 索引：

```sql
ALTER TABLE ai_selection
  ADD COLUMN batch_id     VARCHAR(64)  NOT NULL COMMENT '投递/导入批次 UUID',
  ADD COLUMN batch_label  VARCHAR(255) DEFAULT '' COMMENT '批次名称',
  ADD COLUMN source_ref   VARCHAR(32)  DEFAULT '' COMMENT '来源表',
  ADD COLUMN pushed_by    VARCHAR(32)  DEFAULT '' COMMENT '投递人',
  ADD COLUMN pushed_at    DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '投递时间',
  ADD KEY idx_batch_id (batch_id),
  ADD KEY idx_batch_label (batch_label),
  ADD KEY idx_pushed_by (pushed_by),
  ADD KEY idx_pushed_at (pushed_at),
  ADD KEY idx_batch_id_pushed_at (batch_id, pushed_at);
```

- 已在 MySQL Docker 中执行并验证：batch 列 + 索引全部到位。

## 八爪鱼最新批次导入边界修复

- 根因：无真实 `lotNo` 的自动采集批次通过 `/data/all` 下载时，后端错误使用接口返回的历史累计 `total` 作为目标数量，导致最新批次 50,090 条却重新读取累计 287,753 条。
- 修复：继续导入八爪鱼已经自动采集完成的最新批次，不重新启动采集。后端以 `/cloudextraction/statuses/v2.currentTotalExtractCount` 作为本批次硬上限，只处理 `/data/all` 最前 N 条，到 N 立即停止；`/data/all.total` 仅记录累计量。
- 保护：数据接口总量或分页实际读取量少于 N 时任务失败，不按不完整批次成功收口；带真实 `lotNo` 的系统启动批次仍使用 `/data/lotno/all` 的实际批次总量。
