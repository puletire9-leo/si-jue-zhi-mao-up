- DE 以图识图存在 `TooManyRequests`，与本次榜单"导入 DB"链路无关。

### 根因一：手动导入状态没有正确展示

当前"导入 DB"调用 `POST /api/v1/modules/bazhuayu/trigger`，后端仅通过 `bazhuayuExecutor` 异步执行
`triggerAsync()`，不会创建 `BazhuayuRunStateService` 的运行态。

但前端导入后读取 `run-state` 并期望看到 `DRAINING`；该运行态只属于"启动云端一条龙"链路，
所以手动导入天然会显示 `IDLE`。前后端状态模型不一致。

### 根因二：初筛进度只在全部完成后写回数据库

`AsinImportService.createStreamingTask()` 创建任务时固定写入：

```text
task_status = RUNNING
total_count / pass_count / fail_count / skip_count = 0
```

每页处理的累计统计只保存在内存 `StreamingFilterContext`。只有全部分页完成后，
`finishStreamingTask()` 才一次性把真实统计写回 `asin_import_tasks` 并将状态改为 `READY`。

因此导入处理中任务表长期显示"总数 0"，且服务重启时会丢失未收尾的进度统计。

### 根因三：前端不轮询

八爪鱼控制台仅在页面加载和操作后调用一次 `loadOverview()`，没有对 `RUNNING` 任务定时刷新。
即使后端开始按页持久化进度，页面也不会自动更新。

### 根因四：生产日志 I/O 开销（待核实）

- 生产 Docker 日志实际输出 MyBatis DEBUG SQL 和整页原始 JSON 参数，体积很大。
- 代码侧 `sjzm-product/application.yml` 未设 `log-impl`；`application-prod.yml`（含 `NoLoggingImpl`）
  在单体根模块 `java-backend/src/main/resources/`，不在 `sjzm-product` 的 classpath 里。
  生产 `SPRING_PROFILES_ACTIVE=prod` 走 `sjzm-product` 微服务 jar 时应无 SQL 日志。
  若仍观察到 DEBUG SQL，说明运行镜像与当前代码不一致，需先核实。

### 全局单进程互斥锁（2026-07-13 铁律收口）

**背景铁律：** 卖家精灵调用绝对只能单进程串行，无论 ASIN 还是店铺，任意时刻绝不允许多进程/多线程/多实例并发。

**代码审核发现的破口：** `SellerspriteExecutionGate.acquire()` 只做分钟/月度配额和熔断检查，
不做互斥。请求中心后台 worker 走单线程池 `sellerspriteRequestExecutor`（core=max=1）自身串行，
但手动 `POST /tasks/{runId}/consume` 端点在 Tomcat HTTP 线程同步调 `consumeNext` → gateway，
可与后台 worker 并发；生产多实例时单线程池也只在单 JVM 内串行，跨实例无互斥。二者均违反铁律。

**修复：** `DefaultSellerspriteExecutionGateway.execute()`（全系统卖家精灵唯一 HTTP 收口点）
最外层加 Redisson 全局互斥锁 `sellersprite:execution:global-lock`：
- `tryLock(180s 等待, 90s 租约)`：worker 排队等待，持锁线程崩溃后租约到期自动释放防死锁。
- 锁内调 `executeLocked()`（原 `execute` 主体），包住配额检查 + HTTP 调用整段。
- 无论走哪条链路、多少线程、多少实例，卖家精灵同一时刻只有一个在途请求。
- 手动 consume 端点保留，但被全局锁自动串行化，不再能与 worker 并发。

**待部署：** 此改动需重新构建 `prod-java-product` 并滚动重启后生效（当前生产镜像尚未含此锁）。

### 并发计数与幂等收口（2026-07-13 代码审核修复）

**问题一：并发双计数（skipped_count 虚高）。** 手动 `/consume` 端点与自动 worker 若并发消费同一 run，
两个线程抢同一子项：一方 `claimRunning` 成功计 success，另一方 `claimed==0` 计 skipped，计数漂移。
- **修复：** `consumeNext` 加 per-run 内存互斥 `consumingRuns`（`ConcurrentHashMap.newKeySet()`）。
  同一 runId 同时只允许一个线程进入消费循环，第二个直接返回"正在被另一消费者处理"。
  原方法体改名 `consumeNextGuarded`。卖家精灵实际调用另有全局锁保证串行，此锁只防计数漂移。

**问题二：手动/通用创建路径并发重复建任务（重复扣费窗口）。**
`createTask` / `createManualAsinTask` 只做"查活跃任务→无则插入"的乐观检查，`idempotency_key`
无 UNIQUE 约束，并发同 key 请求会双双读到 null 各插一条。
- **修复：** 新增 `withCreateLock(idempotencyKey, action)`，用 Redisson 锁
  `sellersprite:request-center:create-lock:{key}` 串行化"查→插"。因创建方法是 `@Transactional`，
  锁通过 `TransactionSynchronization.afterCompletion` **延迟到事务提交后再释放**，
  确保第二个线程拿锁时已能查到前者插入的 run，杜绝并发重复创建。无事务时立即释放。
  `createTaskFromStreamingResult` 走的是 `selectByIdForUpdate` 行锁，本就安全，不受影响。

**问题三：手动 ASIN 幂等键顺序敏感。** `buildManualAsinIdempotencyKey` 对 `List asins` 用
`List.hashCode`，换序提交得到不同 key，绕过复用。
- **修复：** ASIN 先 `Collections.sort` 再入 hash，同批 ASIN 换序命中同一 key。

**待部署：** 与全局锁一并重新构建 `prod-java-product` 滚动重启。

### 稳定 2 秒请求间隔节流（2026-07-14 铁律补齐）

**背景铁律：** 卖家精灵请求必须稳定 2 秒/次，不管 ASIN 还是店铺。突发打满会触发限流导致中断。

**根因：** 新链路（请求中心 gateway）只做了全局锁 + 分钟/月度配额计数 + 熔断，**丢了旧链路
`AsinImportService` 的 `Thread.sleep(2000)` 稳定节流**。配额计数只保证"每分钟不超 40 次"，
但不保证请求间隔均匀——全局锁内两次请求可毫无间隔连打。生产实测请求间隔 5.3s/2.8s 不稳定，
task #174 重导时某批"结果未知"触发 `WAITING_RETRY` + `PAUSED_SYSTEM`，正是突发限流所致。

**修复：** `SellerspriteExecutionGate.acquire()` 末尾加 `enforceMinInterval()`：
- 常量 `MIN_REQUEST_INTERVAL_MS=2000`。
- Redis key `sellersprite:execution:last-request-ms` 记上次请求时刻（跨实例一致）。
- 与上次不足 2 秒则 `Thread.sleep` 补足。因 `acquire` 始终在全局执行锁内被调用，请求本就串行，
  sleep 补间隔不会造成并发问题。
- 节流作用在真实 HTTP 粒度：`doLookupAndSave` 每翻一页都是一次独立 `gateway.execute()`，
  各自过 acquire 各自被节流，翻页也被 2 秒隔开。
- Redis 读写失败不阻断请求（仅记录），节流是尽力而为的稳定层，全局锁+配额是硬保证。

**生产验证（2026-07-14）：** 重新构建部署后，日志确认请求间隔精确稳定在 2.000 秒
（09:36:28→30→32→34→36→38→40→42），task #174 重导 success 111 / failed 0 稳定推进。

### 新品榜读不到新链路数据：补清洗层收尾（2026-07-14）

**现象：** #174 重导完成、`competitor_products` 已写入 14940 行，但新品榜看不到。

**根因：** 新链路（请求中心 `doLookupAndSave`）写完 `competitor_products` 后，**缺了旧链路
`AsinImportService` 的两步导入收尾**：
1. `scoringService.updateWeekTags()` —— 给本周新数据打业务周标（`week_tag`）+ `is_current=1`。
2. `cleanLayerService.cleanWeekBatch(mp, weekTag)` —— 增量刷 `competitor_products_clean`。

结果 14900 行 `week_tag=NULL`。清洗 SQL `refreshByWeekTag` 有 `week_tag IS NOT NULL` 过滤，
NULL 数据被跳过（只会被 `refreshBatch` 归到 `month-W00` 占位批次）；新品榜/方法卡读 clean 表按当前周批次
查，故看不到。旧链路无此问题（导入 DONE hook 已调这两步）。

**根治（代码）：** `SellerspriteRequestCenterService.finalizeRun()` 末尾加 `finalizeCompetitorCleanLayer()`：
ASIN 类任务（`ASIN_BATCH_LOOKUP`/`MANUAL_ASIN_LOOKUP`/`ASIN_LOOKUP`）进终态且 `success>0` 时，
自动调 `updateWeekTags` + `cleanWeekBatch`，与旧链路一致。异常只记日志不影响任务完结。
店铺类任务走 `shop_products` 独立链路，不触发此收尾。已注入 `ScoringService`、`CleanLayerService`（无循环依赖）。

**补历史数据（#174 这批）：**
1. SQL 给 14900 行 NULL week_tag 打上 `2026-W29` + `is_current=1`。
2. 执行等效 `refreshByWeekTag('UK','2026-W29')` 清洗 → clean 表 W29 批次 9750 行（父体去变体后代表数）。
3. 验证 `GET /api/v1/method-cards/M01/products?marketplace=UK` 返回 total=284，新品榜可读。

### 请求中心闭环缺口系统审计 + 修复（2026-07-14）

借 #174 这次 clean 层缺失，系统对比新链路（请求中心）与旧链路（`AsinImportService`）的导入后收尾，
排查还有哪些同类闭环缺口（因请求中心将成为亚马逊数据统一入口）。审计结论：旧链路跨模块收尾只有
`updateWeekTags` + `cleanWeekBatch` 两件事（评分/店铺画像/m01_active 等本就不在导入收尾里），
但请求中心还漏了 3 处，全部修复：

**缺口 1（高）：`SELLER_BATCH_LOOKUP` 漏 clean 收尾。** 它同样用 `doLookupAndSave` 写
`competitor_products`，但清洗触发判定集合只含 ASIN 类，漏了它 → 卖家名批量数据进不了 clean 表，
新品榜看不到（与 #174 同类 bug）。
- **修复：** `isAsinLookupType` 改名 `writesCompetitorProducts`，成员改为
  `ASIN_BATCH_LOOKUP / MANUAL_ASIN_LOOKUP / SELLER_BATCH_LOOKUP`。

**缺口 2（中）：`MANUAL_ASIN_LOOKUP` 漏写 skip_asins「API已请求」。** 旧链路每批成功后把请求过的
ASIN 写 skip_asins，下次去重不重复扣费。ASIN_BATCH_LOOKUP 因初筛阶段已写 skip_asins（filterReasons=初筛PASS）
不受影响，但手动 ASIN 查询不经初筛，缺此环会重复扣费。
- **修复：** ASIN 分支 `doLookupAndSave` 成功后调 `markAsinsRequested(asins, marketplace)` 写
  skip_asins「API已请求」。注入 `SkipAsinMapper`，`insertBatchIgnoreDup` 幂等，重复写无害，异常不阻断。

**缺口 3（低）：`ASIN_LOOKUP` 死类型。** 它在清洗判定集合里，但 `consumeSellerSpriteItem` 无对应分支
（会落到默认 shop_products 分支），是历史预留常量。
- **修复：** 从 `writesCompetitorProducts` 集合移除，避免误导。
