## 生产计划：运营领星数据逐步迁移到远程 RDS

### 目标与执行边界

- 第一阶段只迁移运营物流使用的领星事实数据和运营进度结果，不切换整个 `sjzm-product`，
  不迁移选品、店铺、财务、Python/Celery 等其他业务数据。
- 远程目标固定为 RDS `sijuelishi`，不得写入用户中心使用的 `ai_platform`。
- 本节仅记录生产执行计划；本轮不连接 RDS、不执行 DDL、不复制数据、不修改生产环境变量、不部署。
- 生产执行由负责人按阶段逐项确认，每个阶段失败立即停止，不允许跳过校验继续切换。

- 暂停 `OPS_LOGISTICS_DAILY` 注册项，确认没有 `PENDING/RUNNING` 的运营物流任务。
- 记录本地 7 张表的行数、主键最大值、业务唯一键数量、最新业务时间和最新同步时间。
- 对本地 7 张表执行可恢复备份；备份文件必须保存在生产数据卷之外，并记录 SHA-256。
- 确认 RDS 连接使用独立环境变量和最小权限账号，密码只进入 Git 忽略的 secrets 文件。
- 禁止从文档复制明文凭证，禁止把 RDS 密码写入代码、SQL、日志或命令历史。

阶段门禁：备份不可恢复、存在运行中的运营任务或 RDS 权限不清晰时，停止迁移。

### 阶段 1：补齐 RDS 表结构

- 以当前代码和 `java-backend/sql/` 的运营物流迁移脚本为准，核对 RDS 7 张表，不使用 8 月 14 日旧结构快照直接覆盖。
- 重点核对 `ppg_sn`、可用量字段、SP 完整字段、唯一业务键、状态索引和时间索引。
- DDL 必须幂等；只允许创建缺失表、列和索引，不删除 RDS 现有表或数据。
- 完成后逐表比较列名、类型、可空性、默认值、主键、唯一键和普通索引。

阶段门禁：7 张表结构未完全一致时，不复制数据。

### 阶段 2：历史数据首次复制

- 按依赖顺序复制：采购计划 → 采购单 → 采购明细 → 本地仓批次 → SP 计划 → SP 实际 → 运营结果。
- 使用主键/业务唯一键幂等写入；首次复制不得清空或覆盖其他 RDS 业务表。
- 大表分批提交，记录每张表的读取数、写入数、跳过数和失败数；失败批次可以单独重跑。
- 复制期间生产运营链路仍写本地库，RDS 暂时只作为影子数据源，不对飞书和页面提供结果。

阶段门禁：任何表存在失败记录、唯一键冲突未解释或数据量不一致时，不进入增量追平。

### 阶段 3：增量追平

- 使用首次复制开始时间作为追平下界，再同步这段时间内新增或变化的采购、本地仓和 SP 数据。
- 采购单优先按 `update_time` 增量，并定向复查本地未完成采购单。
- 本地仓按业务日期同步，每个日期成功后记录游标，同日重跑默认复用。
- SP 实际按更新时间增量；SP 计划只按本轮变化 SP 的唯一 `seq` 获取，SKU 仅作无法关联时的补偿。
- 已发货终态数据不进入持续请求池，但历史记录必须完整保留在 RDS。

### 阶段 4：双读校验，不切生产写入

- 保持本地库为生产事实源，同时让校验程序分别读取本地和 RDS，比较相同时间窗的运营计算结果。
- 至少核对：总记录数、待到货/待发货/已发货数量、终态数量、采购量、入库量、可用量和有效 SP 数量。
- 必须抽查已知样本及新增、待到货、待发货、已发货四类记录，逐字段确认 PPG、SKU、状态和进度一致。
- 连续完成不少于 3 次增量同步且零未解释差异后，才能申请切换。

### 阶段 5：生产切换

- 再次暂停运营自动化，执行最后一次本地 → RDS 增量追平。
- 给 `sjzm-product` 配置独立运营 RDS 数据源，只将上述运营 Mapper/服务绑定到 RDS；
  默认产品数据源继续连接本地 MySQL。
- 先部署但保持 `OPS_LOGISTICS_DAILY` 停用，执行只读健康检查和一条人工运营任务。
- 验证领星原始事实、运营进度结果均写入 RDS，本地 7 张表不再新增或更新。
- 验证飞书只更新 source hash 发生变化的记录，已发货终态不再重复请求和写入。
- 人工验收通过后再恢复每日自动排期。

### 回滚方案

- 切换后本地 7 张表至少保留一个完整观察周期，不删除、不清空。
- 如果 RDS 连接、事务、数据一致性或任务耗时异常，立即停用运营自动化并把运营数据源切回本地。
- 回滚只切换数据源配置，不反向覆盖本地历史数据；RDS 异常期间产生的数据单独审计后再决定如何补回。
- 回滚后重新核对飞书绑定，防止同一业务键重复创建记录。

## 领星自动化请求注册与统一排期

### 现状核对

- 运营物流业务任务、三状态加工和飞书投递已经存在，但生产配置为
  `enabled=0`、`next_run_at=NULL`，此前只能人工触发，不能算完整自动运行。
- 现有 `lingxing_request_task` 已具备持久化队列、单 worker、状态和审计，
  但没有业务处理器，也缺少“哪个自动化在什么时间请求领星”的注册排期层。

### 本次实现

- 新增 `lingxing_automation_request_registry`：登记自动化任务、处理器类型、
  每日/每周/固定延迟周期、时区、优先级、错峰分组、槽位顺序、最小间隔、
  请求载荷、下一次执行时间和最近任务状态。
- 注册调度器每 30 秒扫描到期项，只向 `lingxing_request_task` 入队；不在调度
  线程直接调用领星。多实例通过注册行 `FOR UPDATE` 锁避免重复入队。
- 请求队列改为 `priority DESC, id ASC`，高优先级先执行、同优先级保持 FIFO；
  仍由单线程 worker 和 `LingxingClient` 账号锁双重保证不并发请求领星。
- 新增运营物流处理器 `OPERATIONS_LOGISTICS_PURCHASE_PROGRESS`，从请求中心
  进入自动化中心，复用运行审计、采购/SP 同步、数据处理和飞书幂等投递。
- `automation_job` 只保留 `MANUAL` 业务编排；实际周期统一由领星注册表控制，
  避免旧自动化调度和新请求调度重复执行。
- 默认注册 `OPS_LOGISTICS_DAILY`，每日 02:10，载荷固定开启 SP 同步；注册项
  默认停用，需完成数据库迁移、部署和人工验证后再启用。

## 运营物流自动化：PPG 创建批次号与 SKU 到货状态修复

### 8 月 SP 跨月错配修复

- 样本 `PPG260803001 / PO260803020 / SKU 2255766`：采购及入库 20，
  `SP260807043` 于 8 月 11 日实际发货 20，最新本地仓批次余额为 0；原结果却为
  `待发货`。
- 根因是 8 月任务只同步了 8 月 SP，却把 5 月、7 月采购收货也加入 FIFO，唯一的
  8 月 SP 被缺少历史 SP 配对的旧采购批次抢占。
- 修复为采购收货候选和任务使用同一 `startDate/endDate`，只在统一时间窗内按
  `SKU + 本地仓 + 入库时间` 分配 SP，避免不完整历史事实污染当前月份。

### 问题

- 飞书主列错误展示 `PO...` 采购单号；业务需要的是采购决策批次
  `lingxing_purchase_plan.ppg_sn`，即 `PPG...` 创建批次号。
- 状态计算直接使用采购单整体 `status_shipped`。同一 PO 中只要有其他 SKU
  未到齐，已经完整入库的 SKU 也会被错误标为“待到货”。
- 采购计划事实表停留在 8 月 11 日。领星采购计划接口传入带时分秒的日期时
  返回空结果，导致 `PPG260813018` 等新批次未同步。

### 修复

- `operations_logistics_purchase_progress` 增加 `ppg_sn`，由采购子项
  `plan_sn` 关联 `lingxing_purchase_plan.ppg_sn`。
- 飞书主字段“采购单号”原地改名为“创建批次号”，自动化改写 `ppg_sn`。
- 到货状态改为采购子项口径：无有效 SP 时，`received_quantity >=
  purchase_quantity` 为待发货，否则为待到货。
- FIFO 入库候选也按采购子项是否全部入库判断，不再要求整张 PO 全部到货。
- 自动化执行时同步采购计划，并将时间参数规范为 `yyyy-MM-dd`。

### 请求中心审计结论

- 项目原有 `modules/requestcenter` 是卖家精灵请求中心，不是领星请求中心。
- 原有领星同步由多个 Controller/定时任务直接调用，各调用链之间没有账号级全局串行门禁；产品表现服务仅在自身分页间等待 10 秒，无法阻止不同入口并发请求领星。
- 因此不能继续用独立 Python 脚本或多个同步接口并发拉取。正确方案是领星专用持久化任务中心：开始接口只创建任务并立即返回任务 ID，后台单线程按 FIFO 执行。
- 状态固定为 `PENDING/QUEUED → RUNNING → SUCCESS/FAILED`，任务结果需要记录排队、数据拉取、历史缺口补拉、落库、加工、飞书发布等阶段耗时。
- 同一天存在排队或运行任务时应返回原任务；终态后允许重跑，并按日期和人员/分类业务键原位更新飞书。
