# 8.18 运营物流双数据源改造 + 生产构建内存受限

## 一、背景

承接 8.17 规划：运营领星数据全链路迁移到远程 RDS `sijuelishi`。当前 sjzm-product 是单数据源（本地 MySQL 自动装配），运营 8 张表混在本地库、且都是无用测试数据。目标：RDS 建表 + 双数据源路由 + 增量请求链路 + 直接请求测试。

用户决策：
1. **全链路进 RDS**：运营 6 张领星事实表 + 运营进度结果表 + 游标表都走 RDS。
2. **跨库 JOIN 死代码暂时禁用**：采购 Mapper 里 JOIN 本地 `lingxing_target_sku_pool` 的未上线分析方法直接禁用。
3. 双数据源作为长期基础设施（后续还有多个"部分表走 RDS"场景）。

## 三、卡点：生产构建被宿主机内存拖死（未解决）

走唯一部署入口 `scripts/deploy/deploy_prod.ps1 -Component java`，构建在 `mvn clean package` 步骤反复崩溃：

```
failed to receive status: rpc error: code = Unavailable desc = error reading from server: EOF
```

**这不是编译错误，是 WSL2 后端被 OOM 杀掉**（Docker daemon 所在虚拟机崩了）。

根因是宿主机没内存，不是构建异常：
- 宿主物理内存 15.75GB，**空闲仅 0.3~0.9GB**。
- WSL2 上限 9GB，实测 vmmemWSL 已占约 4.7GB。
- 10 个生产容器基线约 4~5GB（prod-java-product 1.1GB、nacos 1.06GB、mysql 0.54GB 等）。
- Maven `spring-boot:repackage` 对 gateway/user/product 三个可执行模块各跑一次，峰值叠加超出可用内存 → daemon 崩。

已做的降峰措施：
- Dockerfile.prod 构建步骤从 `-T 4`（4 模块并行）改为 `MAVEN_OPTS="-Xmx1536m" mvn --offline clean package -DskipTests -T 1`（串行 + 限堆）。降低了峰值但仍不够。

两条待选出路（均未执行）：
1. 抬高 WSL 内存：改 `.wslconfig` 后 `wsl --shutdown`（会重启所有容器，生产需谨慎）。
2. 构建期间临时腾内存：`docker stop` 若干非关键容器（backend/celery/ai-center），构建完再 `start`（严禁 `down`）。
