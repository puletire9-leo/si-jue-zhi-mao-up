## 修复领星 refresh token 失效导致同步卡死（+ 拉齐7月完整数据 + 月度明细表）

### 事故现象
触发每周同步后，`lingxing_data_sync_run` 长时间 RUNNING，fetched/upserted 全 0，不推进。
日志反复刷：`领星 API 临时失败: 领星 API 错误 [2001009] refresh token is invalid，第N次重试，等待…ms`。

### 根因（LingxingClient token 管理 bug）
领星 token 机制：appId+secret 换 access_token + refresh_token；access_token 到期用 refresh_token 续约，**refresh_token 2小时有效且一次性**。

- access_token 过期 → `ensureToken()` 调 `refreshAccessToken()` 续约
- 但 refresh_token 也已失效（过期/用尽）→ 领星返回 **2001009**
- `isTokenInvalidCode()` **只认 2001001/2001002/2001005，没有 2001009**
- 于是 2001009 走 `sendWithRetry` 的通用 catch 分支，被当"临时失败"重试 8 次（30/60/…/240s，累计约20分钟），每次都失败（refresh_token 不会自己恢复）
- 8次耗尽才抛异常，`ensureToken` 才 fallback 到 `getAccessToken()`——但此时任务早已被人为超时/重启，留下僵死 RUNNING 记录

### 修复（LingxingClient.java 两处）
1. `isTokenInvalidCode()` 增加 `2001009`：refresh_token 失效码归为 token 失效类，抛 `TokenInvalidException` 快速处理，不进无限重试
2. `ensureToken()` 续约失败时先 `refreshToken = ""` 作废失效 token，再 `getAccessToken()` 换全新 token——避免下次还拿失效 refresh_token 续约

### 验证（2026-08-03）
重编 + `docker compose up -d` 重建容器（清掉僵死进程），清理残留 RUNNING 记录，重新触发同步：
- `领星 access_token 获取成功` —— token 自动换新，不再卡 2001009
- 中途 `领星 access_token 续约成功` —— 续约路径也正常
- 全流程 SUCCESS：店铺1497 → 本地产品38090 → 产品表现2935(7-27~8-02周) → 周表23861行(2026-W31) → 统一表6996 → 本地清理(11开发人,删20529) → listing7612 → 回填open_date 6996

### 附带产出
- 拉齐 7 月完整数据（补上最新周 7-27~8-02，此前缺）
- 补拉 7 月亚马逊 FBA 费：sidMskus 444→625（新周销量>10 ASIN 变多），覆盖 100%
- 7月明细表更新：423→598 行（`产品数据/产品表/理实产品开发表/fba配送费对比表/7月销量大于10_ASIN明细.xlsx`）

### 踩坑 + 修复
1. **出单率分子写错**：初版误把"截止月最后一周销量"当近30天销量（7天当30天用），出单率偏低约4倍。修复：分子改回整月 SUM(volume)，FBA 可售仍用月末周快照，两者拆成独立查询。

### 口径变化说明（非 bug，是升级）
1. **起算月漂移**：统一表 model_start_month 用 `listing_open_date`（真实上架日）替代旧的"商品创建时间兜底"（覆盖率更高更准，创建兜底归零），叠加含 7 月数据重算 → 部分 ASIN 批次归属变化。
2. **留存利润率整体下降**（合计 0.1428 → 0.1032）：**旧版利润率虚高**。旧版利润率 = 结算利润 / **结算销售额**（财务口径偏小分母，如 2132）；新版 = gross_profit / **amount 毛销售额**（如 2686，= 旧版"总销售额"）。同样利润除以更大分母 → 新版更低但**分子分母同源、更诚实**。

## 初筛规则升级：已采过 ASIN 上架<90天 + 导入超一月放行重抓（跨月批次并存）

### 需求背景
八爪鱼榜单每周采集 → 初筛 → 人工确认调卖家精灵。此前只要 ASIN 命中 `skip_asins` 就一律 SKIP_BLACKLIST 拦截，新品（上架<90天）首次采过后无法重复获取最新数据（价格/评论/BSR 随时变化）。
需求演进（用户明确）：**已采过 + 上架<90天 + 系统导入超一月** 的 ASIN 才放行重抓，作为**新月度批次**写入，旧批次保留、跨月并存，便于对比 ASIN 信息变化。

### 规则变化（两版）
| 版本 | 放行条件 | 说明 |
|------|---------|------|
| v1 | 已采过 + `listing_days < 90` | 初版，同月内也会放行重抓 |
| v2 | 已采过 + `listing_days < 90` + `skip_asins.created_at` 距今超 1 个月 | 收紧：同月内不重复获取，避免覆盖旧批次 |

### 判定顺序（新）
```
ASIN格式 → 文件内去重 → 硬性黑名单(历史淘汰) → 价格 → 评论 → 已采过放行判断 → 主表已有(SKIP_MAIN) → PASS
```
- 硬性黑名单 = `skip_asins` 中 `filter_reasons` 非 `API已请求`/`初筛PASS`（价格/评论/精筛淘汰）
- 已采过放行：`listingDays < 90` 且 `skipAsins.createdAt < now-1month` → PASS；否则 SKIP_BLACKLIST
- SKIP_MAIN 语义不变

### 跨月批次并存的实现（无需改唯一键）
`competitor_products` 唯一键 `uk_asin_month (marketplace, asin, month=yyyyMM)` 天然支持跨月并存。
请求中心 `createTaskFromStreamingResult` 里 `triggerRef.month = resolveDataMonth(初筛任务)` = 初筛创建月；重新采集发生在下月时初筛任务本身就是新月 → 写入新月 → 旧行保留、新行插入。
clean 层 `competitor_products_clean` 唯一键 `(marketplace, effective_week_tag, dedup_key)` 本就支持跨周快照并存（W29~W32 已验证）。
