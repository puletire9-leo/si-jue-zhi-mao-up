## 三、统一表上架时间口径改造（最终定稿 + 已部署）

### 需求（用户拍板）

统一表只保留**一个上架时间字段**，一眼看懂就是"真实上架日期"。计算方法写代码里，表里字段要简单。**首次获取后锁定不变**——上架日期确定了就不再改。

### 最终结构

字段：**`listing_date DATE`**（单一字段，真实上架日期）。旧的 5 字段全删（`fba_first_available_month/basis`、`listing_open_date`、`model_start_month/basis`）。

优先级（Mapper XML `LingxingProductUnifiedMapper.xml`）：

```text
新 ASIN（8月后首次进入）：
  listing.open_date（真实上架日，日级精度）
    → FBA可售首现月（周表首次 afn>0，补月初 -01）
    → 商品创建时间（product_create_time 前 10 位）
老 ASIN（8月前已存在）：保持现有值（原 FBA首现月，已迁移为 -01）
```

**为什么新老 ASIN 优先级不同**：亚马逊 `open_date` 会变（卖家调整页面就变），老 ASIN 只能用稳定的 FBA 首现（精度损失可接受）；8月后新增的 ASIN 首次获取 open_date 就锁定，之后不再改，能拿到日级精度。

### 写入机制（首次锁定）

- `rebuildAll`：只 INSERT 统一表还不存在的新 ASIN，此时计算 `listing_date`；
- `updateMetrics`：每周只刷新经营指标（销量/利润/快照），**不动 `listing_date`**；
- 删除了 listing 覆盖同步后的 `backfillUnifiedListingTime` 回填（避免 open_date 变动覆盖已锁定值）。
- 准入不变：仅 6 个目标标签 ASIN。

### 部署（2026-08-11 已完成）

- DDL：`migrate_unified_listing_date.sql`（加 `listing_date` → 迁移旧数据 `2026-05`→`2026-05-01` → 删 5 旧列 → 加索引）；
- Java：Entity/DTO/Mapper/Service 全改 `listingDate`（LocalDate），版本 `UNIFIED_V3_2026-08-11`；
- 前端：`lingxingShopData.ts`/`lingxingProduct.ts`/`queryRuntime.ts`/`lingxing-workspace` 改 `listingDate`；
- 验证：SchemaGuard 通过（67 表），7151 ASIN 全部有 `listing_date`（2024-11-01 ~ 2026-08-01）。

## 三-补、上架时间口径二次修正：4 信号取最早（V3→V4，已部署）

### 为什么又改

V3 上线后用户抽查 `B0H28Z1H64`：真实 5 月上架、6 月就卖货，V3 却记 **2026-08**。根因——V3 优先用 `open_date` 但**兜底仍是 FBA可售首现（afn>0）**，而 FBA可售**严重滞后**：货在途（调拨预留>0）、甚至已开卖（volume>0）时，`afn_fulfillable_quantity` 仍为 0，要等入仓可售才计数。此 ASIN afn 首现拖到 8 月。

影响评估：全表 7151 个 ASIN，**7048 个（98.5%）** 的 V3 值都因此偏晚。

### 新口径：4 信号取最早（用户拍板"哪个最早用哪个"）

`listing_date = LEAST(非空信号)`，精确到日：

| 信号 | 周表字段 | 取值 |
|------|---------|------|
| 1 FBA可售首现 | `afn_fulfillable_quantity > 0` | MIN(week_start) |
| 2 可用库存首现 | `afn + reserved_fc_transfers + reserved_customerorders + reserved_fc_processing + stock_up_num > 0` | MIN(week_start)（领星"可用库存"口径：FBA可售+待调仓+预留+入库中）|
| 3 销量首现 | `volume > 0` | MIN(week_start) |
| 4 创建时间 | `lingxing_listing.open_date` + `product_create_time` | 都参与取最早（不再只当兜底）|

验证 `B0H28Z1H64`：min(FBA可售 8/3, 可用库存 6/8, 销量 6/8, open_date 5/19, 创建 5/14) = **2026-05-14** ✓

### 踩坑

- `product_create_time` 有字面 `'null'`/空串，`STR_TO_DATE` 报 `Incorrect datetime value`。修复：`CASE WHEN ... REGEXP '^[0-9]{4}-[0-9]{2}-[0-9]{2}'` 先校验再转。
- 空信号用 `'9999-12-31'` 占位参与 LEAST，最后 `NULLIF(..., '9999-12-31')` 还原 NULL。

### 部署（V4）

- Mapper XML `rebuildAll`：新增 `sig_fba/sig_inv/sig_vol` 三个 CTE，`listing_date` 改 `LEAST(4信号 + 创建时间)`；`updateMetrics` 不动（锁定）。
- Service 版本 `UNIFIED_V3` → **`UNIFIED_V4_2026-08-11`**。
- 重刷历史：`tmp/refresh_listing_date.sql` 一次性 UPDATE 全表（修 7049 行）。
- 验证：SchemaGuard 通过，7151 全有值（2023-10-21 ~ 2026-08-04），`B0H28Z1H64=2026-05-14`。

## 六、4月新建SKU 备货情况跟踪（二/三次备货率 + 利润）—— 进行中

### 需求

### 口径（引用模型文档）

备货批次口径来自 [精铺测品二批转正模型.md](../../精铺模式模型算法/算每批sku的不同出单率的盈亏平衡点/精铺测品二批转正模型.md) §20：

- **一个有效采购单 = 一个备货批次**：`lingxing_purchase_order` + `lingxing_purchase_order_item`，按 `order_sn` 去重，排除作废单 `status IN (-1,124)` 和 `item.is_delete=1`，按 `order_time` 排序。
- Q1/Q2/Q3 量 = 各批次 `quantity_real`（实际采购量，非计划量 quantity_plan、非库存快照）。
- **二次备货率 = 有≥2批次SKU / 有采购(≥1批)SKU**；三次备货率 = ≥3批/≥1批；三/二转化 = ≥3批/≥2批。分母用"有采购记录的主SKU"，剔除无采购记录的（否则低估）。

### 组合SKU / 子件的判定（关键踩坑）

用户要求："子SKU不算，组合SKU算一个"（组合品才是要跟踪的单位，拆出来的子件不计）。

- **`lingxing_local_product.is_combo` 不可靠**：抽查用户举例的 2610111(组合「1加2」)/2610112(子「1」)/2610113(子「2」)，三者 `is_combo` 全是 0、`spu` 全 NULL、`aux_relation_list` 都只指向同一辅料 2270356，**彼此无父子引用**。本地产品表根本没存这个组合关系。
- **正解在采购计划表 `lingxing_purchase_plan`**：该表有 `is_combo` / `is_aux` 字段，全表 440 条计划 / 241 个组合SKU 标 `is_combo=1`（品名可见"2pc..."组合特征）。用户指认 `PPxxx` 采购计划号即组合SKU来源。→ **组合判定应以 `lingxing_purchase_plan.is_combo=1` 为准**，不是 local_product。
- 注：8月的采购计划（PP2608*）疑似未同步（查不到），但用 is_combo 字段判定不依赖具体计划号。

### 利润：一个SKU跨多国多ASIN怎么算

- 一个 `local_sku` 可能同时在 UK+DE 等多国、多个 ASIN 出单。按 `local_sku` 聚合（自动覆盖名下所有 ASIN），不按 ASIN。
- **核心难点是币种**：`lingxing_profit_asin.gross_profit` 各国记**本币**（UK=GBP、DE=EUR、其余 EUR/USD/PLN/SEK/CAD/MXN），直接相加错误。
- **领星无本位币(CNY)字段**：`profit_asin.raw_json` 全表 10055 行皆空，周表也只有 GBP/EUR 无统一币列。故**不做汇率换算**。
- 用户拍板："UK毛利(GBP)/DE毛利(EUR) 分两列展示，不相加"——保真，避免汇率误差。需人民币口径时另定固定汇率。
- **利润数据源选周表**：`lingxing_sku_weekly_performance` 经 `lingxing_listing`(asin) 映射，覆盖 437/619；`profit_asin` 仅覆盖 307 且金额异常小，弃用。

#### 技术口径（详见模型文档§21）

- **国家归属**：按采购批次创建人硬分（余江燕=DE，其他=UK）
- **批次归属**：`purchase_order_item.plan_sn` 反查 `purchase_plan.creator_real_name`，一个order多plan时取多数creator
- **利润归属**：周表销售按 `listing.marketplace`（英国/德国）直接归国，再按该国内批次序列分Q1/Q2/Q3（每国独立排序）
- **组合判定**：`purchase_plan.is_combo=1`（6个组合SKU算入分母）；辅料 `is_aux=1`（排除）
- **一次连接**：pymysql 直连3310端口，避免高频 `docker exec` 再次打爆WSL2

### 事故：高频 docker exec 打爆 WSL2 内存（第二次）

分析过程中用 Python 高频 `docker exec prod-mysql mysql` + 后台并发脚本，把 WSL2（限 9GB）打满，Docker daemon 卡死。已记入 [docker命令经验.md](../../docker使用经验/docker命令经验.md) 顶部铁律：**分析类查数据禁止高频 docker exec，改一次连接批量查（pymysql 直连 或 多条SQL拼一次 exec）**。用户暂不改 .wslconfig（16G 机器 9GB 已接近上限，加内存非解药）。
