# 优化模型（主线任务）

> 本文件只记录团队整体开品模型的长期思考、假设、验证方法和演进结论。
> 具体某一天要开发的页面或功能，记录在当日日志中，不与整体模型混写。

---

## 一、模型现状

| 环节 | 当前口径 |
|------|------|
| 开品节奏 | 每周 5 天滚动处理；开发当天完成并交运营，运营次日提交采购计划，采购审核后当天完成 |
| 规模 | 每月约 1000 个 SKU，月总量不因节奏改变 |
| 物流 | 下单后空运约 1 个月，到亚马逊仓后才能销售 |
| 数据成熟 | 开售首月数据不稳定，可信判断至少要再观察约 2 个月 |
| 反馈周期 | 从下单到可信反馈约 3 个月，具体组成仍需验证 |
| 原首批备货 | 10 / 15 / 20 件为主，平均约 15 件 |
| 新备货方向 | 根据开发评级分档配置 Q1：爆款、推荐、正常 |

正式流程来自 08.07 V2 优化方案：

```text
开发每天 17:00 前完成产品信息和对接表
    -> 开发主管 18:00 前复核并交运营
    -> 运营次日 10:00 前提交采购计划
    -> 采购审核后当天完成采购单
```

因此，业务口径应写成“每日开品、当天交接、次日采购”，不能笼统写成“开品当天下单”。

## 二、从每周 2 次转为每周 5 次的正确理解

月度总量仍约 1000 个时，每周 2 次约 125 个/次、每周 5 次约 50 个/次，只表示采购操作被拆细，不表示模型样本减少。

```text
操作批次：每天约 50 个，服务流程执行
统计样本：按 SKU、滚动窗口、周 cohort 或月 cohort 汇总
```

“每天 50 个导致统计噪声变大”只有在错误地把每天当成独立统计结论时才成立。稳定统计仍可按周/月合并，并按开发人、品线、评级和 Q1 分层。

单个 SKU 的可信反馈时间近似为：

```text
可信反馈日 = 实际采购日 + 物流/入仓时长 + 销售观察窗口
```

每周 5 次不能消除物流和销售成熟期，但能减少新品机会进入开品、复核和采购队列的等待。对于新品，提前几天可能改变竞品数量、评论差距、排名和热度，所以月总量相同不等于经营结果相同。

## 三、模型从批次复盘转为日流水反馈

旧方式容易形成：

```text
集中开一批 -> 等物流 -> 等观察期 -> 整批复盘
```

新方式应按每个 SKU 的相对年龄持续更新：

```text
发现机会
  -> 开品/采购
  -> 到仓/开售
  -> 7 天早期信号
  -> 14 天初步筛查
  -> 30 天补货或继续观察
  -> 60 天放量或淘汰倾向
  -> 90 天稳定经营反馈
```

稳定运行约 3 个月后，每天都会有一批 SKU 到达不同观察节点，模型从“定期复盘工具”变为“每天回流、每天校准”的持续系统。

## 四、新品时效模型

完整链路应从市场机会出现开始，而不是只从采购日开始：

```text
市场信号出现 -> 进入候选池 -> 开品决策 -> 采购 -> 到仓 -> 开售 -> 反馈
```

每个 SKU 至少记录：

```text
signal_date     新品市场信号日/首次发现日
candidate_date  进入候选池日
open_date       开品日
order_date      实际采购日
warehouse_date  到仓可售日
on_sale_date    首次开售日
```

核心时效指标：

```text
机会响应时长 = order_date - signal_date
团队处理时长 = order_date - candidate_date
供应链时长   = on_sale_date - order_date
```

模型需要比较同类新品在发现后 0-1 天、2-3 天、4-7 天、7 天以上采购时，90 天出单率、亏损率和回本率是否不同，以验证团队的时间优势。

## 五、开发评级与分档 Q1

08.07 V2 方案新增开发自评级：

| 评级 | 市场容量 | 市场竞争 | 产品优势 | 建议备货 |
|------|------|------|------|------:|
| 爆款 | 竞品月销大于 80；自发货大于 30 | 竞争者少于 4 个；FBA 卖家不多且上架时间短 | FBA、价格或款式优势明显 | 大于 30 |
| 推荐 | 竞品月销大于 30；自发货大于 10 | 竞争不大；新上架产品都有销量 | 在 FBA、价格或款式上有一定优势 | 15-30 |
| 正常 | 满足基础开品标准 | 按基础门槛审核 | 严控利润率和价格/款式优势 | 正常备货 |

正常档基础标准：

- 利润率目标 20%，并具备价格或款式优势；
- 客单价 4.99-15.99，原则上不超过 19.99；
- 标品上架 180 天以内，非标品不超过 300 天；
- 竞品月销量原则上超过 50，小微类目超过 30，自发货超过 5。

开发评级是开品前预测，不是产品最终事实：

```text
开品前：评级 + 判断依据 + 建议 Q1
开售后：7/14/30/60/90 天真实经营结果
最终：校准评级准确性和不同评级的合理 Q1
```

## 六、分档备货对原模型的影响

原模型中平均 Q1 约 15；新方案中爆款大于 30、推荐 15-30，Q1 变成由开发评级驱动的差异化资金配置。

- 评级正确：好品库存更充足，降低断货风险，更快获取销量和排名。
- 评级错误：爆款档失败品的库存损失会明显放大。
- 模型要求：把评级准确率加入 Q1 盈亏平衡，不能只比较不同 Q1 的总体出单率。

评级效果也不能直接用销量比较。爆款档库存更多，本身就可能带来更高销量。评估时必须同时控制：

```text
开发评级 + 建议 Q1 + 实际 Q1 + 品线 + 价格带
+ 上架年龄 + 断货情况 + 广告投入 + 90 天销量/利润/回本
```

应分开回答两个问题：

1. 开发评级是否真的判断得更准；
2. 多给库存产生的增量收益是否覆盖误判损失。

## 七、模型输出层级

| 层级 | 输出 |
|------|------|
| 实时层（每日） | SKU 年龄、7/14/30 天信号、库存和建议动作 |
| 运营层（周） | 品线、开发人、评级、Q1 的早期表现 |
| 经营层（月） | cohort 销量、亏损率、回本及 Q1/Q2/Q3 |

成熟度不足的 SKU 和月份不得与成熟 cohort 直接比较。

## 八、验证指标

| 模型部分 | 指标 |
|------|------|
| 流程 SLA | 17 点开发完成率、18 点交接率、次日 10 点采购计划完成率、采购当日完成率 |
| 新品时效 | 首次发现到采购、采购到开售、首次可信反馈中位数和 P90 |
| 评级分布 | 爆款/推荐/正常数量及占比，按开发人和品线拆分 |
| 评级校准 | 各评级 30/60/90 天出单率、亏损率、回本率 |
| 评级偏差 | 爆款未跑出率、正常实际跑出率、开发人评级偏差 |
| 备货执行 | 建议 Q1、实际 Q1、偏差原因和特殊审批 |
| 库存影响 | 断货率、首批售罄天数、滞销件数和资金占用 |
| 经济结果 | 每档总投入、回收余额、单 SKU 期望利润和失败品损失 |

## 九、待验证问题

- [ ] 确认首月数据不稳定是数据回写延迟还是新品真实爬坡。
- [ ] 用真实时间戳计算每周 2 次与每周 5 次的机会响应差异。
- [ ] 验证发现到采购时长与 90 天成功率的关系。
- [ ] 建立 SKU 年龄 7/14/30/60/90 天滚动输出。
- [ ] 明确爆款、推荐条件是全部满足还是部分满足。
- [ ] 把主观条件拆成可记录证据，减少不同开发人的标准漂移。
- [ ] 明确“正常备货”的实际数量区间。
- [ ] 计算爆款大于 30 件所需的最低评级准确率。
- [ ] 区分评级判断能力与增加库存带来的销量提升。
