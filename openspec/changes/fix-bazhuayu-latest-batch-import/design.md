## Context

当前链路先通过 `/cloudextraction/statuses/v2` 获取最新执行状态，并从 `startExecuteTime` 派生页面批次号。该接口对网页手动或八爪鱼定时启动的任务通常不返回内部 `lotNo`，而 `/data/lotno/all` 需要真实的长整型批次标识。系统主动调用 `/cloudextraction/start` 时能够取得真实 `lotNo`。

现有 `fetchBatchDataStreaming` 在无 `lotNo` 时退回 `/data/all`。该接口的 `total` 是任务历史累计存量，不是最新批次数量。当前实现以该累计 `total` 为读取目标，直接造成历史全量重读。仓库 7 月 20 日的旧策略曾以 `currentTotalExtractCount` 为 N，只读取 `/data/all` 最新前 N 条；后续为了兼容云端去重导致的计数差异，改成信任累计 `total`，但由此失去了批次边界。

开放接口的限制意味着：没有真实 `lotNo` 时，系统无法从 `/data/all` 数学上证明每一行都属于目标批次，只能依赖该接口“最新数据优先”的已验证排序契约。因此设计需要同时提供立即止损路径和长期精确路径，并清楚记录信任边界。

## Goals / Non-Goals

**Goals:**

- 一次“导入 DB”最多读取页面确认批次的 N 条数据，绝不按历史累计 `total` 扫描。
- 有真实 `lotNo` 时只读取该批次，并持久化可审计的批次标识。
- 点击导入与异步执行之间发生新批次切换时拒绝执行。
- 导入失败不产生 READY/SUCCESS 假象，重复点击同一配置同一批次保持幂等。
- 日志和前端能够区分 `EXACT_LOT_NO` 与 `LATEST_BOUNDED_SNAPSHOT`。

**Non-Goals:**

- 不猜测或伪造八爪鱼内部 `lotNo`，页面显示的时间批次号不是内部 `lotNo`。
- 不使用 `/data/notexported` 实现人工精品导入；该接口具有全任务游标副作用，且不能证明仅含一个批次。
- 不在本次变更中改造八爪鱼云端任务配置或关闭其现有定时计划。
- 不通过 ASIN 去重数量反推批次完整性；热销榜允许同 ASIN 多次出现，采集计数与存储行数可能不同。

## Decisions

1. **批次读取采用显式策略枚举。** 在批次快照或下载上下文中引入 `EXACT_LOT_NO`、`LATEST_BOUNDED_SNAPSHOT`，禁止通过 `lotNo == null` 隐式选择全量逻辑。日志、任务响应和前端均暴露该模式。

2. **真实 `lotNo` 始终优先。** 系统调用 `/cloudextraction/start` 后立即保存 `lotNo`，等待 Finished 后再次校验开始/结束时间，并使用 `/data/lotno/all` 分页。精确接口的 `total` 是该批次的实际存量，允许与 `currentTotalExtractCount` 因云端去重存在差异，但必须记录差值。

3. **无 `lotNo` 时恢复 N 条硬边界。** N 取二次校验后的 `currentTotalExtractCount`。`/data/all.total` 只用于记录 `cumulativeTotal`，循环终止条件固定为 `readCount == N`，最后一页必须裁剪到剩余数量，永远不读取第 N+1 条。该模式依赖已验证的“最新优先”排序契约，响应和日志标记为受限快照而非精确批次。

4. **批次校验执行两次。** Controller 接受页面批次元数据后同步校验一次；异步 worker 在任何数据写入前再次请求状态并校验批次号、开始时间、结束时间、数量与 Finished 状态。批次变化则将已创建的 QUEUED 任务置 ERROR，不切换到新批次。

5. **分页异常失败关闭。** N 大于零但 `/data/all` 在 N 之前返回空页、`restTotal` 提前归零、offset 不增长、响应缺失 `data` 数组，均抛出带任务、批次、N、已读数量的业务异常。是否允许“云端去重后实际少于 N”不能通过累计接口可靠判断，因此受限模式不把短读当成功；需要完整兼容该场景时必须取得真实 `lotNo`。

6. **写入保持流式但任务只有全链路完成后 READY。** 页面写入仍按现有事务/幂等键处理；异常时调用 `failStreamingTask`，不执行 `finishStreamingTask`。已写原始行可由既有唯一键承受重试，任务统计必须显示 ERROR 和实际已处理数量。

7. **产品入口引导精确模式。** 前端“导入 DB”显示目标批次和数量。若是系统启动链路，显示精确批次；外部批次显示受限快照。错误提示建议用户使用“启动采集”获得真实 `lotNo`，而不是提示重试全量读取。

8. **发布采用先止损、后增强。** 第一阶段修复后端 N 条硬上限和测试，可独立上线；第二阶段补模式字段、前端展示和可观测性；第三阶段用真实任务做只读分页探针和受控小批次验收。任何阶段都不得恢复按累计 `total` 导入。

## Risks / Trade-offs

- [无 `lotNo` 时最新批次实际存量少于采集计数] → 受限模式会失败而不是混入历史数据；用户改用系统启动采集的精确模式。数据安全优先于自动成功率。
- [`/data/all` 最新优先排序发生变化] → 上线前以非写入探针验证首尾样本；运行时记录模式与累计量。无法确认排序契约时关闭受限模式。
- [流式写入到中途才发现短读] → 任务标记 ERROR，依赖唯一键幂等重试；实现时评估是否能先拉取轻量批次清单或用临时 staging 降低部分写入。当前不引入大内存全量缓存。
- [用户继续使用八爪鱼网页定时启动] → 仍可使用受限快照，但 UI 明确其不是 `lotNo` 精确模式；关键任务建议迁移到系统启动。
- [前端旧版本不识别模式字段] → 新字段保持向后兼容；核心保护完全在后端执行。

## Migration Plan

1. 先部署后端止损：无 `lotNo` 时固定以最新批次 N 为硬上限，并补充失败关闭检查。
2. 在开发环境用模拟累计 `total=287753`、批次 `N=50090` 验证只消费 50,090 条且不请求下一页。
3. 部署模式字段和前端状态展示；旧前端仍可调用，但后端执行相同保护。
4. 在生产使用真实任务做只读探针，确认 `/data/all` 最新优先及分页 offset 语义；随后选择一个小批次执行人工导入，核对任务 raw/pass/fail 计数和数据库批次字段。
5. 推广“系统启动采集并导入”以获取真实 `lotNo`；监控受限模式使用量、短读错误和累计量差值。
6. 回滚应用时不得回滚到按 `/data/all.total` 读取；若必须回滚功能，则临时禁用无 `lotNo` 的人工导入，仅保留精确模式。

## Open Questions

- 八爪鱼是否存在可按 taskId 查询历史执行列表并返回真实 `lotNo` 的开放接口？若有，应优先增加解析器，将外部定时批次也升级为精确模式。
- `/data/all` 的“最新优先”是否为官方稳定契约，还是当前实测行为？生产启用受限模式前必须确认。
- 云端 `currentTotalExtractCount` 与 `/data/lotno/all.total` 的差值是否能从任务类型或状态字段稳定解释？该答案只影响完整性提示，不得放宽批次边界。
