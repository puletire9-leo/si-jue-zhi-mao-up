## Context

当前品线分析页面基于Vue 3 + TypeScript + Element Plus，通过SSE（Server-Sent Events）实现实时进度更新。现有架构存在以下问题：
- **状态管理简单**：仅用`isAnalyzing`布尔值控制分析状态，无法支持暂停/继续等复杂状态
- **无持久化状态**：分析状态完全依赖前端内存，页面刷新或断线后状态丢失
- **API设计局限**：后端仅支持启动和停止，不支持暂停/继续/选择性分析等操作
- **结果管理缺失**：无历史批次管理、对比分析、结果导出功能

技术约束：
- 前端：Vue 3 Composition API + Element Plus + TypeScript
- 后端：Python FastAPI + Celery（异步任务队列）
- 通信：SSE（单向推送） + REST API（请求-响应）
- 数据库：MySQL 8.0 + Redis 7

## Goals / Non-Goals

**Goals:**
- 实现完整的分析生命周期管理（暂停/继续/停止/断点续传/失败重试）
- 支持选择性分析（品类选择、增量分析、跳过已完成）
- 增强进度展示（预计时间、吞吐量图表、浏览器通知）
- 完善结果管理（历史批次、对比分析、多格式导出）
- 优化用户体验（空状态引导、暗色模式、响应式布局）
- 保持现有SSE通信机制的兼容性
- 确保分析状态的可靠性和一致性

**Non-Goals:**
- 不改变现有的SSE基本通信协议
- 不重新设计整个分析引擎（仅扩展前端交互）
- 不支持多用户并发分析同一批次（未来可扩展）
- 不实现复杂的权限管理系统

## Decisions

### 1. 分析状态管理方案
**决策**：采用有限状态机（FSM）模式管理分析状态
- **状态定义**：`idle` → `starting` → `running` → `paused` → `resuming` → `completed` / `failed` → `retrying`
- **存储位置**：前端Pinia Store + 后端Redis状态缓存
- **理由**：
  - FSM提供清晰的状态转换逻辑，易于维护和调试
  - Redis缓存确保状态持久化，支持断点续传
  - Pinia Store提供响应式状态，与Vue组件无缝集成
- **替代方案**：
  - 纯前端状态（不可靠，刷新丢失）
  - 数据库状态（过于复杂，延迟高）

### 2. 暂停/继续实现机制
**决策**：SSE + REST API混合方案
- **暂停**：前端发送REST请求 `/api/v1/analysis/pause/{taskId}`，后端标记任务状态
- **继续**：前端发送REST请求 `/api/v1/analysis/resume/{taskId}`，后端从断点恢复
- **SSE推送**：后端通过SSE推送状态变更通知前端
- **理由**：
  - REST API提供可靠的请求-响应，确保操作成功
  - SSE保持实时进度更新，用户体验连贯
  - 分离控制流（REST）和数据流（SSE），架构清晰

### 3. 选择性分析实现
**决策**：参数化SSE请求 + 后端过滤
- **前端**：提供品类多选组件，将选中品类ID列表作为SSE请求参数
- **后端**：解析参数，过滤分析任务队列，仅处理选中品类
- **增量分析**：后端对比数据库已分析记录，自动跳过未变化品类
- **理由**：
  - 参数化SSE保持现有通信机制
  - 后端过滤确保数据一致性
  - 增量分析减少重复计算，提升效率

### 4. 进度增强方案
**决策**：扩展SSE事件 + 前端计算
- **预计剩余时间**：基于历史分析速度和剩余品类数量计算
- **吞吐量图表**：前端使用ECharts绘制实时吞吐量曲线
- **浏览器通知**：使用Notification API，分析完成/异常时触发
- **理由**：
  - 扩展SSE事件保持向后兼容
  - 前端计算减少后端压力
  - ECharts提供丰富的图表功能，社区活跃

### 5. 结果管理架构
**决策**：历史批次表 + 前端对比逻辑
- **数据库**：新增`analysis_batches`表，记录批次元数据和状态
- **对比分析**：前端加载两个批次结果，使用差异算法高亮变化
- **导出功能**：前端生成PDF（使用jsPDF）/Excel（使用SheetJS）
- **理由**：
  - 数据库存储确保历史数据持久化
  - 前端对比减少后端计算压力
  - 纯前端导出无需后端支持，部署简单

### 6. 响应式布局方案
**决策**：CSS Grid + Element Plus响应式组件
- **桌面**：多列布局，完整功能展示
- **平板**：自适应列数，优化触控交互
- **移动端**：单列布局，简化非核心功能
- **理由**：
  - CSS Grid提供灵活的布局能力
  - Element Plus内置响应式组件，开发效率高
  - 渐进式增强，确保核心功能可用

## Risks / Trade-offs

### 风险1：状态一致性问题
- **风险**：前端状态与后端状态可能不同步（网络延迟、并发操作）
- **缓解**：定期心跳检查状态，冲突时以后端状态为准，前端强制同步

### 风险2：SSE连接稳定性
- **风险**：长时间分析可能遇到SSE连接断开
- **缓解**：实现自动重连机制，断线期间缓存事件，重连后重放

### 风险3：大数据量性能
- **风险**：历史批次对比可能因数据量大导致性能问题
- **缓解**：分页加载、虚拟滚动、差异算法优化

### 风险4：浏览器通知权限
- **风险**：用户可能拒绝通知权限，影响通知功能
- **缓解**：优雅降级，无权限时使用页面内通知，引导用户开启权限

### 风险5：移动端交互复杂度
- **风险**：平板/移动端的触控交互可能影响复杂操作体验
- **缓解**：简化移动端功能，提供清晰的操作引导，避免复杂手势

### 权衡点
- **功能完整性 vs 开发复杂度**：选择核心功能优先，非核心功能可后续迭代
- **实时性 vs 可靠性**：SSE提供实时性，REST API确保可靠性，混合使用平衡两者
- **前端计算 vs 后端计算**：前端计算提升响应速度，后端计算确保数据一致性，根据场景选择

2. **断点续传策略**：是保存每个节点的中间结果，还是仅保存小类级别的完成状态？
3. **增量分析算法**：如何判断品类是否"变化"？基于时间戳？数据版本号？
4. **通知策略**：哪些事件应该触发浏览器通知？完成？异常？特定关键节点？
5. **导出格式优先级**：先实现PDF还是Excel？用户更需要哪种格式？
6. **移动端功能范围**：移动端应该支持哪些核心功能？哪些可以简化或省略？

## 开发规范遵循

### 前端规范
- 新增组件放 `views/ProductLineAnalysis/components/` 下，PascalCase命名
- 新增API放 `api/` 下，使用 `utils/request.ts` 的axios实例
- 新增类型放 `types/` 下，禁止使用 `any`
- 样式用SCSS，变量在 `styles/variables.scss`

### 后端规范
- 新增API路径遵循 `/api/v1/{resource}/` 格式
- 使用FastAPI依赖注入，避免硬编码配置
- 异步任务使用Celery，确保任务可重试和状态跟踪

### 测试策略
- 单元测试：覆盖状态机逻辑、工具函数
- 集成测试：覆盖API调用、SSE通信
- E2E测试：覆盖核心用户流程（启动→暂停→继续→完成）
