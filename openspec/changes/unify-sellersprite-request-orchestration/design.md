## Context

卖家精灵的同一 `competitor-lookup` 外部接口目前由四套 HTTP 客户端分别调用：ASIN 竞品查询、店铺全集、邓总店铺和卖家名导入。请求中心已能管理部分 ASIN、候选池和精品复抓任务，但它管理的是任务表而非唯一执行通道；店铺同步仍可绕过它。

2026-07-13 的 UK ASIN 任务发生连接超时后，前五批触发熔断，旧循环仍继续把后续批次标记 `API_FAIL`。该事故暴露了错误分类、熔断状态、恢复语义和调用审计均未统一的问题。系统现有 MySQL、Redis/Redisson、Resilience4j、SchemaGuard 和请求中心的运行/子项表可作为改造基础。

## Goals / Non-Goals

**Goals:**

- 让 Java 产品服务中的每一次卖家精灵 HTTP 调用都通过唯一执行网关。
- 让所有面向用户或批量业务的卖家精灵调用都创建请求中心运行任务，并可在同一页面查看进度、失败原因、使用次数和恢复时间。
- 对网络、熔断、限流、鉴权、参数和上游业务错误给出可操作且不会误标的持久化语义。
- 在重启、暂停、停止、重试和多任务并发下避免重复扣费、重复写入和错误扩大。

**Non-Goals:**

- 不改变八爪鱼采集、下载、初筛和非卖家精灵数据处理的执行方式。
- 不替换卖家精灵 API，不推断或修复卖家精灵上游服务的可用性。
- 首期不实现跨区域多活调度；但限流与熔断状态必须不依赖单个工作线程。

## Decisions

### 1. 建立唯一的 SellerspriteExecutionGateway

所有 `/product/competitor-lookup` 调用改为通过一个网关执行。网关拥有唯一的 `HttpClient`、密钥获取、请求超时、请求脱敏日志、调用审计和异常映射；`SellerspriteApiService`、`ShopProductSyncService`、`DengZongShopService` 和 `AsinImportService` 不再自行构造 HTTP 请求。

网关返回类型化结果或类型化异常，至少区分：`CONNECT_TIMEOUT`、`READ_TIMEOUT`、`NETWORK`、`CIRCUIT_OPEN`、`RATE_LIMIT`、`AUTH`、`INVALID_REQUEST`、`UPSTREAM_ERROR` 和 `PARSE_ERROR`。调用审计记录请求是否已发出、是否收到卖家精灵成功响应、尝试次数、关联 run/item 和原始错误摘要。

备选方案是保留四个客户端，仅抽公共工具类；拒绝该方案，因为熔断、失败计数和恢复语义仍会分散。

### 2. 请求中心成为唯一的业务调度入口

请求中心扩展为所有异步卖家精灵业务的唯一入口，支持 `ASIN_BATCH_LOOKUP`、`MANUAL_ASIN_LOOKUP`、`SHOP_FULL_LOOKUP`、`CANDIDATE_BATCH`、`PREMIUM_REFRESH`、`DENG_ZONG_SHOP_SYNC` 和 `SELLER_BATCH_LOOKUP`。每个 item 用显式 payload 表达 ASIN 批次、店铺名、来源记录和目标写入域，避免以 `seller_name` 或 `trigger_ref` 隐式猜测。

原 `/competitor/lookup`、`/asin-import/execute`、`/asin-import/seller/execute`、`/deng-zong-shop/sync` 和候选池同步确认接口改为创建运行任务并返回 `runId`。兼容期内可保留路由，但不得直接执行外部请求。

备选方案是仅把八爪鱼 ASIN 加入请求中心；拒绝该方案，因为店铺链路会继续绕过熔断和统一审计。

### 3. 使用持久化的运行状态和失败策略

运行新增 `PAUSED_SYSTEM`，子项新增 `WAITING_RETRY`；子项持久化 `attempt_count`、`next_retry_at`、`error_code`、`error_summary`、`request_dispatched` 和 `usage_confirmed`。运行持久化系统暂停原因与恢复时间。

- 连接建立失败、DNS 临时失败和卖家精灵明确的短期限流可有限自动重试，使用指数退避和抖动。
- 读取超时或请求已发出但结果未知时不自动重复扣费；子项进入 `WAITING_RETRY`，由恢复策略或操作员明确重试。
- 鉴权、额度耗尽、参数校验和不可恢复的上游业务错误直接失败，并保留原始可读原因。
- 熔断打开时，当前 item 进入等待或系统暂停，所有待处理运行停止发起新请求；不得将未发出的 ASIN/店铺标记为失败。

备选方案是把熔断异常当成普通 item 失败并继续下一个 item；拒绝该方案，因为会重现 UK 任务的批量误标。

### 4. 全局限流与熔断门禁使用 Redis/Redisson 协调

网关通过 Redisson 协调卖家精灵全局分钟配额与熔断门禁，避免同一产品服务的多个 worker、重启恢复任务或未来多副本各自计数。MySQL 保留月度用量和不可变调用审计；Redis 门禁失效时以安全失败方式暂停新请求，而不是绕过限流。

Resilience4j 可继续用于单实例调用失败统计，但其 OPEN 状态必须同步为持久化/Redis 可见门禁，供请求中心和前端展示恢复时间。

### 5. 暂停、停止和重启按请求边界生效

暂停/停止在当前 HTTP 请求完成后生效，并在每个分页请求、重试等待和子项领取前检查。容器重启不将整个运行一律标记错误：未完成的 `RUNNING` 子项回收为可恢复状态；已发出但结果未知的子项进入人工确认的等待状态。

### 6. 迁移采用入口分批切换

先落地网关与请求中心状态模型，再迁移 ASIN 入口、店铺全集入口、邓总店铺和卖家名批量入口。每批迁移完成后，将旧入口改为创建同类 run，最后移除旧执行器与独立 HTTP 客户端。这样可以在每条业务链路上线后独立验证，不把未迁移入口静默丢弃。

## Risks / Trade-offs

- [统一入口改变同步 API 语义] → 保留兼容路由，返回 `runId` 和迁移提示；前端先完成跳转请求中心。
- [重试可能重复消耗卖家精灵额度] → 仅自动重试确认未建立连接或卖家精灵明确限流的情形；结果未知请求转人工/延后重试。
- [Redis 门禁不可用造成任务停滞] → 显示 `PAUSED_SYSTEM` 和明确错误；禁止降级为无门禁直连。
- [大店铺多页抓取无法立即停止] → 每页之间检查运行状态，UI 明确“当前页完成后停止”。
- [迁移期双入口重复执行] → 对来源任务、候选记录和店铺目标建立活跃运行幂等键，旧入口仅代理创建 run。
- [审计表增长与日志泄漏] → 审计保存脱敏元数据和截断错误，不记录完整密钥或整批 ASIN JSON；设置保留策略。

## Migration Plan

1. 添加请求中心状态、尝试和审计关联字段，以及卖家精灵全局门禁持久化/Redis 键的 SchemaGuard 迁移。
2. 实现网关、错误分类、Redisson 限流门禁和健康/熔断查询接口，并以小规模手工 ASIN 验证。
3. 迁移请求中心现有 ASIN、候选池和精品复抓消费者到网关，验证暂停、网络超时、熔断和重试。
4. 迁移通用竞品查询、ASIN 导入/重试、卖家名批量导入、邓总店铺同步和候选池旧确认入口。
5. 前端统一跳转请求中心，移除旧进度轮询和同步等待文案；执行前端构建、Java 编译及真实 UK/US/DE 验收。
6. 观察一个发布周期后，将旧执行器改为明确拒绝或移除；保留审计和回滚脚本。

回滚时保留新表和审计数据，停止新 worker，并将前端入口恢复到已验证的兼容代理；不得通过重启容器中断运行中的请求。

## Open Questions

- 卖家精灵是否提供可查询单次请求结果或幂等键，以判定读取超时后是否已计费？首期按结果未知处理。
- 自动重试次数、退避上限和操作员恢复权限是否需要按环境配置？首期应可由配置中心调整。
- 邓总店铺是否必须保留独立目标表，还是可在请求中心结果写入后由投影服务同步？首期保留独立目标表。
