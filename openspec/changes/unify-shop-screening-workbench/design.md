## Context

生产库当前有 1642 条观察池记录、1139 个 `shop_products` 店铺和 92649 条店铺商品。观察池接口返回全量列表；店铺详情接口固定最多查询 100/1000 个候选后在 JVM 过滤；旧店铺画像仍读取只有 44 个店铺的 `deng_zong_shop`，并使用 `batch_date` 日期批次。真实抓取链路已经把 ISO 周批次写入 `shop_products.batch_code`，因此三页的数量、批次和筛选结果不一致。

## Goals / Non-Goals

**Goals:**

- 三页统一读取 `shop_products` 店铺全集，并以 `batch_code` 周批次作为上层筛选批次。
- 商品条件先在数据库过滤，再按店铺聚合“通过筛选商品数”，支持服务端分页、筛选和排序。
- 观察池只在统一店铺筛选结果上叠加观察池成员信息，避免全量渲染和重复聚合。
- 店铺详情和店铺画像展示全部符合条件的店铺，不受固定 limit 或 JVM 后置过滤影响。
- 查询在现有生产数据规模下保持可交互，默认请求目标小于 1 秒，复杂组合筛选目标小于 3 秒。

**Non-Goals:**

- 不改变卖家精灵抓取和每店 10 次请求上限。
- 不重新定义 M01 商品规则；仅复用现有 `M01Rule`。
- 不删除 `deng_zong_shop`、旧画像快照或历史日期批次数据。
- 本期不实现新的店铺评分模型或 AI 推荐。

## Decisions

### 1. 建立单一店铺筛选分页接口

新增请求 DTO 和分页响应，输入包含站点、周批次列表、店铺名称列表/关键词、商品范围条件、店铺聚合条件、排序字段和分页。Mapper 在一个 SQL 查询中完成父体去重、商品筛选、店铺聚合和分页，并用独立 count 查询返回总店铺数。

选择数据库聚合而非先拉 1000/5000 条到 JVM，是因为后置过滤会漏店且耗时随店铺数线性增长。

### 2. 总商品口径与通过筛选口径分离

同一周批次中，`productCount` 表示店铺父体去重后的总商品数；`passedProductCount` 表示命中当前商品筛选模板的商品数。M01 命中数独立返回，用户可同时按 M01 和人工商品条件筛选。

### 3. ISO 周批次是三页唯一上层批次

列表和筛选统一使用 `shop_products.batch_code`（如 `2026-W29`）。未选择时默认最新可用周；支持多周合并。`batch_date` 和 `source_run_id` 继续用于单店快照详情，但不再作为三页列表的主筛选控件。

### 4. 三页共享筛选模型和组件

前端新增店铺筛选状态/composable 与共享筛选条，复用 `RangeFilterPanel` 的价格、销量、上架天数、BSR、重量、变体、配送、类目字段。三页只通过模式参数区分：全部已抓店、观察池成员、画像分析列表。

### 5. 正式观察池服务端分页

观察池不再调用返回全量实体的旧接口。统一筛选 SQL 通过 `EXISTS`/JOIN 限制观察池成员，并返回观察池 id、状态、来源和原因；更新/删除后只刷新当前页。

### 6. 索引与查询计划

补充 `shop_products(marketplace,batch_code,seller_name)`、`shop_products(marketplace,batch_code,listing_days,units)` 和观察池筛选所需组合索引。部署前后使用 `EXPLAIN ANALYZE` 和生产只读冒烟确认未出现全表临时排序放大。

## Risks / Trade-offs

- [复杂聚合 SQL 在多周大范围下仍可能昂贵] → 默认最新周、分页、限制最大页大小，并建立覆盖常用条件的索引。
- [多周合并时同一 ASIN 重复] → 按 `marketplace + seller_name + parent/asin` 选最新记录后再聚合。
- [旧画像快照与新实时画像字段不完全一致] → 列表统一实时工作台；物化快照入口保留在详情/基线页面，不混入主列表。
- [观察池存在同店多来源记录] → 统一筛选按店铺聚合，观察池元数据取最新记录并保留来源计数。

## Migration Plan

1. 新增 DTO、Mapper 查询、分页 API 和幂等索引迁移。
2. 为查询添加 Mapper/服务测试并在生产数据副本验证执行计划。
3. 上线共享前端筛选组件，先切店铺详情，再切正式观察池和店铺画像。
4. 构建部署后核对三页同站点同周的店铺总数和通过筛选数一致。
5. 回滚时保留新索引，仅把前端切回旧接口；历史数据不变。
