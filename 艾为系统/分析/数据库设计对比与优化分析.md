# 数据库设计对比与优化分析

> 生成日期：2026-08-13
> 对比对象：参考系统「艾为系统/sijue-main」(MidwayJS + TypeORM) ↔ 本项目「思觉智贸」(Java Spring Boot + MyBatis-Plus / Python FastAPI)
> 目的：结合我方现有表结构，找出冗余的表和代码，并提炼参考系统中值得学习的设计。
> 依据：均基于代码事实，标注文件/表名。

---

## 一、结论速览（TL;DR）

**我方冗余问题（按严重度）**
1. 🔴 **竞品宽表家族 6 张同构表**（Java）——`competitor_products` 的 ~60 列被克隆到 `ai_selection`/`brs_ranking_raw`/`premium_products`/`shop_products`/`deng_zong_shop`，其中 `ShopProduct`/`DengZongShop` 手抄字段未继承基类，字段漂移风险最高。
2. 🔴 **Python 无 ORM + 无迁移工具**——`backend/app/models/` 除 `system_log.py` 外全是 Pydantic DTO，真实表结构散落在 41 个裸 SQL 里，无 Alembic、无版本表、无序号，执行顺序靠文件名字母序。
3. 🟠 **领星表「注释说已删、代码还在引用」矛盾**——`lingxing_product_performance`/`target_sku_pool`/`sku_store_snapshot` 需实地对账。
4. 🟠 **一次性脚本污染**——Python 侧 7 个 `check_/debug_` 纯查询脚本混在 migrations；Java 侧 `sql/` 87 个脚本平铺，DDL 与 backup/audit/converge 一次性脚本混杂。
5. 🟠 **多版本演进冗余**——Python 侧 `add_grade_fields` vs `_fixed`、`init_scoring_system` vs `_simple` vs `create_scoring_tables`、`add_image_storage_fields` vs `_sijuelishi`（唯一差别是 `USE 库名` 硬编码）等。

**最值得从参考系统学习的 5 点**
1. 幂等防御性迁移（先查 `information_schema` 再建/跳）。
2. 复合唯一键做幂等 upsert（报表/缓存类表 8 列锁一条）。
3. `raw_data` JSON 兜底（宽表建模 + JSON 保底，第三方加字段不必改表）。
4. 统一 API 日志表模板（call_date/api_path/credit_count/duration_ms/is_success/caller/call_location）。
5. 错误日志带处理闭环（handledStatus + 处理人/时间/备注）。

## 二、参考系统（艾为/sijue-main）数据库设计

### 2.1 连接配置（`cool-admin-midway/src/config/config.prod.ts:47-75`）
- 单数据源 `default`，全走 `process.env.MYSQL_*`，DB 凭据零硬编码。
- 生产强约束：`synchronize=false`（注释"线上不要用，可能丢数据"）、`migrationsRun=false`（不随启动自动跑）、`dropSchema=false`、`logging=false`。
- `charset=utf8mb4`、`cache=true`（TypeORM 查询缓存）。
- 实体扫描 `['**/modules/*/entity']`（按模块目录约定）；迁移 `['dist/migration/*']`（注释强调不用 `**` 以免误匹配 src 下 ts）。
- 连接池未显式配置（用默认池）；Redis 走 `cool.redis` 与主库分离。
- CRUD 全局 `upsert:'save'` + `softDelete:true`（框架级全局软删除，`config.default.ts:225-230`）。

### 2.2 实体基类与约定
- `BaseEntity`(@cool-midway/core) 提供：`id`(自增) + `createTime` + `updateTime`（均 `datetime(6)` 微秒，`updateTime` 带 `ON UPDATE` 自动刷新）。
- 表名装饰器显式指定，前缀 `app_amz_`（业务）/`app_`（日志）。
- ⚠️ 字段命名蛇形/驼峰混用（历史演进，老表 `seller_sku`、新表 `storeId`），无强制统一——**反面教材，不照搬**。
- JSON 字段大量用 `@Column({type:'json'})` 且用 TS 接口强类型标注。
- 唯一键两种写法：单列字段级 `@Index()`；复合 `@Index('uk_xxx',[...],{unique:true})`。

### 2.3 迁移机制（`src/migration/`，约 50 个 `{timestamp}-{描述}.ts`）
- 实现 TypeORM `MigrationInterface`（up/down），`@Provide()` 接入 IoC。
- **幂等防御**（范例 `1780629000000-app-error-log.ts`）：建表前查 `information_schema.TABLES`，加索引前查 `information_schema.STATISTICS`，改唯一键前把 NULL 兜底成 `''`。
- 迁移里顺带维护菜单/权限表（把新页面挂侧边栏），down 对应清理。
- `migrationsRun=false`，需手动执行（配合生产安全）。

### 2.4 典型表设计范式
| 范式 | 代表表 | 要点 |
|------|--------|------|
| 超宽表 + raw_data 兜底 | `lingxing_profit_report_msku`(600+ 财务列) | 全平台费用平铺 + `raw_data`/`totalSum` JSON 保底；8 列复合唯一键幂等 |
| EAV 通用维度表 | `lingxing_product_performance_asin` | `summary_field`+`primary_value` 一表承载 asin/父asin/msku 多维度，避免维度爆炸 |
| 缓存表 | `bsr_sales_cache_lingxing` | JSON 存时间序列 `Record<"2026-01",{value,updated_at}>`；`promotion_last_sync` 时间戳与内容解耦 |
| 统一 API 日志 | `app_sellersprite_api_log`/`app_oxylabs_api_log`/`sif_api_log` | 同构模板：call_date/api_path/credit_count/duration_ms/response_code/is_success/error_message/caller/call_location |
| 错误日志闭环 | `app_error_log` | source/level/module/stack + `handledStatus`+处理人/时间/备注，8 索引 |
| 轻量去重登记 | `bsr_deduplicate` | `@PrimaryColumn(asin)` 业务主键，`source` 用 enum |

## 三、本项目现状盘点

### 3.1 Java 后端（sjzm-product/sjzm-user，约 68 个实体）
- **主键三种混用**：雪花 `ASSIGN_ID`（竞品宽表系/shop_products/lingxing_product_unified）、`AUTO`（shops/store_ratings/seller_profiles/analysisbaseline 全系/category_baselines）、SQL 层 `AUTO_INCREMENT`。
- **时间字段三种风格**：竞品系 `created_at`/`updated_at`(FieldFill)；领星 SQL 层 `DEFAULT CURRENT_TIMESTAMP ON UPDATE`；User 混用 `createdAt`(String)+`updatedAt`(LocalDateTime)。
- **无统一软删除** `is_delete`；`ShopPremiumPool` 用 `status=REMOVED` 手工软删，回收站在 Python 侧。
- JSON 用 `LONGTEXT`/`TEXT` 存原始报文（非 MySQL 原生 JSON）。
- 核心分片维度 `(marketplace, asin, month)` / `week_tag` / `batch_date`；领星采购/表现用 `CHAR(64)` SHA-256 `biz_key` 幂等。

### 3.2 Python 后端（backend，FastAPI）
- `app/models/` 10 个文件里 **9 个是 Pydantic DTO**，仅 `system_log.py` 是真 SQLAlchemy ORM（且列名 camelCase `createdAt`，与全项目 snake_case 不一致）。
- 真实表结构定义在 `migrations/*.sql` 裸 SQL。
- DTO 字段靠几十个 `alias="productTitle"` 手工对齐 SQL 列名，改列名无编译期保护。

## 四、冗余的表与代码（可清理清单）

### 4.1 Java —— 竞品宽表家族（最大冗余源）🔴
6 张表共享同一套 ~60 列结构：

| 表 | 来源 | 实体关系 |
|----|------|----------|
| `competitor_products` | 基表 | 基类 `CompetitorProduct` |
| `ai_selection` | `LIKE competitor_products_clean` | extends ✅ |
| `brs_ranking_raw` | `LIKE competitor_products` | extends ✅ |
| `premium_products` | `LIKE competitor_products` | extends ✅ |
| `shop_products` | `LIKE competitor_products` | **未 extends，字段全量手抄** ⚠️ |
| `deng_zong_shop` | 手写，字段镜像竞品宽表 | **既不 LIKE 也不 extends** ⚠️ |

> **建议**：`ShopProduct`、`DengZongShop` 改为 `extends CompetitorProduct`。基表加字段（如 `salesTier`/`m01Active`）时这两个手抄实体极易漏同步。

### 4.2 Java —— 领星表矛盾与孤儿 🟠
- **矛盾**：`LingxingSkuDataLayerMapper` 注释称 `lingxing_product_performance`/`target_sku_pool`/`sku_store_snapshot` 已删，但 `LingxingProductPerformance` 实体+Mapper+SyncService+Controller 仍在用，`LingxingSkuWeeklyMapper.xml` 仍 `FROM lingxing_product_performance`。→ **实地 `SHOW TABLES LIKE 'lingxing_%'` 对账**，清死 SQL 或修正过时注释。
- **孤儿表**（有建表 SQL 无实体）：`sku_pool`（零引用，高度疑似废弃）、`lingxing_data_sync_run`、`lingxing_sku_weekly/monthly_performance`、`lingxing_target_sku_pool`、`lingxing_purchase_plan/_order/_order_item`、`lingxing_developer_fba`。
  - 注：领星走"薄 Mapper + 手写 SQL"是有意设计（加工/同步表非 CRUD 对象），本身不算 bug；`sku_pool` 最可疑。
- **SQL 脚本冗余**：`create_competitor_products_clean_view.sql`（v1 VIEW，已废弃）与 `create_competitor_products_clean_table.sql`（v2 物化表，权威）并存；`migrate_unified_listing_time.sql`（被 `migrate_unified_listing_date.sql` DROP 掉，已作废）。
- **建表脚本未回填迁移最终态**：`create_lingxing_product_unified.sql` 原始 DDL 仍写 `listing_time`/`listing_time_source` 及一批 `inventory_first_*`/`fba_*` 列，与实体（`listingDate DATE`）不符——**新环境按原始脚本建表会 schema 不一致，需更新建表脚本为最终态**。
- **一次性脚本堆积**：`backup_rbac_*`/`restore_rbac_*`/`audit_bazhuayu_*`/`cleanup_*`/`diagnose_*`/`converge_*`/`seed_nonstandard_carriers_*`。建议 `sql/` 拆 `schema/` 与 `oneoff/`。

### 4.3 Python —— 迁移目录冗余 🟠
**多版本演进冗余（确认可删）**
| 重复组 | 差异 | 处置 |
|--------|------|------|
| `add_grade_fields.sql` vs `_fixed.sql` | 前者 `ADD COLUMN IF NOT EXISTS`（MySQL8 部分不支持），后者 `INFORMATION_SCHEMA+PREPARE` | 留 fixed |
| `init_scoring_system.sql` vs `_simple.sql` vs `create_scoring_tables.sql` | 建同样两表，仅 upsert 写法不同 | 三选一，留 `create_scoring_tables.sql` |
| `add_image_storage_fields.sql` vs `_sijuelishi.sql` | 唯一差别 `USE sijuelishi_dev` vs `USE sijuelishi`（库名硬编码） | 合一，移除 `USE` |
| `add_original_image_metadata.sql` vs `_single.sql` | 逐条 ALTER vs 一条批量+索引 | 留 single |
| `init_database.sql` vs `init_database_dev.sql` | dev/prod 两份同结构 | 参数化库名后合一 |
| `fix_carrier_sku.sql` → `remove_carrier_sku.sql` | 先改 sku 允许 NULL 后直接 DROP 该列 | 归档（自我否定演进） |

**一次性排查脚本（应移出迁移目录）**：`check_columns/check_country_values/check_data/check_product_type/check_source/check_uk_source.sql`、`debug_country.sql`（纯 SELECT，无 DDL）。

**回收站表冗余模式**：`material_library_recycle_bin`/`carrier_library_recycle_bin`/`final_draft_recycle_bin` 各把主表字段整列复制。更优解：主表加 `deleted_at`/`deleted_by` 软删列，省掉三张影子表。

**模型职责重叠评估**：
- `material_library` vs `carrier_library`：字段高度重合（batch/developer/images/`local_thumbnail_*`×5/回收站结构一致），但语义不同（素材=设计物料，载体=物理产品），**不建议合表**，可把 `local_thumbnail_*` 5 字段下沉为共享 mixin。
- `product` vs `product_sales`：不重叠（后者是无表纯 DTO，实为 sales analytics，命名易误解）。
- `final_draft` vs `material_library`：字段几乎同源但属不同业务阶段（定稿 vs 素材），合表风险高。

**备份 dump**：`backend/backup/` 下 7 个整库 dump 已确认在 gitignore 内、未被跟踪（正确）。

## 五、值得学习并落地的设计改进

### 5.1 高优先级（直接收益）
1. **引入迁移工具**：Python 侧上 Alembic（用 `system_log.py` 已有 `declarative_base` 反向补齐 ORM）；Java 侧考虑 Flyway 统一版本管理。杜绝裸 SQL 字母序执行、幂等写法三种混用。
2. **幂等防御性迁移**（学参考系统）：所有 DDL 先查 `information_schema` 判断表/索引存在再建/跳；改唯一键前 NULL 兜底空串。使迁移可重复执行不炸。
3. **收敛竞品宽表家族**：`ShopProduct`/`DengZongShop` 改继承 `CompetitorProduct`，消除字段漂移。
4. **建表脚本回填最终态**：`create_lingxing_product_unified.sql` 等更新为迁移后真实结构。

### 5.2 中优先级（规范统一）
5. **统一 API 日志表**（学参考系统模板）：`competitor_lookup_log`/`product_click_log` 等升级为标准结构 `call_date/api_path/credit_count/duration_ms/response_code/is_success/error_message/caller/call_location`，服务于 API 用量看板与卖家精灵配额核算（呼应 memory「卖家精灵配额」概念）。
6. **raw_data JSON 兜底**：领星/卖家精灵等字段易变外部源，宽表之外保留 `raw_data` JSON，第三方加字段不必立即改表。当前用 `LONGTEXT` 存报文可平滑升级 MySQL8 原生 `JSON` 类型 + 生成列索引。
7. **错误日志处理闭环**：`system_log`/错误日志加 `handled_status`+处理人/时间/备注，从"只读"变"可运营跟进"。
8. **补齐唯一键防重复**：`seller_profiles` 应 `(marketplace, month, seller_name)` 唯一；`Product30DayNew`/`store_ratings` 确认唯一键（历史已出过重复，如 `add_marketplace_to_deng_zong_shop_unique_key.sql` 是补救）。
9. **主键策略统一**：同类业务表统一雪花或 AUTO，便于后续分库分表与数据迁移。

### 5.3 低优先级（可读性/长期）
10. **目录治理**：Java `sql/` 拆 `schema/`（权威建表）与 `oneoff/`（一次性脚本）；Python migrations 清出 check_/debug_。
11. **命名一致性**：修正 `system_log.py` camelCase、`User.createdAt`(String) 等历史包袱；坚持 CLAUDE.md 铁律统一 snake_case。
12. **缓存新鲜度解耦**（学参考系统）：缓存类表加独立 `xxx_last_sync` 时间戳字段，判断刷新无需解析 JSON。

## 六、参考系统的反面教材（不建议照搬）
- 字段命名蛇形/驼峰混用（历史演进遗留）。
- 600+ 列极端宽表（利润表）可读性差，raw_data 只能缓解不能根治列爆炸。
- 用 `varchar(2)` 存 "0/1" 布尔（应 tinyint）、重复注释字段等技术债。

> 核实说明：memory「baseline 已删除、lingxing_product_unified 替代」「competitor_products vs clean」均已核实——clean 是 v2 物化去重表，v1 VIEW 脚本已废弃。领星「已删表仍被引用」的矛盾需实地对账运行库确认。
