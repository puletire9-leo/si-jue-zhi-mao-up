# 艾为系统采购发货管理模块 - 整体架构分析

## 一、系统技术栈

### 后端（cool-admin-midway）
- **框架**: Midway.js（阿里开源的 Node.js 企业级框架）
- **ORM**: TypeORM（实体映射、Repository模式）
- **核心库**: @cool-midway/core（提供BaseService/BaseController/CoolController装饰器）
- **架构模式**: 分层架构（Controller → Service → Entity → Repository）

### 前端（cool-admin-vue）
- **框架**: Vue 3 + TypeScript
- **UI组件**: Element Plus
- **模块化**: cool-admin插件式模块系统

## 二、核心设计模式

### 1. CoolController 装饰器模式（后端）

```typescript
@CoolController({
    api: ['add', 'delete', 'update', 'info', 'list', 'page'],
    entity: AppAmzBsrPurchasePlanLingxingEntity,
    service: AppAmzBsrPurchasePlanLingxingService,
    pageQueryOp: {
        fieldEq: ['status', 'plan_sn'],           // 精确匹配字段
        keyWordLikeFields: ['sku', 'product_name'], // 模糊搜索字段
        addOrderBy: { createTime: 'DESC' }         // 默认排序
    }
})
```

**借鉴价值**：
- 通过装饰器自动生成CRUD接口，极大减少重复代码
- `pageQueryOp` 统一分页查询配置（我们当前每个Controller都手写分页逻辑）
- `api` 数组声明需要的标准接口，未声明的自动403

**对比我们的系统**：
```java
// 我们当前的写法（需要每个方法手写）
@GetMapping("/inventory-batch")
public Result<Map<String, Object>> listInventoryBatch(
    @RequestParam(defaultValue = "1") int current,
    @RequestParam(defaultValue = "50") int size,
    @RequestParam(required = false) String developer,
    @RequestParam(required = false) String dataDate,
    @RequestParam(required = false) String sku) {
    return Result.success(inventoryBatchService.query(current, size, developer, dataDate, sku));
}
```

**建议**：
- 考虑封装通用的 `@CrudController` 注解，减少样板代码
- 将 pageQueryOp 概念迁移到 MyBatis-Plus 的 wrapper 构建器

### 2. Service 层职责分离

**三层架构清晰**：
```
Controller (路由+参数校验)
   ↓
Service (业务逻辑+事务管理)
   ↓
Repository (数据访问+SQL封装)
```

**示例：批量发货Service**
```typescript
async submit(params: BatchShipSubmitParams) {
    // ① 幂等校验（client_submit_token）
    if (clientSubmitToken) {
        const existing = await this.batchRepo.findOne({
            where: { client_submit_token: clientSubmitToken }
        });
        if (existing) return this.buildBatchSubmitResult(existing, [], true);
    }
    
    // ② 数据展开和校验
    const detailDrafts = this.expandRecordsToDetailDrafts(records);
    this.validateSubmitDetails(detailDrafts);
    await this.revalidateCurrentShippableQty(detailDrafts);
    
    // ③ 创建批次主记录
    const batch = await this.createBatch(records, detailDrafts, ...);
    
    // ④ 创建明细记录
    const savedDetails = await this.createDetails(batch, detailDrafts);
    
    // ⑤ 按规则分组构建请求
    const requestGroups = this.buildRequestGroups(savedDetails);
    
    // ⑥ 分批提交到领星（带限流）
    for (const group of requestGroups) {
        await this.waitBeforeLingxingRequest(index);
        const result = await this.submitSingleGroup(group);
        submitResults.push(result);
    }
    
    // ⑦ 更新批次状态
    return this.finishBatch(batch, submitResults);
}
```

**借鉴价值**：
1. **幂等性设计**：`client_submit_token` 防重复提交（前端生成UUID，后端去重）
2. **分批+限流**：大批量操作自动分组 + 延迟控制（避免打爆第三方API）
3. **明确的步骤划分**：每个步骤独立方法，易测试易维护

**对比我们的系统**：
- 我们当前的 `syncDaily` 也有分页拉取，但缺少幂等token机制
- 建议：在所有大批量操作接口（同步/导入/批处理）加幂等token

### 3. Entity 设计模式

**状态枚举字符串化**：
```typescript
@Column({ 
    comment: '批次状态 submitting/success/partial_failed/failed',
    length: 30, 
    default: 'submitting' 
})
status: string;
```

**索引策略明确**：
```typescript
@Index('uk_bsr_batch_ship_batch_no', ['batch_no'], { unique: true })
@Index('uk_bsr_batch_ship_client_token', ['client_submit_token'], { unique: true })
@Index('idx_bsr_batch_ship_status', ['status'])
```

**借鉴价值**：
- 状态用**字符串枚举**而非数字（可读性强，数据库直接看懂）
- **在Entity上直接声明索引**（我们当前SQL和Entity分离，容易漏加索引）
- **唯一索引覆盖业务键**（`batch_no` + `client_submit_token`）

**建议**：
- 我们的 `LingxingInventoryBatchDetail` 可加 `@Index` 在 `dataDate` 和 `developer`
- 状态字段考虑从数字改为字符串枚举（如 `PENDING/IN_PROGRESS/COMPLETED`）

## 三、前后端交互模式

**后端返回**：

### 2. 分页请求标准化

**后端**：

**建议**：

### 3. 智能缓存 + 降级机制

**悬浮预览场景**（bsr_purchase_plan_lingxing.vue）：
```typescript
/**
 * 悬浮查看计划明细（带缓存过期与降级机制）
 */
@Post('/hoverDetails', { summary: '获取悬浮展示计划明细' })
async hoverDetails(@Body() param: any) {
    const result = await this.purchasePlanService.getPlanDetailsForHover(param.plan_sns);
    return this.ok(result);
}
```

**Service 实现逻辑**：
```typescript
async getPlanDetailsForHover(planSns: string[]) {
    // ① 先查本地缓存（1分钟有效期）
    const cached = await this.cache.get(`hover_${planSns}`);
    if (cached) return cached;
    
    // ② 缓存失效，尝试查领星API
    try {
        const fresh = await this.lingxingApi.getPlanDetails(planSns);
        await this.cache.set(`hover_${planSns}`, fresh, 60);
        return fresh;
    } catch (err) {
        // ③ 领星API失败，降级到本地数据库
        const local = await this.planRepo.find({ where: { plan_sn: In(planSns) } });
        return this.formatLocalDataForHover(local);
    }
}
```

**借鉴价值**：
1. **多级降级**：API失败→本地数据库→空结果（不让前端卡死）
2. **短时缓存**：高频悬浮操作不重复打API
3. **明确的超时策略**：1分钟缓存 + 3秒API超时

**对比我们的系统**：
- 我们当前直接查数据库，没有API调用和缓存
- 如果未来接入外部API（如领星、卖家精灵），可参考这个模式

## 四、数据同步策略

### 1. 双向同步模式

**本地→领星（创建采购计划）**：
```typescript
async createPurchasePlan(param: any) {
    // ① 调用领星API创建
    const lingxingResp = await this.lingxingClient.createPlan({
        sku: param.sku,
        quantity: param.quantity,
        ...
    });
    
    // ② 立即回写本地数据库
    const localRecord = {
        plan_sn: lingxingResp.plan_sn,
        sku: param.sku,
        status: lingxingResp.status,
        ...
    };
    await this.planRepo.save(localRecord);
    
    return lingxingResp.plan_sn;
}
```

**领星→本地（定时/按需同步）**：
```typescript
async syncPlansFromLingxing(planSns: string[]) {
    const planList = await this.lingxingApi.batchGetPlans(planSns);
    
    for (const plan of planList) {
        await this.planRepo.upsert({
            plan_sn: plan.plan_sn,
            status: plan.status,
            quantity_actual: plan.quantity_actual,
            is_deleted_remote: plan.deleted ? 1 : 0,
            synced_at: new Date()
        }, ['plan_sn']);
    }
}
```

**借鉴价值**：
- **创建即回写**：调用外部API成功后立即落库（避免数据漂移）
- **状态标记**：`is_deleted_remote` 标记领星侧删除（软删除，本地保留历史）
- **synced_at 字段**：记录最后同步时间，智能判断是否需要刷新

**对比我们的系统**：
```java
// 我们当前只有 领星→本地 单向同步
Map<String, Object> result = inventoryBatchService.syncDaily(date, date, null);
```

**建议**：
- 如果未来有"本地创建推送到领星"需求，参考这个双向模式
- 加 `is_deleted_remote` 和 `synced_at` 字段，支持智能刷新

### 2. 批量同步的限流策略

```typescript
async submit(params) {
    // ...
    for (let index = 0; index < requestGroups.length; index += 1) {
        await this.waitBeforeLingxingRequest(index);  // 🔑 关键：每批之间延迟
        const result = await this.submitSingleGroup(group);
    }
}

private async waitBeforeLingxingRequest(index: number) {
    if (index === 0) return;  // 第一批不等待
    const delay = 2000;       // 2秒间隔
    await new Promise(resolve => setTimeout(resolve, delay));
}
```

**借鉴价值**：
- **主动限流**：防止打爆第三方API（领星可能有rate limit）
- **索引判断**：第一批立即执行，后续批次间隔2秒

**对比我们的系统**：
```java
// 我们当前循环翻页时有 sleep(1500)
for (int pg = 1; pg <= totalPages; pg++) {
    JsonNode items = page.path("list");
    // ... 处理数据
    if (pg < totalPages) {
        Thread.sleep(1500);  // 🔑 间隔1.5秒
    }
}
```

**建议**：
- 继续保持我们的间隔策略（已经合理）
- 可提取为配置项：`lingxing.api.rate-limit-ms=1500`
