# 领星所需 SKU 池基线（2026-07-09）

> 2026-07-10 口径修正：本文的 6,560 只代表 `2026-W29` 当前快照的同步覆盖基线，不能作为 1~6 月历史 Cohort 的 SKU 池。历史模型必须使用各周当时符合 6 个标签的 point-in-time 快照；详见 `docs/精铺模式模型算法/数据体检日志/Q1出单率模型数据体检_2026-07-10.md`。

## 当前同步覆盖基线

当前所需 SKU 池基线是：

```text
lingxing_target_sku_pool active rows = 6,560
```

这个 6,560 是 `2026-W29` 当周同步任务的正确覆盖基线。不要把 SKU 单独去重后再作为当周覆盖基线；那会把同一个 SKU 在不同店铺下的数据合并掉，导致后续拉取和分析少数据。

它不是历史月份的正确基线。每周都会新增、淘汰和变更标签，历史 Cohort 必须使用该周当时的 `snapshot_week + marketplace + sid + sku` 集合。禁止把 W29 当前池反向套用到 1~6 月，否则会漏掉历史淘汰 SKU、混入后期新增 SKU，产生幸存者偏差。

## 基线适用范围

### 当前同步覆盖

本文的 6,560 仅用于验证 `2026-W29` 当前同步是否覆盖了当周全部目标 listing：

```text
2026-W29 + active + marketplace + sid + sku
```

当前周同步仍按该基线校验，不允许对 `sku` 单字段去重。

### 历史生命周期与 Cohort 分析

历史分析不能使用 W29 的 6,560 行作为固定 SKU 池。原因：

- 每个月、每周都会有新 SKU 上架；
- 失败或淘汰 SKU 后续会停售、删除或离开目标标签；
- 某些 SKU 后期才加入，不属于早期月份；
- 用当前池回看历史会漏掉失败样本，产生幸存者偏差。

历史分析需要两套按时间保存的事实：

```text
1. 当周目标 SKU 池快照
   snapshot_week + marketplace + sid + sku

2. 当月/当周领星商品实际表现快照
   period + marketplace + sid + sku + msku
```

历史池应保存“当时出现过和当时符合标签的对象”，淘汰或离开标签后不得删除其历史记录。

当前数据库只有 `2026-W29` 的目标池快照；因此 W29 可用于当前覆盖校验，不能作为 2026 年 1~6 月 Cohort、Q1 出单率或淘汰率的历史分母。

## 当前 W29 同步口径

表：

```text
lingxing_target_sku_pool
```

过滤条件：

```text
snapshot_week = 当前快照周
is_active = 1
```

业务键：

```text
snapshot_week + marketplace/mid + sid + sku
```

当前快照：

```text
snapshot_week = 2026-W29
```

当前基线 SQL：

```sql
SELECT COUNT(*) AS required_sku_rows
FROM lingxing_target_sku_pool
WHERE snapshot_week = '2026-W29'
  AND is_active = 1;
-- 6560
```

校验业务键不重复：

```sql
SELECT
  COUNT(*) AS required_sku_rows,
  COUNT(DISTINCT CONCAT(snapshot_week, '|', mid, '|', sid, '|', sku)) AS baseline_key_count
FROM lingxing_target_sku_pool
WHERE snapshot_week = '2026-W29'
  AND is_active = 1;
-- required_sku_rows = 6560
-- baseline_key_count = 6560
```

站点拆分：

| marketplace | required_sku_rows |
|-------------|------------------:|
| UK | 5,913 |
| DE | 647 |
| 合计 | 6,560 |

目标店铺拆分：

| marketplace | target_store_count | required_sku_rows |
|-------------|-------------------:|------------------:|
| UK | 13 | 5,913 |
| DE | 3 | 647 |
| 合计 | 16 | 6,560 |

周数据更新时按国家分组同步这 16 个目标店铺的 `summary_field=msku` 全量表现，然后再用 `snapshot_week + marketplace + sid + sku` 标记目标 SKU。不要把 6,560 行按 `search_value` 每 50 个拆批作为主链路；那只适合精确验证和小样本测试。

2026-04-08 ~ 2026-04-14 实测结果：

```text
目标 marketplace+sid+sku 覆盖 = 6,560 / 6,560
周表目标 listing 行 = 6,618
```

周表目标行比目标池多 58，是因为少量同一店铺同一 SKU 有多个 MSKU/ASIN listing；这是保留明细，不是覆盖错误。

## 禁止口径

不要用：

```sql
COUNT(DISTINCT sku)
```

原因：

- 同一个 SKU 可以存在于不同店铺。
- 不同店铺下的同一个 SKU 后续周数据、月数据、标签状态、listing 状态都可能不同。
- 单独去重 SKU 会减少所需分析对象数量，造成“数据少了”的假象。

`COUNT(DISTINCT sku)` 只能作为诊断信息，不能作为所需 SKU 池、周数据、月数据的覆盖率或正确性基线。

## 当前 W29 同步与历史月度快照的后续规则

### 当前周同步

拉取当前周 SKU 表现时，可以继续以 `lingxing_target_sku_pool` 当前 active 行反查需要同步的店铺池，再按国家分组同步 `summary_field=msku`。当前周覆盖率继续按：

```text
lingxing_sku_weekly_performance 的 week_start/week_end + sid_scope + sku
```

校验，且不做 SKU 单字段去重。

### 历史月度回补

回补历史月份时，不能用当前 W29 的 6,560 个 SKU 作为请求过滤条件。应按历史范围内的 UK/DE 店铺全集请求领星产品表现：

```text
POST /bd/productPerformance/openApi/asinList
summary_field = msku
is_recently_enum = false
start_date / end_date = 目标月份
不传 search_value
```

每个月的接口原始响应、请求参数、分页信息和展开后的 listing 行必须作为独立月度实际快照保存。月度快照先用于找回历史出现、后续消失或淘汰的 SKU；不能直接拿当前标签反标为历史标签。

### 2026-01 试跑

第一轮测试：

```text
1. 拉取 2026-01 UK 全部范围店铺的月度实际数据快照；
2. 校验 UK 完成后，再拉取 2026-01 DE 全部范围店铺；
3. 校验每个国家的请求、分页、原始响应、listing 行、store-sku 行、零销量/有销量行和异常行；
4. 试跑通过后，按 2026-02 至 2026-06 逐月回补；
5. 月度历史并集形成后，再筛需要按周复盘完整生命周期的 SKU。
```

`lingxing_sku_monthly_performance` 是从周表聚合的派生表，不是领星接口实际月度响应快照，不能替代本规则中的月度实际快照表。
