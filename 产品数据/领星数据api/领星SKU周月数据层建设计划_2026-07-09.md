# 领星 SKU 周/月数据层建设计划（2026-07-09）

> 目标：把 UK/DE 前台可见店铺的 SKU、目标标签 SKU、SKU 周表现、SKU 月汇总沉淀成稳定数据层。先用 2026-04、2026-05、2026-06 三个月测试，确认字段、口径、性能，再扩到长期任务。

## 当前前提

已经确认：

- 前台 `sku.md` 新增店铺和国家后，正确对照口径是 `SKU + 店铺 + 国家`。
- SKU 池全量店铺不能只取 `status=1`，必须包含 `status IN (1,2)`。
- SKU 池建池链路使用产品表现 `summary_field=sku` 和 `is_recently_enum=false`；周数据主链路使用目标店铺按国家分组的 `summary_field=msku`。
- SKU、店铺、国家要从 `raw_json.price_list[*]` 展开，不要只取 `price_list[0]`。
- 国家用 `price_list[*].mid`，不要用历史 `sid_scope`。
- SKU 池前台对照已做到缺口 0。

## 数据层目标

已落地 4 张核心业务表，外加 1 张同步运行表：

| 层 | 表 | 用途 |
|----|----|------|
| 运行记录 | `lingxing_data_sync_run` | 记录每次同步参数、时间窗、店铺范围、成功失败、拉取行数 |
| 全量底表 | `lingxing_sku_store_snapshot` | 每周保存 UK/DE 前台可见店铺的全量 SKU listing 快照 |
| 目标池 | `lingxing_target_sku_pool` | 从全量底表/产品表现标签中过滤出的 6 标签分析 SKU |
| 周事实表 | `lingxing_sku_weekly_performance` | 每个 SKU 在每个店铺、每个国家、每周的完整表现数据 |
| 月汇总表 | `lingxing_sku_monthly_performance` | 从周表聚合出来的月度分析缓存 |

## 1. 全量 SKU 店铺快照表

表名：`lingxing_sku_store_snapshot`

粒度：

```text
snapshot_week + marketplace + sid + country + sku
```

用途：

- 回答“UK/DE 所有前台可见店铺到底有哪些 SKU”。
- 保留店铺维度，避免同一个 SKU 在多店铺、多 ASIN、多 MSKU 下被提前合并。
- `seller_sku/asin/parent_asin` 作为辅助字段保留代表值，不作为主口径。
- 作为目标标签 SKU 池的来源之一。

关键字段：

- 周期：`snapshot_week`、`snapshot_date`
- 店铺：`marketplace`、`mid`、`sid`、`store_name`
- SKU/listing：`sku`、`seller_sku`、`asin`、`parent_asin`
- 商品：`product_name`、`local_name`、`pic_url`
- 领星状态：`listing_status`、`is_delete`
- 标签：`tag_ids`、`tags`
- 留底：`raw_json`、`source_run_id`

## 2. 目标标签 SKU 池表

表名：`lingxing_target_sku_pool`

粒度：

```text
snapshot_week + marketplace + sid + country + sku
```

用途：

- 只保存我们要分析的 6 个目标标签 SKU。
- 后续 SKU 周/月数据只围绕这张表跑。
- 保留首次出现、最近出现、是否有效，方便看标签池变化。

目标标签：

|------|---------------|
| 绿标 | `907657425150046095` |
| 欧洲精铺2025 | `907563170455592213` |
| 欧洲精铺2025非标品 | `907654877317203632` |
| 欧洲精铺2025季节性断货 | `907596133278666918` |
| 欧洲精铺2025待淘汰 | `907585847123066054` |
| 欧洲精铺2025淘汰 | `907585631391968576` |

## 3. SKU 周数据事实表

表名：`lingxing_sku_weekly_performance`

粒度：

```text
week_start + week_end + marketplace + sid_scope + sku
```

原则：

- API 读到什么，尽量结构化保存；结构化字段不够的，`raw_json` 整包留底。
- 周表是事实源，不要为了眼前分析过早裁剪。
- 同一个时间窗可反复重跑，必须幂等 upsert。
- 注意：领星 `summary_field=sku` 返回行可能是多店铺聚合，不能强行拆成单店铺销量；周表保留 `sid_scope`，只有单店铺行才填 `sid`。

字段分组：

| 分组 | 字段 |
|------|------|
| 周期 | `week_start`、`week_end`、`year_month`、`month_week_no`、`iso_year`、`iso_week` |
| 店铺 | `marketplace`、`mid`、`sid`、`store_name` |
| SKU/listing | `sku`、`seller_sku`、`asin`、`parent_asin`、`product_name`、`local_name` |
| 标签 | `tag_ids`、`tags`、`is_target_sku` |
| 销售 | `volume`、`order_items`、`amount`、`net_amount`、`avg_volume`、`avg_custom_price` |
| 利润 | `gross_profit`、`predict_gross_profit`、`gross_margin`、`roi` |
| 广告 | `spend`、`tacos`、`acos`、`acoas`、`ad_order_quantity`、`ad_sales_amount` |
| 流量 | `sessions_total`、`page_views_total`、`clicks`、`impressions`、`ctr`、`cvr` |
| 库存 | `afn_fulfillable_quantity`、`fbm_quantity`、`available_days`、`stock_up_num` |
| 退货评价 | `reviews_count`、`avg_star`、`return_count`、`return_rate`、`return_goods_count` |
| 留底 | `raw_json`、`source_run_id`、`synced_at` |

## 4. SKU 月数据汇总表

表名：`lingxing_sku_monthly_performance`

粒度：

```text
year_month + marketplace + sid_scope + sku
```

来源：

```text
lingxing_sku_weekly_performance -> 聚合 -> lingxing_sku_monthly_performance
```

不建议月表直接调领星月时间窗作为主链路。原因：

- 周表能看首周出单、第几周断货、连续几周不动、周环比。
- 月表从周表聚合，可重算。
- 算法口径调整时，不需要重新拉 API。

月表用途：

- 懒人看月销量、月销售额、月毛利、月广告、月退款。
- 快速筛选 4/5/6 三个月表现。
- 后续做 SKU 分层、淘汰回测、转正率、利润模型。

## 实施步骤

### 阶段 1：建表和落库脚本（已完成）

1. 执行 `java-backend/sql/create_lingxing_sku_data_layer.sql`。
2. 已创建 `LingxingSkuDataLayerMapper`、`LingxingSkuDataLayerService`。
3. 已接入接口：
   - `POST /api/v1/modules/lingxing/sku-data-layer/backfill-existing`
   - `POST /api/v1/modules/lingxing/sku-data-layer/weekly/backfill-existing`
   - `POST /api/v1/modules/lingxing/sku-data-layer/monthly/rebuild`
   - `GET /api/v1/modules/lingxing/sku-data-layer/stats`

### 阶段 2：全量 SKU 店铺快照（已用现有真实数据回填）

1. 从 `productPerformance/asinList` 拉 UK/DE `status IN (1,2)` 店铺。
2. 展开 `price_list[*]` 写入 `lingxing_sku_store_snapshot`。
3. 按 `SKU+店铺+国家` 与前台 `sku.md` 验证。

### 阶段 3：目标标签 SKU 池（已用现有真实数据回填）

1. 展开 `raw_json.tag_set`。
2. 按 6 个 `global_tag_id` 过滤。
3. 写入 `lingxing_target_sku_pool`。
4. 对照当前 `sku_pool`，确认差异为 0 或解释清楚。

### 阶段 4：周数据拉取（当前已接入未来同步后的规范写入）

1. 从 `lingxing_target_sku_pool` active 目标池反查包含目标 SKU 的店铺。
2. 按 marketplace 分组请求目标店铺：DE 一组、UK 一组。
3. 产品表现接口使用 `summary_field=msku`，不传 `search_value`。
4. 每个周时间窗写一批 `lingxing_sku_weekly_performance`。
5. 保存 `raw_json` 整包；当前结构化字段先保留稳定核心指标，其余从 `raw_json` 追溯，避免领星字段类型漂移导致整批失败。
6. 禁止把 6,560 个目标 SKU 每 50 个拆批作为主链路；该方式只保留给精确验证和小样本 smoke test。

### 阶段 5：月数据聚合（已接入）

1. 从周表聚合 4 个时间段。
2. 写入 `lingxing_sku_monthly_performance`。
3. 月表不直接调用领星，除非要做对账。

### 阶段 6：三个月测试验收

验收指标：

- 4/5/6 每个月都有 4 个周段。
- 周表同一 `week_start/week_end + sid + sku + seller_sku + asin` 不重复。
- 月表能从周表重算，重算结果稳定。
- `source_run_id` 能反查每次同步。
- 任意 SKU 能查到：全量快照 -> 目标池 -> 周表现 -> 月汇总。

## 风险和补充

1. 领星 API 限流严，UK/DE 串行；`103`、`3001008`、网络超时必须自动重试。
2. 店铺范围必须用 `status IN (1,2)`，并在同步前刷新店铺表。
3. 周数据更新不能按 6,560 个目标 SKU 每 50 个拆批；应从 `lingxing_target_sku_pool` 反查包含目标 SKU 的店铺，再按国家分组同步这些有用店铺的 `summary_field=msku` 全量周表现。
4. 当前 2026-W29 目标店铺基线：UK 13 个、DE 3 个，合计 16 个；这是周数据同步的默认店铺池。2026-04-08 ~ 2026-04-14 实测 2 个国家分组 5.51 分钟完成。
5. 周表目标标记必须按 `snapshot_week + marketplace + sid + sku`，不能只按 `marketplace + sku`，避免同 SKU 跨店铺误标。
6. `summary_field=sku` 多店铺请求会产生多 sid 聚合，不作为周数据主链路；`search_field=local_sku/search_value` 只用于精确验证或小样本 smoke test。
7. 不能只存 SKU，要保留 `sid/store_name/seller_sku/asin`。
8. 月表是缓存表，事实源永远是周表和 raw_json。
9. 字段不确定时先写 `raw_json`，后续再补结构化列。
10. 先跑 4/5/6 三个月，确认数据量、速度、字段质量后再扩历史。

## 所需 SKU 池基线口径

从 2026-07-09 起，所需 SKU 池基线固定为：

```sql
SELECT COUNT(*) AS required_sku_rows
FROM lingxing_target_sku_pool
WHERE snapshot_week = '2026-W29'
  AND is_active = 1;
-- 6560
```

业务键：

```text
snapshot_week + marketplace/mid + sid + sku
```

禁止把 `sku` 单独去重后作为分析基线。去重 SKU 只能作为诊断信息，不作为拉取、分析、对账、月/周表覆盖率口径。

## raw_json 文件归档与清理

后续 `product-performance/sync` 除继续写 DB `raw_json` 外，也会把获取到的每行原始 JSON 写入 gzip JSONL 文件：

```text
data/lingxing/raw-json/product-performance/summary-sku/yyyy-MM/{run_id}/part-001.jsonl.gz
```

可配置环境变量：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `LINGXING_RAW_ARCHIVE_ENABLED` | `true` | 是否启用文件归档 |
| `LINGXING_RAW_ARCHIVE_DIR` | `data/lingxing/raw-json` | raw JSON 归档根目录 |
| `LINGXING_RAW_ARCHIVE_RETENTION_DAYS` | `180` | 文件保留天数 |
| `LINGXING_RAW_ARCHIVE_MAX_FILE_MB` | `50` | 单个 gzip JSONL 文件轮转阈值 |

清理机制：每次产品表现同步结束后自动删除超过保留期的 `.jsonl.gz` 文件，并清理空目录。数据库规范表和月/周聚合不随文件清理删除。
