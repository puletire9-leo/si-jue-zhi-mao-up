# 领星 API 实战经验总结（2026-07-09）

> 本文是这次 UK/DE 领星 SKU 池、listing 标签、产品表现 API 排查后的统一经验文件。以后排查领星数据，先看这份，再看代码和接口文档。

## 一句话结论

领星前台 listing 标签页、`productPerformance/asinList` OpenAPI、本地产品 `productList` 不是同一个数据面。  
当前系统已经可以全自动从 OpenAPI 获取 UK/DE 商品表现并按 6 个目标 listing 标签生成 SKU 池；本次新增店铺/国家列后确认，之前少的几百个主要是因为只同步了 `status=1` 店铺，漏掉了前台仍展示的 `status=2` UK 店铺。

这不是模糊匹配问题。

## 关键口径

### 前台 `sku.md`

文件路径：`产品数据/领星数据api/sku.md`

这是用户确认的前台 listing 标签正确对照。它不是唯一 SKU 表：

- 一行可能包含逗号分隔的多个 SKU。
- 有重复 SKU。
- 有少数异常行，SKU 列可能不是数字。
- 对比 API 时必须先拆逗号、过滤非数字、再去重。

### `sku_pool`

表：`sku_pool`

这是系统生成的业务 SKU 池，唯一口径是：

```text
sku + marketplace + snapshot_week
```

因此 `sku_pool` 行数不是前台唯一 SKU 数。一个 SKU 同时出现在 UK 和 DE，会有两行。

### `lingxing_product_performance`

表：`lingxing_product_performance`

来源接口：`POST /bd/productPerformance/openApi/asinList`

关键字段都在 `raw_json`：

- listing 标签：`raw_json.tag_set`
- SKU/站点/店铺：`raw_json.price_list[*].local_sku`、`raw_json.price_list[*].mid`、`raw_json.price_list[*].sid`
- 商品基础信息：`item_name`、`asins`、`parent_asins` 等

注意：

- 不要只取结构化列 `p.sku`，它来自首个 `price_list`，会漏同一 listing 下其他 SKU。
- 不要只取 `price_list[0]`，必须展开 `price_list[*]`。
- 不要用旧 `sid_scope` 判断国家。历史 ASIN 聚合数据里 `sid_scope` 可能是 `4401,9854,12809` 这种多店拼接，`CAST` 会出错。
- SKU 池站点判断必须用 `price_list[*].mid`。

### `lingxing_local_product`

表：`lingxing_local_product`

来源接口：`POST /erp/sc/routing/data/local_inventory/productList`

适合补充：

- 开发人
- 采购成本
- 图片
- 状态
- 本地产品主数据

不适合作为 listing 标签主来源。实测 `raw_json.global_tags` 有少量标签，但对本次 6 个 listing 标签覆盖不稳定；之前缺口 SKU 在这里存在但 `global_tags` 为空，真正原因是没有同步对应 `status=2` 店铺的产品表现。

## 已修正的坑

### 1. 不要用手工文件作为长期链路

用户要求是全自动：获取 UK/DE 两国店铺所有 SKU，再筛标签。  
`sku.md` 只能作为前台验收对照，不作为生产主链路。

### 2. 不要只查活跃商品

`productPerformance/asinList` 的 `is_recently_enum` 默认是 `true`。  
SKU 池必须传 `false`，否则淘汰 SKU 会少。

### 3. 不要只取 `price_list[0]`

同一 listing 可能有多个本地 SKU。  
必须展开：

```sql
JSON_TABLE(p.raw_json, '$.price_list[*]' ...)
```

### 4. 不要用 `sid_scope` 判断国家

历史数据中 `sid_scope` 可能是单 sid，也可能是多 sid 拼接。  
SKU 池国家必须使用：

```text
raw_json.price_list[*].mid
```

### 5. 不要把前台行数和 SKU 池行数直接相减

前台 `sku.md` 是 listing/SKU 展示口径。  
`sku_pool` 是 `sku + marketplace + snapshot_week` 口径。  
必须先明确是否比较：

- 原始行
- 展开行
- 去重 SKU
- `sku+marketplace`
- listing
- `sku+sid`
- `sku+sid+asin`

### 6. `global_tags` 不是 listing 标签主来源

`lingxing_local_product.raw_json.global_tags` 是产品标签。  
这次目标是 listing 标签，应以 `productPerformance.raw_json.tag_set` 为主。

### 7. 限流和超时必须自动重试

已纳入自动重试：

- `3001008`
- `103 请勿频繁请求`
- 网络超时

重试策略：最多 8 次，30s × attempt 递进等待。

### 8. 前台可见店铺不等于 `status=1`

这次新增店铺/国家列后确认，前台还包含 `status=2` 店铺。  
SKU 池要按“前台可见店铺”取数，不能只取 active/status=1。

### 9. 周数据更新按目标店铺分组，不按目标 SKU 拆批

`lingxing_target_sku_pool` 的 6,560 行是 `snapshot_week + marketplace + sid + sku` 业务对象。  
拉周表现时不要把 6,560 行按 `search_value` 每 50 个拆成 139 批；这会严重浪费领星产品表现接口的令牌桶。

正确主链路：

1. 先用 UK/DE 全量店铺建立全量 SKU 和目标 SKU 池。
2. 从目标池反查实际有目标 SKU 的店铺。
3. 按国家把目标店铺 sid 分组。
4. 用 `summary_field=msku` 拉周表现，不传 `search_value`。
5. 落库后再按 `snapshot_week + marketplace + sid + sku` 标记目标 SKU。

当前 2026-W29 基线：UK 13 个目标店铺、DE 3 个目标店铺，合计 16 个。  
2026-04-08 ~ 2026-04-14 实测：2 个 marketplace 请求组、5.51 分钟完成，原始/周表 15,166 行，目标 `marketplace+sid+sku` 去重正好 6,560。

注意：

- `summary_field=sku` 多店铺请求会产生多 sid 聚合行，不适合作为 `sku+店铺` 周数据主链路。
- 单店铺逐个请求虽然精确，但会把 16 个目标店铺拆成 16 次请求，领星 `103` 会拖慢。
- `search_field=local_sku/search_value` 只用于精确验证和小样本测试，不作为全量周数据更新主链路。

## SKU 池自动流程

```text
1. 同步店铺
   -> lingxing_seller

2. 取 UK(mid=4) / DE(mid=5) 的 status IN (1,2) sid

3. 调 productPerformance/asinList
   -> summary_field=sku
   -> is_recently_enum=false
   -> UK 和 DE 串行

4. 落库 lingxing_product_performance
   -> 结构化列 + raw_json 整包
   -> SHA-256 biz_key 幂等 upsert

5. 重建 sku_pool
   -> 展开 raw_json.tag_set
   -> 展开 raw_json.price_list[*]
   -> 用 price_list.mid 限定 UK/DE
   -> 用 6 个 global_tag_id 筛选
   -> left join lingxing_local_product 补主数据
   -> upsert sku_pool

6. 用 sku.md 做验收对照
   -> 拆逗号 SKU
   -> 过滤非数字 SKU
   -> 去重
   -> 和 sku_pool 去重 SKU 对比
```

## SKU 周数据自动流程

```text
1. 读取 lingxing_target_sku_pool
   -> snapshot_week=2026-W29
   -> is_active=1
   -> 保留 sid/store_name/marketplace 维度

2. 反查目标店铺池
   -> 当前 UK 13 个、DE 3 个
   -> 只同步这些有目标 SKU 的店铺

3. 按国家把目标 sid 分组调 productPerformance/asinList
   -> summary_field=msku
   -> is_recently_enum=false
   -> 不传 search_value

4. 落库 lingxing_product_performance 和 raw JSON gzip

5. 回填 lingxing_sku_weekly_performance
   -> 用 snapshot_week + marketplace + sid + sku 标记 is_target_sku
   -> 非目标 SKU 也可保留，供后续分析店铺背景
```

## 核心 SQL

### 从产品表现验证目标标签 SKU

```sql
SELECT
  pl.mid,
  COUNT(*) AS rows_count,
  COUNT(DISTINCT pl.local_sku) AS distinct_sku
FROM lingxing_product_performance p
JOIN JSON_TABLE(
  p.raw_json,
  '$.tag_set[*]'
  COLUMNS (
    global_tag_id VARCHAR(64) PATH '$.global_tag_id',
    tag_name VARCHAR(255) PATH '$.tag_name'
  )
) jt
JOIN JSON_TABLE(
  p.raw_json,
  '$.price_list[*]'
  COLUMNS (
    local_sku VARCHAR(128) PATH '$.local_sku',
    mid VARCHAR(16) PATH '$.mid'
  )
) pl
WHERE pl.mid IN ('4', '5')
  AND pl.local_sku IS NOT NULL
  AND pl.local_sku <> ''
  AND jt.global_tag_id IN (
    '907657425150046095',
    '907563170455592213',
    '907654877317203632',
    '907596133278666918',
    '907585847123066054',
    '907585631391968576'
  )
GROUP BY pl.mid
ORDER BY pl.mid;
```

### 查看 SKU 池统计

```sql
SELECT
  marketplace,
  COUNT(*) AS rows_count,
  COUNT(DISTINCT sku) AS distinct_sku
FROM sku_pool
WHERE snapshot_week = '2026-W29'
  AND is_active = 1
  AND source = 'LINGXING_PERFORMANCE_TAG_SET'
GROUP BY marketplace
ORDER BY marketplace;
```

### 检查 SKU 池是否有空标签

```sql
SELECT
  COUNT(*) AS rows_count,
  SUM(tags IS NULL OR tags = '') AS empty_tags
FROM sku_pool
WHERE snapshot_week = '2026-W29'
  AND is_active = 1
  AND source = 'LINGXING_PERFORMANCE_TAG_SET';
```

## 后续如果要继续保持 100% 对齐前台

当前路线已经通过新增店铺/国家后的 `sku.md` 验证到 0 缺口。后续要保持一致，需要：

1. 每次同步前先刷新 `lingxing_seller`，避免店铺状态变化导致漏店。
2. SKU 池链路继续使用 `status IN (1,2)`。
3. 若前台以后出现 status 之外的新店铺状态，要先按 `SKU+店铺+国家` 对照定位。
4. `sku.md` 继续作为验收对照，不作为生产主链路。

## 最重要的判断规则

遇到领星数量不一致时，先问五个问题：

1. 比的是前台原始行、展开行、去重 SKU，还是 `sku+marketplace`？
2. 产品表现是否传了 `is_recently_enum=false`？
3. 是否展开了 `price_list[*]`？
4. 国家是否来自 `price_list[*].mid`，而不是 `sid_scope`？
5. 前台缺口是否集中在某些 `status=2` 或其他非 active 店铺？

这五个问题能解释本次“前台 6400 多，API 只有 6000 左右”的核心差异。

## 精铺模型里的备货量口径

2026-07-09 复盘精铺测品模型时确认：首批备货数量 Q1 不能用领星产品表现的库存快照倒推，必须来自精确的备货/入仓/库存批次数据。

当前已掌握的数据边界：

| 数据源 | 能回答什么 | 不能回答什么 |
|--------|------------|--------------|
| `lingxing_product_performance.raw_json.available_inventory` | 查询时间窗对应的库存快照：FBA 可售、FBM、在途、入库中、预留、调仓 | 不能证明首批备货数量 Q1 |
| `lingxing_sku_weekly_performance.afn_fulfillable_quantity` | 当周是否在售、当周 FBA 可售库存状态 | 不能当作首批备货量 |
| `lingxing_sku_weekly_performance.volume` | 出单量/销量 | 不能反推出精确备货量 |
| `lingxing_local_product` | 采购成本、交期、箱规、供应商报价、采购备注 | 当前没有稳定的每次备货数量/入仓批次数量 |

实测边界：

- 2026-04/05/06 的 `summary_field=msku` 原始产品表现行：`181,980`。
- `available_inventory`、`afn_fulfillable_quantity` 在这些原始行中都有返回。
- `local_quantity`、`oversea_quantity`、`whs_value` 多数只是 JSON null，不是可用的精确仓库数量。
- `custom_fields` 字段存在但当前展开为空，不能指望从这里取 Q1。
- 5 月产品表现中 `afn_fulfillable_quantity` 最大值超过 300，而精铺首批通常不应超过 50；这证明它是库存状态快照，不是首批备货数量。

后续要做“备货量和出单率关系”模型，必须新增或找到下列数据之一：

```text
1. 领星采购单/备货单接口：SKU、批次、备货数量、创建时间、目的仓/店铺/国家
2. 领星入仓/发货/shipment 接口：SKU、入仓批次、发货数量、签收/入库时间
3. 仓库库存流水：SKU、数量变动、单据类型、时间、关联批次
```

在拿到上述精确 Q1 来源前，现有周/月表现表只能用于：

```text
出单量 = volume
在售 SKU = afn_fulfillable_quantity > 0
上架周 = 首次 afn_fulfillable_quantity > 0 的周
断货/售罄信号 = 曾经 afn_fulfillable_quantity > 0 后变成 0
广告/利润表现 = spend、tacos、acoas、predict_gross_profit 等字段
```

这是一个硬规则：库存快照可以做库存轨迹分析，但不能替代精确备货量。

## 采购接口补齐后的备货量来源

2026-07-10 新增采购接口文档后，精铺模型的 Q1/Q2 不再只能等待未知仓库接口，已经可以先从采购计划和采购单建立精确批次层。

新增文档：

```text
产品数据/领星数据api/文档/采购/查询采购计划列表.md
产品数据/领星数据api/文档/采购/查询采购单列表.md
```

接口：

| 接口 | API Path | 作用 |
|------|----------|------|
| 查询采购计划列表 | `/erp/sc/routing/data/local_inventory/getPurchasePlans` | 查询计划采购量、计划编号、批次号、SKU、店铺、仓库 |
| 查询采购单列表 | `/erp/sc/routing/data/local_inventory/purchaseOrderList` | 查询实际采购量、到货入库量、采购单状态、物流和采购单子项 |

关键字段：

| 来源 | 字段 | 判断 |
|------|------|------|
| 采购计划 | `quantity_plan` | 计划采购量，不是最终备货量 |
| 采购计划 | `plan_sn` / `ppg_sn` | 采购计划和批次识别 |
| 采购计划 | `sku` / `sid` / `wid` | 关联 SKU、店铺、仓库 |
| 采购单子项 | `item_list.quantity_real` | 实际采购量，优先作为 Q1/Q2 主口径 |
| 采购单子项 | `item_list.quantity_entry` | 到货入库量，用于确认实际入库 |
| 采购单子项 | `item_list.quantity_receive` | 待到货量，只能作为未完成部分 |
| 采购单子项 | `item_list.plan_sn` / `relation_purchase_plan` | 采购单回连采购计划 |
| 采购单 | `status` | `9` 完成；`-1`、`124` 作废不进入模型 |
| 采购单 | `status_shipped` | `3` 全部到货；`2` 部分到货；`1` 未到货 |

模型口径更新：

```text
Q1 = SKU 首个有效采购单子项的 item_list.quantity_real
Q1_entry = 同一采购批次的 item_list.quantity_entry
Q2 = Q1 之后下一次有效采购单子项的 item_list.quantity_real
```

过滤建议：

```text
1. 作废采购单不进入模型：status IN (-1, 124)
2. 删除子项不进入模型：item_list.is_delete = 1
3. 若只看已完成批次，优先 status = 9 且 status_shipped = 3
4. 若部分到货，备货决策量可看 quantity_real，但已入库可用量只能看 quantity_entry
```

和周/月表现表的分工：

```text
采购接口：解决“备了多少、哪一批、什么时候采购/到货”
产品表现接口：解决“什么时候 FBA 可售、什么时候出单、什么时候断货”
```

这意味着后续应新增一层采购事实表，至少包括：

```text
lingxing_purchase_plan
lingxing_purchase_order
lingxing_purchase_order_item
```

然后用 `sku + sid` 连接到 `lingxing_target_sku_pool` 和 `lingxing_sku_weekly_performance`。如果采购单的 `sid` 为 0 或缺失，需要用 `msku`、`fnsku`、本地产品关系或计划单关系补齐店铺维度，不能直接丢弃。
