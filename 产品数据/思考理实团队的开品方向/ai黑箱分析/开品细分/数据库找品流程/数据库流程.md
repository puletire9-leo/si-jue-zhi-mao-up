# 数据库找品流程

> 目的：把"十几二十万行数据怎么分析得动"讲清楚。核心思路一句话：
> **先聚合降维（机器干 20 万行），再下钻，最后才逐品分析（人只看几十个）。**
>
> 字段依据见 `数据库找品可用字段.md`。分析口径：**先不看图，用「标题+利润+竞品信息+我们数据库」判断。**
>
> ⚠️ **不要重造轮子**：系统里已经有两件现成工具，找品流程是把它们串起来，不是自己写 SQL 聚合。
> - **筛选层 = 方法卡**（M01 新品加速 / M03 FBM 简单道），已实现、有阈值。
> - **分桶层 = 品线分析页面**（`/api/v1/product-line/*`），已把数据按类目分成两级桶 `bsr_id → node_id`。

## ★ 目标形态：品线选品页 = 统一市场选品入口

> 这是正在做的升级。品线选品页面即将集成 **两个数据源（新品榜 + 店铺选品）× 所有筛选方法卡**，
> 类目已分好桶。**以后从市场选品，只从品线选品页面进**，不再手写 SQL / 单独调接口。

三条已定口径（升级时遵守）：

1. **同 ASIN 去重按最新导入时间**：一个 ASIN 可能既在新品榜又在店铺选品，**不管哪个源、不管什么 ASIN，一律取"最新导入时间"那条数据为准**，只留一条。
2. **数据源标签暂不区分**：新品榜 vs 店铺选品的来源标签现在不管，**两个源直接合在一起看**，之后再细分。
3. **方法卡两个源都能用**（纠正之前的错误说法）：
   - `m01_active` **字段级打标**只写在 `competitor_products`/`clean`（导入时算好存列）。
   - 但**店铺选品是"查询时实时套 M01 规则"**（`ShopScreeningService` 拿 `M01Rule.forMarketplace()` 阈值现算，支持 `m01Only` / `m01HitCount` 排序 / fulfillment=FBM 过滤）。
   - **结论：M01/M03 方法卡对新品榜和店铺选品都能筛**，只是机制不同（新品榜读打标列、店铺选品实时算），效果一致。

> 升级后 L1（方法卡筛）+ L2（类目分桶）都在页面内完成，人的工作真正从"看热点桶"开始。

## ★★ 找品前必做：锁定「国家 + 批次」（此前遗漏，必须补齐）

> ⚠️ 之前的找品没区分三国、没锁批次，一把捞全表 = 混批次混国家的脏结果。
> **任何一次找品，先回答两问：找哪个国家？取哪个批次日期？**
>
> 纠正：系统对外**已经统一成按天批次**（`yyyy-MM-dd`），不是两套完全不同的业务模型。
> 两表只是**底层存储列不同**，页面/API 已用同一套 DayBatch 展示。

### 1. 国家字段（两表统一）
两表都用 `marketplace` 存国家，取值 **`UK` / `DE` / `US`**（大写）。找品一次只锁一个站点，因为：
- 关键词不同（DE 用德语）、价格区间不同（P1）、销量门槛不同（M01/M03）。
- **上架英德但选品优先看 US**（见 `01总纲`），所以常见是「US 找验证 → 查 UK/DE 是否已有」，两次查询分别锁 US 和 UK/DE。

### 2. 批次口径：对外统一按天，底层列不同

| 层 | 统一口径 | 说明 |
|---|---|---|
| **页面 / API** | `batchDates = ['yyyy-MM-dd', ...]` | 两源同一套 DayBatch 模型 |
| **店铺选品** `shop_products` | 底层列 `batch_date`（`yyyyMMdd`） | 内部把 `2026-07-20` 归一成 `20260720` 再过滤 |
| **新品榜** `competitor_products` / `clean` | 底层按 **`DATE(created_at)`** 匹配 | 没有业务用 `batch_date` 列；`week_tag` / `is_current` 是旧周标签，**找品优先用按天批次，不要再主用 week_tag** |

代码依据：
- `ProductLineTreeService`：两源同为 `yyyy-MM-dd` 展示；新品榜 `DATE(created_at)`，店铺 `batch_date`
- `CompetitorService`：批次过滤统一 `DATE(created_at) IN (...)`
- `ShopProductMapper`：`batch_date` 格式化回 `yyyy-MM-dd` 给前端

### 3. 三国批次日期不对齐（这才是真正要盯的）

本周（2026-07-20 ~ 2026-07-24）实际有数据的天：

| 国家 | 店铺选品 `shop_products` 批次 | 新品榜 `DATE(created_at)` 批次 |
|---|---|---|
| **DE** | 7/20、**7/24** | 7/20、7/22 |
| **UK** | 7/20、7/21、**7/22**（暂无 7/24） | 7/20、7/22 |
| **US** | 7/20、**7/24** | 7/20、7/22 |

注意：
1. **三国最新天不一样**。UK 店铺最新到 7/22，DE/US 店铺到 7/24。写死 `= 2026-07-24` 会把 UK 漏掉。
2. **同国两源最新天也可能不一样**。例如 7/24 店铺有数据，新品榜当前最新是 7/22。
3. 本次找品标准：**本周 = 2026-07-20 到 2026-07-24**，用区间/多天列表，不取“最新一天”偷懒。

### 4. 标准查询骨架（找品第一步固定套这个）

```sql
-- 店铺选品·本周·锁单国（示例 UK）
SELECT *
FROM shop_products
WHERE marketplace = 'UK'
  AND batch_date BETWEEN '20260720' AND '20260724'
  AND /* 赛道卡的关键词/类目/阈值 */ ;

-- 新品榜·本周·锁单国（示例 UK）
-- 优先按天批次，不主用 week_tag
SELECT *
FROM competitor_products_clean
WHERE marketplace = 'UK'
  AND DATE(created_at) BETWEEN '2026-07-20' AND '2026-07-24'
  AND /* 赛道卡的关键词/类目/阈值 */ ;
```

页面/API 侧等价写法：
```text
marketplace = UK | DE | US
batchDates  = ['2026-07-20','2026-07-21','2026-07-22','2026-07-23','2026-07-24']
dataSource  = new | shop | all
```

> 每建一张赛道卡（如 `找非标品/挂牌.md`），**国家分别查**；关键词/类目段按 UK/US 英文、DE 德语分别写；批次统一锁本周日期。

## 〇、系统现有能力（找品流程直接复用）

### 筛选层 · 方法卡（作用在 `competitor_products_clean` 新品榜）
| 卡 | 作用 | 关键阈值 | 打标 |
|---|---|---|---|
| **M01 新品榜加速法** | 筛主流 FBA 铺量新品 | 站点分档：UK £4.99-17.99 / <300g / <90天 / 销量按 30-60-90 天分档达标（UK 30天≥2、60天≥10、90天≥30）/ BSR<20000 | ✅ 写 `m01_active`（1/0），导入时打+每日摘超期标 |
| **M03 FBM 自发货简单道** | 只看 FBM 自发货 | `fulfillment='FBM'` + <90天 + 销量门槛（UK≥5/DE≥10/US≥20），不看价格/重量/BSR | ❌ 纯查询筛，不打标 |
| M02 郑总同行跟随法 | 从 `deng_zong_shop` 筛郑总盘验证品 | — | ❌ |

> 你要的"2 个 M01（新品加速）+ M03（FBM）做筛选"就是这套现成引擎。**L1 筛选层 = 直接调 M01 已打标结果 + M03 查询，不自己写阈值。**

### 分桶层 · 品线分析页面（`/api/v1/product-line/*`）
- **已实现的桶**：两级类目桶 `bsr_id`（大类） → `node_id`（小类），node 内 <10 品的桶当噪声丢弃。
- 每桶已算好：`productCount`、`avgPrice/priceMin/max`、`avgRating`、`totalUnits/Revenue`、`avgBsr`、**`unitsGrowthRate`（增长率★）**、`bsrChangeRate`、`topBrands`、`sampleProducts`。
- `/tree` 支持叠加 M01 口径分桶（`countByNodeIdForM01`）。
- **⚠️ 现状与缺口**：
  - 只按类目分桶，**没有**按新老品分层（`m04_tier`）或销量档（`sales_tier`）分桶。
  - 数据源：`/tree` 走 `competitor_products` 新品榜、`/aggregated-data` 走 `deng_zong_shop`。
  - **`shop_products`（店铺选品，大头）还没接进品线分析**——你正在补这块。品线页完善后再用。

## 一、两种找品模式（差在"入口"）

| 模式 | 入口 | 本质 | 问题 |
|---|---|---|---|
| **A · 从已开过的品去找** | 我们的 163 SKU → 其竞品 ASIN → 相似品 | 被自己锚死，只能找现有方向的变体 | **太局限**，天花板低，不是想要的 |
| **B · 分析市场数据拓展** ★ | 对整池聚合，不锚我们的 SKU | 直接问市场"哪些类目/元素在冒新品且在涨" | 能发现没碰过的新方向，**这是要的** |

**结论**：主攻 B 模式。A 模式的价值降级为"拓展结果出来后，用现有方向去打标"（见 L5）。

---

## 二、保留 vs 拓展的平衡（放在流程末端用"打标+配比"控制）

不是二选一。B 模式聚合出热点后，拿**现有开品方向**（元素池 T1-T6、载体库、07.16 已验证方向）给每个热点打标：

- 命中现有方向 → **强化**（保留、低风险、复用现成产线）
- 没命中但能落地 → **拓展**（新方向、高上限、需验证）

平衡 = 一个**可调配比**（如 强化:拓展 = 7:3），在 L5 显式控制，不拍脑袋。
> ⏳ 配比初值待定（你补 L0→L1 时一起定）。

## 三、分层漏斗（20 万行怎么分析得动）

绝不逐行看。升级后 **L0→L2 全部在品线选品页面内完成**（合两源、方法卡筛、类目分桶），人只从热点桶开始看。

```
L0  全池          店铺选品 shop_products ~20万 + 新品榜 competitor_products_clean ~6千
     │  【页面内】同 ASIN 按最新导入时间去重、两源合并
     ▼
L1  筛选层        【页面内】方法卡：M01 新品加速 + M03 FBM（两源都能筛）
     │  【页面内】品线分析类目分桶（bsr_id → node_id，已算好 unitsGrowthRate 等）
     ▼
L2  桶排序        几十个类目桶：按 新品数 + unitsGrowthRate + 利润 + 竞争度 排出热点桶
     │  桶内下钻（只看热点桶，按 units_gr↓ / listing_days↑ 取 top）
     ▼════════════ 以上页面自动化；以下人工方法论 ════════════
L3  候选单品      几百个候选
     │  逐品 E02（标题抽元素/功能 + 利润校验 + 竞品验证 + 映射载体/现有方向）
     ▼
L4  真候选        几十个
     │  红线过滤 + 打标分流
     ▼
L5  分流          强化筐 / 拓展筐（按配比）
```

**关键**：20 万行只在 L0→L2 被页面（去重+方法卡+分桶）扫一遍；人从 L3 起只面对几十个桶、几十个品。这就是"分析得动"。

## 四、各层职责

### L0~L2 · 品线选品页面自动化（复用系统能力）

> 升级后这三层都在页面内完成，人不写 SQL。

- **L0 合池**：店铺选品 + 新品榜两源合并，**同 ASIN 按最新导入时间去重**，源标签暂不分。
- **L1 方法卡筛**：M01 新品加速 / M03 FBM，**两源都能筛**（新品榜读 `m01_active` 打标列、店铺选品 `ShopScreeningService` 实时套 `M01Rule` 阈值）。阈值以代码 `M01Rule`/`M03Rule` 为准。
- **L2 类目分桶 + 排序**：桶按 `bsr_id → node_id` 分好，每桶带 `unitsGrowthRate` 等。找热点 = 排序：新品数多 + `unitsGrowthRate` 高 + 均价/利润够 + 卖家不扎堆。
- ⏳ 待补：热点排序加权公式；两源合并后桶粒度怎么定。

### L3 · 逐品分析（人工，先不看图）
- 每品四件套：标题（抽元素/功能）+ 利润（P1/P3）+ 竞品信息 + 我们数据库（载体库/元素池/已开品去重）
- 逼出一句 E02："我们相对竞品强在___"，用数据校验别自打脸

### L4 · 红线过滤（人工）
- P1 售价 / P2 采购 / P3 利润率 / P10 图案密度 / P11 单单毛利（见 `04_硬红线P1-P11.md`）
- 触线打红旗、人工二审，不一刀切否

### L5 · 打标分流（人工/方法论）
- 对现有方向打标 → 强化 / 拓展两筐，按配比输出
- ⚠️ "这个热点是强化还是拓展"页面不会自动判，是人在 L3-L5 结合元素池/载体库判断（未来可给页面加"是否命中现有方向"标签）
