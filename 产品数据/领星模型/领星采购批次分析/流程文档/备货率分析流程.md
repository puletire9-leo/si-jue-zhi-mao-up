# 精铺模式备货率分析流程

> 新建SKU备货情况跟踪与利润归属分析

**最后更新**: 2026-08-14  
**适用范围**: 按开发人跟踪某月新建SKU的备货批次数、采购量、销量、利润  
**输出**: Excel报表（汇总+明细Sheet）+ 运营策略问题清单

> ⚠️ **口径修正（2026-08-14）**：备货批次从"采购计划(PPG)"改为"采购单(PO)"。
> 本文档下方部分章节仍以PPG举例，**实际以采购单(PO)为准**——只有真正下过采购单才算备货。
> 原因：采购计划只是运营决策，1-7月有701个SKU(16.7%)只有计划从未下单；前端产品详情也按采购单显示。
> 最新口径与代码以 `脚本/generate_report.py` 和 `脚本/README_脚本使用说明.md` 第四节为准。

## 一、分析目标

### 核心指标
1. **备货率**
   - 有采购SKU数 / 主SKU总数（运营采购率）
   - 二次备货率 = ≥2批SKU / 有采购SKU
   - 三次备货率 = ≥3批SKU / 有采购SKU
   - 三/二转化率 = ≥3批SKU / ≥2批SKU

2. **利润归属**
   - Q1/Q2/Q3各批次的销量、销售额、毛利、毛利率
   - 汇总（全周期）毛利

3. **运营分国**
   - UK（余江燕以外的采购人）
   - DE（余江燕创建的采购批次）

### 业务价值
- 验证精铺测品模型假设（首批筛选、二批验证、三批转正）
- 发现补货决策失误（多批补货但销量差）
- 评估开发人的选品质量和运营节奏

## 三、核心处理逻辑

### 3.1 批次定义（关键修正）

**错误做法（已废弃）**: 按采购单（PO）统计批次  
**正确做法**: 按采购计划批次（PPG）统计

**原因**: 
- PO是执行层（王亚成操作），一个PPG可能拆成多个PO，或多个PPG合并成一个PO
- PPG是决策层（李杉/余江燕创建），才是真实的补货决策单位

**批次识别SQL**:
```sql
SELECT sku,
       COUNT(DISTINCT ppg_sn) AS batch_count,
       SUM(quantity_plan) AS total_plan
FROM lingxing_purchase_plan
WHERE sku IN (清单SKU)
  AND status = -2              -- 只看已完成，排除待采购/待审批/已作废
  AND ppg_sn IS NOT NULL       -- 有批次号
  AND create_time IS NOT NULL  -- 有创建时间
GROUP BY sku
```

**同SKU同国同日多PPG合并为1批**:
```python
# 按 DATE(create_time) 去重，同一天多个PPG算1批
sku_country_date_ppg[sku][country][ppg_date].append(ppg_sn)
```

### 3.2 国家归属（运营分国）

**规则**:
```python
country = "DE" if creator_real_name == "余江燕" else "UK"
```

**原因**: 余江燕负责DE市场，其他采购人（李杉/唐若/张亚芳等）负责UK市场

**批次国家判定SQL**:
```sql
SELECT sku, ppg_sn, creator_real_name, DATE(create_time) AS ppg_date,
       SUM(quantity_plan) AS qty_plan
FROM lingxing_purchase_plan
WHERE sku IN (清单SKU) AND status=-2
GROUP BY sku, ppg_sn, creator_real_name, DATE(create_time)
```

**结果**: 每个SKU拆分成UK/DE两条独立记录（如果该SKU在两国都有采购）

### 3.3 批次周期边界

**边界定义**: PPG创建时间（`create_time`）

**周期划分**（同SKU同国）:
```
假设SKU 2551413 UK侧有3批PPG：
- PPG260423020: 2026-04-23 创建，10件
- PPG260615006: 2026-06-15 创建，30件
- PPG260617029: 2026-06-17 创建，20件

Q1周期 = [2026-04-23, 2026-06-15)  ← 首批到二批前
Q2周期 = [2026-06-15, 2026-06-17)  ← 二批到三批前
Q3周期 = [2026-06-17, ∞)          ← 三批到现在
```

**局限性**（已知但可接受）:
- PPG创建时间 ≠ 到货时间（可能晚15-45天）
- 库存重叠（Q2到货时Q1可能还剩货），无法精确区分每批销售
- 首批周期相对准确（基本清仓才触发Q2），后续批次模糊

### 3.4 利润归属

**数据源**: `lingxing_sku_weekly_performance` 周表  
**映射**: 通过 `lingxing_listing.asin` 连接到 local_sku

**归属规则**:
```python
for week_start, asin, volume, gross_profit in 周表行:
    # 1. 通过listing表找到该ASIN的marketplace和local_sku
    country = "UK" if marketplace=="英国" else "DE"
    
    # 2. 拿该SKU在该国的批次序列
    batches = sku_country_batches[sku][country]
    
    # 3. 判断week_start落在哪个批次周期
    for i, batch in enumerate(batches, 1):
        if week_start >= batch.create_time:
            batch_idx = i
        else:
            break
    
    # 4. 累加到对应批次
    agg[sku][country][batch_idx].gross_profit += gross_profit
```

**SQL示例**:
```sql
SELECT l.local_sku, l.marketplace, w.week_start,
       w.volume, w.amount, w.gross_profit
FROM lingxing_listing l
JOIN lingxing_sku_weekly_performance w ON w.asin = l.asin
WHERE l.local_sku IN (清单SKU)
```

**币种问题**:
- `gross_profit` 各国记本币（UK=GBP, DE=EUR）
- **不做汇率换算**，UK/DE分列显示
- 领星无本位币字段（`raw_json`全表空）

## 七、常见问题与修正历史

### 7.1 BUG修复记录

#### BUG #1: 批次单位用PO而非PPG（已修复）
**现象**: 2551413显示UK 1批/DE 2批，实际应为UK 3批/DE 1批  
**原因**: 用采购单（PO）统计批次，一个PPG可能对应多个PO或order_time=NULL  
**修复**: 改用PPG（`ppg_sn`）作为批次单位，按`create_time`排序

#### BUG #2: status过滤错误（已修复）
**现象**: 大量SKU显示0批次但有销量  
**原因**: 初版过滤`status NOT IN (-1)`，但`-1`不存在，应排除`-3`和`124`（已作废），或直接用`status=-2`（已完成）  
**修复**: 改为`status = -2`，只统计已完成的采购计划

#### BUG #3: order_time=NULL导致批次统计错乱（已修复）
**现象**: 有采购记录的SKU显示0批次  
**原因**: 部分采购单`order_time=NULL`，脚本默认2000-01-01，排序错乱  
**修复**: PPG版本改用`create_time`，且增加`IS NOT NULL`过滤

### 7.2 口径演进

| 版本 | 批次单位 | status过滤 | 时间字段 | 问题 |
|------|----------|-----------|---------|------|
| v1.0 | PO (order_sn) | `NOT IN (-1)` | order_time | 批次数错误、0批次SKU多 |
| v2.0 | PO (order_sn) | `NOT IN (-3,124)` | order_time | 批次数仍不对 |
| v3.0 | PPG (ppg_sn) | `= -2` | create_time | **最终版，批次准确** |

需补充FBA库存表（`lingxing_fba_inventory`）的历史快照
