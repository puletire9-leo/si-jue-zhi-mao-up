## 三、关键异常：产品表现原始表空，加工层却满

```
lingxing_product_performance   = 0 行   ← 原始表空
        │（本应是加工来源）
        ▼
lingxing_sku_weekly_performance = 460,873 行  ← 加工产物却是满的
lingxing_asin_monthly_performance = 98,602 行  ← 加工产物也满
```

**矛盾点**：README 声明周表/月表由产品表现 `raw_json.tag_set` 展开加工而来，但原始表现在是空的。可能解释：
1. 原始表现表是"过路表"——加工完周表后被清空回收空间（394MB 原始 raw_json 很占地）；
2. 加工链路实际从 Python 脚本 / raw-json 归档文件读，不依赖这张 MySQL 表；
3. 曾同步过后被 TRUNCATE。

**这与代码侧「Java 找不到 ProductPerformanceSyncService」的发现一致**——但真相已在 `LingxingController.java:43-44` 注释揭晓：2026-07 主动清理废弃端点时删除了 product-performance/sku-pool/sampling-model 的同步代码。原始表遂空，加工层（周/月表）由 Python 脚本/归档文件继续维护。

## 五、字段丰富度（加工层字段很全，可直接支撑模型页）

- **周表 `lingxing_sku_weekly_performance`（66 列）**：销量/订单/金额/净额/毛利/毛利率/ROI/广告花费/TACOS/ACOS/曝光/点击/CTR/CVR/FBA 可售库存/可售天数/评论数/星级/退货率 + `raw_json`。
- **月表 `lingxing_asin_monthly_performance`（80+ 列）**：含同比环比（volume_mom/yoy）、类目排名、B2B、促销、多段 FBA 库存（在途/待入库/不可售）、AWD、采购量、周转天数、断货日 stockout_date 等。
- **基准表 `lingxing_asin_baseline`（28 列）**：首月 FBA 库存/可售、model_start_month、观测状态、数据覆盖截止——生命周期模型的锚点。
- ✨**Listing `lingxing_listing`（64 列）**：商品创建时间 open_date / 首单 first_order_time / 开售 on_sale_time / 排名 seller_rank+small_rank / 变体 variant / 尺寸 dimension_info / FBA分段库存（可售/不可售/待调仓/在途/计划入库）/ 7日14日30日销量额 / 负责人 principal / 全局标签 global_tags。补强了周/月表缺的"真正上架日 open_date"和实时排名——生命周期模型此前用 `lx_create_time` 近似 cohort，现在有 open_date 作真相锚点。

字段密度足以直接支撑 P1 的「月度经营 / 生命周期 / ASIN 深审」模型页，数据层不是瓶颈，**瓶颈在同步的新鲜度**（产品表现原始链路已查清为主动删除，不属故障）。
